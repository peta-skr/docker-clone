さらに先へ

中心命題の回収 — 仮想化を 1 行も書いていない

序章の 1 行目に、こう書きました。「コンテナは軽量な仮想マシンではない」。あのときは、そう言われても半信半疑だったはずです。ここで回収します。

ここまでの 7 章で、仮想化のコードを 1 行も書いていません。 思い返してください。仮想の CPU を作りましたか。作っていません。メモリを仮想化しましたか。していません。ゲスト OS のカーネルをロードして起動しましたか。していません。ブートローダも、デバイスのエミュレーションも、ハイパーバイザも、この教材には一度も出てきませんでした。

代わりに書いたのは、次の 3 種類だけです。

書いたものの全部 ① 視界を区切る clone(2) にフラグを足す。台帳を別にする。 → コードとしては「定数を OR で並べる」だけ ② 上限を書く cgroup のディレクトリを作り、数字をファイルに書き、 cgroup.procs に PID を書く → コードとしては「文字列をファイルに書く」だけ ③ 根を替える 伝播を切る → bind → pivot_root → 古い根を切り離す → コードとしては「mount(2) を正しい順に呼ぶ」だけ この3つに「イメージを HTTP で取ってくる」「レイヤを重ねる」が足されたものが、 いま手元にある mydocker のすべてである。仮想化は、どこにも無い。

それでも、できあがったものの中で ps を打つと自分だけが PID 1 として並び、hostname はホストと違い、ls / には alpine の中身が出ます。仮想マシンのように見えるものが、仮想化なしで作れてしまった。 これが「コンテナは軽量な仮想マシンではない」という命題の意味です。軽量な仮想マシンなのではなく、そもそも仮想マシンではないのです。

数字でも確かめておきます。キャッシュ済みの alpine で /bin/true を実行したときの起動時間は 12〜15 ms（5 回計測で 15 / 13 / 12 / 12 / 12 ms）でした。対照として、ホストで /bin/true を直接実行すると 3 ms です。差はおよそ 10 ms。この 10 ms の中身は、overlay のマウント、cgroup のディレクトリ作成、state.json の書き込み、そして fork と exec です。OS の起動時間はここに入っていません。起動する OS が無いからです。

そして隔離の側。コンテナの中の ps は 1 個（ヘッダを除いた行数）で、同じ瞬間のホストは 85 個です。この 85 個は消えていません。同じマシンで、同じカーネルの上で、いまも動いています。見えないのは、参照している台帳が別だからです。

★足りないもの — 正直な棚卸し

ここからが、この章の本番です。できたことを並べるのは簡単ですが、できていないことを名前をつけて並べるほうがずっと難しく、ずっと役に立ちます。

「動くものができた」で終わる教材は、読者に間違った自信を持たせます。mydocker は動きます。E2E も 56 項目通ります。しかしそれは「私が書いたテストの範囲では壊れていない」以上のことを何も意味しません。何をテストしていないかを言えなければ、そのテストは信頼の根拠になりません。

これから 8 つのステップで、足りないものを一つずつ棚卸しします。それぞれ必ず 3 点セットで書きます。

足りないものの並べ方（3点セット） ① 何が無いか コードのどこに、どのフラグ・どの呼び出しが無いのか 「なんとなく足りない」ではなく、名前で指す ② 無いと何が起きるか 実際に困ること。攻撃されうること。壊れる場面。 ★ここを書かないと、ただの TODO リストになる ③ 実装するなら何が要るか 必要なシステムコール・仕様・順序・難所。 「やればできる」で済ませない。難所を先に名指しする

Step 1ネットワークの隔離

第08章で丸ごと 1 章を使って地図を描いたところです。ここでは棚卸しの 1 項目として、3 点セットの形に圧縮して置き直します。

① 何が無いか。 CLONE_NEWNET です。internal/container/run.go の Cloneflags を見ると、並んでいるフラグは 4 つだけです。

internal/container/run.go（第01〜02章で書いた部分）
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags: syscall.CLONE_NEWUTS | // ホスト名
			syscall.CLONE_NEWPID | // プロセス番号
			syscall.CLONE_NEWNS | // マウント
			syscall.CLONE_NEWIPC, // プロセス間通信
		// ⚠ これを忘れると、コンテナ内で行ったマウントがホスト側にも伝播する。
		//    pivot_root が EINVAL で落ちる原因にもなる。「なぜか動かない」の筆頭。
		Unshareflags: syscall.CLONE_NEWNS,
	}

UTS・PID・NS・IPC。NET が入っていません。 名前空間の種類としては他に user（第08章では触れず、この章の Step 3 で扱います）と cgroup 名前空間もありますが、いま欠けていて実害が最も分かりやすいのは NET です。

② 無いと何が起きるか。 コンテナはホストのネットワーク名前空間をそのまま共有します。共有するというのは、比喩ではなく文字どおりです。コンテナの中で ip -o addr を打つと、ホストの eth0 がそのまま出ます。

▸ 動かして確認

コンテナの中からネットワークインタフェースを見ます。lo も eth0 も、ホストのものがそのまま見えます。

$ mydocker run --quiet alpine /bin/sh -c 'ip -o addr'
1: lo    inet 127.0.0.1/8 scope host lo\       valid_lft forever preferred_lft forever
2: eth0    inet 192.0.2.2/24 brd 192.0.2.255 scope global eth0\       valid_lft forever preferred_lft forever

この 192.0.2.2/24 はホストのアドレスそのものです。コンテナ用に割り当てたアドレスではありません。

ここから具体的な帰結が並びます。ポートが衝突します——コンテナの中で 8080 番を待ち受けると、それはホストの 8080 番です。同じイメージのコンテナを 2 つ起動して両方が 8080 を掴もうとすれば、2 つめは EADDRINUSE で失敗します。ポートフォワード（-p 8080:80）が実装できません——転送する先と元が同じ名前空間にあるので、転送するという概念自体が成立しません。コンテナからホストのループバックが見えます——ホストの 127.0.0.1:5432 で待っている DB に、コンテナの中から素通りで接続できます。隔離されているつもりで動かした処理が、ホストのサービスに手を伸ばせます。コンテナ同士を別のネットワークに分けられません——全員が同じ 1 つのネットワークにいるので、「この 2 つだけ通信させる」ができません。

⚠ 落とし穴 · CLONE_NEWNET を足しただけでは、通信が全部止まる

「では Cloneflags に CLONE_NEWNET を 1 つ足せばいいのでは」と思うところですが、そこが第08章の出発点でした。新しいネットワーク名前空間はほぼ空で作られます。あるのは lo（ループバック）だけ、しかも down 状態です。物理インタフェースもルーティング表も DNS の設定もありません。

つまり、フラグを 1 つ足した瞬間に コンテナは完全に沈黙します。名前解決もできず、外にも出られず、ホストとも通信できません。隔離は達成されますが、同時に何もできなくなります。ここから「使える状態」に戻すために、次の 4 段が必要になります。

③ 実装するなら何が要るか。 第08章で描いた 4 段構えです。

ネットワークを通すための4段（1つでも欠けると通信できない） ① 線を1本作る veth ペア（仮想イーサネットの「両端」）を作る 片方をホストに残し、片方をコンテナの名前空間へ移す ② 橋につなぐ ホスト側の端を bridge に挿す bridge が「コンテナたちが集まるスイッチ」になる ③ 住所を配る コンテナ側に IP を振り、up にし、 既定の経路（default route）を bridge 側へ向ける ④ 出るときに書き換える 外向きの通信の送信元アドレスをホストのものに差し替える （NAT / MASQUERADE）。これが無いと戻りが返ってこない ★ 難所は「どれが欠けているか分からない」こと。 ping が通らないとき、①〜④のどこで止まっているのかを切り分ける手間が MVP から外した最大の理由だった。

加えて、この教材の制約が効いてきます。Go の標準ライブラリだけで書くという前提です。veth の作成も bridge への接続も、実体は netlink というカーネルとのやりとり用のソケットプロトコルです。ip コマンドがやっているのもこれです。外部ライブラリを使わないなら、AF_NETLINK のソケットを開き、メッセージのバイト列を自分で組み立てて送ることになります。NAT の設定に至っては、iptables あるいは nftables 相当の設定を自前で書くことになり、これは単独で 1 つのプロジェクトの規模です。

LINUX メモ · ネットワーク名前空間は「箱」であって「線」ではない

ネットワーク名前空間が区切るのは、インタフェース・ルーティング表・iptables のルール・ソケットの一覧・ポート番号空間です。区切られた箱の中に何も入れなければ、その箱は空のままです。

ここが他の名前空間と決定的に違う点です。PID 名前空間は作った瞬間に「自分が PID 1」という使える状態になります。UTS 名前空間も、ホスト名を書けばすぐ使えます。しかしネットワーク名前空間だけは、作った後に道具を持ち込まないと何もできないのです。だから実装量が跳ね上がります。

Step 2権限の絞り込み — capabilities と seccomp

ここがこの章でいちばん大事な項目です。 ネットワークが無いのは不便ですが、これが無いのは危険です。読み飛ばさないでください。

⚠ 最重要 · 名前空間は「見える範囲」を区切るが、「できること」は区切らない

これがこの章で一番覚えて帰ってほしい一文です。ここまで 7 章かけて積んできた名前空間は、すべて「何が見えるか」の台帳を差し替える仕組みでした。プロセス一覧の台帳、ホスト名の台帳、マウントの台帳、プロセス間通信の台帳。どれも「見え方」の話です。

「そのプロセスが何をしてよいか」は、名前空間とはまったく別の仕組みで決まります。 そして mydocker は、その別の仕組みに一切手を付けていません。

① 何が無いか。 capabilities の絞り込みと、seccomp によるシステムコールのフィルタです。どちらも src/ に該当するコードがありません。internal/container/init.go がやっているのは、ホスト名を書き、根を挿げ替え、特殊なファイルシステムを貼り、目的のコマンドを exec することだけです。権限を落とす処理は、どこにもありません。

② 無いと何が起きるか。 ここを丁寧に見ます。

コンテナの中で id を打つと uid=0(root) と出ます。この root は、飾りではありません。ホストの root と同じ、本物の uid 0 です。 user 名前空間を使っていない（Step 3）ので、ID の対応付けも起きていません。コンテナの中の uid 0 は、カーネルから見て文字どおりホストの uid 0 です。

「見える範囲」と「できること」は別の軸 見える範囲 できること （namespace） （capabilities / seccomp / LSM） ─────────────────────────────────────────────────────────────── mydocker が UTS PID MNT IPC ★何もしていない やったこと の4つを区切った = ホストの root と同じ全権 runc が 同じ + NET + USER 既定で 14 個程度の capability やっていること + cgroup 名前空間 だけを残し、それ以外は落とす seccomp で数百のシステムコールを塞ぐ AppArmor / SELinux も併用 ★ 名前空間だけでは、この右側の列が空のままになる。 「見えないから安全」は成り立たない。見えなくても、呼べてしまう。

本物の root が持つ全権のうち、Linux では権限が capability という単位に分割されています。CAP_SYS_ADMIN、CAP_NET_ADMIN、CAP_MKNOD、CAP_SYS_MODULE、CAP_SYS_BOOT——といった具合です。コンテナの中のプロセスは、これらを全部持っています。

持っているとどうなるか。いちばん分かりやすい証拠は、私たち自身が書いたコードです。第03章で pivot_root を呼び、マウントの伝播を切り、/proc を貼り直しました。第09章のいま気づいてほしいのは、それができたのは CAP_SYS_ADMIN を持っていたからだということです。そして、その同じ CAP_SYS_ADMIN は、コンテナの中のプロセスも持ったままなのです。

つまり、コンテナの中のプロセスは、自分で mount できます。自分で pivot_root できます。 第03章で「chroot は破れるが pivot_root は破れない」と確かめました。あれは正しいのですが、前提があります。相手が権限を持っていなければという前提です。CAP_SYS_ADMIN を持ったプロセスは、マウント木を自分で操作できます。第09章の視点から言い直すと、私たちが作った隔離は「破れないから安全」なのではなく、「破る権限を持ったまま、破らないでいてくれているから成立している」だけです。

もう一つ具体例を挙げます。第03章の判断 9 で、/dev に tmpfs を敷き、必要なノードだけ mknod で作りました。ホストの /dev を bind mount すると、コンテナからホストのブロックデバイスに手が届いてしまうからです。この判断は正しかったのですが、CAP_MKNOD が残っている以上、コンテナの中のプロセスは自分で mknod できます。ホストのディスクに対応するデバイスノードを自分で作り、それを開いて読めば、pivot_root で切り離したはずのホストのファイルシステムの中身がそのまま読めます。これは理屈上の話ではなく、権限が揃っているという事実そのものです。

LINUX メモ · capability の 5 つの集合

capability は「持っている／持っていない」の 1 ビットではなく、プロセスごとに 5 つの集合を持ちます。おおまかには次のとおりです。

  • Permitted — 持つことが許されている capability の全体
  • Effective — いま実際に効いているもの。カーネルが権限判定に使う
  • Inheritable — exec をまたいで引き継がれる候補
  • Bounding — その先で二度と取り戻せないようにする天井。ここから落とすと復活できない
  • Ambient — 特権の無いプログラムを exec しても残るもの（新しめの仕組み）

「権限を落とす」というとき、実務上いちばん効くのは Bounding set から落とすことです。Effective から外すだけでは、条件次第で戻せてしまうからです。この集合の多さが、capability の実装が「1 行足す」で済まない理由です。

③ 実装するなら何が要るか。 2 つの仕組みを、正しい順序で入れることになります。

まず capabilities。 目的のコマンドを exec する直前に、要らない capability を落とします。Bounding set から落とすには prctl(PR_CAPBSET_DROP, ...) を必要な回数だけ呼び、現在の集合を書き換えるには capset(2) を呼びます。難所は順序です。 init 側のコードは、pivot_root するにも /proc を貼るにも CAP_SYS_ADMIN を必要とします。ですから落とすタイミングは「マウント作業を全部終えた後、exec する直前」という一点しかありません。1 行早く落とすと自分のコードが動かなくなり、1 行遅らせると（exec の後になり）落とせません。

次に seccomp。 こちらは capability よりも細かく、システムコール単位で「呼んでよい／エラーを返す／プロセスを殺す」を決めます。実体は BPF のプログラムで、システムコール番号や引数を見て判定するフィルタを組み立て、prctl(PR_SET_NO_NEW_PRIVS, 1) を立ててから seccomp(SECCOMP_SET_MODE_FILTER, ...) で装着します。PR_SET_NO_NEW_PRIVS が先に要るのは、setuid されたプログラムを exec して権限を取り戻す経路を塞ぐためです。これを忘れると、フィルタをかけた意味が薄れます。

Go の標準ライブラリだけでこれを書くなら、BPF の命令列（比較・ジャンプ・戻り値）を構造体の配列として自分で組み立てることになります。数百のシステムコールを列挙した表を持ち、アーキテクチャごとに番号が違うことも扱う必要があります。「フラグを 1 つ足す」では絶対に終わりません。

参考として、runc の既定はおおよそ次のようになっています。capability は既定で 14 個程度だけを残し、それ以外は落とします。seccomp では数百のシステムコールを塞ぎます（reboot、カーネルモジュールの読み込み、kexec、swapon といった、コンテナの中から呼ぶ理由が無いものが並びます）。mydocker はこのどちらも1 つもやっていません。ここが、自作したものと本物の実行環境との間にある、いちばん深い谷です。

⚠ 落とし穴 · 「隔離されている」と「安全である」は別のこと

ここまで来た読者が最も間違えやすいのが、この 2 つの混同です。ps が 2 行になり、ls / が alpine になった状態を見ると、「守られている」と感じます。しかし見えているのは隔離であって、安全ではありません。

隔離は「うっかり」を防ぎます。安全は「わざと」を防ぎます。mydocker が防げているのは前者だけです。信用できないコードを mydocker の中で走らせてはいけません。 それは隔離ではなく、単に root でそのコードを実行しているのと変わりません。

Step 3rootless（user 名前空間）

① 何が無いか。 CLONE_NEWUSER と、それに伴う ID の対応付け（/proc/<pid>/uid_map と gid_map の書き込み）です。src/README.md の冒頭に「これらを触るには特権（CAP_SYS_ADMIN など）が要る」と書いてあるとおり、mydocker は最初から最後まで root で動かすことを前提にしています。第00章で用意した開発環境が特権付きの Linux コンテナだったのも、そのためです。

② 無いと何が起きるか。 まず単純に、管理者権限が無いと 1 行も動きません。共有サーバや、権限が絞られた CI 環境では使えません。

より重要なのは事故のときの被害です。mydocker 自身が root で動き、コンテナの中も root です。ですから、tar の展開先の検証（第06章の safeJoin）に穴が 1 つあれば、それはホストの任意のファイルを root 権限で上書きできる穴になります。 第06章で 3 段の検証を入れ、E2E で細工した tar を実際に投入して確かめたのは、この危険度が理由でした。「テストを書いたから大丈夫」ではなく、「失敗したときの被害が最大だから、そこまでやった」という順番です。

③ 実装するなら何が要るか。 ここが面白いところです。「コンテナの中の root を、ホストの一般利用者に対応付ける」という発想の転換が要ります。

user 名前空間による ID の対応付け 【いま（特権前提）】 【rootless】 コンテナの中 ホスト コンテナの中 ホスト ─────────── ───── ─────────── ───── uid 0 (root) ══同一══ uid 0 uid 0 (root) ──対応── uid 100000 uid 1000 ══同一══ uid 1000 uid 1000 ──対応── uid 101000 ... ... ★中の root は ★中では全権に見えるが、 本物の root ホストから見ればただの一般利用者 対応付けを書く場所: /proc/<pid>/uid_map （gid は gid_map） 書式: 「中の開始 ID」「ホストの開始 ID」「個数」を空白区切りで1行ずつ 0 100000 65536 ↑ ↑ ↑ │ │ └ この範囲を対応させる │ └ ホスト側の開始 └ コンテナ内の開始（0 = root）

Go では、syscall.SysProcAttr に UidMappings と GidMappings というフィールドがあり、CLONE_NEWUSER と組み合わせるとランタイムが対応付けの書き込みまで面倒を見てくれます。ですから「フラグと対応表を渡すだけ」に見えます。問題はその対応表の中身をどうやって手に入れるかです。

難所その 1、範囲を確保する権限。 特権の無い利用者が自分で uid_map に書ける対応は、原則として自分自身の 1 つの ID だけです。上の図のように 65536 個の範囲を対応させるには特権が要ります。ここで登場するのが newuidmap / newgidmap という、setuid された小さな外部プログラムです。これらは /etc/subuid と /etc/subgid という設定ファイルを読み、「この利用者にはこの範囲を使ってよい」と管理者が事前に許可した範囲だけを、代理で書き込みます。

つまり rootless は、「まったく特権が要らない」わけではありません。管理者が事前に /etc/subuid に範囲を割り当てておく必要があり、その範囲を書き込むために setuid されたヘルパを呼ぶ必要があります。特権を「実行時」から「事前の設定」へ移動させた、というのが正確な理解です。そして、この教材の「標準ライブラリだけ」という制約に照らすと、外部プログラムを呼ぶことになる時点で少し話が変わってきます。

難所その 2、ファイルの所有者。 イメージの tar の中には uid 0 所有のファイルが並んでいます。rootless で展開すると、chown できません（一般利用者は他人の ID に所有者を変えられません）。解決策は、user 名前空間の中に入ってから展開すること（中では自分が root なので chown が通る）、あるいは ID をずらして記録しておくことです。どちらにせよ、第06章で書いた展開処理はそのままでは動きません。

難所その 3、overlayfs。 user 名前空間の中から overlayfs をマウントすることは、長らくできませんでした。カーネル 5.11 以降で条件付きに許されるようになりましたが、それ以前は不可能でした。rootless の実行環境が fuse-overlayfs（ユーザ空間で overlay 相当を実現する FUSE ファイルシステム）を使っていたのは、この制約が理由です。第06章で「カーネルに重ね合わせを任せられる」と言えたのは、特権があったからこそでした。

⚠ MVP で特権を前提にしたのは、これを先送りするため

ここを曖昧にしないために、はっきり書いておきます。この教材が最初から「root で動かす」と決めたのは、rootless の難しさを意図的に先送りしたからです。 技術的に不要だと判断したのではありません。

もし最初から rootless で始めていたら、第01章の re-exec の前に ID の対応付けの話が入り、第03章の pivot_root の前に「その権限を持っているか」の話が入り、第06章の overlayfs は素直にマウントできず、教材の階段が最初の 3 段で崩れていました。要件定義書の §3.2 に「rootless 実行」をスコープ外として明記し、§7 の発展課題に回したのは、この判断の記録です。

Step 4イメージのビルド（Dockerfile 相当）

① 何が無いか。 mydocker build がありません。コマンド表にあるのは run / ps / exec / rm / pull / info の 6 つだけです。イメージを読むことはできますが、作ることはできません。

② 無いと何が起きるか。 自分のアプリケーションを入れたイメージを用意できません。既存のイメージをそのまま動かすか、--rootfs でローカルのディレクトリを根として使うか、--layer で重ねるレイヤを直接指定するか——手で組む方法しかありません。これは第06章の学習用としては十分に働きましたが、道具としては明らかに片肺です。

③ 実装するなら何が要るか。 ここは、いちばん取り組みやすい発展課題です。理由は単純で、すでに構造を知っているからです。

ビルドは「1手順 = 1レイヤ」の繰り返し 手順書 やること できるもの ───────────────────────────────────────────────────────── FROM alpine → pull して展開（実装済み） → 下地のレイヤ RUN apk add curl → 下地を lowerdir にして overlay → upper/ の中身 をマウントし、その中でコマンドを = 「curl を入れた 実行する（= run とほぼ同じ） 　 という差分」1枚 COPY app /app → ホストから upper/ へコピーする → 差分 1枚 CMD ["/app"] → ファイルは1つも変わらない → config だけ更新 ★ 各手順の後で upper/ を tar.gz に固め、digest を計算すれば、 それがそのまま「レイヤ」になる。第06章で読む側から見た構造の、書く側。

やることを具体的に並べると次のようになります。手順書のパーサ（FROM / RUN / COPY / ENV / CMD / WORKDIR あたりから）。各手順の実行——RUN は結局のところ、いま持っているコンテナ起動の仕組みをそのまま再利用します。第01〜04章で書いたものが、そっくりそのまま使えます。差分の取り出し——overlay の upper/ が「その手順で変わったもの」そのものなので、これを tar.gz に固めます。ここで第06章のホワイトアウトの知識が逆向きに要ります（upper/ にあるキャラクタデバイス 0:0 は、tar に書き出すとき .wh.<名前> に翻訳し直す必要があります）。config の生成——第05章で読む側を実装した Env / Cmd / WorkingDir を含む JSON を、今度は自分で書き出します。キャッシュの判定——同じ手順を同じ下地に対して実行するなら、前回のレイヤを再利用します。

LINUX メモ · なぜ「取得（読む側）が先」なのか

要件定義書の §7 に「取得（読む側）が動いてから着手すると、レイヤの構造がすでに理解できているので進めやすい」と書きました。これは順序の好みではなく、デバッグのしやすさの話です。

ビルドを先に作ると、出来上がったレイヤが正しいかどうかを確かめる手段がありません。「自分で作ったものを自分で読む」ので、両方が同じように間違っていれば通ってしまいます。一方、読む側が先にあれば、本物のレジストリから取ってきた本物のイメージという正解が手元にあります。自分が作ったレイヤを、その正解と同じ形式で作れているかで検証できます。正解のあるほうから作る。 これは実装順序を決めるときの一般的な原則でもあります。

Step 5レジストリへの push

① 何が無いか。 書き込み側のレジストリ API です。internal/image/registry.go にあるのは取得の経路（トークン → マニフェスト → レイヤ）だけで、その逆はありません。

② 無いと何が起きるか。 作ったイメージ（Step 4 が実装できたとして）を配れません。手元のマシンだけで完結します。イメージの本質は「同じものが別のマシンで再現できること」なので、配れないイメージは価値の半分を失っています。

③ 実装するなら何が要るか。 取得の逆向きですが、3 点だけ性質が違います。

1 つめ、トークンのスコープ。 第05章で取ったトークンは scope=repository:library/alpine:pull でした。push するには pull,push のスコープを要求し、しかもそのリポジトリに書き込む権限を持つ資格情報で認証する必要があります。匿名では取れません。ここで初めて、レジストリの認証が「誰でも取れるトークン」から「本人確認を伴うトークン」に変わります。

2 つめ、アップロードが多段階であること。 ブロブ（レイヤや config の実体）の送信は、1 回の POST では終わりません。おおまかには、POST /v2/<name>/blobs/uploads/ でアップロード用の場所を確保し、返ってきた場所へ本体を送り、最後に digest を指定して確定させる、という流れになります。大きなレイヤを分割して送ることもできます。

3 つめ、送らなくてよいものを送らない。 レイヤは digest で同一性が決まるので、レジストリに既にあるものは送る必要がありません。送る前に「この digest はもうあるか」を問い合わせ、あればスキップします。これをやらないと、alpine を下地にしたイメージを push するたびに毎回 3.67 MiB を送ることになります。「同じものは 1 度だけ」という、第06章のレイヤ共有と同じ考え方が、ネットワーク越しにも適用されているわけです。

最後に、すべてのブロブを送り終えてからマニフェストを送ります。順序が逆だと、「マニフェストは登録されたが中身が無い」という壊れたイメージを作ることになります。ここでも順序が本質です。

Step 6ボリューム管理

① 何が無いか。 docker run -v に相当するもの、つまり「コンテナが終わっても残る置き場」です。run のオプションにあるのは --memory / --cpus / --pids / --hostname / --rootfs / --layer / --quiet の 7 つで、ボリュームはありません。

② 無いと何が起きるか。 コンテナの中で書いたものは、すべて消えます。 書き込みは overlay の upper/ に溜まり、upper/ は /var/lib/mydocker/containers/<ID>/ の下にあり、mydocker rm でまとめて消えます。

これは要件そのものでした。FR-10「終了後に何も残さないこと」を徹底し、E2E でも「10 回起動しても overlay のマウント数が増えない（前 0 件 → 後 0 件）」「テスト全体を通してホストのマウント数が元に戻る（開始 22 → 終了 22）」を実数で検査しています。意図した設計であって、バグではありません。 ただし、その結果として、データベースのようにデータを持ち越したいものは mydocker では動かせません。

⚠ 落とし穴 · ボリュームは「pivot_root の後」には貼れない

実装しようとすると、すぐに順序の壁に当たります。-v /home/me/data:/data を実現するには、ホストの /home/me/data をコンテナの /data に bind mount します。ではそれをどこで呼ぶか。

pivot_root の後では手遅れです。第03章でやったとおり、古い root は MNT_DETACH で切り離して /.old_root ごと消しています。その時点で、ホストのパスを指す方法がもう残っていません。（これは第03章で「chroot と違って参照ごと消える」と喜んだ性質の、裏返しです。）

ですから貼るのは pivot_root の前、まだホストのパスが見えていて、かつ新しい rootfs（overlay の merged）も見えている一瞬です。merged/data に対してホストのディレクトリを bind mount しておけば、根を挿げ替えた後もそこに残ります。順序が要件を決めているという、この教材で何度も出てきた構図がここにもあります。

③ 実装するなら何が要るか。 bind mount 自体は mount(2) に MS_BIND を付けて呼ぶだけで、コードとしては数行です。難しいのはその周りです。

置き場の管理。 名前付きボリューム（-v mydata:/data）を作るなら、/var/lib/mydocker/volumes/<名前>/ のような置き場と、その一覧・作成・削除のコマンドが要ります。削除の安全。 第07章と同じ問題です——使用中のボリュームを消してはいけないので、どのコンテナが使っているかを数える必要があります。mydocker rm が実行中のコンテナを拒否したのと同じ規律を、ボリュームにも適用することになります。読み取り専用の指定（MS_RDONLY の再マウントが要ります。bind mount と同時には効かないので 2 回呼ぶ必要がある、という細かい罠があります）。所有者と権限。 ホスト側のディレクトリの uid と、コンテナの中の uid が食い違うと、書けたり書けなかったりします。Step 3 の rootless を入れるなら、ここは一段と複雑になります。

Step 7exec のマウント名前空間

これは既知の割り切りとして src/README.md に明記してあるものです。第07章で扱いましたが、棚卸しの一項目として改めて並べます。

① 何が無いか。 mydocker exec が、コンテナ本体のマウント名前空間に参加していません。PID・UTS・IPC の 3 つには setns で参加しますが、マウント名前空間だけは新しく作り、同じ overlay の merged を根にしています。internal/container/run.go の Exec のコメントに、その理由がそのまま書いてあります。

② 無いと何が起きるか。 ここは正直に、実害が小さいと書きます。根にしているのが同一の merged なので、見えるファイルは完全に同一です。プロセス一覧もホスト名も本物の名前空間に参加しています。実測でも、exec したシェルからコンテナ本体の PID 1（sleep 20）がちゃんと見えています。

▸ 動かして確認

実行中のコンテナに exec で入り、ホスト名とプロセス一覧を見ます。PID 1 がコンテナ本体であること、ホスト名が mydocker であることが確認できます。

$ mydocker ps
CONTAINER ID   IMAGE                                 COMMAND    PID     STATUS   CREATED
0c1be9ad663a   mirror.gcr.io/library/alpine:latest   sleep 20   16144   Up       0s
合計 1 件
$ mydocker exec 0c1be9ad663a /bin/sh -c 'hostname; ps'
mydocker
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 20
    8 root      0:00 /bin/sh -c hostname; ps
   15 root      0:00 ps

PID 1 に sleep 20 が並んでいます。これは exec したプロセスが、コンテナ本体と同じ PID 名前空間にいる証拠です。マウント名前空間だけが別、という割り切りが、この出力からは見えません。

では何が起きるのか。コンテナ本体が起動した後に自分で行ったマウントが、exec 側からは見えません。 逆に exec 側でマウントしたものも本体には見えません。ボリューム（Step 6）を実装した場合、貼る場所によってはこの差が表に出てきます。また、/proc/<pid>/mountinfo を比べると 2 つが別物であることが分かります。「見えるファイルが同一」は「マウント名前空間が同一」ではありません。

③ 実装するなら何が要るか。 原因は Go のランタイムにあります。マウント名前空間への setns(2) は、呼び出し元がシングルスレッドでなければ EINVAL で失敗します。Go のランタイムは常に複数のスレッドを持つので、この条件を Go のコードから満たすことができません。runtime.LockOSThread() でスレッドを固定しても駄目です。固定は「今のゴルーチンをこのスレッドに縛る」だけで、プロセス全体のスレッド数を 1 にするわけではないからです。

解決策ははっきりしています。runc と同じことをする——つまり cgo で C のコンストラクタを書き、Go のランタイムが起動してスレッドを増やす前に setns を済ませることです。runc の nsexec がまさにこれで、C の __attribute__((constructor)) を使って main より前に走らせています。この教材が「標準ライブラリだけ」という前提を掲げた結果、唯一妥協した箇所がここです。 cgo を許すなら、この割り切りは解消できます。

GO メモ · runtime.LockOSThread でも足りない理由

runtime.LockOSThread() は「このゴルーチンを、いま乗っている OS スレッドに固定する」関数です。setns のようにスレッド単位で効くシステムコールを扱うときには必須で、Exec でも実際に呼んでいます。PID・UTS・IPC への setns はこれで足ります。

しかしマウント名前空間の条件は「プロセスが単一スレッドであること」です。ゴルーチンを固定しても、ランタイムの GC やシステムコールの待ち受けのために別のスレッドが存在し続けます。Go で書いている限り、この条件は満たせません。 これは Go の欠陥ではなく、「マルチスレッドのプロセスがマウント名前空間を移ると、スレッドごとに見えるファイルシステムが食い違う」というカーネル側の正当な制約です。

Step 8その他の不足 — 長時間動かす道具になっていない

ここまでの 7 つは「大きな機能」でした。最後に、小さいけれど実務では必ず必要になるものをまとめて並べます。共通しているのは、コンテナを「一瞬動かす」のではなく「動かし続ける」ときに効いてくるという点です。

シグナルの転送

① 何が無いか。 親の mydocker が受け取ったシグナルを、コンテナの PID 1 へ転送する処理がありません。internal/container/run.go は signal.Notify でシグナルを受け取ってはいますが、それは親が死んで後片付けが飛ばされるのを防ぐため——受け流して無視するためです。コードのコメントにもそう書いてあります。

② 無いと何が起きるか。 端末から Ctrl-C を押した場合は、シグナルが前景プロセスグループ全体に届くので子にも届きます。しかし、別のところから mydocker のプロセスに SIGTERM を送った場合、それはコンテナの中には伝わりません。 親は無視し、子は何も知らないまま走り続けます。プロセス管理の仕組みから止められない、という状態です。

③ 実装するなら何が要るか。 受け取ったシグナルを子の PID へ送り直すだけなら数行です。ただしどのシグナルを転送し、どれを親自身で処理するかの設計が要ります。SIGCHLD を転送してはいけませんし、後片付けのために親が生き残る必要もあります。

PID 1 としての孤児の回収（zombie reaping）

① 何が無いか。 コンテナの PID 1 が孤児プロセスを回収する処理を持っていません。mydocker init は最後に目的のコマンドを exec するので、PID 1 の中身はそのコマンドそのものに置き換わります。回収してくれるかどうかは、そのコマンド次第です。

② 無いと何が起きるか。 Linux では、親より先に子が終わると、その子の後始末は PID 1 が引き取ることになっています。ホストでは init（systemd など）がこれをやっています。コンテナの中では、PID 1 は私たちが起動したコマンドです。

孤児が溜まる仕組み 【ホスト】 【コンテナの中】 init (PID 1) /app (PID 1) ← 私たちが起動したコマンド │ ちゃんと wait して │ wait を知らない │ 後始末する │ 親プロセス 親プロセス │ │ 子（親より先に死ぬ） 子（親より先に死ぬ） │ │ └→ init が引き取って回収 └→ /app が引き取るが、回収しない = ゾンビとして残り続ける ★ ゾンビは PID を1つ占有する。溜まり続けると PID が枯渇する。 コンテナが「なぜか」プロセスを作れなくなる、という形で表面化する。

/bin/sh は wait するので、この教材の例では問題が表に出ません。しかし、シェルを経由せずにアプリケーションを直接 PID 1 として起動すると、そのアプリが wait を知らない限りゾンビが溜まります。docker run --init というオプションが存在するのは、まさにこのためです。

③ 実装するなら何が要るか。 PID 1 に小さな init を挟みます。exec で置き換えるのをやめ、mydocker init 自身が PID 1 として残って目的のコマンドを子として起動し、SIGCHLD を待って終わった子を回収し続け、目的のコマンドが終わったら自分も終わる、という構造です。ただしこれは「PID 1 が exec で目的のコマンドになる」という、この教材の分かりやすさを一つ手放すことでもあります。 ps の出力の PID 1 が /bin/sh ではなくなるからです。教材としてどちらを取るかは、実際に手を動かすときに考えてみてください。

logs

① 何が無いか。 標準出力・標準エラーの記録です。run は子の標準入出力を自分の標準入出力に直結しているだけなので（FR-1 の「標準入出力が起動した端末とつながる」がそれです）、端末を閉じたら出力は消えます。

② 無いと何が起きるか。 後から出力を読めません。バックグラウンドで動かす仕組み（デタッチ実行）も無いので、そもそも「後から」という状況が作れない、というのが正確なところです。2 つの不足は連動しています。

③ 実装するなら何が要るか。 出力をファイル（/var/lib/mydocker/containers/<ID>/ の下）へも書くようにし、mydocker logs <ID> でそれを読みます。端末に直結する場合と、ファイルに落としつつ端末にも出す場合の切り替えが要ります。デタッチ実行まで踏み込むなら、親プロセスが終了してもコンテナが生き残る構造（親子関係の切り離し）が必要になり、そうすると「誰が後片付けするのか」という第07章の問題が再燃します。ここは見た目より深い変更です。

stop

① 何が無いか。 コンテナを止めるコマンドです。いまあるのは rm（終了したコンテナの痕跡を片付ける）だけで、動いているものを止める手段がありません。実行中のコンテナに rm すると、正しく拒否されます。

▸ 動かして確認

実行中のコンテナを消そうとすると、こうなります。拒否は正しい振る舞いですが、「では止めるにはどうするのか」に対する答えを mydocker は持っていません。

$ mydocker rm 0c1be9ad663a
mydocker: コンテナ 0c1be9ad663a はまだ実行中です。先に終了させてください

③ 実装するなら何が要るか。 作法は決まっています。SIGTERM を送る → 猶予（既定 10 秒など）を待つ → まだ生きていたら SIGKILL です。「行儀よく終わる機会を与えてから、強制する」という 2 段構えです。

実装上の注意が 2 つあります。1 つめ、PID 1 のシグナルの扱いは特別です。 PID 名前空間の PID 1 に対しては、そのプロセス自身がハンドラを登録していないシグナルは、カーネルが握りつぶします。つまり SIGTERM のハンドラを持たないプログラムを PID 1 として動かすと、SIGTERM は効きません。「docker stop が必ず 10 秒待たされる」という、よく知られた現象の正体がこれです。序章の FAQ で触れたとおりです。2 つめ、確実に止めたいなら cgroup の freezer を使う手もあります——プロセス群をまとめて凍らせてから処理する方法で、取りこぼしがありません。第04章で使った cgroup には、上限をかける以外にこういう使い道もあります。

複数コンテナのオーケストレーション

最後に、要件定義書の §3.2 でスコープ外にした最大の項目です。複数のコンテナをまとめて定義し、起動し、停止する仕組み。docker compose に相当するものです。

これについては「実装するなら何が要るか」より先に、順序を書いておきます。ネットワーク（Step 1）とボリューム（Step 6）が揃ってから着手する——要件定義書にもそう書きました。理由は明白で、複数のコンテナをまとめる意味は「それらが通信すること」と「データを共有すること」にあるからです。その 2 つが無い状態で「まとめて起動する」機能だけ作っても、できるのは「複数のコンテナをまとめて起動する」だけです。それは for ループで足ります。

OCI ランタイム仕様との差

足りないものを 8 つ並べました。ここで視点を変えます。「Docker と比べてどうか」ではなく、「標準規格と比べてどうか」という見方です。

OCI ランタイム仕様（Open Container Initiative Runtime Specification）というものがあります。これは実装ではなく、取り決めです。ひとことで言うと、「バンドルを渡されたら、こう振る舞え」という約束を文章で定めたものです。

OCI ランタイム仕様が定めているもの 【バンドル】= ランタイムに渡される入力。これだけ。 bundle/ ├── config.json ★何をどう動かすかが全部書いてある JSON └── rootfs/ コンテナの / になるディレクトリ木 config.json に書かれていること（抜粋）: - process : 実行するコマンド・環境変数・作業ディレクトリ ・capabilities の5つの集合・rlimits - root : rootfs のパス・読み取り専用かどうか - mounts : どこに何をどうマウントするか（順序も含めて全部） - linux.namespaces : どの名前空間を作るか（または既存のどれに入るか） - linux.resources : cgroup の上限 - linux.seccomp : 許すシステムコール・拒否するシステムコール - hooks : 起動の前後に走らせる外部プログラム ★ 仕様が定めるのは「振る舞い」であって「実装」ではない。 だから同じ config.json を渡せば、どの実装でも同じ結果になる（べき）。

ここが大事なところです。runc は、この仕様の実装の 1 つにすぎません。 唯一の実装ではありません。C で書かれた crun、Rust で書かれた youki、仮想マシンで隔離を強化する kata-containers、ユーザ空間でシステムコールを横取りする gVisor（runsc）——どれも同じ config.json を受け取って動きます。「コンテナランタイム」という言葉が指しているのは、この仕様を満たす実装のことです。

仕様はもう一つ、状態のライフサイクルも定めています。ランタイムは create / start / state / kill / delete という操作を持ち、コンテナは次の状態を遷移します。

状態意味mydocker にあるか
creating作成の処理中無い（状態として存在しない）
created作り終わったが、まだ走らせていない無い（作ると同時に走る）
running実行中state.json の生死判定で代用
stopped終了済み無い（終了＝記録が消えるだけ）
⚠ 曖昧にしない · mydocker は OCI ランタイム仕様に準拠していない

ここははっきり書きます。mydocker は OCI ランタイム仕様に準拠していません。 「一部準拠」でも「準拠を目指している」でもなく、準拠していません。理由は 2 つあり、どちらも構造的なものです。

1 つめ、config.json を読みません。 mydocker の入力はコマンドライン引数（イメージ名・コマンド・オプション）です。バンドルという概念がありません。したがって、他のツールが用意したバンドルを mydocker で動かすことも、mydocker が作ったものを他のランタイムに渡すこともできません。

2 つめ、状態のライフサイクルを持ちません。 上の表のとおり、created（作ったがまだ走らせていない）という状態が存在しません。mydocker run は作成と起動が一体です。この created 状態は、上位のツールが「コンテナを準備してから、タイミングを合わせて一斉に起動する」ためにあるもので、仕様の中でもかなり本質的な部分です。

準拠していないことは失敗ではありません。要件定義書に「OCI 準拠」と書いていないからです。 目的は「コンテナの正体はプロセスであることを体で理解する」ことであって、互換性のある実装を作ることではありませんでした。ただし、準拠していないものを準拠しているかのように語るのは、この教材で最もやってはいけないことです。

層の分かれ方 — 自作したのはどこか

では mydocker は、実際の道具立ての中でどこに位置するのでしょうか。docker と打ったときに動くものの層を並べてみます。

docker run と打ったときに動くもの（層の分かれ方） ┌──────────────────────────────────────────────┐ │ docker CLI / dockerd │ 利用者向けの窓口 │ ビルド・レジストリ・ネットワーク・ボリューム・compose │ 「使いやすさ」の層 ├──────────────────────────────────────────────┤ │ containerd │ 常駐して面倒を見る層 │ イメージの管理・スナップショット・コンテナの寿命管理 │ gRPC の API を持つ ├──────────────────────────────────────────────┤ │ containerd-shim │ 親が死んでも │ コンテナ1つにつき1つ。標準入出力と終了コードを預かる │ コンテナが生き残る仕組み ├──────────────────────────────────────────────┤ │ runc （OCI ランタイム仕様の実装） │ ★ここが「作る」層 │ bundle を受け取り、名前空間・cgroup・rootfs・ │ 一瞬だけ動いて消える │ capabilities・seccomp を整えて exec する │ ├──────────────────────────────────────────────┤ │ Linux カーネル │ clone / mount / cgroup │ namespace cgroup overlayfs capabilities seccomp │ 実際に隔離しているのは └──────────────────────────────────────────────┘ ここ ★ mydocker がいるのは runc の位置。ただし ・config.json を読まない（バンドルを受け取らない） ・capabilities / seccomp を触らない ・NET / USER 名前空間を作らない ・状態のライフサイクルを持たない → 「runc の位置の、ごく一部」というのが正確な言い方。 そのうえで、上の層の仕事も少しだけ持っている: ・イメージの取得（本来 containerd の仕事） ・レイヤの展開と重ね合わせ（本来 containerd のスナップショッタの仕事） ・CLI（本来 docker CLI の仕事）

この図の見方を 2 つ書きます。

1 つめ、runc は常駐しません。 コンテナを 1 つ起動するとき、runc は呼ばれ、名前空間と cgroup と rootfs を整え、目的のコマンドを exec して、消えます。コンテナが動き続けている間、runc のプロセスはもういません。これは mydocker とは違うところで、mydocker run は子の終了を待つために生き続けます（後片付けをするためです）。「誰が後片付けするか」を解決するために、本物の道具立てでは shim という層が挟まっています。 第07章で「親が死んだら誰が片付けるのか」に悩んだ問題への、業界の答えがこれです。

2 つめ、mydocker は層をまたいでいます。 イメージの取得は本来 containerd の仕事で、runc はイメージを知りません。runc が受け取るのは、もう展開済みの rootfs/ です。mydocker がレジストリと会話するのは、教材として「イメージとは何か」を扱うためで、層の分け方としては正しくありません。学習用の 1 本のバイナリだから、こう作ってあります。

runc が実際にやっていること

層の位置が分かったところで、同じ位置にいる runc が、mydocker と比べて何を余計にやっているのかを並べます。これは「runc はすごい」という話ではありません。「なぜ runc のソースは読みにくいのか」という話です。

runc がやっていること何のためかmydocker
cgo による nsexecGo のランタイムが起動する前にマウント名前空間へ setns するためやらない（Step 7 の割り切り）
capabilities の絞り込み中の root から全権を取り上げるやらない（Step 2）

cgo による nsexec は、Step 7 で書いたとおり、マウント名前空間への setns のための仕掛けです。C の __attribute__((constructor)) で main より前に走らせ、Go のランタイムが動き出す前に名前空間の切り替えを済ませます。runc のソースを読み始めた人が最初に面食らうのがここです——Go のプロジェクトなのに、いきなり C のファイルが出てきて、しかもそれが実行順序の最初にいるからです。第07章の割り切りの、本命の解決策がこれだと分かっていれば、読む理由がはっきりします。

フックは、一見地味ですが構造的に重要です。runc はネットワークの設定を自分ではやりません。prestart フックで外部のプログラム（CNI プラグインなど）を呼び、そちらに任せます。第08章で「ネットワークは難しい」と書きましたが、業界の答えも「難しいので別の層に切り出す」でした。 責務の分割としては、この教材で internal/cli を薄く保ったのと同じ発想です。

⚠ 大事なこと · これらは全部「本番運用に必要な分岐と抽象」である

上の表を見て「runc には敵わない」と思う必要はありません。むしろ逆で、ここに自作した意味があります。

要件定義書の §1.1 に、こう書きました——「既存のコンテナランタイムのソースを読む道もあるが、runc や containerd は本番運用に必要な分岐と抽象で厚く覆われており、核となる仕組みが埋もれている」と。上の表の 9 項目が、まさにその「厚く覆っているもの」です。

runc のソースで pivot_root を呼んでいる箇所を探すと、たしかに見つかります。しかしその前後には、rootless かどうかの分岐、config.json のマウント指定を順に適用する処理、SELinux ラベルの付与、読み取り専用の再マウント、エラー時の巻き戻しが並んでいます。「伝播を切る → bind → pivot_root → 古い根を捨てる」という 4 行の骨格は、その中に埋まっています。

私たちは、その骨格だけを先に自分の手で書きました。だから今なら、覆いの下に何があるかを知った状態で runc を読めます。 これが「自作した意味」です。

ここから先の進み方

足りないものが 8 つ並び、runc との差も見えました。では、次に何をすればよいのか。順序を提案します。 難易度と、学べることの密度で並べてあります。

おすすめの順序（下から積む、という原則はここでも同じ） 5. runc のソースを読む ← ここまで来れば読める ↑ 4. OCI 仕様を読み、config.json を読めるようにする ↑ 3. ネットワークを実装する（第08章の地図をなぞる） ↑ 2. capabilities を落としてみる（何が壊れるかを見る） ↑ 1. mydocker に stop を足す（シグナルの扱いを学ぶ） ← 最初の一歩 ★ 1 と 2 は、どちらも「小さく始めて、すぐ結果が見える」もの。 3 は大きい。4 は読み物。5 は目的地。

1. mydocker に stop を足す。 いちばん小さい一歩です。state.json から PID を読み、SIGTERM を送り、猶予を待ち、まだ生きていたら SIGKILL。コード量は少ないのに、学べることが多い課題です。PID 1 のシグナルの特別扱い（ハンドラが無いシグナルは握りつぶされる）に必ずぶつかりますし、「生きているかどうか」の判定（第07章で state.json に PID と起動時刻を両方書いた理由）が効いてくる場面でもあります。何より、対照実験がしやすい——SIGTERM を受け取るシェルスクリプトと、受け取らないコマンドの両方で試せば、挙動の差がその場で見えます。

2. capabilities を落としてみる。 実装する前に、壊してみるのがおすすめです。init の exec の直前で CAP_SYS_ADMIN を落とすコードを入れ、コンテナを起動してみてください。何が起きるでしょうか。次に、落とす位置を pivot_root の前に動かしてみてください。今度は何が起きるでしょうか。この 2 つの差が、Step 2 で書いた「順序が一点しかない」という話の実体験になります。 そのうえで、どの capability が本当に要るのかを 1 つずつ確かめていくと、runc の既定が 14 個程度である理由が腑に落ちます。

3. ネットワークを実装する。 ここから大きくなります。第08章の 4 段構えの地図をなぞってください。おすすめは、いきなり mydocker に組み込まないことです。 まず ip コマンドで手動で 4 段を通し、コンテナから外に ping が通る状態を作ってください。手で通せないものはコードでも通せません。手で通ってから、その手順を 1 段ずつ Go に移していきます。切り分けのコストが MVP から外した理由だったので、切り分けやすい進め方をするのが対策です。

4. OCI 仕様を読み、config.json を読めるようにする。 仕様そのものは、思ったより読みやすい文書です。そして、ここまで実装してきた読者にとってはほとんどが既知のことです。linux.namespaces の項目を読めば「ああ、Cloneflags のことか」と分かりますし、linux.resources.memory.limit を読めば「memory.max に書く値だな」と分かります。仕様の各項目が、自分の書いたコードのどの行に対応するかを指させる——これが、この段階で得られるものです。実装としては、config.json を読んで Config を組み立てる変換を書けば、既存の Run がそのまま使えます。

5. runc のソースを読む。 目的地です。ここまで来れば読めます。 読む順番も提案しておきます——まず nsexec の C のコードを見て「Go が動き出す前に名前空間を切り替えている」ことを確認し、次に libcontainer の初期化の流れの中から pivotRoot を探し、その前後の分岐が何を吸収しているのかを見ます。骨格は自分が書いたものと同じです。 違うのは、その周りに何が積まれているかだけです。

大きなプロジェクトのソースを読むとき、いちばん効くのは「自分が書いたことのある処理を探す」ことです。全体を上から順に読もうとすると、抽象の層に迷ってどこにいるか分からなくなります。

総括 — 「動くはず」がいちばん危険だった

最後に、この教材全体を通して繰り返し出てきた教訓を 1 つにまとめます。技術の話ではなく、確かめ方の話です。

実装ログの最後に、こう書きました——「動いている時間より、動かない理由を探している時間のほうが長い。そしてその大半は、『効いていないように見えるが実は効いている』か、『効いているように見えるが実は効いていない』のどちらかだった」と。

この 2 つが、この教材の落とし穴ボックスのすべての出所です。そして共通する根っこは 1 つです。設定が通ったことと、効いていることは、別物である。

誤認 ① — ps が 87 個

第02章で PID 名前空間を作った直後の話です。ps -e を打つと、ホストのプロセスがずらりと出ました。しかも数えると 87 個。同じ瞬間のホストは 85 個です。隔離したはずなのに、ホストより多い。

手で確かめた実測がこれです。

▸ 動かして確認

unshare で PID 名前空間だけを作った場合と、/proc も貼り直した場合の差です。

$ unshare --pid --fork sh -c 'ps -e --no-headers | wc -l'
87
$ ps -e --no-headers | wc -l
85
$ unshare --pid --fork --mount-proc sh -c 'ps -e --no-headers | wc -l'
3

87 → 3。差を作ったのは --mount-proc、つまり /proc を貼り直したかどうかだけです。名前空間は最初から効いていました。

名前空間は最初から効いていたのです。 ps はプロセスを直接数えているのではなく、/proc の下のディレクトリを読んでいます。その /proc がホストのものを指したままだったので、見えていたのは名前空間の中身ではなく /proc の中身でした。ホストより 2 個多いのは、unshare 自身と sh が増えたからです。

ここで「名前空間が効いていない」と結論して Cloneflags をいじり始めたら、永遠に直りません。 直すべき場所は 1 つ下の層——ファイルシステムのほうにありました。

誤認 ② — 上限は書けているのに死なない

第04章の cgroup です。memory.limit_in_bytes に 10485760（10 MB）を書き、読み返すと 10485760 が返ってきます。memory.failcnt も 37 まで増えていて、上限に当たった回数が記録されています。それなのに、テストしたプロセスが死にません。

このとき最初に書いたテストがこれでした。

最初に書いた（間違っていた）テスト
mydocker run --memory 10m alpine sh -c 'head -c 100000000 /dev/zero | wc -c'

結果は 100000000 が表示されて終了コード 0。「上限が効いていない」と思いかけました。しかし間違っていたのはテストのほうです。 head | wc はストリームを流すだけでメモリを溜めません。1 億バイトを読みますが、一度に持っているのはバッファ 1 個分です。10 MB の上限には決して当たりません。

確かめ方を変えました。dd に大きな bs を与えて、1 回で 100 MB のバッファを確保させます。しかも上限あり・上限なしの両方で走らせて差を見ます。

▸ 動かして確認

対照実験です。同じコマンドを、上限なしと上限ありの 2 回走らせます。

$ mydocker run --quiet alpine /bin/sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1'
1+0 records in
1+0 records out
104857600 bytes (100.0MB) copied, 0.047161 seconds, 2.1GB/s
$ echo $?
0
$ mydocker run --quiet --memory 10m alpine /bin/sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1'
$ echo $?
137

上限なしなら成功（0）、上限ありなら OOM で強制終了（137 = 128 + SIGKILL）。この「差」が出て初めて、上限が効いていると言えます。

教訓は、片方だけを走らせないことです。 上限ありだけを走らせて失敗したとき、失敗しているのが上限なのかテストなのか分かりません。上限なしでも同じように走らせて差を見る——これで初めて、上限が原因だと言えます。E2E には対照をペアで入れてあります。

破って確かめる、という規律

この 2 つの誤認から出てきた規律が、「破って確かめる」です。

「隔離できているか」を確かめるのに、いちばん弱いのは「隔離できているように見える」という観察です。ps の出力が空でないことを見ても、/proc の貼り直しを忘れていれば通ってしまいます（そのときはホストのプロセスがずらりと出るので、むしろ「空でない」は簡単に通ります）。だから、破りにいきます。

  • 第03章：chroot を実際に破りました。Python で chroot の前にディレクトリの fd を掴んでおき、fchdir で戻って .. を登り切り、chroot(".") で牢を付け替える。「破れると聞いた」ではなく、自分の手で破りました。
  • 第04章：上限を「書けたか」ではなく「効いたか」で確かめました。対照実験と、137 という終了コードで。
  • 第06章：展開先の外にファイルを作る tar を自分で作って投入しました。「弾いているはず」で済ませず、外にファイルが作られないことをファイルの有無で確認しています。
  • 第07章：mydocker 自身を SIGKILL で殺して残骸を作り、それを rm が安全に回収できることを確かめました。正常系だけを試していたら、この経路は一度も通りません。
  • 全体：「多すぎ」側を検査しました。ps は行数ちょうど、一覧は合計 N 件。「1 つ以上ある」ではなく「ちょうどこの数である」を見る。

E2E の 56 項目は、このために書かれています。機能が動くことを確かめるためではなく、動いているように見えて実は動いていない状態を弾くために書かれています。

つまずき FAQ

これは Docker の代わりに使えますか?

使えません。 学習用です。この章で並べた 8 つの不足のうち、実務で使うなら最低でもネットワーク（Step 1）、権限の絞り込み（Step 2）、stop と logs（Step 8）が必須です。どれも実装していません。

もう少し正確に言うと、「Docker の代わり」という言い方自体が層を混同しています。Docker が提供しているのは、ビルド・レジストリ・ネットワーク・ボリューム・compose・API を含む一式です。mydocker が触れているのは runc の位置の一部と、containerd の仕事のごく一部だけです。比べる相手としては runc のほうが近く、その runc と比べても足りないものが表で 9 行あります。

ただし、「Docker の中で何が起きているか」を説明する道具としては、Docker より優れています。 9.0 MB のバイナリ 1 つで、依存ライブラリが 1 つも無く、全部読めるからです。用途が違います。

本番で使ってはいけない理由を一言で言うと?

コンテナの中の root が、ホストの root だからです。

これで足ります。capabilities を落としていないので CAP_SYS_ADMIN も CAP_MKNOD も残っており、seccomp も無いので危険なシステムコールも呼べます。user 名前空間も使っていないので ID の対応付けもありません。つまり、mydocker の中でコードを走らせることは、そのコードを root で走らせることとほとんど変わりません。

ネットワークが隔離されていないこと（ホストのポートを直接掴む、ホストの 127.0.0.1 に届く）も、単体で十分に本番失格の理由になります。

逆に言えば、自分で書いたコードを、自分のマシンで、学習のために動かす用途なら問題ありません。危険なのは「信用していないものを、隔離されているつもりで動かす」ことです。

56 項目のテストが全部通っているのに「足りない」というのは矛盾していませんか?

矛盾していません。テストが検査しているのは「要件を満たしているか」であって、「安全か」ではないからです。

E2E のセクション構成を見てください。8 つのセクションがそれぞれ FR-1 〜 FR-10 に対応しています。要件定義書に書いた要件を、全部検査しています。そして要件定義書の §3.2 には、seccomp も rootless もネットワークも「スコープ外」と書いてあります。 テストは、スコープ外のものを検査しません。

ここが「テストが通る」の限界です。テストは自分が書いた仕様に対する検査であって、仕様そのものの妥当性は検査しません。仕様に穴があれば、テストも同じ形の穴を持ちます。だから、テストの外側にあるものを言葉で並べる作業（この章の前半）が要るのです。

capabilities を落とすと、mydocker 自身が動かなくなりませんか?

落とすタイミングを間違えると、そうなります。これは実装するときに必ず踏む落とし穴です。

mydocker init がやることを順に並べると、ホスト名を書き（CAP_SYS_ADMIN が要る）、マウントの伝播を切り（要る）、bind mount し（要る）、pivot_root し（要る）、/proc と /dev を貼り（要る）、mknod でデバイスノードを作り（CAP_MKNOD が要る）、最後に目的のコマンドを exec します。

権限を落としてよいのは、この最後の exec の直前だけです。 1 行早いと自分の作業ができなくなり、exec の後では自分のコードはもう存在しません。「たった一点」というのは比喩ではなく、文字どおり順序上の 1 か所です。

ちなみに、この「一点」の存在自体が、名前空間と権限が独立した仕組みであることの証拠でもあります。名前空間は作った瞬間に効き、あとは何をしても効き続けます。権限は、落とした時点から効きます。効き方の時間軸が違うのです。

rootless にすれば「危なくない」ということですか?

被害の上限は下がりますが、「危なくない」にはなりません。

rootless の効果は、事故ったときにホストの一般利用者の権限しか奪われないことです。tar 展開の検証に穴があっても、書けるのはその利用者が書ける場所だけになります。これは大きな改善です。

ただし、rootless にしても Step 2（capabilities / seccomp）は別途必要です。user 名前空間の中ではその名前空間の範囲で全権を持つので、CAP_SYS_ADMIN 相当のことができます。範囲が限られているとはいえ、そこからカーネルの脆弱性を突く経路は残ります。実際、user 名前空間そのものを起点にしたカーネルの脆弱性は繰り返し報告されています。

「隔離の仕組みを 1 つ足したから安全」という考え方自体が危険です。本物の実行環境が namespace・cgroup・capabilities・seccomp・AppArmor/SELinux を全部重ねているのは、どれか 1 つでは足りないと分かっているからです。

ここまで作ったのに、結局 runc を読まないと駄目なんですか?

「駄目」ではありません。読めるようになった、というのが正しい言い方です。

要件定義書の §1.1 に書いたとおり、この教材が生まれた動機は「runc のソースを読もうとしたが、本番運用に必要な分岐と抽象で核が埋もれていて読めなかった」という問題でした。その問題に対する答えが、「先に骨格を自分で書く」でした。

いま、骨格は手元にあります。pivot_root の前後 4 行、Cloneflags の 4 つ、cgroup.procs に PID を書く 1 行、lowerdir の逆順。runc の中で同じことをしている場所を探せば、そこから読み広げられます。 覆いの下に何があるか知っているので、覆いを覆いとして認識できます。

読まなくても構いません。読まなくても、この教材の目的（コンテナの正体はプロセスであると理解すること）は達成されています。ただ、読みたくなったときに読める状態にはなりました。それがこの 9 章分の、いちばん実用的な成果かもしれません。

理解度チェック

最終章なので、総復習にします。第01章から第07章まで、各章から 1 問ずつです。自分の言葉で答えてから開いてください。 答えられなかった章があれば、その章に戻る合図です。

Q1.（第01章）なぜ「自分をもう一度起動する」必要があったのですか? 素直に unshare(CLONE_NEWPID) を呼んではいけない理由は?

PID 名前空間は、unshare を呼んだプロセス自身には適用されないからです。 適用されるのは、その後に作られた子プロセスからです。ですから自分が PID 1 になることは原理的にできません。

実際に手で確かめた差がこれでした。

$ unshare --pid sh -c 'echo "自分の PID: $$"'
自分の PID: 25171
$ unshare --pid --fork sh -c 'echo "自分の PID: $$"'
自分の PID: 1

--fork（＝子を作る）を挟んで初めて 1 になります。Go では、/proc/self/exe を init という別のサブコマンドとして Cloneflags 付きで起動することが、この --fork に相当します。clone(2) のフラグとして名前空間を渡すので、子は生まれた瞬間から新しい名前空間の中にいます。

もう一つの理由もありました。Go のランタイムはマルチスレッドなので、unshare(CLONE_NEWNS) のようなスレッド単位の操作を素直に扱えません。この制約は、第07章の exec の割り切りとしてもう一度出てきました。

Q2.（第02章）PID 名前空間を作った直後、ps -e が 87 個も出ました。ホストは 85 個です。何が起きていましたか?

名前空間は効いていました。壊れて見えていたのは /proc のせいです。

ps はカーネルに直接問い合わせているのではなく、/proc の下の数字のディレクトリを読んでいます。PID 名前空間を作っただけでは /proc はホストのものを指したままなので、ps にはホストのプロセスが全部見えます。見えていたのは名前空間の中身ではなく、/proc の中身でした。

ホストより 2 個多いのは、unshare 自身と sh が増えたからです。--mount-proc（＝新しい /proc を貼り直す）を足すと 3 になります。

この 87 という数字は、「名前空間が効いていない」ようにしか見えないのに効いている、という誤認の典型例です。 ここで Cloneflags を疑い始めると永遠に直りません。直すべきは 1 つ下の層でした。

Q3.（第03章）chroot でも「/ の見え方」は変わります。それなのに pivot_root を選んだのはなぜですか?

chroot は破れるからです。しかも簡単に。

手口は単純で、chroot する前にディレクトリのファイルディスクリプタを掴んでおき、chroot 後に fchdir でそこへ戻り、.. を登り切ってから chroot(".") するだけです。実際に Python で再現しました。

chroot 直後の ls / : ['bin', 'inner']
脱獄後の  ls / : ['bin', 'bin.usr-is-merged', 'boot', 'container_info.json', 'dev', 'etc', 'home', 'lib', 'lib.usr-is-merged', 'lib64', 'lost+found', 'media']

原因は、chroot が「/ の見え方」を変えるだけで、プロセスが既に持っている外側への参照を無効化しないことです。

pivot_root は古い root を put_old に押し出し、それを MNT_DETACH でマウント木から切り離します。参照ごと消えるので、同じ手は使えません。 実際、コンテナの中に /.old_root は残っていません。

ただし第09章の Step 2 で見たとおり、これは「相手が CAP_SYS_ADMIN を持っていなければ」という前提の上に成り立っています。 権限を持ったままの相手には、マウント木を操作されうるという別の話が残ります。

Q4.（第04章）cgroup のディレクトリを作り、memory.limit_in_bytes に 10485760 と書きました。読み返すと 10485760 が返ります。これで上限は効いていますか?

効いていません。 まだ何も起きません。

上限を書いただけでは、その上限が誰に適用されるかが決まっていないからです。効かせるには cgroup.procs に対象プロセスの PID を書く必要があります（internal/cgroup/cgroup.go の Apply がやっていることです）。作っただけでは効かない——これが第04章の山場でした。

さらに 2 つ、この章から持ち帰るべきものがあります。1 つめ、いつ書くか。 子を起動してから PID を書くまでの数ミリ秒の間に、子は既に走り始めています。だからパイプで同期し、cgroup への登録が終わるまで子を待たせています。2 つめ、効いたことをどう確かめるか。 読み返して期待値が返ることは、効いた証拠になりません。上限あり・上限なしの対照実験で 137 という差を見る必要があります（この章の誤認 ②）。

Q5.（第05章）alpine:latest のマニフェストを取ったら layers がありませんでした。何が返ってきたのですか? そして「最初の項目を取る」実装が壊れるのはなぜですか?

返ってきたのはマニフェストリスト（OCI インデックス）です。イメージそのものではなく、「アーキテクチャごとのマニフェストの一覧」です。だから layers がありません。

そして、そのリストにはイメージではないものが混ざっています。実測したインデックスの中には、"platform":{"architecture":"unknown","os":"unknown"} で、注釈に "vnd.docker.reference.type":"attestation-manifest" と書かれた項目が入っていました。これは署名の付随物であって、イメージではありません。

ですから「最初の項目を取る」実装は、これを掴んで確実に壊れます。 しかも「取れた JSON に layers が無い」という同じ症状が 2 回続くので、原因の切り分けが紛らわしくなります。

対処は、platform.os と platform.architecture で明示的に絞ることでした（pickPlatform）。見つからなければ、あるものの一覧を添えてエラーにします。「たぶん最初のやつ」で済ませない、というのがこの章の教訓です。

Q6.（第06章）レイヤの中の .wh.foo.txt を見つけたとき、なぜ foo.txt を削除せずに、キャラクタデバイス 0:0 を作るのですか?

レイヤをキャッシュとして共有できるようにするためです。

全レイヤを 1 つのディレクトリに順に展開し、.wh. を見たら実体を削除する方法（平坦化）でも、結果のファイル木は正しくなります。しかし、その結果はそのイメージ専用になります。他のイメージと同じレイヤを共有できず、digest によるキャッシュが効きません。

レイヤごとに独立して展開し、.wh.<名前> を overlayfs の削除印（キャラクタデバイス 0:0）に、.wh..wh..opq を trusted.overlay.opaque="y" という拡張属性に翻訳しておけば、各レイヤは digest をディレクトリ名にした独立・不変のキャッシュになります。重ね合わせの判断はカーネルに任せられます。

「後で組み合わせられる形で保存する」という設計判断です。 同じ考え方が、この章の Step 5（push のときに既にあるレイヤを送らない）にも出てきました。

Q7.（第07章）mydocker exec は PID / UTS / IPC には setns で参加するのに、マウント名前空間だけ新しく作っています。なぜですか?

マウント名前空間への setns(2) は、呼び出し元がシングルスレッドでなければ EINVAL で失敗するからです。 Go のランタイムは常に複数のスレッドを持つので、この条件を Go のコードから満たせません。

runtime.LockOSThread() でゴルーチンをスレッドに固定しても足りません。固定は「このゴルーチンをこのスレッドに縛る」だけで、プロセス全体のスレッド数を 1 にするわけではないからです。

採った解決策は、PID / UTS / IPC には setns で参加し、マウント名前空間だけは新しく作って同じ overlay の merged を根にすることでした。見えるファイルは完全に同一になります。

これは「できたふり」ではありませんが、完全でもありません。 本体が起動後に自分で行ったマウントは exec 側から見えません。src/README.md に既知の割り切りとして明記してあります。本命の解決策は cgo で、runc の nsexec がまさにそれをやっています（この章の Step 7）。

✓ 完了の合図

全11ページ、読み終わりました。 序章から第09章まで、地図を見て、環境を作り、自分を再実行し、視界を区切り、根を挿げ替え、資源を締め、イメージを取ってきて、層を重ねて、道具にして、足りないものを並べました。

最後にもう一度だけ、手を動かしてください。コンテナを起動して、ps を打ちます。

$ mydocker run alpine /bin/sh
/ # ps
PID   USER     TIME  COMMAND
    1 root      0:00 /bin/sh
    7 root      0:00 ps
/ # hostname
mydocker

PID 1 に自分だけが並びます。ホスト名は mydocker です。

そして、いまならこの 2 行が何によって作られているかを全部指させるはずです。PID 1 になっているのは clone(2) に CLONE_NEWPID を渡したから（第01〜02章）。ホストの 85 個が見えないのは /proc を貼り直したから（第03章）。/bin/sh が alpine のものなのは pivot_root で根を替えたから（第03章）、その根がレジストリから取ってきた 1 枚のレイヤを OverlayFS で重ねたものだから（第05〜06章）。ホスト名が mydocker なのは CLONE_NEWUTS と Sethostname（第02章）。

この出力の全部の理由が言えたら、この教材は完了です。 そして——ここに仮想化は 1 つも出てこないことも、あわせて確認してください。序章の 1 行目が、ここで回収されます。

まとめ — ここから先は、自分の手で

この教材で得たもの。 「コンテナは軽量な仮想マシンではない」という一文を、比喩ではなくコードとして持っている状態になりました。clone(2) にフラグを並べ、cgroup のファイルに数字を書き、mount(2) を正しい順に呼ぶ——書いたのはそれだけで、仮想化は 1 行もありません。それでも ps は 2 行になり、起動は 12〜15 ms（ホストで /bin/true を直接実行すると 3 ms）で、ホストの 85 個は見えなくなりました。加えて、もっと持ち帰る価値があるものがあります。「設定が通ったこと」と「効いていること」は別物だ、という感覚です。ps が 87 個出ても名前空間は効いていて、memory.limit_in_bytes が期待値を返しても上限は確かめられていない。この 2 つの誤認を実際に踏み、対照実験と「破って確かめる」という規律で抜けてきました。E2E の 56 項目は、その規律の形をしています。

それでもまだ足りないもの。 この章で 8 つ並べました。ネットワークは隔離されておらず、コンテナの中の root は本物の root のまま、rootless でもなく、イメージを作ることも配ることもできず、データは終了とともに消え、exec は別のマウント名前空間にいて、stop も logs もありません。OCI ランタイム仕様には準拠していません——config.json を読まず、created という状態も持ちません。層で言えば runc の位置の、しかもごく一部です。この列挙ができることが、この章の到達点です。 何が足りないかを言えない人は、自分が作ったものが何なのかも言えません。逆に、足りないものを 8 つ名前で言えるなら、作ったものの輪郭がはっきり見えているということです。runc のソースが「本番運用に必要な分岐と抽象で厚く覆われている」というのは、この 8 つ（と表の 9 行）のことでした。

そして、ここから先へ。 この教材にはもう次章がありません。次の一歩を決めるのは読者です。順序は提案しました——stop を足す（小さい。シグナルと PID 1 の特別扱いが学べる）、capabilities を落としてみる（壊れ方を見る。落とす位置を 1 行動かすだけで結果が変わる）、ネットワークを実装する（大きい。まず ip コマンドで手動で通してから移す）、OCI 仕様を読む（仕様の各項目が自分のコードのどの行かを指す）、runc を読む（骨格は同じ。覆いを覆いとして認識できる）。どれから始めても構いませんし、どれも始めなくても構いません。ただ、次に docker run と打ったときには、その一行の下でカーネルが何をしているかが見えているはずです。 それはもう、比喩ではありません。自分で書いたコードとして知っていることです。その状態から先は、教材ではなく、あなたの手が続きを書きます。
