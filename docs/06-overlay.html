Layer— 使い捨ての正体

層を重ねる

前章で alpine のレイヤを取ってきて、/var/lib/mydocker/layers/ の下に展開しました。8.7 MB、516 ファイル。ここまでは「材料」です。この材料を、書き換えても汚れない形でコンテナに渡さなければいけません。コンテナを消してもイメージが無傷で残る——あの当たり前を、この章で自分の手で作ります。着地点は一行で言えます。コンテナを消すというのは、upperdir を捨てるだけのことです。

◈ この章のゴール

internal/overlay/overlay.go と internal/image/extract.go を読み切り、次の4つを自分の言葉で説明できるようになる。①lowerdir / upperdir / workdir / merged がそれぞれ何を担当しているか。②lowerdir の並び順がイメージのレイヤ順と逆である理由。③tar の中の .wh. を普通に展開してはいけない理由と、その翻訳先。④umount の失敗を握りつぶすとなぜイメージが消えるのか。仕上げに、手で mount -t overlay を打って重ね合わせを作り、mydocker が作った overlay マウント行を /proc/mounts で確かめる。

まず、素朴にやってみる — イメージをコピーする案

前章の終わりで、私たちの手元にはこういう状態のディレクトリがあります。alpine のレイヤを1枚展開したものです。

/var/lib/mydocker/layers/sha256_55afa1ecc21d…/ ├ bin/ ├ etc/ ← /etc/alpine-release に "3.24.1" が入っている ├ lib/ ├ usr/ └ … （展開後 8.7 MB / 516 ファイル）

さて。ここを pivot_root の行き先にすれば、第03章でやったとおりコンテナは立ち上がります。実際、立ち上がります。……そして、コンテナの中で apk add curl なり rm -rf /etc なりをやった瞬間、このディレクトリが書き換わります。次に別のコンテナを起動すると、前のコンテナが残した傷がそのまま見えます。docker run alpine を2回打って、2回目が1回目の残骸だらけだったら、誰も使いません。

では、起動のたびにコピーすればいい? これが素朴案です。私も最初にこれを考えました。

【素朴案】起動のたびに丸ごとコピーする layers/sha256_55afa…/ ──cp -a──▶ containers/a10f2703bb37/rootfs/ （8.7 MB, 516 ファイル） （8.7 MB, 516 ファイル） ──cp -a──▶ containers/0c1be9ad663a/rootfs/ ──cp -a──▶ containers/f280be2460e3/rootfs/ コンテナ 3 個 = 26.1 MB。ubuntu なら 1 個 80 MB 級。 そして起動のたびに 516 ファイルの I/O が走る。

破綻の仕方は2つです。容量と時間。alpine は小さいので 8.7 MB で済みますが、実務のイメージは数百 MB あります。コンテナを10個立てたら数 GB。そして起動のたびに全ファイルをコピーするので、起動が「一瞬」ではなくなる。私たちが最終的に到達する起動時間は12〜15 ms です。516 ファイルのコピーは、どう頑張ってもその桁には入りません。

ここで発想を変えます。コピーしないで、重ねる。

重ねる、という発想

読み取り専用の材料はそのまま置いておいて、その上に透明な板を1枚載せる。読むときは上から順に覗いて、最初に見つかったものを返す。書くときは一番上の板にだけ書く。下の材料には触らない。これが union filesystem の考え方で、Linux では overlayfs がその実装です。

3枚重ねたときの見え方 ┌──────────────────────────────┐ upperdir（書き込み用・空） │ │ ← コンテナが書いたものだけ └──────────────────────────────┘ lowerdir 上（レイヤ3） │ app.jar config.yml │ lowerdir 中（レイヤ2） │ curl config.yml(旧) │ lowerdir 下（レイヤ1 = ベース） │ sh ls cat config.yml(元) │ └──────────────────────────────┘ ↓ 上から探して最初に当たったものを返す merged（コンテナに見える /） │ sh ls cat curl app.jar config.yml ←レイヤ3のもの └──────────────────────────────┘ config.yml は 3 枚すべてにあるが、コンテナから見えるのは **一番上の1枚だけ**。 下の 2 枚は隠れているだけで、消えてはいない。

大事なのは config.yml の扱いです。3枚とも持っているのに、merged から見えるのは一番上のもの1つ。下の2つは消えたのではなく、隠れているだけです。この「隠れているだけ」という性質が、この章の後半でホワイトアウトの話に効いてきます。

LINUX メモ · union filesystem

複数のディレクトリツリーを重ね合わせて、1つのツリーとして見せるファイルシステムの総称です。「合併（union）」という名前のとおり、ファイルの集合としては和集合になり、同じパスが衝突したときは優先順位の高い層が勝つというルールで解決します。

Linux の歴史の中では UnionFS、aufs、overlayfs などがこの役割を担ってきました。長らく本流はカーネル本体の外（out-of-tree パッチ）にあり、Docker は初期に aufs を使っていましたが、overlayfs は Linux 3.18 で本体に取り込まれたので、追加のカーネルモジュールなしに使えます。私たちの環境は 6.18.5 なので、当然入っています。

overlayfs の用語は4つだけ覚えれば足ります。lowerdir（読み取り専用の下層。複数可）、upperdir（書き込み先。1つだけ）、workdir（カーネルが内部作業に使う場所）、そして重ね合わせた結果が現れるマウントポイント（この教材では merged と呼びます）。

用語表 — この章で出てくる4つの場所と3つの印

先に表にしておきます。読みながら迷ったらここに戻ってきてください。

名前正体この教材での実体

Step 1手で重ねてみる

コードを書く前に、シェルで一度やります。overlayfs は「マウントオプションを3つ渡すだけ」で使える、驚くほど素朴な仕組みです。まず4つのディレクトリを用意します。

/tmp/ovl/ ├ lower/ ← 読み取り専用にしたい材料（イメージのつもり） ├ upper/ ← 書き込みが溜まる場所（空のまま用意する） ├ work/ ← カーネルの作業場所（空のまま用意する） └ merged/ ← ここに重ね合わせた結果が現れる（空のまま用意する）

この4つを作ったら、mount を1回打つだけです。

▸ 動かして確認

mount -t overlay に3つのオプションを渡します。-t overlay の直後の overlay は「デバイス名」の位置ですが、overlayfs には実デバイスが無いので慣習でこの文字列を置きます。マウントできたら mount で確かめます。

$ mount -t overlay overlay -o lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work /tmp/ovl/merged
$ mount | grep overlay
overlay on /tmp/ovl/merged type overlay (rw,relatime,lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work,uuid=on)

これだけです。/tmp/ovl/merged を ls すれば lower の中身が見え、そこにファイルを作れば upper の下に現れます。カーネルが全部やってくれます。uuid=on はカーネルが自分で付けた既定値で、私たちは指定していません。

コマンド1つで済むということは、Go 側も syscall.Mount を1回呼ぶだけということです。実際そうなります。ただしその1回を安全に呼ぶために、前後に地味な準備がいる——この章はほぼその話です。

まずファイルの入り口から読みます。パッケージのコメントに、この章の結論がそのまま書いてあります。

internal/overlay/overlay.go
// Package overlay は OverlayFS で複数のレイヤを1つのファイルシステムに重ね合わせる。
//
// コンテナの「使い捨て」の正体はここにある。
// 読み取り専用の下層（lowerdir）はイメージそのままで、書き込みは全部 upperdir に溜まる。
// コンテナを消すときは upperdir を捨てるだけでよい。イメージには指一本触れていない。
package overlay

import (
	"fmt"
	"os"
	"path/filepath"
	"strings"
	"syscall"
)

// Mount は1つの overlay マウントを表す。
type Mount struct {
	Merged string   // 重ね合わせた結果が見えるディレクトリ（＝コンテナの /）
	Upper  string   // 書き込み先。コンテナを消すときはここを捨てる
	Work   string   // overlayfs が内部で使う作業場所
	Lowers []string // 下から上の順（先頭が最下層）
}

構造体は、さっきシェルで打った4つの場所とそのまま対応しています。Merged・Upper・Work が1つずつ、Lowers だけがスライス。下層は何枚あってもよく、上層は1枚だけという overlayfs の非対称性が、型にそのまま出ています。

Lowers のコメントに 「下から上の順（先頭が最下層）」 と書いてあるのを覚えておいてください。Step 2 の山場がここです。

次は「そもそもこの環境で overlayfs が使えるか」を調べる関数です。

internal/overlay/overlay.go
// Supported はこの環境で overlayfs が使えるかを返す。
// /proc/filesystems に overlay が並んでいるかで判定する。
func Supported() bool {
	b, err := os.ReadFile("/proc/filesystems")
	if err != nil {
		return false
	}
	for _, line := range strings.Split(string(b), "\n") {
		if strings.TrimSpace(line) == "nodev\toverlay" || strings.HasSuffix(strings.TrimSpace(line), "\toverlay") ||
			strings.TrimSpace(line) == "overlay" {
			return true
		}
	}
	return strings.Contains(string(b), "overlay")
}

逐行で見ます。

/proc/filesystems は「このカーネルが今扱えるファイルシステムの一覧」です。1行が1つのファイルシステムで、デバイスを必要としないものには行頭に nodev とタブが付きます。overlayfs は実デバイスを持たないので nodev 側に並びます。

判定が3つ並んでいるのは、この行の書式がカーネルのバージョンや表示のされ方で微妙に揺れるからです。nodev\toverlay ちょうど、末尾が \toverlay、行そのものが overlay——どれかに当たれば true。最後の strings.Contains は保険で、上の3つがどれも当たらなくても文字列として含まれていれば通します。ここは厳密さより「使えるのに使えないと誤判定して機能を落とす」ことを避けるほうを優先した書き方です。

この関数の戻り値は、mydocker info の表示にそのまま出ます。

▸ 動かして確認

mydocker info は、状態の置き場・資源制限の方式・overlayfs が使えるか・今いくつ overlay が張られているかを1画面で出します。Supported() が true を返すと「利用可能」の行になります。

$ mydocker info
状態の置き場: /var/lib/mydocker
資源制限:     cgroup v1 (/sys/fs/cgroup, 利用可能: memory cpu pids)
overlayfs:    利用可能
overlay 数:   0 件

overlay 数: 0 件 は、この後で読む CountMounts("overlay") の戻り値です。「起動と終了を繰り返しても、この数が増えていかないこと」がこの章の裏テーマになります。

Step 2lowerdir は左が上 — 並べる順を逆にする

ここが1つめの落とし穴です。しかもエラーにならない種類の落とし穴なので、たちが悪い。

イメージのレイヤは、マニフェストの layers 配列に並んでいます。この並びは「後のものほど上」です。ベースイメージが先頭で、その上に RUN や COPY が積み上がっていく。人間の直感どおりです。

ところが lowerdir のオプション文字列は逆です。lowerdir=A:B:C と書いたとき、一番左の A が最も優先度の高い（＝上の）層になります。

イメージのレイヤ順 と lowerdir の文字列は 逆 になる 【マニフェストの layers 配列】 【overlayfs から見た積み方】 layers[0] ベース ─────▶ ┌────────────┐ 上（優先） layers[1] curl を入れた ─────▶ │ layers[2] │ layers[2] 設定を書いた ─────▶ │ layers[1] │ │ layers[0] │ （後のものほど「上」） └────────────┘ 下 ↓ これをオプション文字列にすると… lowerdir=layers[2]:layers[1]:layers[0] └──左が上───┘ └下┘ ⚠ そのまま layers[0]:layers[1]:layers[2] と書くと、 ベースが最優先になり、後から書いた設定が **ベースに隠される**。 エラーは出ない。ただ「更新が反映されていない」ように見えるだけ。

この間違いが怖いのは、マウントは成功するところです。syscall.Mount はエラーを返しません。コンテナは起動します。ただ、中に入ると curl が入っていなかったり、書いたはずの設定が古いままだったりする。原因を「イメージのビルドが反映されていないのかな」と疑い始めると、丸一日溶けます。

だから mydocker では、呼び出し側には人間の直感どおりの順（下から上）で渡してもらい、逆転は New の中に閉じ込めることにしました。New の全文です。

internal/overlay/overlay.go
// New は base の下に merged / upper / work を用意し、lowers を重ねてマウントする。
// lowers は **下から上の順**（先頭が最下層）で渡すこと。イメージのレイヤ順そのままでよい。
func New(base string, lowers []string) (*Mount, error) {
	if len(lowers) == 0 {
		return nil, fmt.Errorf("重ねる下層が1つもありません")
	}
	for _, l := range lowers {
		if fi, err := os.Stat(l); err != nil || !fi.IsDir() {
			return nil, fmt.Errorf("下層が見つかりません: %s", l)
		}
		// ⚠ lowerdir のオプション文字列は ":" 区切り、"," でオプションが切れる。
		//    パスにこれらが混ざると文字列が壊れる。digest 由来のパスなら起きないが、念のため弾く。
		if strings.ContainsAny(l, ":,") {
			return nil, fmt.Errorf("下層のパスに : か , が含まれています: %s", l)
		}
	}

	m := &Mount{
		Merged: filepath.Join(base, "merged"),
		Upper:  filepath.Join(base, "upper"),
		Work:   filepath.Join(base, "work"),
		Lowers: append([]string(nil), lowers...),
	}
	for _, d := range []string{m.Merged, m.Upper, m.Work} {
		if err := os.MkdirAll(d, 0o755); err != nil {
			return nil, err
		}
	}
	// ⚠ workdir は空でなければならない。前回の残骸があると EINVAL で落ちる。
	//    ⚠ upperdir と同じファイルシステム上に無いと EXDEV / EINVAL になる。
	//      ここでは同じ base の下に作っているので条件を満たす。
	if err := emptyDir(m.Work); err != nil {
		return nil, err
	}

	// ⚠ lowerdir は **左が上（優先）**。
	//    イメージのレイヤは「後のものほど上」なので、並べる順を逆にする必要がある。
	//    ここを間違えると、古い層が新しい層を隠して「更新が反映されていない」ように見える。
	rev := make([]string, 0, len(lowers))
	for i := len(lowers) - 1; i >= 0; i-- {
		rev = append(rev, lowers[i])
	}
	opts := fmt.Sprintf("lowerdir=%s,upperdir=%s,workdir=%s",
		strings.Join(rev, ":"), m.Upper, m.Work)

	if err := syscall.Mount("overlay", m.Merged, "overlay", 0, opts); err != nil {
		return nil, fmt.Errorf("overlay のマウントに失敗しました (%s): %w", opts, err)
	}
	return m, nil
}

上から順に読みます。

①下層が0枚なら即エラー。 lowerdir が空の overlay は作れません。ここで弾かないと、あとで意味の分からないマウントエラーになります。

②各下層が本当にディレクトリとして存在するか確かめる。 os.Stat でエラーが出るか、ディレクトリでなければ弾きます。err != nil || !fi.IsDir() の短絡評価が効いていて、err != nil のときは fi が nil なので fi.IsDir() は評価されません。順序を入れ替えると panic します。

③パスに : か , が入っていたら弾く。 これは overlayfs のオプションが「ただの文字列」であることに由来する制約です。lowerdir=A:B,upperdir=C という1本の文字列をカーネルが自分でパースするので、パスの中に区切り文字が混ざると意味が変わってしまいます。私たちのパスは sha256_55afa1ecc21d… のような digest 由来なので実際には起きませんが、「起きないはず」を「起きない」に変えるのがこの3行です。

④3つのディレクトリのパスを組み立てて作る。 base の下に merged / upper / work。この「同じ親の下に3つ」という配置が Step 3 の制約を自動的に満たします。

⑤Lowers のコピー。 append([]string(nil), lowers...) は Go でスライスを複製する定番の書き方です。呼び出し元が渡してきたスライスをそのまま持つと、あとで呼び出し元が中身を書き換えたときに Mount の状態が黙って変わります。ここでコピーを取っておけば、この Mount は自分の値を自分で持ちます。

⑥そして逆転。 ここが本題です。

internal/overlay/overlay.go（New の中・再掲）
	rev := make([]string, 0, len(lowers))
	for i := len(lowers) - 1; i >= 0; i-- {
		rev = append(rev, lowers[i])
	}

make([]string, 0, len(lowers)) は「長さ0・容量 len(lowers) のスライス」を作ります。長さ0から append していくので、要素は先頭から詰まっていきます。容量を最初に確保してあるので、途中で内部配列の作り直しは起きません。

ループは i を末尾から先頭へ動かします。len(lowers)-1 から始めて 0 まで、i--。取り出した要素を順に append するので、rev には元の並びが反転して入ります。lowers = [A, B, C]（A が最下層）なら rev = [C, B, A]。

これを strings.Join(rev, ":") で連結すると C:B:A になり、最上層の C が一番左＝最優先という overlayfs の期待どおりの文字列になります。

⑦オプション文字列を組み立てて syscall.Mount。 第1引数 "overlay" はデバイス名の位置（実デバイスが無いので慣習の文字列）、第2引数がマウント先、第3引数がファイルシステム型、第4引数のフラグは 0、第5引数が今組み立てたオプション文字列です。Step 1 でシェルに打ったものと、1対1で対応しています。

⑧エラーメッセージに opts をそのまま埋めているのは意図的です。overlayfs のマウント失敗は EINVAL の一言で返ってくることが多く、何が悪いのかカーネルは教えてくれません。せめて「どの文字列で失敗したか」が手元に残っていれば、パスの綴りや順序を目で追えます。%w で元のエラーを包んでいるので、呼び出し元は errors.Is で syscall.EINVAL かどうかを判定できます。

⚠ 落とし穴 · lowerdir の順序を逆にすると、エラーは出ずに「更新が消える」

もう一度書きます。lowerdir は左が上（優先）です。 イメージのレイヤ配列は「後のものほど上」なので、そのまま : で繋ぐと上下が引っくり返ります。

そして最悪なことに、この間違いはマウントに成功します。カーネルには「どちらが正しい順か」を知る手段がありません。ただ言われたとおりに重ねるだけです。症状として現れるのは「新しいレイヤで入れたはずのコマンドが無い」「変更したはずの設定ファイルが古い」——つまりビルドの問題に見える症状です。

見分け方を1つ。/proc/mounts の lowerdir= を見て、一番左に来ているのが最後に積んだレイヤかどうかを確かめてください。ここが合っていれば順序は正しい。合っていなければ、rev の for 文を疑ってください。

Step 3workdir の制約 — 同じ FS 上・空であること

workdir は、私たちが中身を読むことも書くこともない場所です。カーネルが copy-up の途中経過などを一時的に置くために使います。「何もしなくていいなら気楽だ」と思うところですが、この workdir には2つの厳しい制約があり、どちらも破ると mount がその場で失敗します。

制約1: upperdir と同じファイルシステム上になければならない。

理由は copy-up の実装にあります。下層のファイルに書き込もうとしたとき、カーネルは workdir の中に一時ファイルを作って中身をコピーし、それを upperdir の目的地へ rename で移すという手順を踏みます。rename(2) は同じファイルシステムの中でしか成立しません。別のファイルシステムをまたぐ rename は EXDEV（cross-device link）というエラーになります。

この「原子的に完成品を置く」という性質が要るので、workdir と upperdir は同居していなければならない。違反すると mount の時点で EXDEV か EINVAL で弾かれます。たとえば upperdir をディスク上に置いて workdir を /tmp（tmpfs）に置く、といった配置がこれに当たります。

制約2: 空でなければならない。

前回の work の残骸——たとえばプロセスが強制終了して work/work/ の下に中途半端なファイルが残っている状態——があると、mount は EINVAL で落ちます。カーネルは「この作業場所は自分だけのものだ」という前提で使うので、知らないものが置いてあると使用を拒否します。

workdir の 2 つの制約 【制約1】upperdir と同じファイルシステム上に置く base/ ← 同じ FS の中 ├ upper/ ──┐ ├ work/ ──┴─ rename(2) で移動できる ✓ └ merged/ upper=/var/lib/…/upper （ディスク） work =/tmp/work （tmpfs） ── rename が FS をまたぐ ✗ → EXDEV / EINVAL 【制約2】空であること work/ work/ （空） ✓ └ work/ ← 前回の残骸 ✗ → EINVAL └ #3f2a…（中途半端な一時ファイル）

mydocker では、制約1は配置で、制約2はコードで満たしています。

制約1のほうは New の中でこう書いてありました。filepath.Join(base, "upper") と filepath.Join(base, "work")。同じ base の下に並べるので、どんな base を渡されても2つは必ず同じファイルシステムに乗ります。設定項目にせず、構造で保証しているわけです。コメントの3行目「ここでは同じ base の下に作っているので条件を満たす」がそれを言っています。

制約2のほうが emptyDir です。

internal/overlay/overlay.go
func emptyDir(dir string) error {
	entries, err := os.ReadDir(dir)
	if err != nil {
		return err
	}
	for _, e := range entries {
		if err := os.RemoveAll(filepath.Join(dir, e.Name())); err != nil {
			return err
		}
	}
	return nil
}

短い関数ですが、書き方に選択があります。

os.RemoveAll(dir) して os.MkdirAll(dir) し直す——つまりディレクトリごと作り直す——ほうが1行短くなります。それをしていないのは、dir 自身のパーミッションや所有者を保ちたいのと、作り直しの一瞬だけディレクトリが存在しない状態が生まれるのを避けたいからです。ここでは「入れ物は残して、中身だけ空にする」。

os.ReadDir で一覧を取り、os.RemoveAll で1つずつ消します。Remove ではなく RemoveAll なのは、残骸がディレクトリのこともあるからです（overlayfs は work/work/ というサブディレクトリを自分で作ります）。エラーは握りつぶさず、最初の1つで返します。消せない残骸がある状態でマウントに進んでも、どうせ EINVAL で落ちるので、ここで止まったほうが原因が分かりやすい。

そして呼び出しの位置。New の中で MkdirAll の直後・syscall.Mount の前に置いてあります。「毎回マウントの直前に必ず空にする」という順序にしておけば、前のコンテナがどんな終わり方をしていても、次の起動は必ず綺麗な work から始まります。

⚠ 落とし穴 · workdir の制約を破ると、原因を教えてくれない EINVAL が返る

overlayfs のマウント失敗は、ほとんどが invalid argument（EINVAL）です。何が invalid なのかは返ってきません。 犯人はだいたいこの3つのどれかです。

①workdir が upperdir と別のファイルシステムにある。②workdir が空でない。③lowerdir のパスの綴りが違う、または存在しない。

デバッグの順番としては、まず New が吐くエラーメッセージの中の opts 文字列をそのままコピーして、シェルで mount -t overlay overlay -o <その文字列> /tmp/試し と打ってみるのが速いです。dmesg の末尾に overlayfs が理由を書いていることもあります。カーネル側のヒントはそこにしか出ません。

なお workdir を upperdir の中に作るのも駄目です（upper/work のような配置）。workdir の中身が merged から見えてしまい、overlayfs はこれも拒否します。base の下に3つ並べて置くのが正解です。

Step 4書き込みは upperdir に溜まる（copy-up）

ここで、この章の一番気持ちのいい部分に来ます。コンテナの「使い捨て」の正体です。

overlayfs の読み書きのルールは、たった2行で書けます。

読むときは、上から順に探して最初に見つかったものを返す。
書くときは、必ず upperdir に書く。

問題は「下層にしか無いファイルを書き換えたい」ときです。下層は読み取り専用なので書けません。かといって「書けません」と返したら、ほとんどのプログラムが動かなくなります。overlayfs はここでcopy-upという動作をします。書き込みが起きた瞬間に、そのファイルを下層から upperdir へまるごとコピーし、コピーのほうに書くのです。以後そのパスを読むと、上層のコピーが先に見つかるので、下層の原本は永遠に隠れます。

copy-up — 「下層のファイルに書く」瞬間に何が起きるか 【1】書く前 【2】echo "v2" > /etc/conf を実行 upper │ （空） upper │ etc/conf ("v2") ← ここにコピーされて、書かれた │ │ ▲ lower │ etc/conf ("v1") lower │ etc/conf ("v1") ← 原本は無傷のまま隠れる │ bin/sh │ bin/sh ──────┼────────────── ──────┼────────────── merged │ etc/conf ("v1") merged │ etc/conf ("v2") ← 上が先に見つかる │ bin/sh │ bin/sh ※ コピーは「書き込みが起きたファイル1つ」だけ。bin/sh は触られていない。 ※ 読むだけなら copy-up は起きない。lower から直接読む（コピーもメモリも増えない）。

copy-up の効き方には、地味だけれど決定的な特徴があります。

コピーされるのは、触られたファイルだけ。 alpine の 516 ファイルのうち、コンテナが書き換えたのが1つなら、upperdir に増えるのは1ファイルです。残りの 515 は下層のまま、しかもすべてのコンテナで物理的に同じ実体を共有しています。素朴案の「起動のたびに 8.7 MB コピー」が、「書いたぶんだけ」に変わりました。

読むだけなら何も起きない。 コンテナが /bin/sh を実行しても、下層のページキャッシュをそのまま使います。10個のコンテナが同じ /bin/sh を動かしていても、メモリ上のコードは1つです。これがコンテナが「軽い」と言われる理由の実体で、起動時間が 12〜15 ms で済むのもここが効いています。

そして——本題です。

コンテナを消す、とは何をすることか containers/a10f2703bb37/ ├ merged/ ← まずアンマウント（重ね合わせを解く） ├ upper/ ← ★これを rm -rf する。コンテナが書いたものは全部ここ └ work/ ← これも rm -rf layers/sha256_55afa1ecc21d…/ ← ここには **指一本触れていない** └ 8.7 MB / 516 ファイル、次のコンテナがそのまま使う 「コンテナは使い捨て」の実装 = upperdir を捨てるだけ。

これがパッケージコメントの最後の一文、「コンテナを消すときは upperdir を捨てるだけでよい。イメージには指一本触れていない。」の意味です。

普段 docker run --rm と打つとき、私たちは何気なく「コンテナは使い捨て」と言っています。その「使い捨て」に対応する実装は、驚くほど素朴でした。書き込み先のディレクトリを1つ消すだけ。 イメージ側には何のロールバック処理もトランザクションも要らない。最初から一度も書いていないからです。

逆に言うと、この設計を成立させるために upperdir を1つに限定し、下層をすべて読み取り専用にしている、とも読めます。「消しやすさ」は後付けの機能ではなく、構造からの帰結です。

Step 5ホワイトアウト — 「消した」を tar でどう運ぶか

ここから後半、internal/image/extract.go の話に移ります。重ねる材料をどう作るかの話です。

問題設定から始めます。イメージのレイヤは tar で配られます。tar は「ファイルの一覧」です。ファイルを追加することは表現できます。ファイルを書き換えることも、同じパスで新しい中身を入れれば表現できます。では——

「下の層にあるファイルを、この層で削除した」を tar でどう表現するのでしょうか?

tar には「このファイルを消せ」というエントリの種類がありません。Dockerfile に RUN rm /etc/foo と書いたとき、そのレイヤの tar には何が入るのか。答えは約束ごとです。.wh. という接頭辞を付けた、中身が空のファイルを入れます。

tar の中の ホワイトアウト（whiteout） 【下の層の tar】 【上の層の tar】 etc/hosts etc/.wh.hosts ← "etc/hosts を消した" という意味 etc/passwd usr/bin/curl bin/sh var/.wh..wh..opq ← "var/ の下層の中身を全部隠す" この 2 つは **普通のファイルではない**。tar の上での「印」であって、 そのまま展開すると .wh.hosts という名前のゴミファイルが1つ増えるだけで、 肝心の etc/hosts は消えないまま残る。

接頭辞は .wh.（whiteout）。ディレクトリまるごとの場合は .wh..wh..opq（opaque）という、見るからに事故を避けたい名前になっています。extract.go の冒頭で、この2つを定数にしています。

internal/image/extract.go
// whiteoutPrefix は「このファイルは上の層で削除された」ことを表す印。
// 例: 下層の /etc/hosts を消したいとき、上層の tar には .wh.hosts というエントリが入る。
const whiteoutPrefix = ".wh."

// whiteoutOpaque は「このディレクトリの下層の中身をまるごと隠す」印。
const whiteoutOpaque = ".wh..wh..opq"

さて、これを普通のファイルとして展開すると何が起きるか。2つのことが同時に起きます。

①消えるべきファイルが残る。 下層の etc/hosts はそのままなので、重ね合わせると見えてしまいます。削除したはずのファイルが生き残る。イメージのビルド時に「秘密鍵を消した」つもりのレイヤがあったら、それは消えていません。

②変な名前のファイルが増える。 etc/.wh.hosts という 0 バイトのファイルが、コンテナの中に見えます。ls -a /etc したときに .wh. で始まるものが並んでいたら、それはこの処理を書き忘れた証拠です。

では、正しくはどうするか。ここで大事なのは、私たちがやりたいのは「削除」ではないということです。

思い出してください。レイヤは digest をディレクトリ名にしたキャッシュとして、他のイメージと共有したい。だから各レイヤは独立して展開されます。「下の層」は、展開している時点では手元に無いかもしれないし、あっても触ってはいけません。削除しようにも、削除する相手がここには居ないのです。

やりたいのは、「あとで重ね合わせたときに、カーネルがこれを見て下層を隠してくれる」印を残すこと。overlayfs には、そのための約束があります。

LINUX メモ · キャラクタデバイス 0:0 という約束

overlayfs は、上層にあるメジャー番号 0・マイナー番号 0 のキャラクタデバイスを「このパスは削除された」という印として扱います。lowerdir に同名のファイルがあっても、merged からは見えなくなります。デバイスファイル自体も見えません。ただ「無い」ように振る舞います。

なぜデバイスファイルなのか。普通のファイルや空ディレクトリでは「本物のファイル」と区別が付かないからです。0:0 というデバイス番号は Linux では実在のデバイスに割り当てられていないので、これを印として使っても本物と衝突しません。ファイルシステムのメタデータだけで表現でき、tar にも（キャラクタデバイスのエントリとして）そのまま入れられる。手近にあった空き番地を約束の場所にした、という感じの設計です。

作るには mknod(2) を使います。シェルなら mknod path c 0 0、Go なら syscall.Mknod(path, syscall.S_IFCHR|0o000, 0)。デバイスファイルを作るには root（正確には CAP_MKNOD）が要りますので、イメージの展開は特権付きで行う必要があります。

ちなみに ls -l でこの印を見ると、行頭が c（キャラクタデバイス）になり、サイズの欄が 0, 0 と表示されます。レイヤのディレクトリを直接覗いたときにこれが並んでいたら、それは正しく翻訳されている証拠です。

ホワイトアウトが効いている状態 upper（コンテナの書き込み） │ │ lower 上（レイヤ2） │ crw------- 0, 0 gone.txt ★印 │ version.txt("v2") lower 下（レイヤ1） │ -rw-r--r-- gone.txt │ version.txt("v1") keep.txt ─────────────────────────────┼──────────────────────────────────┤ merged（コンテナに見える） │ （gone.txt は無い） │ version.txt("v2") keep.txt ・レイヤ1 の gone.txt は **消えていない**。ディスク上に今もある ・レイヤ2 の 0:0 デバイスが、それを覆い隠している ・レイヤ2 を外して重ね直せば、gone.txt はまた見えるようになる

ディレクトリまるごとを隠す .wh..wh..opq のほうは、デバイスファイルではなく拡張属性で表現します。そのディレクトリに trusted.overlay.opaque="y" を付けると、overlayfs は「このディレクトリについては下層を一切見ない」と解釈します。

なぜ違う仕組みなのか。ディレクトリを 0:0 デバイスで潰してしまうと、そのディレクトリ自体が消えてしまうからです。.wh..wh..opq がやりたいのは「var/ は残したまま、var/ の下層の中身だけを無かったことにする」。ディレクトリを生かしたまま印だけ付ける必要があるので、ファイルの実体ではなくメタデータ（xattr）に印を置きます。

⚠ 落とし穴 · .wh. を普通のファイルとして展開してはいけない

archive/tar でループを回して、ヘッダの型どおりに素直に書き出す——という実装は、1レイヤのイメージでは完全に正しく動きます。alpine はレイヤ1枚なので、テストも通ります。

壊れるのは2枚目以降を持つイメージを引いたときです。しかも壊れ方が「エラー」ではありません。ls -a に .wh. で始まる 0 バイトのファイルが並び、消したはずのファイルが見えている。気付くのはずっと後です。

だから ExtractLayer は、ファイルの型で分岐するより先に名前で分岐します。ホワイトアウトの判定を switch hdr.Typeflag の前に置く——この順序が本質です。

Step 6翻訳するか、平坦化するか

実装に入る前に、私が実際に迷った分かれ道を1つ見せます。ホワイトアウトの扱いには、もう1つ素朴でまっとうな案があります。

案A: 全レイヤを1つのディレクトリに順に展開し、.wh. を見たら実体を削除する。

レイヤを下から順に同じディレクトリへ展開していけば、上のレイヤが下を自然に上書きします。.wh.foo に出会ったら、その時点で foo を os.Remove すればいい。overlayfs すら要りません。 出来上がった1枚のディレクトリを pivot_root の行き先にすれば動きます。第03章までの知識だけで完成します。

案A（平坦化） vs 案B（翻訳） 【案A】レイヤを1枚に潰す 【案B】レイヤごとに独立して展開する layers/ layers/ nginx-flat/ ← nginx 専用 sha256_aaa…/ ← ベース（共有できる） （ベース+nginx を潰したもの） sha256_bbb…/ ← nginx の層 redis-flat/ ← redis 専用 sha256_ccc…/ ← redis の層 （ベース+redis を潰したもの） nginx = aaa + bbb ベースの中身が **2 回** ディスクに乗る redis = aaa + ccc ベースだけ更新しても両方を作り直し ★ aaa は 1 つで済む digest でのキャッシュ判定が効かない ★ digest = ディレクトリ名 = 不変のキャッシュ

案Aを却下した理由は1つです。平坦化した結果は、そのイメージ専用になる。

前章でレイヤを digest ごとにキャッシュした意味を思い出してください。sha256:55afa1ecc21d… というレイヤは、それを使うどのイメージから見ても同じ中身です。だから一度取ってくれば、次からはネットワークに出なくていい。mydocker pull の2回目が「キャッシュ:（ネットワークにはアクセスしません）」と即答できるのは、この不変性のおかげでした。

平坦化すると、その不変性が壊れます。「ベース+nginx を潰したもの」には digest がありません。ベースを共有している別のイメージが来ても、共有できる部分が無い。ディスクは重複し、キャッシュの判定もできなくなります。

だから採ったのは案B——「overlayfs が理解する形への翻訳」です。

3つ、先に押さえておきたい点があります。

①filepath.EvalSymlinks(dest) で「本物の展開先」を求めている。 これが Step 7 の検証の基準点になります。dest 自体がシンボリックリンクだったり、途中に /var → /private/var のようなリンクが挟まっていたりすると、文字列比較での安全判定が意味をなさなくなります。比較する前に、両方を実体のパスに揃える——これが鉄則です。

GO メモ · archive/tar と compress/gzip

Go の標準ライブラリだけで tar.gz を読めます。compress/gzip の Reader は io.Reader を受け取って io.Reader を返し、archive/tar の Reader も io.Reader を受け取ります。つまりそのまま数珠つなぎにできます。

問題は「今流れてくるのが gzip かどうか」です。レイヤの mediaType は application/vnd.oci.image.layer.v1.tar+gzip なので普通は gzip ですが、非圧縮の tar が来ることもあります。そこで先頭2バイトを覗いて自分で見分けます。gzip のマジックナンバーは 1f 8b です。

ただし「覗く」ためには読んでしまった2バイトを戻せなければいけません。io.Reader にはそんな機能はない。ここで bufio.Reader の Peek が効きます。Peek(n) は先頭 n バイトを返すが、読み位置は進めません。 バッファに溜めて見せてくれるだけです。

internal/image/extract.go
// newTarReader は gzip 圧縮されている場合だけ展開してから tar として読む。
// レイヤは通常 tar.gz だが、非圧縮の tar が来ることもあるので先頭2バイトで見分ける。
func newTarReader(r io.Reader) (*tar.Reader, func(), error) {
	br := bufio.NewReader(r)
	magic, err := br.Peek(2)
	if err != nil && !errors.Is(err, io.EOF) {
		return nil, func() {}, err
	}
	if len(magic) == 2 && magic[0] == 0x1f && magic[1] == 0x8b {
		zr, err := gzip.NewReader(br)
		if err != nil {
			return nil, func() {}, fmt.Errorf("gzip として読めませんでした: %w", err)
		}
		return tar.NewReader(zr), func() { zr.Close() }, nil
	}
	return tar.NewReader(br), func() {}, nil
}

Peek(2) のエラーで io.EOF だけ許しているのは、2バイト未満の入力（空のレイヤなど）を異常扱いしないためです。その場合 magic の長さが 2 未満になるので、次の if が自然に false になり、素の tar として扱われて即 EOF で終わります。

戻り値の func() が2種類あることにも注目してください。gzip のときは func() { zr.Close() }、そうでないときは何もしない func() {}。呼び出し側に if を書かせないための書き方です。Go では「nil かもしれない Closer」より「何もしない関数」のほうが安全に扱えます。

tr.Next() でヘッダを1つ進める。 archive/tar の Reader は「次のエントリのヘッダを読む → tr 自身をそのエントリの中身の io.Reader として使う」という作りです。io.EOF が返ったら終わり。errors.Is を使っているのは、ラップされたエラーでも判定できるようにするためです。

PAX ヘッダを飛ばす。 TypeXGlobalHeader と TypeXHeader は、長いパス名や大きな uid を運ぶためのメタ情報のエントリで、実体のファイルではありません。archive/tar は中身を解釈して次のヘッダに反映してくれるので、私たちは無視すればいい。ここで無視し忘れると、PaxHeaders/… という妙なファイルが展開先に生えます。

safeJoin でパスを検証しつつ絶対パスに変換。 Step 7 の主役です。ここでエラーが出たらその場で展開を打ち切ります。「そのエントリだけ飛ばして続行」ではありません。展開先の外を狙うエントリが1つでも入っているイメージは、もう信用できないからです。

base と parent に分ける。 ホワイトアウトの判定はファイル名の部分だけで行います。etc/.wh.hosts なら base は .wh.hosts、parent は <dest>/etc。パス全体に strings.Contains をかけたりすると、/opt/.wh.d/normal.txt のようなパスで誤判定します。

opaque の処理。 base が .wh..wh..opq ちょうどなら、その親ディレクトリに xattr を付けます。var/.wh..wh..opq というエントリが意味するのは「var/ を opaque にせよ」なので、印を付ける相手は parent です。付ける前に MkdirAll(parent) しているのは、tar の中でディレクトリのエントリが先に来ているとは限らないからです。

xattr が付けられなくてもエラーにしない。 ここは判断が分かれるところですが、trusted.* 名前空間には CAP_SYS_ADMIN が要るので、権限の無い環境では必ず失敗します。そこで展開全体を止めてしまうと、非特権環境でイメージを覗くことすらできなくなる。かといって黙って通すと、後で「下層が透けて見える」という分かりにくい不具合になります。だから標準エラーに警告を出して続行する、という中間を採りました。「黙って無視せず警告する」とコメントに書いてあるのはそういう意味です。

.wh. の処理。 base が .wh. で始まるなら、接頭辞を外した名前が「消したい相手（victim）」です。.wh.hosts → hosts。parent と繋いで victim のフルパスを作ります。

os.RemoveAll(victim) を先にやる。 エラーを _ で捨てているのは、無くて当たり前だからです。ではなぜ呼ぶのか。同じレイヤの tar の中で、先に hosts の実体が来ていた場合に備えています。その状態で Mknod すると EEXIST で失敗します。順序に依存しないようにするための1行です。

syscall.Mknod(victim, syscall.S_IFCHR|0o000, 0)。 ここが翻訳の核心です。第2引数はモードで、S_IFCHR（キャラクタデバイスである）に 0o000（誰にも読み書きさせない）を OR しています。第3引数の 0 がデバイス番号で、メジャー 0・マイナー 0。この 0 こそが overlayfs との約束です。

そして Mknod のエラーは握りつぶしません。ここが失敗するということは削除の印を作れないということで、そのまま進めば消えるべきファイルが見えるイメージが出来上がります。静かに壊れるより、その場で止まったほうがいい。

どちらの分岐も count++ して continue。 印もエントリとして数えます。そして continue で型ごとの分岐に絶対に到達させません。ホワイトアウトのエントリは tar 上ではただの空ファイル（TypeReg）なので、下まで流すと普通のファイルとして書き出されてしまいます。

LINUX メモ · 拡張属性（xattr）と trusted 名前空間

拡張属性（extended attributes）は、ファイルやディレクトリに「名前 = 値」のメタデータを追加でぶら下げる仕組みです。中身（データ）でもなく、パーミッションや時刻（標準の inode 情報）でもない、第三の置き場所だと思ってください。setfattr / getfattr コマンドで人間も触れます。

名前は必ず「名前空間.属性名」の形をしていて、4つの名前空間があります。

  • user.* — 誰でも付けられる。アプリケーションが自由に使う
  • trusted.* — CAP_SYS_ADMIN が無いと読み書きできない。一般ユーザーからは存在すら見えない
  • security.* — SELinux などのセキュリティモジュール用
  • system.* — ACL などカーネルが使う

overlayfs が trusted.overlay.* を使うのには理由があります。もし user.* を使っていたら、コンテナの中から自分で「このディレクトリは opaque だ」と宣言できてしまう。ファイルシステムの構造をユーザーが書き換えられるということです。trusted.* にしておけば、印を付けられるのは特権を持つ側（＝私たちの展開処理）だけになります。

実務上の注意が1つ。ファイルシステムによっては xattr が使えません。 古い設定の tmpfs や、一部のネットワークファイルシステムがそうです。レイヤの置き場所をそういう場所にすると、opaque の印が黙って落ちます。ExtractLayer が警告を標準エラーに出しているのは、まさにこの状況を人間に気付かせるためです。

Step 7tar 展開のパス検証（Zip Slip）

ここはセキュリティの話です。この章で一番、手を抜くと本当に危ないところです。

前提を確認します。私たちが展開している tar は、私たちが作ったものではありません。 レジストリからダウンロードしてきた、他人が作ったバイト列です。前章で digest を検証したので「配信途中で改竄されていない」ことは保証できますが、作った本人が悪意を持っている可能性は digest では何も潰せません。正しく配信された悪意あるイメージ、というものが存在します。

tar のエントリ名は、ただの文字列です。カーネルもレジストリも、その文字列が「展開先の中を指しているか」など気にしません。だから展開する側が確かめるしかない。この種の脆弱性には Zip Slip という名前が付いています（zip でも tar でも同じ話です）。

素朴な攻撃はすぐ思い付きます。

素朴な 2 つの手口 【手口1】絶対パス エントリ名: /etc/passwd ナイーブな実装が filepath.Join(dest, "/etc/passwd") をすると… → Join は先頭の / を潰すので dest/etc/passwd になる（この実装なら助かる） → だが自前で dest + name と文字列連結していると /etc/passwd に直撃 【手口2】.. で登る エントリ名: ../../../../etc/passwd dest/ = /var/lib/mydocker/layers/sha256_xxx .. を 4 回登ると /var/lib → /var/lib/../../etc/passwd … 登り切れば本物の /etc/passwd に届く

この2つは、名前を見れば分かります。先頭が / なら拒否、要素に .. があれば拒否。これで手口1と手口2は塞がります。

——そして、私が実装中に気付いたのは、この2つだけでは足りないということでした。

3つめの手口は、名前がまったく無害に見えます。

【手口3】シンボリックリンクで踏み台を作る エントリ1: foo -> / （シンボリックリンク。名前に .. も / も無いので ①② を通過） エントリ2: foo/etc/passwd （名前は無害。しかし書き込み先は本物の /etc/passwd） 展開の様子: ステップ1 ステップ2 dest/ dest/ └ foo ─────────┐ └ foo ─────────┐ ▼ ▼ / （ホストの根） / └ etc/ └ passwd ★ここに書かれる ・エントリ1 の名前は "foo"。絶対パスでも .. でもない → ① ② を通過 ・エントリ2 の名前は "foo/etc/passwd"。これも絶対パスでも .. でもない → ① ② を通過 ・しかし dest/foo は / を指しているので、実際の書き込み先は /etc/passwd 文字列だけを見ていては絶対に防げない。**ファイルシステムの実体を見る**必要がある。

手口3の核心は、攻撃者が2手に分けていることです。1手目で踏み台（シンボリックリンク）を置き、2手目でそこを通り抜ける。それぞれの手は完全に無害です。組み合わせだけが有害なので、エントリ名を1つずつ眺めていても永遠に見つかりません。

防ぐには、書き込む直前に、そのパスの親が本当に dest の中にあるかをファイルシステムに聞くしかありません。それが3段目の検証です。

safeJoin の全文です。

internal/image/extract.go
// safeJoin は tar のエントリ名を dest 配下の絶対パスに変換する。
// ⚠ ここがイメージ展開のセキュリティの要である。3段で守る:
//
//  1. 絶対パス（"/etc/passwd"）を拒否する
//  2. ".." を含むパス（"../../etc/passwd"）を拒否する
//  3. 途中のディレクトリが dest の外を指すシンボリックリンクになっていないか確認する
//
// 3 が要るのは、レイヤが先に「foo -> /」というリンクを作り、
// 次に "foo/etc/passwd" を書こうとする手口があるため。1 と 2 だけでは通ってしまう。
func safeJoin(realDest, name string) (string, error) {
	if name == "" {
		return "", ErrPathEscape
	}
	// tar の中の区切りは常に "/"
	clean := filepath.Clean("/" + strings.ReplaceAll(name, "\\", "/"))
	if strings.HasPrefix(name, "/") {
		return "", ErrPathEscape
	}
	for _, part := range strings.Split(name, "/") {
		if part == ".." {
			return "", ErrPathEscape
		}
	}
	target := filepath.Join(realDest, clean)
	if target != realDest && !strings.HasPrefix(target, realDest+string(os.PathSeparator)) {
		return "", ErrPathEscape
	}

	// 途中の実体がシンボリックリンクで外へ抜けていないかを確かめる。
	// 親ディレクトリが既に存在する場合だけ検査すればよい（無ければこれから作る＝外へは出ない）。
	parent := filepath.Dir(target)
	if realParent, err := filepath.EvalSymlinks(parent); err == nil {
		if realParent != realDest && !strings.HasPrefix(realParent, realDest+string(os.PathSeparator)) {
			return "", ErrPathEscape
		}
	}
	return target, nil
}

1段ずつ読みます。

0段目: 空の名前を拒否。 name == "" は正常な tar には現れません。壊れた tar か、細工されたものです。

正規化。 strings.ReplaceAll(name, "\\", "/") でバックスラッシュをスラッシュに揃えます。tar の中の区切りは常に / と決まっているので、\ が出てくること自体が異常ですが、Windows 由来のツールが作った tar で混ざることがあります。放っておくと ..\..\etc のような形で .. の検査をすり抜けかねないので、先に潰します。

その上で filepath.Clean("/" + …)。先頭に / を付けてから Clean することで、.. が根より上へ突き抜けないよう Go 側が丸めてくれます。/a/../../b は /b になります。

1段目: 絶対パスを拒否。 strings.HasPrefix(name, "/")。ここで見ているのは clean ではなく元の name です。clean は必ず / で始まるように作ったので、そちらを見ても意味がありません。「攻撃者が書いた文字列そのもの」を検査するのが大事です。

2段目: .. を含むパスを拒否。 こちらも元の name を / で分割して、要素として .. ちょうどのものがあれば拒否します。strings.Contains(name, "..") のような雑な検査にしていないのは、foo..bar や a..b/c のような正当なファイル名を誤って弾かないためです。逆に、要素単位で見れば .. は絶対に正当なファイル名になりません。

連結と、念のための文字列検査。 filepath.Join(realDest, clean) で目的地を作り、それが realDest そのものか、realDest/ で始まるかを確かめます。1段目・2段目を通っていればここは必ず通るはずですが、「はず」を残さないための帯とサスペンダーです。realDest+string(os.PathSeparator) と区切り文字まで含めて比較しているのが要点で、これを忘れると /var/lib/mydocker/layers/sha256_aaa に対して /var/lib/mydocker/layers/sha256_aaa_evil が前方一致で通ってしまいます。

3段目: 親の実体を確かめる。 ここが手口3への答えです。

filepath.Dir(target) で親ディレクトリを取り、filepath.EvalSymlinks に渡します。この関数はパスに含まれるシンボリックリンクを全部辿って、実体のパスを返します。dest/foo が / を指すリンクなら、dest/foo/etc の実体は /etc です。文字列としては dest/ の中に見えていたものが、実体では外に出ていることがここで初めて分かります。

あとは同じ前方一致の検査を、今度は実体のパスに対して行うだけ。realParent が realDest の中でなければ拒否します。

エラーを無視して err == nil のときだけ検査しているのはなぜか。 EvalSymlinks は、パスが存在しないとエラーを返します。tar の展開では親ディレクトリがまだ作られていないことが普通にあります（これから MkdirAll するので）。まだ存在しないディレクトリは、当然シンボリックリンクでもないので、外を指しようがない。だから「存在するときだけ検査すればよい」——コメントの「無ければこれから作る＝外へは出ない」がそれを言っています。

GO メモ · filepath.EvalSymlinks

filepath.EvalSymlinks(path) は、パスに含まれるシンボリックリンクをすべて解決した実体のパスを返します。最後の要素だけでなく、途中の全要素を辿るのがポイントです。/a/b/c の b がリンクなら、そこも展開されます。パスが存在しない場合はエラーになります。

似た関数に filepath.Abs（相対パスを絶対パスにするだけ。リンクは辿らない）と filepath.Clean（文字列として . や .. を畳むだけ。ファイルシステムを一切見ない）があります。この3つの違いを取り違えると、そのまま脆弱性になります。 Clean は文字列処理、EvalSymlinks はファイルシステムへの問い合わせです。

正直に書いておくと、EvalSymlinks による検査はTOCTOU（検査した瞬間と使う瞬間のずれ）に対して完璧ではありません。検査した直後に別のプロセスがそのパスをリンクに差し替えれば、理屈の上ではすり抜けます。本当に厳密にやるなら openat2(2) の RESOLVE_BENEATH のように、カーネルに「この下から出るな」と指示する仕組みを使います。この教材では標準ライブラリの範囲に留めましたが、限界があることを知って使っているか、知らずに使っているかは大きな違いです。

もう1つ、書き込みそのものにも同じ穴があります。writeFile を見てください。

internal/image/extract.go
func writeFile(target string, r io.Reader, mode os.FileMode) error {
	// 既存を上書きするときは一度消す。シンボリックリンクを開くと
	// リンク先（＝展開先の外かもしれない）に書いてしまうため。
	_ = os.Remove(target)
	f, err := os.OpenFile(target, os.O_CREATE|os.O_WRONLY|os.O_EXCL, mode)
	if err != nil {
		return err
	}
	if _, err := io.Copy(f, r); err != nil {
		f.Close()
		return err
	}
	return f.Close()
}

普通に書くなら os.OpenFile(target, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, mode) です。既にあれば切り詰めて上書き。1行で済みます。

それが穴になります。 target が既にシンボリックリンクとして存在していたら、open はリンクを辿った先を開きます。リンク先が /etc/passwd なら、そこに tar の中身が書かれる。safeJoin の3段目は親ディレクトリを見ますが、最後の要素そのものがリンクである場合はそこでは捕まえていません。

O_TRUNC と Remove→O_EXCL の違い 【危ない】O_TRUNC で開く dest/foo は既に「-> /etc/passwd」というリンク open("dest/foo", O_CREATE|O_WRONLY|O_TRUNC) └─ リンクを辿る ─▶ /etc/passwd を開いて 0 バイトに切り詰め、書き込む ✗ 【安全】一度 Remove してから O_EXCL で作る os.Remove("dest/foo") ← リンク **そのもの** を消す（リンク先は無傷） open("dest/foo", O_CREATE|O_WRONLY|O_EXCL) └─ 何も無い場所に新規作成。既にあれば EEXIST でエラー ✓

だから必ず一度 os.Remove してから作ります。os.Remove はシンボリックリンクを辿らず、リンクそのものを消します（unlink(2) の挙動です）。リンク先の /etc/passwd には何も起きません。

そして開くときは O_TRUNC ではなく O_EXCL。「既に存在したらエラー」という意味です。直前に Remove しているので通常は存在せず、もし存在したら、それは想定外の何かが起きた証拠なので止まるべきです。Remove と O_EXCL は必ずセットで使います。

順に見ます。

TypeDir。 0o755 で作って、本来の mode は dirs に控えておきます。Step 6 で触れた「後で当て直す」ためです。

TypeReg。 writeFile に tr をそのまま渡します。archive/tar の Reader は、現在のエントリの中身を読む io.Reader としてそのまま振る舞います。io.Copy がエントリの終わりで自然に止まってくれるので、サイズを自分で数える必要はありません。

TypeSymlink。 ここが面白いところです。リンク先（hdr.Linkname）は検証していません。 foo -> / というリンクを、そのまま作ります。

危なく見えますが、正しいのです。理由は2つ。第一に、リンク先が展開先の外を指すこと自体は正当です。コンテナの中の /bin/sh -> /bin/busybox のようなリンクは、展開先ディレクトリを基準にすれば「外」を指しています。コンテナが pivot_root した後の世界では正しく解決されます。ここで弾いたら、まともなイメージがほとんど展開できません。

第二に、危ないのはリンクを作ることではなく、リンクを通り抜けて書き込むことです。そして通り抜けようとした瞬間に safeJoin の3段目が捕まえます。コメントの「実際にそこへ書き込むときに safeJoin が弾く」はこの意味です。防御を、危険が実現する一点に集中させている。

TypeLink（ハードリンク）。 こちらはリンク先も safeJoin にかけます。シンボリックリンクと違い、ハードリンクは作った瞬間に相手の inode そのものを掴みます。/etc/shadow へのハードリンクを展開先に作られたら、レイヤのディレクトリ経由でホストの /etc/shadow が読めてしまう。しかもハードリンクは実体そのものなので、後から「通り抜けるとき」に捕まえる機会がありません。作る前に止めるしかないので、ここで検証します。

シンボリックリンクは検証せず、ハードリンクは検証する——この非対称は、気まぐれではなく2つのリンクの性質の違いから来ています。

デバイス・FIFO。 hdr.FileInfo().Mode().Perm() でパーミッションを取り、型に応じて S_IFCHR / S_IFBLK / S_IFIFO を OR します。mknod(2) のモード引数は「ファイル種別 + パーミッション」を1つの整数に詰めたものなので、この OR が必要です。デバイス番号は mkdev で組み立てます。

ここでは失敗しても警告だけで続行します。デバイスノードの作成には特権が要り、非特権環境では必ず失敗するからです。そしてデバイスノードが無くてもコンテナはたいてい動きます（/dev は起動時に別途用意します）。Step 6 のホワイトアウトの Mknod がエラーで止まるのと対照的ですが、これも理由があります。ホワイトアウトが作れないと、消えるべきファイルが見える＝正しさが壊れる。 デバイスノードが作れないのは機能が1つ減るだけ。壊れ方の質が違います。

所有者。 Chown と Lchown を型で使い分けています。Chown はシンボリックリンクを辿るので、リンクに使うとリンク先の所有者を変えてしまいます。リンクそのものの所有者を変えるには Lchown。ここも「辿るか辿らないか」の違いです。エラーを _ で捨てているのは、非 root で展開する場合に必ず失敗するからで、所有者が合わないことは致命ではありません。

最後にディレクトリのパーミッションを当てる。 for i := len(dirs) - 1; i >= 0; i-- と逆順に回しています。dirs には tar に現れた順（＝浅いものから深いものへ）で入っているので、逆順に回すと深いものから当たります。浅いディレクトリを先に 0555 にしてしまうと、その下のディレクトリを chmod できなくなるかもしれない。深い側から順に閉じていけば、その心配がありません。

// mkdev は major/minor からデバイス番号を組み立てる（Linux の makedev 相当）。
func mkdev(major, minor uint32) uint64 {
	return uint64(minor&0xff) | (uint64(major&0xfff) << 8) |
		((uint64(minor) &^ 0xff) << 12) | ((uint64(major) &^ 0xfff) << 32)
}

C の makedev() マクロをそのまま Go に書き写したものです。デバイス番号は「メジャーとマイナーを1つの整数にビットで詰め込んだもの」で、歴史的な事情から詰め方が飛び飛びになっています。マイナーの下位8ビットが最下位に、メジャーの下位12ビットがその上に、残りがさらに上に。&^ は Go 独自の AND NOT 演算子で、x &^ 0xff は「下位8ビットを落とす」という意味です。

この式を暗記する必要はまったくありません。「デバイス番号は単なる整数のパックである」ことだけ分かっていれば十分です。ちなみに Step 6 で使った 0:0 は、この式に入れると当然 0 になります。

Step 8アンマウントの安全 — ここを間違えるとイメージが消える

最後です。そして、この章で一番怖い話です。

コンテナを消す手順は、Step 4 で見たとおり2つです。①重ね合わせをアンマウントする。②upper と work を rm -rf する。 順番はこれ以外にありません。

では、①が失敗したのに②に進んだら、何が起きるでしょうか。

アンマウントに失敗したまま rm -rf したときに起きること 【正しい順序】 【①の失敗を無視した場合】 1. umount merged ✓ 1. umount merged ✗ EBUSY（無視した） 2. rm -rf merged upper work 2. rm -rf merged upper work │ merged は空のディレクトリに戻って │ merged はまだ overlay のまま いるので、消えるのは入れ物だけ ▼ rm が merged の中を歩く layers/sha256_…/ ← 無傷 ✓ = overlay 越しに **lowerdir の中身** を消しにいく ▼ layers/sha256_55afa1ecc21d…/ が空になる ✗✗✗ = **イメージのキャッシュが破壊される** 他のコンテナも、次の pull も、全部道連れ

rm -rf merged は、merged が「重ね合わせの窓」であることを知りません。ただディレクトリを歩いて、見えるファイルを消していきます。その窓の向こうにあるのは lowerdir の実体、つまり全コンテナが共有しているイメージです。

しかも overlayfs のルール上、merged 越しの削除は本来なら「上層にホワイトアウトを作る」だけのはずです。しかし upper と work も同時に rm -rf の対象になっているので、削除の途中で upper が消え、overlayfs の整合性が崩れ、その先で何が起きるかは順序次第になります。運が悪ければ下層まで届きます。「たぶん大丈夫」で済ませてよい種類の話ではありません。

そして厄介なのは、umount は日常的に失敗するということです。特別な異常事態ではありません。

  • コンテナのプロセスがまだ生きている（merged を根にしているので当然使用中）
  • 自分のシェルの作業ディレクトリが merged の中にある（cd したまま忘れた）
  • そのファイルシステム上のファイルを誰かが開いたままにしている
  • merged の下にさらに別のマウント（/proc など）が残っている

どれも普通に起きます。返ってくるのは EBUSY（device or resource busy）。この EBUSY を握りつぶすと、イメージが消えます。

Unmount の全文です。コメントに、今の話がそのまま書いてあります。

internal/overlay/overlay.go
// Unmount は重ね合わせを外す。
//
// ⚠ umount は EBUSY（デバイスが使用中）で日常的に失敗する。
// コンテナのプロセスが残っていたり、シェルの作業ディレクトリがその中だったりするだけで起きる。
// ここでエラーを握りつぶして呼び出し元が rm -rf に進むと、
// **マウント越しに lowerdir の実体（＝イメージの中身）まで消える。**
// だから失敗は必ずエラーとして返す。呼び出し元は削除に進んではいけない。
func (m *Mount) Unmount() error {
	if err := syscall.Unmount(m.Merged, 0); err != nil {
		// MNT_DETACH は「今すぐ切り離し、参照が切れたら実際に外す」遅延アンマウント。
		// EBUSY のときの最後の手段として一度だけ試す。
		if err2 := syscall.Unmount(m.Merged, syscall.MNT_DETACH); err2 != nil {
			return fmt.Errorf("overlay を外せませんでした (%s): %w", m.Merged, err)
		}
	}
	// ★本当に外れたかを確認してからでなければ、呼び出し元は削除に進んではいけない。
	if IsMountPoint(m.Merged) {
		return fmt.Errorf("overlay がまだマウントされたままです: %s", m.Merged)
	}
	return nil
}

3段構えになっています。

1段目: 普通の umount。 syscall.Unmount(m.Merged, 0)。うまくいけばこれで終わりです。

2段目: MNT_DETACH で遅延アンマウント。 これは「今すぐ名前空間のツリーから切り離す。実際の解除は、最後の参照が消えたときに行う」という指定です（umount -l と同じ）。使用中でも切り離せます。

これを1回だけ試すのがミソです。MNT_DETACH は便利ですが、問題を先送りするだけでもあります。切り離しても、プロセスがまだファイルを掴んでいれば実体は残り続けます。だから「最後の手段として一度だけ」。無限にリトライしたり、常用したりはしません。

返すエラーは err（1回目のもの）で、err2 ではないのも意図的です。人間が知りたいのは「EBUSY だった」という元の原因であって、「MNT_DETACH も駄目だった」という後始末の失敗ではありません。

3段目: 本当に外れたかを確認する。 ここが Unmount の一番大事な行です。

syscall.Unmount が nil を返した——それでも IsMountPoint で確かめます。「成功したと言っているのだから外れているはずだ」と信じません。MNT_DETACH で切り離した場合、システムコールは成功しますが実体はまだそこにあることがあります。そのまま rm -rf に進めば、最初のシナリオに一直線です。

ここでエラーを返せば、呼び出し元は削除に進みません。コンテナのディレクトリは残りますが、イメージは無事です。 ディスクに残骸が残るのと、全コンテナ共有のイメージが壊れるのとでは、被害の桁が違います。迷ったら、消さない側に倒す。

その確認をする IsMountPoint は、驚くほど単純です。

internal/overlay/overlay.go
// IsMountPoint はパスがマウントポイントかを返す。
// 自分の st_dev と親ディレクトリの st_dev を比べる（mountpoint(1) と同じ考え方）。
func IsMountPoint(path string) bool {
	var st, parent syscall.Stat_t
	if err := syscall.Lstat(path, &st); err != nil {
		return false
	}
	if err := syscall.Lstat(filepath.Dir(path), &parent); err != nil {
		return false
	}
	return st.Dev != parent.Dev
}

原理はこうです。stat の結果には st_dev（そのファイルが乗っているデバイスの番号）が入っています。同じファイルシステムの中にあるものは、必ず同じ st_dev を持ちます。

st_dev の比較でマウントポイントを見分ける 【マウント中】 【アンマウント後】 containers/a10f…/ st_dev = 8:1 containers/a10f…/ st_dev = 8:1 └ merged/ st_dev = 0:47 └ merged/ st_dev = 8:1 ▲ ▲ 親と違う → マウントポイント ✓ 親と同じ → ただのディレクトリ ✓ ※ merged の中身が overlay になった瞬間、merged 自身の st_dev が overlay の匿名デバイス番号に変わる。だから親と比べるだけで分かる。

ディレクトリに別のファイルシステムがマウントされると、そのディレクトリを stat したときに返るのはマウントされた側の情報になります。だから merged の st_dev は overlay のものになり、親ディレクトリ（普通のディスク上のディレクトリ）と違う値になる。アンマウントすれば元のディレクトリが見えるようになり、親と同じ値に戻ります。親子で st_dev を比べるだけでマウントポイントかどうかが分かる——これは mountpoint(1) コマンドがやっているのとまったく同じ判定です。

Stat ではなく Lstat を使っているのは、パスがシンボリックリンクだった場合に辿らずにリンク自身を見るためです。リンクを辿ってしまうと、まったく別の場所のマウント状態を見て「外れている」と誤答しかねません。

エラー時に false を返す点は、少し議論の余地があります。Lstat が失敗するのはパスが存在しないときなので、「存在しない＝マウントポイントではない」は妥当です。ただし Unmount の文脈では、false は「削除に進んでよい」という意味になります。そこは Unmount 側が syscall.Unmount の成否も見ているので、二重の関所として機能しています。

	return n, nil
}

/proc/mounts の各行は空白区切りで「デバイス マウント先 種別 オプション dump pass」の6欄です。3欄目（f[2]）が種別なので、そこが "overlay" の行を数えれば張られている overlay の数が分かります。len(f) >= 3 の確認は、空行やちぎれた行で index out of range にならないためです。

この関数がなぜ大事か。リークは、静かに起きるからです。 アンマウント漏れがあっても、その場では誰も困りません。mydocker run は普通に成功します。ただ /proc/mounts の行が1つずつ増えていく。100 回動かして初めて「なんか重い」と気付く。

だから「増えていないこと」を数で確かめる。mydocker info の「overlay 数」も、E2E の「前 0 件 → 後 0 件」も、この関数の戻り値です。

⚠ 落とし穴 · umount の失敗を無視して rm -rf に進む

この章で唯一、取り返しのつかない落とし穴です。他の間違いは動かないか変な挙動になるだけですが、これはデータを消します。しかも消えるのは自分のコンテナのデータではなく、全コンテナが共有しているイメージのキャッシュです。

典型的なコードはこう書かれます。「後片付けはベストエフォートでいいや」という気持ちで。

_ = m.Unmount() の次の行に os.RemoveAll(base)。これだけです。_ = が付いた瞬間に地雷になります。

規律は3つ。①Unmount は必ずエラーを返す。②呼び出し元はエラーなら削除に進まずそこで戻る。状態ファイルも残して人間が調べられるようにする。③削除の直前にもう一度マウント状態を確認する（RemoveRecord がやっています）。

「残骸が残るのは格好悪い」と思うかもしれません。残骸は人間が消せます。消えたイメージは戻りません。

▸ 動かして確認

実行中のコンテナに rm をかけると、削除の前に止まります。

$ mydocker rm 0c1be9ad663a
mydocker: コンテナ 0c1be9ad663a はまだ実行中です。先に終了させてください

逆に、mydocker 自身を SIGKILL して後片付けが走らなかった状況を作ると、overlay が1つ残ります。mydocker ps は 0 件と言っているのに、mount には残っている——これが「リーク」の見え方です。そして rm で回収できます。

$ mydocker ps
CONTAINER ID   IMAGE   COMMAND   PID   STATUS   CREATED
合計 0 件
$ mount | grep -c overlay
1
$ mydocker rm f280be2460e3
f280be2460e3
$ mount | grep -c overlay
0

1 → 0。この数字が戻ることを、目で確かめられるようにしておくのが大事です。数えられないものは、漏れていても気付けません。

つまずき FAQ

mount -t overlay が invalid argument で失敗します。どこから見ればいいですか?

overlayfs のマウント失敗はほぼ EINVAL で、カーネルは理由を教えてくれません。当たる順番を決めておくと速いです。

①workdir は空か。 前回の残骸、特に work/work/ が残っていると落ちます。emptyDir を通しているか確かめてください。②workdir と upperdir は同じファイルシステムか。 stat -fc %T を両方に打って、種別が一致するか見ます。③lowerdir のパスは全部存在するディレクトリか。 綴り違い、digest の桁落ち、シンボリックリンク。④パスに : や , が混ざっていないか。

それでも分からなければ dmesg の末尾を見てください。overlayfs はカーネルログに理由を書くことがあります。ユーザー空間には返ってこない情報がそこにだけ出ます。

あと一つ。New が返すエラーメッセージには opts 文字列がそのまま入っています。それをコピーして mount -t overlay overlay -o <その文字列> /tmp/試し と手で打つのが、結局いちばん速い切り分けです。

コンテナの中で作ったファイルは、ホストのどこにありますか? 直接見てもいいんですか?

/var/lib/mydocker/containers/<ID>/upper/ の下に、コンテナから見たのと同じパス構造でそのままあります。コンテナが /etc/foo を作ったら upper/etc/foo です。普通のファイルなので、ホストから cat できます。

見るだけなら問題ありません。デバッグでは非常に役に立ちます。「このコンテナは結局どのファイルを触ったのか」が find upper -type f で一望できます。

書き換えるのは避けてください。 overlayfs は「upperdir と lowerdir はマウント中に外部から変更されない」ことを前提にしています。マウント中に upper を横から書き換えると、カーネルのキャッシュと実体がずれて、コンテナから見える内容が不定になります。読むのは自由、書くのはアンマウント後。

lowerdir の順序が逆だと「更新が反映されない」とのことですが、どうやって気付けばいいですか?

症状からは気付けません。見に行くしかないです。

grep overlay /proc/mounts で自分のマウント行を出し、lowerdir= の値を : で分解してください。一番左に来ているのが、イメージの一番最後のレイヤ（＝最新の変更が入っている層）かどうか。ここが合っていれば順序は正しいです。

もう1つ確実な方法があります。同じファイルを2つのレイヤに置いて、中身を変えておくこと。E2E がやっているのがまさにこれで、下の層に version.txt（中身 v1）、上の層に version.txt（中身 v2）を置きます。重ねて v2 が見えれば正しい。v1 が見えたら逆さまです。この「対照」を1つ用意しておくだけで、順序のバグは一生踏まなくなります。

ちなみに alpine のようにレイヤが1枚のイメージでは、逆順にしても同じ文字列になるのでバグが表に出ません。1枚のイメージだけでテストしていると、この地雷は必ず後で踏みます。

レイヤを展開したディレクトリの中に .wh. で始まるファイルがありました。これは正常ですか?

異常です。 ホワイトアウトの翻訳が働いていない証拠です。

正しく翻訳されていれば、そこにあるのは .wh. という名前のファイルではなく、接頭辞を外した名前のキャラクタデバイスです。ls -l して行頭が c、サイズの欄が 0, 0 になっていれば正解。

.wh.foo という 0 バイトの通常ファイルが見えているなら、①ExtractLayer のホワイトアウト判定を通っていない（switch hdr.Typeflag より後ろに置いてしまった、など）か、②そもそも他のツールで展開したディレクトリを使っている、のどちらかです。

opaque のほうは目に見えません。xattr なので ls には出ない。確かめるには getfattr -n trusted.overlay.opaque -m - <ディレクトリ> のように明示的に問い合わせる必要があります（trusted.* なので root で）。付いていないのに付いているつもりでいると「下層が透けて見える」不具合になるので、ExtractLayer は付けられなかったときに標準エラーへ警告を出します。その警告を見逃さないこと。

シンボリックリンクのリンク先を検証しないのは、本当に安全なんですか? 怖いのですが。

怖いのは正しい感覚です。ただ、この設計には理由があります。

まず、リンク先が展開先の外を指すこと自体は正常です。コンテナの中の /bin/sh -> /bin/busybox は、展開先ディレクトリを基準にすれば「絶対パスで外」を指しています。コンテナが pivot_root した後の世界では正しく解決される。ここで弾いたら、まともなイメージがほぼ展開できません。

次に、リンクは「作られた」だけでは何も起こしません。 危険なのは、そのリンクを通り抜けて書き込むときです。そして safeJoin の3段目が、書き込む直前に EvalSymlinks で親の実体を確かめる。危険が実現するその一点に、防御を集中させているわけです。

対照的に、ハードリンク（TypeLink）は作った瞬間に相手の inode を掴みます。後から止める機会がないので、作る前に safeJoin にかけています。この非対称は、2つのリンクの性質の違いから来ています。

限界も正直に書いておきます。EvalSymlinks による検査は TOCTOU に対して完璧ではありません。厳密にやるなら openat2(2) の RESOLVE_BENEATH です。限界を知って使っているかどうかが、この種のコードでは大きな差になります。

MNT_DETACH があるなら、最初からそれを使えばよくないですか?

楽なのですが、問題を隠すだけになります。

MNT_DETACH（umount -l）は「名前空間のツリーからは今すぐ外す。実際の解除は最後の参照が消えたとき」という指定です。システムコールは成功します。 でも、ファイルを掴んでいるプロセスが生きている限り、実体は残り続けます。

これを常用すると何が起きるか。「アンマウントは常に成功する」ので、後片付けが漏れていることに永久に気付けません。mount の出力からは消えるので、数えても分かりません。裏でファイルシステムが積み上がっていきます。

だから mydocker では、普通の umount を先に試し、失敗したときの最後の手段として1回だけ MNT_DETACH を使います。そしてどちらの経路を通っても最後に IsMountPoint で確認する。「成功した」と「外れた」を別のこととして扱うのがこの関数の設計です。

copy-up されたファイルは、コンテナを消したら本当に全部消えますか? 一部残ったりしませんか?

全部消えます。overlayfs は、書き込みを upperdir の外に漏らしません。 これは実装の丁寧さではなく、構造からの帰結です。lowerdir は読み取り専用としてマウントされているので、書き込む経路が存在しません。

ただしoverlay の外に出た書き込みは別です。コンテナが /proc や /sys や /dev（tmpfs）に書いたものは upperdir に入りません。それらは別のマウントだからです。-v でホストのディレクトリをバインドマウントしたら、当然その先に直接書かれます。

つまり正確に言えば、「overlay 越しの書き込みは全部 upperdir に溜まる」です。この境界を意識しておくと、「消したはずのデータがどこかに残っている」という事故を防げます。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。答えを読んで「知っていた」と思ったら、もう一度、口に出して説明できるかを試してみてください。

Q1. lowerdir=A:B:C と書いたとき、A・B・C のどれが「上」ですか? そしてイメージのレイヤ配列をそのまま繋いではいけないのはなぜですか?

A が一番上（最優先）です。lowerdir は左が上。

一方、イメージのマニフェストの layers 配列は「後のものほど上」です。layers[0] がベースで、その上に順に積まれる。つまり両者は逆向きなので、配列をそのまま : で繋ぐと上下が引っくり返ります。

New はこれを rev のループで反転してから strings.Join します。呼び出し元は人間の直感どおり「下から上の順」で渡せばよく、逆転の知識は New の中に閉じ込められています。

間違えたときの症状がエラーではなく「更新が反映されていないように見える」ことも、セットで覚えてください。これが一番怖いところです。

Q2. workdir の2つの制約は何ですか? それぞれ破るとどうなり、mydocker はそれをどう満たしていますか?

制約1: upperdir と同じファイルシステム上にあること。 copy-up の実装が workdir 内の一時ファイルを upperdir へ rename で移すからで、rename(2) はファイルシステムをまたげません（EXDEV）。破ると mount が EXDEV / EINVAL で失敗します。

制約2: 空であること。 前回の残骸があると EINVAL で失敗します。

mydocker は、制約1を配置で満たしています。filepath.Join(base, "upper") と filepath.Join(base, "work") と、必ず同じ base の下に並べるので、どんな base でも自動的に同居します。制約2はコードで——emptyDir(m.Work) を syscall.Mount の直前に必ず通します。

Q3. 「コンテナを消す」とは、具体的にどのディレクトリに何をすることですか? そのときイメージには何が起きますか?

①merged をアンマウントする。②upper と work を削除する。 これだけです。

イメージには何も起きません。指一本触れていません。 lowerdir は読み取り専用としてマウントされていたので、そもそも一度も書かれていない。ロールバックもトランザクションも要らないのは、元に戻す必要がないからです。

コンテナが書いたものは、copy-up されたファイルも新規作成したファイルも削除の印も、すべて upperdir の下にあります。だからそこを1つ消せば、コンテナは跡形もなく消える。これが「使い捨て」の実装です。

順序が①→②である理由も一緒に言えたら完璧です（Q6 で扱います）。

Q4. tar の中の .wh.foo を普通のファイルとして展開すると、何が2つ起きますか? 正しくはどう翻訳しますか?

①消えるべき foo が残ります。 下層の foo はそのままなので、重ね合わせると見えてしまいます。②変な名前のファイルが増えます。 .wh.foo という 0 バイトのファイルがコンテナの中に見えます。

正しくは、foo の位置にキャラクタデバイス 0:0 を作ります（syscall.Mknod(victim, syscall.S_IFCHR|0o000, 0)）。overlayfs はこれを「削除された」印として扱い、下層の同名ファイルを隠します。

ディレクトリ丸ごとの .wh..wh..opq は、その親ディレクトリに xattr trusted.overlay.opaque="y" を付けます。ディレクトリ自体は残したまま、下層の中身だけを隠したいので、実体ではなくメタデータに印を置きます。

そして「なぜ削除ではなく翻訳なのか」——レイヤは独立したキャッシュでなければならないから。展開している時点で下層は手元に無いかもしれないし、あっても触ってはいけません。

Q5. エントリ名に / も .. も含まないのに、展開先の外にファイルを作らせる手口を説明してください。どう防ぎますか?

2手に分けます。

1手目に foo -> / というシンボリックリンクを置く。名前は foo だけなので、絶対パス検査も .. 検査も通ります。2手目に foo/etc/passwd を書く。この名前も絶対パスでも .. でもない。しかし dest/foo は / を指しているので、実際の書き込み先は本物の /etc/passwd です。

どちらの手も単体では完全に無害で、組み合わせだけが有害。だからエントリ名を1つずつ眺めていても永遠に見つかりません。

防ぎ方は3段目の検査——書き込む直前に filepath.EvalSymlinks(parent) で親ディレクトリの実体を求め、それが realDest の内側かを確かめます。文字列ではなくファイルシステムに聞くのがポイントです。

加えて、書き込みそのものでも O_TRUNC を使わず必ず一度 os.Remove してから O_EXCL で作ります。target 自身がリンクだった場合、O_TRUNC で開くとリンク先に書いてしまうからです。os.Remove はリンクを辿らずリンク自身を消します。

Q6. umount の失敗を握りつぶして rm -rf に進むと、なぜイメージが消えるのですか?

merged がまだマウントされたままなので、rm -rf merged は重ね合わせの窓の中を歩きます。その窓の向こうにあるのは lowerdir の実体、つまり全コンテナが共有しているイメージのキャッシュです。rm は自分がどこを消しているか知りません。

しかも upper と work も同時に消えていくので、削除の途中で overlayfs の整合性が崩れ、その先は順序次第になります。運が悪ければ下層まで届きます。

そして umount は日常的に失敗します。コンテナのプロセスが残っている、シェルの作業ディレクトリがその中にある、誰かがファイルを開いたまま——どれも EBUSY です。特別な異常事態ではありません。

だから Unmount は、失敗を必ずエラーとして返し、成功した場合でも IsMountPoint で本当に外れたかを確認します（MNT_DETACH はシステムコールとしては成功しても実体が残ることがあるため）。呼び出し元はエラーなら削除に進まずそこで戻る。残骸は人間が消せますが、消えたイメージは戻りません。

Q7. IsMountPoint は、どうやってマウントポイントかどうかを見分けていますか?

自分の st_dev と、親ディレクトリの st_dev を比べています。 違えばマウントポイント、同じならただのディレクトリ。

原理はこうです。st_dev は「そのファイルが乗っているファイルシステムの識別子」で、同じファイルシステムの中では必ず同じ値になります。ディレクトリに別のファイルシステムがマウントされると、そのディレクトリを stat したときに返るのはマウントされた側の情報になるので、親と値が食い違います。アンマウントすれば元に戻り、親と一致します。

これは mountpoint(1) コマンドとまったく同じ考え方です。/proc/mounts を文字列で検索するより、2回の stat で済むぶん確実です（パスの表記ゆれやエスケープに悩まされません）。

Stat ではなく Lstat なのは、パスがシンボリックリンクだったときに辿らずリンク自身を見るためです。

✓ 完了の合図

4つのディレクトリを作って、手で1回 overlay を張れればこの章は完了です。mount の出力に lowerdir / upperdir / workdir の3つが並び、その意味と制約を自分の言葉で説明できること。

$ mount -t overlay overlay -o lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work /tmp/ovl/merged
$ mount | grep overlay
overlay on /tmp/ovl/merged type overlay (rw,relatime,lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work,uuid=on)

そして mydocker 側では、コンテナを起動して /proc/mounts に同じ形の行が現れ、終了すると消えていることを確かめてください。mydocker info の「overlay 数」が起動前と終了後で同じ値に戻れば、後片付けは効いています。

$ mydocker info
状態の置き場: /var/lib/mydocker
資源制限:     cgroup v1 (/sys/fs/cgroup, 利用可能: memory cpu pids)
overlayfs:    利用可能
overlay 数:   0 件
実行中:       0 件

最後に、遊びを1つ。/tmp/ovl/merged の中でファイルを作ったり、lower にあるファイルを書き換えたりしてから、/tmp/ovl/upper を覗いてみてください。触ったものだけがそこに現れているのが見えます。それが copy-up です。

まとめ — 次の層へ

この章で、コンテナの「使い捨て」の正体を手に入れました。読み取り専用のレイヤを何枚も重ね、その上に書き込み用の板を1枚だけ載せる。読むときは上から探し、書くときは copy-up して上の板に置く。だからコンテナを消すというのは、upperdir を捨てるだけのことで、イメージには最初から一度も書いていない。素朴案の「起動のたびに 8.7 MB コピー」が、「書いたぶんだけ」に変わりました。あわせて、この重ね合わせを成立させるための地味な作法も全部見ました。lowerdir は左が上だから並べる順を逆にすること。workdir は upperdir と同じファイルシステム上で、かつ空であること。tar の中の .wh. は普通に展開せず、キャラクタデバイス 0:0 と trusted.overlay.opaque に翻訳すること。他人が作った tar は3段で検証し、書き込みは必ず Remove してから O_EXCL で作ること。そして——umount の失敗は絶対に握りつぶさないこと。

ところが、いま私たちが持っているのはまだ run だけです。コンテナは起動します。隔離されます。上限もかかります。イメージも取ってきて重ねられます。……それだけです。いま何が動いているのかを一覧できません。 起動したコンテナに後から入って様子を見ることもできません。プロセスを走らせたまま別の作業をしたいのに、それを管理する仕組みがない。そして何より、後片付けが漏れれば静かにホストが埋まっていきます。この章で CountMounts を書いて「数えられるようにした」のは、まさにその予感があったからです。マウントが1つ残り、ディレクトリが1つ残り、cgroup が1つ残る。どれもその場では誰も困らない。100 回動かして初めて気付く。道具として使うには、状態を持ち、それを見せ、確実に片付ける仕組みが要ります。

次章で、これを道具にします。コンテナ1つにつき状態ファイルを1つ持ち、mydocker ps で一覧し、mydocker exec で動いているコンテナの中に入り、mydocker rm で確実に回収する。CLI の設計と状態管理、そして後片付けを正面から扱います。「アンマウントが失敗したら削除に進まない」というこの章の規律が、そこで呼び出し元の側からもう一度出てきます。ばらばらに作った部品が、ここで1つのコマンドラインツールになります。
