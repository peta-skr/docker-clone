Cgroup— 世界に底を入れる

資源に上限をかける

ここまでで、コンテナは自分だけの世界を持ちました。プロセス番号も、ホスト名も、ファイルシステムの根も、ホストとは別物です。けれど、その世界には底がありません。中で走るプロセスは、ホストのメモリを好きなだけ食えるし、CPU を独占できます。この章では、その底を入れます。やることは驚くほど単純です。ディレクトリを作り、ファイルに数字を書き、もう1つのファイルに PID を書く。それだけです。

◈ この章のゴール

internal/cgroup/cgroup.go を頭から終わりまで読み切り、「cgroup とは要するにファイル操作である」ことを自分の手で確かめる。そのうえで v2 と v1 の2つのバックエンドがなぜ両方必要になったのかを、この環境の実測から説明できるようになる。仕上げに、上限なしなら成功し、上限 10m なら exit 137 で殺されるという対照実験を自分で走らせる。

底の無い世界は、隣を殺す

前章までに作ったコンテナを思い出してください。中で ps を打つと自分のプロセスしか見えず、hostname は mydocker を返し、ls / は alpine の中身を返しました。見事に隔離されています。

ところが、この隔離は「見え方」の隔離でしかありません。名前空間は、プロセスに見せる名札の集合を分けているだけです。分けていないものがあります。実際の物、つまりメモリと CPU と、プロセス表の枠です。コンテナの中で 8GB のメモリを確保するプログラムを走らせれば、ホストのメモリが 8GB 減ります。無限ループで fork し続ければ、ホストのプロセス表が埋まって、ホスト側で新しいコマンドが打てなくなります。

名前空間だけを付けた状態 — 「見え方」は分かれたが、物は共有のまま ┌──────────── ホストの物理資源（メモリ / CPU / プロセス表）────────────┐ │ │ │ ┌── コンテナ A ──┐ ┌── コンテナ B ──┐ ┌── ホストの仕事 ──┐ │ │ │ PID 1,7 だけ │ │ PID 1,5 だけ │ │ sshd, systemd … │ │ │ │ hostname=… │ │ hostname=… │ │ │ │ │ └────────────────┘ └────────────────┘ └──────────────────┘ │ │ ↑ │ │ └─ ここが 8GB 確保すると、B もホストも巻き添えで死ぬ │ └─────────────────────────────────────────────────────────────────────┘ 名前空間 = 名札を分ける仕組み cgroup = 物の取り分に上限をかける仕組み ← この章で足すもの

つまり、名前空間と cgroup は別の道具です。名前空間は「見えるもの」を仕切り、cgroup は「使えるもの」を仕切ります。この2つが揃って初めて、コンテナは「他人に迷惑をかけない実行単位」になります。docker run --memory 512m の --memory が担っているのが、まさにこの後者です。

cgroup とは何か — ディレクトリと数字だけ

「control groups」という名前と、カーネル機能という響きから、身構えてしまうかもしれません。私も最初はそうでした。ioctl のような専用のシステムコールを呼ぶのだろう、と。

違いました。cgroup の操作は、ほぼ全部がふつうのファイル操作です。専用のファイルシステム（cgroupfs）が /sys/fs/cgroup にマウントされていて、そこにディレクトリを作ると新しいグループができ、その中に自動的に現れるファイルに数字を書くと上限が決まり、cgroup.procs というファイルに PID を書くとそのプロセスがグループに入ります。

cgroup v2 の階層 — mydocker が作るもの /sys/fs/cgroup/ ← cgroupfs のルート（v2 なら単一の木） ├ cgroup.controllers 「この階層で使えるコントローラ」の一覧（読み取り専用） ├ cgroup.subtree_control 「子に配るコントローラ」を指定する（書き込む） ├ cgroup.procs このグループに属する PID の一覧 │ └ mydocker/ ← ① 親（mydocker が作る。groupName） ├ cgroup.subtree_control ← ② ここでも子に配る指定が要る └ a10f2703bb37/ ← ③ 葉（コンテナ ID ごと。ここに入れる） ├ memory.max "10485760" … メモリ上限（バイト） ├ memory.swap.max "0" … スワップまで使わせない ├ cpu.max "50000 100000" … 100ms 中 50ms ＝ 0.5 コア ├ pids.max "64" … プロセス数の上限 └ cgroup.procs "23900" ← ★ここに PID を書いて初めて効く

この図の右側にある文字列は、全部ただのテキストです。echo 10485760 > memory.max と打てば上限がかかります。Go から書くなら os.WriteFile の1行です。魔法はどこにもありません。

この章の8割は、この事実に慣れるための時間です。そして残りの2割が、実際にやってみると出てくる「作法」の話 —— subtree_control、内部プロセス禁止、v1 と v2 の違い、そしてこの環境では v2 が使えなかったという実測 —— です。

internal/cgroup/cgroup.go — 定数と型
// cgroup2 のスーパーブロックマジック。statfs の f_type がこの値なら cgroup v2 である。
// /sys/fs/cgroup が tmpfs のこともある（v1 と v2 が同居する hybrid 構成）ので、
// パスの存在ではなくファイルシステムの種類で判定する。
const cgroup2Magic = 0x63677270

// groupName は mydocker が作る親ディレクトリの名前。
// 実際のコンテナはこの下の <コンテナID> に作られる。
const groupName = "mydocker"

// Limits は利用者が指定した上限。ゼロ値は「上限なし」を意味する。
type Limits struct {
	MemoryBytes int64   // 例: 10485760（10MiB）
	CPUs        float64 // 例: 0.5（0.5 コア分）
	PidsMax     int64   // 例: 64
}

// IsZero は上限が1つも指定されていないことを返す。
func (l Limits) IsZero() bool {
	return l.MemoryBytes == 0 && l.CPUs == 0 && l.PidsMax == 0
}

// Cgroup は作成済みの cgroup 1つを表す。
type Cgroup struct {
	version string   // "v2" または "v1"
	dirs    []string // 実際に作ったディレクトリ（後片付けの対象）
	id      string
}

// Version は使ったバックエンドを返す（"v2" / "v1"）。
func (c *Cgroup) Version() string { return c.version }

// Dirs は作成した cgroup ディレクトリの一覧を返す。後片付けの検査に使う。
func (c *Cgroup) Dirs() []string { return append([]string(nil), c.dirs...) }

Cgroup 構造体が持っているのは、バージョン名と「作ったディレクトリの一覧」と ID だけです。ファイルディスクリプタも、カーネルへのハンドルも持ちません。持つ必要がないのです。cgroup の実体はディレクトリなので、パスさえ覚えておけば後から何でもできます。

Dirs() が append([]string(nil), c.dirs...) でコピーを返しているのは、呼び出し側にスライスの中身を書き換えられないようにするためです。ここは Go の定番の作法です。

func New(id string, limits Limits) (*Cgroup, error) {
	if root, ok := findV2Root(); ok {
		return newV2(root, id, limits)
	}
	if roots, ok := findV1Roots(); ok {
		return newV1(roots, id, limits)

Step 1手で触ってみる — ディレクトリを作って数字を書く

コードを読む前に、手を動かします。cgroup が「ただのファイル操作」だと納得するには、実際にファイルを操作するのが一番早いからです。

この環境の /sys/fs/cgroup/memory/ の下にディレクトリを1つ作ってみます。名前は何でもよいので smoketest にします。作った瞬間、そのディレクトリの中にカーネルがファイルを勝手に生やします。私たちは touch も mkdir も何もしていないのに、です。

▸ 動かして確認

ディレクトリを1つ作り、memory.limit_in_bytes に 10485760（＝10MiB）と書いて、読み返します。

$ mkdir -p /sys/fs/cgroup/memory/smoketest
$ echo 10485760 > /sys/fs/cgroup/memory/smoketest/memory.limit_in_bytes
$ cat /sys/fs/cgroup/memory/smoketest/memory.limit_in_bytes
10485760

ついでに pids でも同じことをしてみます。こちらは「同時に存在できるプロセス数」の上限です。

$ mkdir -p /sys/fs/cgroup/pids/smoketest
$ echo 64 > /sys/fs/cgroup/pids/smoketest/pids.max
$ cat /sys/fs/cgroup/pids/smoketest/pids.max
64

これで終わりです。API も、ライブラリも、特別なシステムコールも出てきませんでした。mkdir と echo と cat だけです。

ここで少し中を覗いてみましょう。作ったディレクトリではなく、その親（/sys/fs/cgroup/memory/ 自体）にどんなファイルがあるかを見ると、cgroup が用意している「つまみ」の種類が分かります。

▸ 動かして確認

memory コントローラのディレクトリに並ぶファイル（抜粋）。

名前を眺めるだけで、だいたい何ができるか想像がつきます。memory.usage_in_bytes は現在の使用量、memory.max_usage_in_bytes はこれまでの最大値、memory.failcnt は上限に当たった回数。cgroup.procs は所属プロセスの一覧です。全部テキストファイルとして読み書きできます。

LINUX メモ · cgroup.procs と tasks の違い

cgroup v1 のディレクトリには cgroup.procs と tasks の2つがあります。紛らわしいのですが、意味がはっきり違います。

tasks は「スレッド」単位です。ここに書いた番号のスレッド1本だけが移動します。マルチスレッドのプロセスなら、他のスレッドは元のグループに残ります。

cgroup.procs は「プロセス」単位です。PID を書くと、そのプロセスに属する全スレッドがまとめて移動します。私たちが欲しいのは当然こちらです。コンテナの中の /bin/sh のスレッドが1本だけ制限されても意味がありません。

cgroup v2 では、この混乱を減らすためにスレッド単位の扱いが別枠（threaded mode）に切り出され、通常の cgroup.procs はプロセス単位に統一されました。mydocker は v1 でも v2 でも cgroup.procs だけを使います。

⚠ 落とし穴 · cat で確認しただけで満足する

今やったことを整理すると、「echo で書いて、cat で読んだら同じ値が返ってきた」だけです。これは「ファイルに値が入った」ことの証明でしかありません。

「上限が効いている」ことの証明にはまったくなっていないのです。値が入っていても、そのグループにプロセスが1つも入っていなければ、誰も制限されません。実際この後の Step 7 で見るとおり、cgroup.procs に PID を書き忘れると、memory.max に値が入っているのに1バイトも制限されない cgroup ができあがります。

次の Step 2 は、まるごとこの話に使います。

Step 2「書けた」は「効いた」ではない

10MB の上限を書いた smoketest グループが手元にあります。ここに実際にプロセスを入れて、200MB を確保しにいかせます。効いていれば、途中で殺されるはずです。効いていなければ、200MB 確保して平然と終わるはずです。どちらになるかを見ます。

使ったのは Python 3 で書いた 4 行のプログラムです。1行目で自分自身の PID を cgroup.procs に書き込んで、グループに入っています。あとは 1MiB ずつ 200 回、バイト列を足していくだけです。

/tmp/hog.py（疎通実験で使ったスクリプト）
import os
open("/sys/fs/cgroup/memory/smoketest/cgroup.procs","w").write(str(os.getpid()))
b = bytearray()
for i in range(200):
    b += bytearray(1024*1024)
print("allocated", len(b))

注目してほしいのは print("allocated", len(b)) の行です。最後まで走り切れば、この行が印字されます。逆に言えば、この行が出なければ、途中で殺されたということです。合否の判定がはっきりします。

▸ 動かして確認

10MB の上限がかかったグループの中で、200MB を確保しにいきます。

$ python3 /tmp/hog.py; echo "exit=$?"
/bin/bash: line 32:  5187 Killed                  python3 /tmp/hog.py
exit=137
$ cat /sys/fs/cgroup/memory/smoketest/memory.failcnt
37

効きました。読み取れることが3つあります。

① allocated ... が印字されていない。プログラムは最後まで到達しませんでした。上限の中で 200MB は確保できなかったということです。

② シェルが Killed と報告し、終了コードが 137 になっている。137 は 128 + 9 です。9 は SIGKILL の番号なので、「SIGKILL で殺された」を意味します。誰が殺したかというと、カーネルの OOM killer です。

③ memory.failcnt が 37 に増えている。これはカーネル側の帳簿です。「このグループが上限に当たった回数」が 37 回記録されています。私たちの実験が偶然クラッシュしたのではなく、カーネルが上限として認識して、何度もブロックした結果だと分かります。

LINUX メモ · OOM killer

OOM は Out Of Memory の略です。Linux は、メモリが足りなくなったときにプロセスを選んで強制終了するという荒っぽい解決策を持っています。それが OOM killer です。

普通は「マシン全体のメモリが枯渇したとき」に発動しますが、cgroup の memory コントローラを使うとそのグループの中だけで発動させることができます。グループの使用量が memory.max（v1 なら memory.limit_in_bytes）を超えそうになると、カーネルはまずページを回収しようとし、それでも足りなければそのグループの中から犠牲者を選んで SIGKILL を送ります。

ここで重要なのは、殺されるプロセスは自分が殺されることを知らないという点です。SIGKILL は捕捉も無視もできません。「メモリ確保に失敗した」というエラーが返ってくるのではなく、いきなり消えます。だからこそ、上限超過を検出する手段は「エラーメッセージ」ではなく「終了コード 137」になります。Step 9 で、この 137 をきちんと利用者まで届ける話をします。

⚠ 落とし穴 · テストのほうが間違っていることがある

実は、mydocker の実装中に一度ここで転びました。最初に書いた確認コマンドはこうでした。

$ mydocker run --memory 10m alpine sh -c 'head -c 100000000 /dev/zero | wc -c'

「10MB 制限の中で 100MB 読ませれば死ぬだろう」という発想です。ところが結果は 100000000 が表示されて exit=0。私は「上限が効いていない」と思いかけました。

間違っていたのはテストのほうでした。head | wc はストリームを流すだけで、メモリに溜めません。パイプのバッファ（せいぜい 64KB）を通り抜けていくだけなので、10MB の上限には永遠に当たりません。100GB 流しても死にません。

そこで確認の方法を変えました。dd に大きな bs（ブロックサイズ）を与えて、1回で 100MB のバッファを確保させるのです。dd if=/dev/zero of=/dev/null bs=100M count=1 なら、読み込みバッファとして 100MB を一度に取ろうとするので、確実に上限に当たります。

教訓は2つあります。(1) メモリ上限のテストは「溜める」操作でないと意味がない。(2) 上限あり・上限なしの両方を走らせて差を見る。片方だけを見ていると、失敗しているのが上限なのかテストなのか永久に分かりません。この章の関所（後述）は、必ず対照とペアで行います。

Step 3cgroup v2 の作法 — subtree_control と内部プロセス禁止

手で触った感触は掴めました。ここからは Go で同じことをします。ただし今度は cgroup v2 の作法で書きます。v2 は新しい世代で、これから作る環境ではこちらが標準になるからです（Step 4 で、この環境では使えないと分かるのですが、それは後の話です）。

v2 でやることは、v1 とほとんど同じに見えます。/sys/fs/cgroup/mydocker/<コンテナID>/ というディレクトリを作り、その中のファイルに書きます。ファイル名だけが違います。

上限の種類v2 のファイル書く値の例
メモリmemory.max10485760（バイト数をそのまま）
スワップmemory.swap.max0（スワップは一切使わせない）
CPUcpu.max50000 100000（後述）
プロセス数pids.max64
所属プロセスcgroup.procs23900（PID）

cpu.max の "50000 100000" だけ説明が要ります。これは「quota period」の2値で、単位はマイクロ秒です。「100000μs（＝100ミリ秒）の期間ごとに、最大 50000μs（＝50ミリ秒）だけ CPU を使ってよい」という意味になります。割り算すると 0.5 —— つまり 0.5 コア分です。--cpus 0.5 という指定が、この2つの数字に翻訳されるわけです。

そして、v2 に特有の作法が2つあります。ここが引っかかりどころです。

作法① 親の subtree_control でコントローラを配る

v1 では、/sys/fs/cgroup/memory/ の下にディレクトリを作れば、その中に memory.* のファイルが自動的に生えました。木そのものが memory 専用だったからです。

v2 は1本の木に全コントローラが同居します。そのため、「この子ディレクトリでは memory を使う」ということを親が明示的に宣言しなければなりません。その宣言をするファイルが cgroup.subtree_control です。+memory と書き込むと、その時点から子ディレクトリに memory.max などが生えるようになります。

⚠ 落とし穴 · subtree_control を忘れると memory.max が「作られない」

この失敗は、非常に分かりにくい形で現れます。mkdir は成功します。エラーは何も出ません。ところが ls してみると、そこに memory.max というファイルが存在しないのです。

そこへ os.WriteFile で書き込もうとすると no such file or directory で落ちます。この時点でエラーを握りつぶす実装（_ = write(...) のような書き方）をしていると、「上限を設定したつもりのコンテナが、何の制限も受けずに走り出す」という最悪の状態になります。

だから mydocker は、subtree_control への書き込みで memory だけは失敗をエラーにします（cpu と pids の失敗は許します）。メモリ上限がこの教材の Must だからです。

作法② 内部プロセス禁止（no internal processes）

もう1つの規則が、初見だと理不尽に見えるものです。コントローラを子に配っているディレクトリには、プロセスを直接入れられません。プロセスを入れられるのは木の葉（子を持たないディレクトリ）だけです。

v2 の「内部プロセス禁止」規則 ✗ できない配置 ○ できる配置 mydocker/ mydocker/ ├ cgroup.subtree_control ├ cgroup.subtree_control ← +memory を書いた │ ← +memory を書いてある │ ├ cgroup.procs ← ここに PID を ├ a10f2703bb37/ （葉） │ 書くと EBUSY │ ├ memory.max ← 上限を書く └ a10f2703bb37/ │ └ cgroup.procs ← ★PID はここに書く └ 0c1be9ad663a/ （葉） ├ memory.max └ cgroup.procs 規則: コントローラを「子に配っている」ディレクトリは、 自分ではプロセスを持てない（中間ノードは空でなければならない）

なぜこんな規則があるのか。理由は資源配分の計算を素直にするためです。もし親ディレクトリが直接プロセスを持ちながら、同時に子グループにも資源を配っていたら、「親の直属プロセスと子グループを、どういう比率で競わせるのか」という厄介な問いが生まれます。v1 はこれを許していて、実際に配分の意味が曖昧になっていました。v2 は「中間ノードは空にする」と決めることで、この曖昧さを消しました。

実務上の帰結はシンプルです。親（mydocker/）は箱として作るだけ。実際のコンテナは必ずその下に葉として作り、PID は葉の cgroup.procs に書く。mydocker の実装はまさにそうなっています。

階層の設計を誤ると、書き込みが EBUSY（デバイスまたはリソースがビジー）や ENOTSUP（サポートされていない操作）で弾かれます。エラーメッセージからは原因が読み取りにくいので、この2つの規則を先に知っておくと時間を大幅に節約できます。

実装 — newV2

以上を踏まえて、v2 のグループを作る関数です。コメントに落とし穴がそのまま書いてあります。

internal/cgroup/cgroup.go — newV2
func newV2(root, id string, limits Limits) (*Cgroup, error) {
	parent := filepath.Join(root, groupName)
	leaf := filepath.Join(parent, id)

	// ⚠ 親の cgroup.subtree_control でコントローラを有効にしないと、
	//    子ディレクトリに memory.max などのファイルがそもそも作られない。
	if err := enableSubtree(root); err != nil {
		return nil, err
	}
	if err := os.MkdirAll(parent, 0o755); err != nil {
		return nil, fmt.Errorf("cgroup の親ディレクトリを作れませんでした: %w", err)
	}
	if err := enableSubtree(parent); err != nil {
		_ = os.Remove(parent)
		return nil, err
	}
	// ⚠ cgroup v2 の「内部プロセス禁止」規則により、プロセスを入れられるのは葉だけである。
	//    parent には入れず、必ず leaf を作ってそこに入れる。
	if err := os.Mkdir(leaf, 0o755); err != nil {
		return nil, fmt.Errorf("cgroup ディレクトリを作れませんでした: %w", err)
	}

	c := &Cgroup{version: "v2", dirs: []string{leaf}, id: id}

	if limits.MemoryBytes > 0 {
		if err := write(leaf, "memory.max", strconv.FormatInt(limits.MemoryBytes, 10)); err != nil {
			c.Destroy()
			return nil, err
		}
		// スワップまで許すと「上限を超えても死なない」ので、スワップ側も同じ値で締める。
		// swap accounting が無い環境では失敗するが、それは致命ではない。
		_ = write(leaf, "memory.swap.max", "0")
	}
	if limits.CPUs > 0 {
		// cpu.max は "<quota> <period>"。period 100000us(=100ms) のうち何us使えるか。
		const period = 100000
		quota := int64(limits.CPUs * period)
		if err := write(leaf, "cpu.max", fmt.Sprintf("%d %d", quota, period)); err != nil {
			c.Destroy()
			return nil, err
		}
	}
	if limits.PidsMax > 0 {
		if err := write(leaf, "pids.max", strconv.FormatInt(limits.PidsMax, 10)); err != nil {
			c.Destroy()
			return nil, err
		}
	}
	return c, nil
}

逐行で追います。

1〜2行目で parent（<root>/mydocker）と leaf（<root>/mydocker/<ID>）のパスを組み立てます。ここではまだディレクトリは作っていません。

次に enableSubtree(root)。ルート（/sys/fs/cgroup）で「子に memory / cpu / pids を配る」と宣言します。これをしないと、次に作る mydocker/ の中にコントローラのファイルが生えません。

os.MkdirAll(parent, 0o755) で親を作り、もう一度 enableSubtree(parent)。ここがポイントです。subtree_control は1段ぶんしか効きません。ルートで宣言したから孫にも効く、ということはないのです。「親から子へ配る」という宣言なので、階層を1段下るたびに、その段でもう一度配り直す必要があります。ここを忘れると、葉に memory.max が生えません。

os.Mkdir(leaf, 0o755) で葉を作ります。ここは MkdirAll ではなく Mkdir です。親は既に作ってあるので中間ディレクトリの作成は不要ですし、もし同名の葉が既にあれば失敗してほしい（コンテナ ID の衝突は異常事態）ので、あえて厳しいほうを使っています。

そのあとは、指定された上限を順に書くだけです。limits.MemoryBytes > 0 のようにゼロ値を「指定なし」として扱うので、--memory を付けなければメモリ関係のファイルには一切触りません。

失敗したときに c.Destroy() を呼んでから返しているのにも注目してください。途中まで作ったディレクトリを残して立ち去らないためです。この姿勢は Step 8 でもう一度出てきます。

GO メモ · _ = write(...) という書き方

memory.swap.max への書き込みだけ _ = write(...) と、戻り値を捨てています。Go では戻り値を無視するとき、明示的に _ に代入する習慣があります（go vet や linter に「無視し忘れ」と区別させるため）。

ここで失敗を許している理由はコメントのとおりです。スワップの会計（swap accounting）はカーネルの設定で無効になっていることがあり、そういう環境では memory.swap.max が存在しません。存在しないなら、そもそもスワップに逃がされる心配も薄いので、致命的ではないと判断しています。

逆に memory.max の失敗は絶対に許しません。「無視してよい失敗」と「無視してはいけない失敗」を区別して書くこと自体が設計判断です。全部無視するのも、全部エラーにするのも、どちらも間違いです。

subtree_control に書く関数

internal/cgroup/cgroup.go — enableSubtree
// enableSubtree は dir の subtree_control に必要なコントローラを足す。
// 既に有効なものを足しても害はない。権限や構成の都合で一部が拒否されることがあるので、
// 1つずつ書いて「memory すら通らない」ときだけエラーにする。
func enableSubtree(dir string) error {
	path := filepath.Join(dir, "cgroup.subtree_control")
	cur, _ := os.ReadFile(path)
	var memErr error
	for _, ctrl := range []string{"memory", "cpu", "pids"} {
		if hasField(string(cur), ctrl) {
			continue
		}
		err := os.WriteFile(path, []byte("+"+ctrl), 0o644)
		if err != nil && ctrl == "memory" {
			memErr = fmt.Errorf("cgroup v2 で memory を有効にできませんでした (%s): %w", path, err)
		}
	}
	return memErr
}

3つのコントローラを1つずつ別々に書いています。"+memory +cpu +pids" とまとめて書くこともできますが、そうすると1つでも拒否されると全部が失敗します。この環境のように「cpu だけ使えない」ようなケースで、memory の上限まで諦めることになってしまいます。1つずつ書けば、通るものは通ります。

そして memory の失敗だけを memErr に記録して返します。メモリ上限は Must、CPU と PID 数は Should という優先順位が、そのままコードの形になっています。

ついでに — --memory 10m はどう解釈されるか

ここまで一貫して「バイト数」で話してきましたが、利用者が打つのは --memory 10m です。この翻訳をしているのが ParseMemory です。

internal/cgroup/cgroup.go — ParseMemory
// ParseMemory は "10m" / "512k" / "1g" / "1048576" を解釈してバイト数を返す。
func ParseMemory(s string) (int64, error) {
	s = strings.TrimSpace(strings.ToLower(s))
	if s == "" {
		return 0, nil
	}
	mult := int64(1)
	switch {
	case strings.HasSuffix(s, "k"), strings.HasSuffix(s, "kb"):
		mult, s = 1<<10, strings.TrimSuffix(strings.TrimSuffix(s, "b"), "k")
	case strings.HasSuffix(s, "m"), strings.HasSuffix(s, "mb"):
		mult, s = 1<<20, strings.TrimSuffix(strings.TrimSuffix(s, "b"), "m")
	case strings.HasSuffix(s, "g"), strings.HasSuffix(s, "gb"):
		mult, s = 1<<30, strings.TrimSuffix(strings.TrimSuffix(s, "b"), "g")
	}
	n, err := strconv.ParseInt(strings.TrimSpace(s), 10, 64)
	if err != nil {
		return 0, fmt.Errorf("メモリ量として解釈できません: %q（例: 10m, 512k, 1g）", s)
	}
	if n <= 0 {
		return 0, fmt.Errorf("メモリ量は正の数で指定してください: %q", s)
	}
	return n * mult, nil
}

1<<20 は 2 の 20 乗、つまり 1048576 です。10m なら 10 * 1048576 = 10485760 —— Step 1 で手で書いたのと同じ数字になります。

細かいところですが、単位なしの数字（1048576）もそのまま通るようにしてあります。switch のどのケースにも当たらなければ mult は 1 のままだからです。そして 0 や負数は明示的にエラーにします。--memory 0 を「上限なし」と黙って解釈されると事故になるので、意図を確認させるためです。

⚠ 落とし穴 · stat が tmpfs でも「v2 が無い」とは限らない

この節でいちばん誤解しやすいのがここです。stat -fc %T /sys/fs/cgroup/ が tmpfs を返したからといって、「このマシンに cgroup v2 は無い」と結論してはいけません。実際、この環境には /sys/fs/cgroup/unified にちゃんと v2 が居ました。

逆も成り立ちます。/sys/fs/cgroup が cgroup2fs だったとしても、そこで memory が使えるとは限りません。コントローラの取り合いに負けていれば cgroup.controllers に memory は現れません。

つまり、ファイルシステムの種類だけを見ても、パスの存在だけを見ても、判定としては不十分です。「memory が使えるか」を知りたいなら、「memory が使えるか」を直接聞くしかありません。それが次の Step でやることです。

LINUX メモ · cgroup v1 と v2 の違い

v1 は「コントローラごとに別の木」です。memory の木、cpu の木、pids の木 …… とマウント点が分かれています。だから、あるプロセスを「memory の木では A グループ、cpu の木では B グループ」に置くことができました。柔軟ですが、階層が互いに食い違うと配分の意味が説明できなくなります。後片付けの対象も、コントローラの数だけ増えます。

v2 は「1本の木にまとめる」設計です（だから unified hierarchy と呼ばれます）。プロセスの居場所は1つに決まり、その場所に対して各コントローラが上限をかけます。代わりに、どのコントローラを子に配るかを cgroup.subtree_control で明示する必要が生まれ、「内部プロセス禁止」の規則も入りました。柔軟さを捨てて、意味の一貫性を取ったのが v2 です。

ファイル名の対応もだいたい規則的です。memory.limit_in_bytes → memory.max、cpu.cfs_quota_us + cpu.cfs_period_us → cpu.max（2値を1ファイルに統合）。v2 のほうが名前が短く、単位の一貫性もあります。

internal/cgroup/cgroup.go — findV2Root
// findV2Root は「memory コントローラが実際に使える」cgroup v2 のルートを探す。
//
// ⚠ ここが疎通実験でいちばん効いた分岐である。
// cgroup2 がマウントされていても cgroup.controllers に memory が無いことがある。
// hybrid 構成では memory が v1 側に取られており、v2 からは決して使えない。
// 「マウントされているか」ではなく「コントローラが見えるか」で判定する。
func findV2Root() (string, bool) {
	candidates := []string{
		"/sys/fs/cgroup",
		"/sys/fs/cgroup/unified", // hybrid 構成ではここに v2 がぶら下がる
	}
	for _, root := range candidates {
		var st syscall.Statfs_t
		if err := syscall.Statfs(root, &st); err != nil {
			continue
		}
		if uint32(st.Type) != cgroup2Magic {
			continue
		}
		ctrls, err := os.ReadFile(filepath.Join(root, "cgroup.controllers"))
		if err != nil {
			continue
		}
		if !hasField(string(ctrls), "memory") {
			// v2 ではあるが memory が使えない。ここを掴むと memory.max が作られず静かに壊れる。
			continue
		}
		return root, true
	}
	return "", false
}

この関数は3段階の関門になっています。1つでも落ちたら continue で次の候補へ、全部落ちたら「v2 は使えない」と答えます。

関門1: syscall.Statfs で f_type を見る。そのパスが本当に cgroup2fs かを、ファイルシステムのレベルで確認します。cgroup2Magic（0x63677270）と一致しなければ、そこは v2 ではありません。/sys/fs/cgroup が tmpfs だったこの環境では、1つ目の候補はここで落ちます。

関門2: cgroup.controllers が読めるか。v2 なら必ずあるファイルです。読めなければ何かがおかしいので次へ。

関門3: そこに memory が語として含まれるか。ここが Step 4 で得た教訓そのものです。この環境の unified/ は関門1と2を通過しますが、cgroup.controllers が cpuset hugetlb なのでここで落ちます。結果として findV2Root は ("", false) を返し、New は v1 へ落ちていきます。

候補リストに /sys/fs/cgroup/unified を入れているのは、まさに hybrid 構成のためです。ただし、この環境ではその候補も関門3で落ちる —— 「探しにはいくが、使えないと分かったら掴まない」という作りになっています。

GO メモ · syscall.Statfs で f_type を見る

statfs(2) は「そのパスが乗っているファイルシステムの情報」を取るシステムコールです。Go では syscall.Statfs(path, &st) の形で呼び、結果が syscall.Statfs_t 構造体に入ります。

使うのは st.Type フィールドです。ここにはファイルシステムごとに決められたマジックナンバーが入っています。tmpfs なら 0x01021994、cgroup2fs なら 0x63677270。この定数は Linux のヘッダ（linux/magic.h）に載っているもので、stat -fc %T が種類名を表示するときに引いているのも同じ値です。

ちなみに 0x63677270 をバイトごとに ASCII として読むと c g r p になります。マジックナンバーには、こうした遊びがよくあります。

コード中の uint32(st.Type) というキャストは必要です。st.Type の型はアーキテクチャによって int64 だったり int32 だったりするので、比較の前に幅を揃えないと環境によってコンパイルが通らなくなります。

func write(dir, name, value string) error {
	path := filepath.Join(dir, name)
	if err := os.WriteFile(path, []byte(value), 0o644); err != nil {
		return fmt.Errorf("%s に %q を書けませんでした: %w", path, value, err)
	}
	return nil
}

// hasField は空白区切りの一覧に word が含まれるかを返す。
// strings.Contains では "memory" が "memory_foo" に誤ヒットするので、必ず語単位で見る。
func hasField(list, word string) bool {
	for _, f := range strings.Fields(list) {
		if f == word {
			return true
		}
	}
	return false
}

strings.Fields は文字列を空白（スペース・タブ・改行）で分割して、空要素を捨てたスライスを返します。"cpuset hugetlb\n" なら ["cpuset", "hugetlb"] です。あとは完全一致で比べるだけ。10行足らずですが、この関数が判定の正しさを支えています。

internal/cgroup/cgroup.go — findV1Roots
// v1Controllers は v1 で使うコントローラと、そのマウント位置の候補。
var v1Controllers = []string{"memory", "cpu", "pids"}

// findV1Roots は v1 のコントローラごとのマウント位置を返す。
// memory が見つからなければ v1 は使えないと判断する（メモリ上限がこの教材の Must なので）。
func findV1Roots() (map[string]string, bool) {
	roots := map[string]string{}
	for _, ctrl := range v1Controllers {
		dir := filepath.Join("/sys/fs/cgroup", ctrl)
		if fi, err := os.Stat(dir); err == nil && fi.IsDir() {
			// cgroup v1 のディレクトリなら必ず cgroup.procs がある
			if _, err := os.Stat(filepath.Join(dir, "cgroup.procs")); err == nil {
				roots[ctrl] = dir
			}
		}
	}
	if _, ok := roots["memory"]; !ok {
		return nil, false
	}
	return roots, true
}

判定の考え方は v2 のときと同じです。「ディレクトリがある」だけでは信用しません。その中に cgroup.procs があるかまで確かめます。cgroupfs がマウントされていれば必ずあるファイルなので、「本当に cgroup として機能しているディレクトリか」の証拠になります。tmpfs の上に同名の空ディレクトリが偶然あっても、ここで弾かれます。

そして最後の if。memory が見つからなければ、他が全部揃っていても false を返します。メモリ上限がこの教材の Must だからです。「cpu と pids は使えるので部分的にやります」という中途半端な状態を作らない、という判断です。

			return nil, err
		}

		}

			c.Destroy()
			return nil, err
		}
		// スワップ込みの上限。swap accounting が無い環境では失敗するので、失敗は無視する。

			return nil, err
		}

			const period = 100000
			if err := write(dir, "cpu.cfs_period_us", strconv.Itoa(period)); err != nil {
				c.Destroy()
				return nil, err
			}
			if err := write(dir, "cpu.cfs_quota_us", strconv.FormatInt(int64(limits.CPUs*period), 10)); err != nil {
				c.Destroy()
				return nil, err
			}
		}
	}

		dir, ok, err := mk("pids")
		if err != nil {

			return nil, err
		}

			}

長く見えますが、同じ形が3回繰り返されているだけです。「コントローラのディレクトリを作る → 値を書く」を memory / cpu / pids でやっています。

共通部分は mk というクロージャに切り出されています。mk("memory") と呼ぶと、/sys/fs/cgroup/memory/mydocker/<ID>/ を作って、そのパスを c.dirs に追記し、パスを返します。この c.dirs への追記が後片付けの生命線です。作ったそばからリストに載せるので、途中で失敗しても c.Destroy() が「そこまでに作ったもの」を正確に消せます。

3つの扱いの差にも注目してください。memory は !ok（見つからない）をエラーにしますが、cpu と pids は if ok で包んで、無ければ黙って飛ばします。ここでも Must と Should の区別が形になっています。

cpu のところで cpu.cfs_period_us を先に書いているのは意図的です。period を先に確定させてから quota を書くほうが安全だからです。カーネルは quota が period を超えるような組み合わせを拒否することがあるので、順序を逆にすると環境によっては失敗します。

GO メモ · 関数の中で関数を定義する（クロージャ）

mk := func(ctrl string) (string, bool, error) { ... } という書き方は、Go では非常によく使われます。その関数の中でしか使わない小さな処理を、パッケージレベルの関数にせずにその場で定義する形です。

利点は2つあります。1つは名前空間を汚さないこと。mk はこの関数の外からは見えません。もう1つは外側の変数をそのまま掴めることです。mk の中で c.dirs や roots に触れているのに、引数として渡していないのに気づきましたか。クロージャは外側のスコープの変数を「閉じ込めて」持ち歩けるので、引数の受け渡しが要らないのです。

戻り値が (string, bool, error) の3つなのも Go らしい形です。「値」「見つかったか」「失敗したか」を分けて返すことで、呼び出し側が「見つからなかった（正常）」と「失敗した（異常）」を区別できます。この区別があるからこそ、memory は前者もエラーにし、cpu は前者を許す、という書き分けができます。

Step 7Apply — 作っただけでは効かない

ここまでで、ディレクトリができ、上限の数字が書き込まれました。しかしまだ誰も制限されていません。cgroup は「作った」だけでは何もしないからです。プロセスを入れて、初めて効きます。

internal/cgroup/cgroup.go — Apply
// Apply は pid を cgroup に入れる。ここで初めて上限が効き始める。
//
// ⚠ 「作った」と「入れた」は別である。Apply を忘れた cgroup は
// memory.max に値が入っているのに1バイトも制限しない。
func (c *Cgroup) Apply(pid int) error {
	for _, dir := range c.dirs {
		procs := filepath.Join(dir, "cgroup.procs")
		if err := os.WriteFile(procs, []byte(strconv.Itoa(pid)), 0o644); err != nil {
			return fmt.Errorf("cgroup.procs への書き込みに失敗しました (%s): %w", procs, err)
		}
	}
	return nil
}

9行です。c.dirs —— つまり作ったディレクトリすべて —— の cgroup.procs に、PID を10進数の文字列として書き込みます。それだけ。

ループになっているのは v1 のためです。v2 なら c.dirs は葉1つだけなので1回で終わりますが、v1 では memory / cpu / pids の3か所に同じ PID を書く必要があります。c.dirs という抽象のおかげで、Apply はバージョンの違いを一切知らずに済んでいます。

ここで Cgroup 構造体の設計が効いてきます。newV2 と newV1 はまったく違う作法でディレクトリを作りますが、結果として残るのは「作ったパスの一覧」という同じ形です。だから Apply も Destroy も1つで済みます。「バージョンごとの差を、なるべく早い段階で吸収する」というのは設計の定石です。

タイミングの問題 — 第01章の同期パイプがここで効く

さて、ここに厄介な時間の問題があります。手順を並べてみます。

「いつ cgroup に入れるか」の競争 親（mydocker run） 子（コンテナの中身） ① cgroup.New() でディレクトリを作る ② 同期パイプを作る ③ /proc/self/exe を子として起動 ─────────→ 起動した（PID が決まる） │ ④ cg.Apply(pid) で cgroup.procs に書く │ ★もしここで走り出したら? ↑ ここで初めて上限が効く │ まだ上限が効いていない世界で │ メモリを確保できてしまう ⑤ パイプに合図を書く ──────────────────→ ⑥ 合図を読んでから走り出す （ここまで待つ） ⚠ ③ の直後に PID が分かるが、その瞬間の子はまだ cgroup の外にいる。 ④ を終える前に子が走り出すと、上限をすり抜けた確保が起きうる。

	startErr := func() error {
		if cg != nil {
			if err := cg.Apply(pid); err != nil {
				return err
			}
		}
		return st.Save()
	}()
	if startErr != nil {
		syncW.Close() // 合図を送らずに閉じる → 子は何もせず終了する
		_ = cmd.Wait()
		_ = cleanup(cg)
		return 1, startErr
	}

順序が明確です。cg.Apply(pid) が成功してから、合図を送る。そして Apply が失敗したら、合図を送らずにパイプを閉じます。閉じられたパイプからの読み込みは EOF を返すので、子は「合図が来なかった」と分かって何も実行せずに終了します。

上限がかけられなかったコンテナは、走らせない。この章の最初から一貫している方針が、ここでも守られています。

⚠ 落とし穴 · 同期パイプが無いと、この競争に静かに負ける

この競争に負けても、たいていの場合何も起きません。子が走り出してから親が Apply するまでの時間はミリ秒以下で、その間に 10MB を確保するプログラムはそう多くないからです。

だから、同期パイプを省いた実装でも、テストは通ってしまいます。問題が出るのは、たまたま起動が遅れたときや、子が起動直後に大量確保するときだけです。再現しないバグほど厄介なものはありません。

第01章で「なぜわざわざパイプを作って待たせるのか」と思ったかもしれません。理由の半分がこれです。cgroup に入れ終えるまで、子を走らせないためです。層を先に積んでおいたおかげで、この章では Apply を呼ぶ位置を決めるだけで済みました。

Step 8後片付け — rm -rf では消えない

コンテナが終わったら、作った cgroup を消します。ここで最初に驚くのが、rm -rf が効かないことです。

cgroupfs は通常のファイルシステムではありません。中のファイル（memory.max など）はカーネルが提供している窓口であって、実体のあるファイルではありません。だから unlink できません。rm -rf は「中のファイルを全部消してからディレクトリを消す」という手順で動くので、最初の一歩で失敗します。

正しいのは rmdir（ディレクトリだけを消す）です。カーネルは「このディレクトリを消せ」という指示を受け取ると、中の窓口ファイルごと片付けてくれます。Go では os.Remove がそれに当たります。

internal/cgroup/cgroup.go — Destroy
// Destroy は cgroup ディレクトリを片付ける。
//
// ⚠ cgroupfs は通常のファイルシステムではないので rm -rf では消えない。rmdir を使う。
// ⚠ 中にプロセスが残っていると rmdir は EBUSY で失敗する。これは正しい挙動なので、
// 握りつぶさずエラーとして返す。
func (c *Cgroup) Destroy() error {
	var firstErr error
	for _, dir := range c.dirs {
		if err := os.Remove(dir); err != nil && !os.IsNotExist(err) {
			if firstErr == nil {
				firstErr = fmt.Errorf("cgroup ディレクトリを削除できませんでした (%s): %w", dir, err)
			}
			continue
		}
		// 親（.../mydocker）も空になったら片付ける。
		// 他のコンテナが動いていれば ENOTEMPTY で失敗するが、それが正しいので無視してよい。
		_ = os.Remove(filepath.Dir(dir))
	}
	return firstErr
}

読みどころが3つあります。

① os.IsNotExist(err) は許す。「もう無い」のは目的が達成されている状態なので、エラーにしません。Destroy を2回呼んでも安全（冪等）にするための配慮です。実際、newV2 や newV1 の失敗経路で c.Destroy() が呼ばれ、そのあと呼び出し側の cleanup でもう一度呼ばれることがあります。

② EBUSY は握りつぶさない。中にまだプロセスが残っているとき、rmdir は EBUSY で失敗します。ここで「まあいいか」と無視すると、「消したつもりで消えていない cgroup」が積み上がっていきます。それは、コンテナが終わったつもりで終わっていない、ということでもあります。だからエラーとして返し、上位に報告させます。失敗を失敗として扱うことが、この関数のいちばんの仕事です。

③ 親も消す。ただし失敗は無視する。filepath.Dir(dir) は葉の親、つまり .../mydocker です。ここを os.Remove にかけますが、戻り値は _ で捨てています。他のコンテナが同時に走っていれば、mydocker/ の中には別の葉が残っているので ENOTEMPTY で失敗します。それが正しいのです。「空なら消す、空でないなら消さない」という挙動が、rmdir の仕様だけで自然に実現されています。

⚠ 落とし穴 · 親ディレクトリが残り続ける

③ の処理は、最初の実装にはありませんでした。葉（.../mydocker/<ID>）は消えるのに、親の .../mydocker/ が残り続けていたのです。

タチが悪いのは、これで E2E テストが通ってしまったことです。「配下にコンテナのディレクトリが残っていない」という検査は成功します。残っているのは空の親だけなので。しかし ls /sys/fs/cgroup/memory/mydocker が成功してしまう —— つまり痕跡が残っている状態でした。

検査のほうも直しました。find /sys/fs/cgroup -type d -name mydocker -exec find {} -mindepth 1 -maxdepth 1 -type d \; のように「中身のあるものだけ」を数えるようにし、あわせて Destroy で親も rmdir するようにしています。

教訓は、「残っていないこと」の検査は、何を数えているかを疑ってかかるということです。0 件という結果は、正しく片付いた場合にも、間違ったものを数えている場合にも出ます。

Step 9終了コードの翻訳 — 255 では伝わらない

最後の1段です。ここまでで上限は効くようになりました。しかし、実際に mydocker で試したとき、終了コードが 255 になっていました。

期待していたのは 137 です。Step 2 で python3 /tmp/hog.py を直接動かしたときは exit=137 でした。同じ SIGKILL のはずなのに、mydocker 経由だと 255 になる。なぜでしょう。

犯人は Go の標準ライブラリの仕様でした。exec.ExitError の ExitCode() は、シグナルで殺された場合 -1 を返します。シグナル死には「終了コード」というものが存在しないので、Go は「無い」を -1 で表しているわけです。

そして os.Exit(-1) を呼ぶと、実際にプロセスが返すのは 255 です。終了コードは 8 ビットに丸められるので、-1 は 0xFF = 255 になります。

終了コードが 255 に化けるまで カーネル Go の標準ライブラリ mydocker シェル ──────── ────────────────── ──────── ────── SIGKILL(9) で 子を殺した │ └→ WaitStatus に 「シグナル 9 で死んだ」 と記録される │ └→ ExitError.ExitCode() → -1（「終了コードは無い」の意味） │ └→ os.Exit(-1) │ └→ 8ビットに丸められて… → 255 ✗ 欲しいのは: WaitStatus.Signaled() が true なら 128 + int(WaitStatus.Signal()) → 128 + 9 = 137 ○

直し方は、シェルの慣習に合わせることです。シグナル N で死んだプロセスの終了コードは 128+N、という約束が UNIX 系にはあります。SIGKILL は 9 番なので 137。SIGTERM(15) なら 143。この翻訳を自分で書きます。

internal/container/run.go — exitCode
// exitCode は子プロセスの終了状況をシェルの終了コードに翻訳する。
//
// ⚠ シグナルで殺されたプロセスの ExitCode() は -1 を返す。これをそのまま os.Exit に渡すと
// 255 になり、「OOM で殺された」ことが利用者に伝わらない。
// シェルの慣習に合わせて 128+シグナル番号 を返す（OOM kill なら SIGKILL(9) で 137）。
func exitCode(err error) int {
	if err == nil {
		return 0
	}
	var ee *exec.ExitError
	if errors.As(err, &ee) {
		if ws, ok := ee.Sys().(syscall.WaitStatus); ok && ws.Signaled() {
			return 128 + int(ws.Signal())
		}
		return ee.ExitCode()
	}
	return 1
}

ee.Sys() は、OS 固有の生の終了情報を any として返します。Linux では中身が syscall.WaitStatus なので、型アサーションで取り出します。そこに Signaled() と Signal() というメソッドがあり、「シグナルで死んだか」「何番のシグナルか」を教えてくれます。

あとは 128 + int(ws.Signal()) を返すだけ。これで OOM kill が 137 になります。

この変更の値打ちは、テストで検査できるようになったことです。255 は「何かよく分からない失敗」ですが、137 は「SIGKILL で殺された」という具体的な事実です。E2E テストにこう書けます —— 上限超過が OOM による強制終了として報告される (exit 137)。

GO メモ · errors.As と型アサーション

errors.As(err, &ee) は「err のエラー連鎖のどこかに *exec.ExitError があれば、それを ee に入れて true を返す」という関数です。err.(*exec.ExitError) という単純な型アサーションと違い、fmt.Errorf("...: %w", err) で包まれたエラーの中身まで辿ってくれます。

もう1つの ee.Sys().(syscall.WaitStatus) は普通の型アサーションで、, ok の形にしてあります。こうすると、型が違ったときに panic せず ok が false になります。OS 固有の値を扱うところでは、必ずこの形にするのが安全です。Linux 以外では中身が別の型かもしれないからです。

ちなみに errors.As の第2引数がポインタのポインタ（&ee、ee 自体が *exec.ExitError）なのは、関数の中から ee に代入するためです。Go に参照渡しは無いので、書き換えたい変数はアドレスを渡します。

★関所 — 上限を超えさせて、実際に殺されるところを見る

この章の合格判定です。必ず2回走らせてください。上限なしと、上限ありの両方です。

使うコマンドは dd if=/dev/zero of=/dev/null bs=100M count=1。bs=100M によって、1回のブロック読み込みで 100MB のバッファを確保させます。Step 2 の落とし穴で見たとおり、ここを head | wc にするとメモリを溜めないので上限に当たりません。溜める操作であることが重要です。

▸ 動かして確認 — 対照とペアで見る

① 上限なし。100MB のバッファは問題なく確保でき、成功します。

$ mydocker run --quiet alpine /bin/sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1'
1+0 records in
1+0 records out
104857600 bytes (100.0MB) copied, 0.047161 seconds, 2.1GB/s
$ echo $?
0

② 上限 10m。同じコマンドです。違うのは --memory 10m だけ。

$ mydocker run --quiet --memory 10m alpine /bin/sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1'
$ echo $?
137

何も出力されていません。records in の行すら出ていない。dd はバッファを確保した時点で殺されたので、1バイトもコピーできなかったのです。そして終了コードは 137。

この2つを並べて見ることが大事です。①だけを見せられても「上限が無いときは動く」ことしか分かりませんし、②だけを見せられても失敗の原因が上限なのか、コマンドの書き間違いなのか、mydocker のバグなのか、区別がつきません。

2つ並べて初めて、「違いは --memory 10m の有無だけ。だから死因は上限である」と言い切れます。実装中に head | wc で転んだのは、まさにこの対照を取っていなかったからでした。

⚠ 落とし穴 · head -c 100M /dev/zero | wc -c ではメモリを溜めない

もう一度書いておきます。この章でいちばん時間を溶かした失敗です。

head -c 100000000 /dev/zero | wc -c は、100MB 分のバイトを読んで、数えて、捨てるだけです。パイプを通り抜けるだけなので、どの瞬間にもプロセスが保持しているメモリはごくわずかです。10MB の上限には絶対に当たりません。

これを見て「上限が効いていない」と判断すると、正しく動いている実装を延々と直そうとすることになります。疑うべきはテストのほうでした。

メモリ上限を確かめたいなら、「大きな塊を一度に確保する」操作を選んでください。dd に大きな bs を与えるか、Step 2 の Python のように bytearray を積むか、です。「流す」操作ではなく「溜める」操作を。

つまずき FAQ

結局、cgroup ってカーネルの何をしているんですか? ファイルを書いているだけには見えないのですが。

ファイルを書いているだけ、で合っています。ただし書いた先がカーネルの中です。

cgroupfs のファイルは、ディスク上に実体を持ちません。memory.max に書き込むと、その write システムコールをカーネルが受け取り、そのグループのメモリ会計に上限値をセットします。読み出すと、カーネルが現在の値を文字列にして返します。ファイルの形をした窓口だと思ってください。

この設計は Linux のあちこちで使われています。/proc も /sys も同じ考え方です。「専用の API を作らず、ファイルとして見せる」ことで、シェルからも、どんな言語からも、追加のライブラリなしで触れるようになります。この章で外部ライブラリを1つも使わずに済んだのは、そのおかげです。

v2 が使えない環境なんて、そんなに珍しくないんですか? 最近のディストリはみんな v2 だと聞きましたが。

最近のディストリのホストは、確かにほとんど v2 単独（unified hierarchy）です。Ubuntu 22.04 以降も、Fedora も、Debian 11 以降もそうです。

問題になるのはコンテナの中や、管理システムが介在する実行環境です。この教材の開発環境がまさにそれで、/sys/fs/cgroup は tmpfs、v1 が個別マウント、unified/ に v2 も同居、という hybrid 構成でした。CI サービスやクラウドの実行環境、少し古い Docker のホストなどでも同様の構成に出会います。

そして厄介なのは、こういう環境ほど「v2 が見つかる」判定を通してしまうことです。unified/ に cgroup2 は本当にマウントされているのですから。だからこそ、判定を「マウントされているか」ではなく「memory が使えるか」にする必要がありました。

memory.max に書けたのに制限されない、というのが起きるのはどういうときですか?

主に3つです。

(1) cgroup.procs に PID を書いていない。いちばん多い原因です。上限を設定しても、そのグループに誰も入っていなければ、誰も制限されません。Step 7 の Apply がこれを担当しています。

(2) 制限したいプロセスが子孫を作り、その子孫が別のグループにいる。cgroup の所属は fork したときに引き継がれるので、普通は起きません。ただし途中で誰かが別のグループに移すと起きます。

(3) スワップに逃げている。物理メモリの上限は超えているのに、スワップに書き出されて生き延びているケースです。これを防ぐために mydocker は memory.swap.max（v1 なら memory.memsw.limit_in_bytes）も締めています。

いずれの場合も、確認方法は同じです。実際に超過させてみる。cat で値を読んで満足しないことです。

「内部プロセス禁止」って、既にプロセスが入っているディレクトリで subtree_control を書いたらどうなるんですか?

書き込みが EBUSY で失敗します。カーネルは「このディレクトリは既にプロセスを持っているので、コントローラを子に配る役には回れない」と判断するからです。

逆の順序でも同じです。コントローラを子に配っているディレクトリの cgroup.procs に PID を書こうとすると、やはり EBUSY になります。どちらの操作を先にやっても、両立はできません。

ここでよくハマるのが、/sys/fs/cgroup のルートには既にシステムのプロセスが全部入っているというケースです。ルートは例外扱いなので subtree_control を書けますが、その1段下は違います。だから mydocker は「mydocker/ という空の中間ノードを作って、そこから子に配り、実際のコンテナは葉に置く」という形にしています。中間ノードを意図的に空のまま維持するのが、v2 での階層設計の基本です。

コンテナを強制終了させたら cgroup のディレクトリが残ってしまいました。どうすればいいですか?

rmdir で消してください。rm -rf は効きません。

ただし、まず中にプロセスが残っていないか確認してください。cat <ディレクトリ>/cgroup.procs で PID が出てくるなら、そのプロセスがまだ生きています。生きている限り rmdir は EBUSY で失敗します。これは正しい挙動です。先にプロセスを終了させてください。

v1 の場合は、コントローラの数だけディレクトリがあることを忘れずに。/sys/fs/cgroup/memory/mydocker/<ID> を消しても、/sys/fs/cgroup/cpu/mydocker/<ID> と /sys/fs/cgroup/pids/mydocker/<ID> が残っています。Cgroup.dirs がこの一覧を持っているのは、まさにこのためです。

終了コード 137 以外に、覚えておくべき値はありますか?

128+N の形で覚えると全部同じです。よく見るのは次の3つでしょう。

137 = 128+9（SIGKILL）。OOM killer か、誰かが kill -9 した。この章で扱ったのはこれです。

143 = 128+15（SIGTERM）。行儀のよい終了要求。docker stop がまずこれを送ります。

130 = 128+2（SIGINT）。ターミナルで Ctrl-C を押したとき。

128 未満の値は、プログラム自身が exit() で返したものです。0 は成功、それ以外は失敗を意味しますが、具体的な意味はプログラムごとに違います。128 を境に「自分で終わったのか、殺されたのか」が分かれると覚えておくと便利です。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。

Q1. cgroup で上限をかけるのに必要な操作を3つ挙げてください。それぞれ、どんなシステムコールに相当しますか?

① ディレクトリを作る（mkdir）。これで新しいグループができます。中のファイルはカーネルが勝手に生やします。

② 上限のファイルに数値を書く（write）。memory.max や memory.limit_in_bytes に、バイト数を10進の文字列として書きます。

③ cgroup.procs に PID を書く（write）。これで初めて上限が効き始めます。

専用のシステムコールは1つもありません。全部 mkdir と write です。Go の実装でも os.MkdirAll と os.WriteFile しか使っていません。唯一の例外が syscall.Statfs ですが、これは上限をかけるためではなく「そこが cgroup2fs かどうか」を判定するためのものです。

Q2. cat memory.limit_in_bytes が 10485760 を返しました。これで上限が効いていると言えますか? 言えないなら、どう確かめますか?

言えません。それは「ファイルに値が入っている」ことの証明でしかありません。

効いていないケースは実際にあります。いちばん多いのは cgroup.procs に PID を書き忘れているときで、値は入っているのに誰も制限されません。

確かめ方は実際に超過させることです。しかも対照とペアで。上限なしなら成功し、上限ありなら殺されることを、同じコマンドで確認します。

そのとき使うコマンドはメモリを溜めるものでなければいけません。dd if=/dev/zero of=/dev/null bs=100M count=1 は 100MB のバッファを一度に確保するので有効です。head -c 100M /dev/zero | wc -c は流すだけなので無効です。

Q3. この環境で stat -fc %T /sys/fs/cgroup/ は tmpfs を返しました。これは「cgroup v2 が無い」ことを意味しますか?

意味しません。実際、この環境には /sys/fs/cgroup/unified に cgroup2 がマウントされていました。mount | grep cgroup の最後の行がそれです。

/sys/fs/cgroup が tmpfs なのは、そこがただの置き場だからです。その下に v1 のコントローラが1つずつ、それぞれ別のマウントとしてぶら下がり、さらに unified/ に v2 も同居している —— hybrid 構成です。

そして、v2 があっても使えるとは限りません。この環境の unified/cgroup.controllers は cpuset hugetlb だけで、memory は v1 側に取られていました。1つのコントローラは v1 と v2 のどちらか一方にしか結び付きません。

だから判定は3段階にしました。(1) statfs の f_type が cgroup2fs か、(2) cgroup.controllers が読めるか、(3) そこに memory が語として見えるか。3つ目まで通って初めて「v2 が使える」と判断します。

Q4. hasField の代わりに strings.Contains を使うと、どんな問題が起きますか?

部分一致による誤検出が起きます。strings.Contains("memory_foo bar", "memory") は true を返しますが、memory というコントローラは実在しません。

誤検出の結果は深刻です。「v2 で memory が使える」と誤判定して newV2 に進み、しかし葉に memory.max が生えないので書き込みに失敗する —— あるいは、失敗を握りつぶしていれば上限が効かないままコンテナが起動します。この章でいちばん避けたい結末です。

hasField は strings.Fields で空白分割してから完全一致で比べるので、こうした誤りが起きません。「空白区切りの一覧」を扱うときは、必ず語単位で見る。これは cgroup に限らず、/proc や /sys の他のファイルを読むときにも通用する作法です。

Q5. Destroy が親ディレクトリの削除失敗を無視しているのに、葉の削除失敗はエラーにしているのはなぜですか?

失敗の意味が違うからです。

葉（.../mydocker/<ID>）の削除が失敗するのは、たいてい EBUSY —— 中にまだプロセスが残っているときです。これは異常事態です。コンテナが終わったつもりなのに終わっていない、ということですから、握りつぶさずに報告しなければいけません。無視すると「消したつもりで消えていない cgroup」が積み上がります。

親（.../mydocker）の削除が失敗するのは、たいてい ENOTEMPTY —— 他のコンテナがまだ動いているときです。これは正常です。むしろ消えてしまったら困ります。だから _ = os.Remove(...) と戻り値を捨てています。

「空なら消す、空でないなら消さない」が rmdir の仕様なので、条件分岐を書かずに済んでいます。システムコールの仕様をそのまま利用して、判断を1行減らすという書き方です。

Q6. OOM で殺されたコンテナの終了コードが 255 になっていました。原因と直し方を説明してください。

原因は Go の exec.ExitError.ExitCode() が、シグナルで殺された場合に -1 を返すことです。シグナル死には終了コードが存在しないので、Go は「無い」を -1 で表しています。それを os.Exit(-1) に渡すと、終了コードは8ビットに丸められて 255 になります。

直し方は、シェルの慣習に合わせて 128 + シグナル番号 を返すことです。ee.Sys() を syscall.WaitStatus に型アサーションし、ws.Signaled() が true なら 128 + int(ws.Signal()) を返します。SIGKILL は 9 番なので 137 になります。

この修正の値打ちは、テストで検査できるようになることです。255 は「何かよく分からない失敗」ですが、137 は「SIGKILL で殺された」という具体的な事実です。E2E に 上限超過が OOM による強制終了として報告される (exit 137) という項目を書けるようになりました。

まとめ — 次の層へ

この章で、コンテナの世界に底が入りました。名前空間が「見えるもの」を仕切ったのに対し、cgroup は「使えるもの」を仕切ります。やったことは、ディレクトリを作り、ファイルに数字を書き、cgroup.procs に PID を書く —— それだけでした。外部ライブラリはゼロ、システムコールも Statfs が1つだけ。cgroup はただのファイル操作であるという一点を、手で確かめて、コードで確かめて、対照実験で確かめました。同時に、「書けた」と「効いた」がまったく別のことも学びました。cat で値が読めても何の証明にもならず、実際に超過させて exit 137 を見るまでは信じてはいけない。そして、この環境では v2 が使えないという実測から、判定を「マウントされているか」ではなく「memory が語として見えるか」に変え、2つのバックエンドを持つに至りました。

しかし、まだ大きな不自然さが残っています。コンテナが立つ rootfs を、私たちは手で用意しています。第03章で pivot_root の実験をしたとき、/tmp/rootfs のようなディレクトリはどこから来たのでしょう。誰かがどこかから展開して置いたものです。alpine という名前でコンテナを起動できるのも、たまたまそこに alpine の中身が置いてあるからにすぎません。ここまでの4章を通して、「イメージ」という言葉が一度も出てきていないことに気づいたでしょうか。プロセスを隔離し、根を挿げ替え、上限をかける道具は揃いました。けれど、その根に何を置くかを、まだ自分で決められていないのです。docker run ubuntu と打つだけで ubuntu の中身が現れるあの体験は、まだ1ミリも再現できていません。

次章では、そこに取りかかります。docker pull が裏で何をしているのかを、HTTP のレベルから自分で書きます。認証トークンを取り、マニフェストを読み、レイヤの実体をダウンロードする —— レジストリ API は公開された仕様なので、curl で叩いて目で見ることができます。実際、この環境では途中で足をすくわれました。返ってきたマニフェストに layers が無かったのです。なぜそうなるのか、どう対処するのかを含めて、イメージという言葉の中身を開けにいきます。
