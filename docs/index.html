この一文を信じられるようになることが、この教材のゴールです。コンテナの実体は、namespace で視界を区切り、cgroup で資源を締め、pivot_root で根を挿げ替えた、ただのプロセスです。仮想の CPU も、ゲスト OS も、どこにもありません。これから 10 章かけて、その「ただのプロセス」を Go の標準ライブラリだけで自分の手で組み上げます。

◈ この本のゴール

docker run alpine /bin/sh と打ったときに Linux カーネルの中で何が起きているかを、暗記ではなく理解している状態になること。そのために、同じことをする mydocker というプログラムを、外部ライブラリを 1 つも使わずに自分で書きます。containerd も runc も libcontainer も使いません。docker pull も呼びません。使うのは Go の標準ライブラリと、Linux カーネルが提供するシステムコールだけです。

最終的にできあがるのは、run / ps / exec / pull / rm / info を持つ、約 9.0 MB のバイナリ 1 つです。

中心命題 — コンテナは軽量な仮想マシンではない

「コンテナは軽い仮想マシンみたいなもの」という説明を、一度は聞いたことがあると思います。分かりやすい比喩ですし、使う側でいるあいだは、それで困りません。ただ、この比喩は作る側に回った瞬間に完全に破綻します。比喩のまま進むと、これから読むコードが 1 行も理解できません。ですからここで捨てます。

仮想マシンは、ハードウェアそのものを模倣します。仮想の CPU があり、仮想のメモリがあり、仮想のディスクがあり、その上にもう 1 つ別の OS カーネルが載ります。ゲスト OS はブートローダから起動し、自分専用のカーネルを初期化し、init を立ち上げ、デーモンを並べます。だから起動に時間がかかり、イメージも大きくなります。

コンテナには、その層が1 枚もありません。コンテナの中で動いているプロセスは、ホストのカーネルにそのまま話しかけています。read() も write() も fork() も、あなたが普段 Linux で走らせているプログラムとまったく同じカーネルが処理します。カーネルは 1 つしかありません。「コンテナ」という名前の実体は、カーネルの中のどこにも存在しません。

仮想マシンとコンテナ — 積み方が違う 【仮想マシン】 【コンテナ】 ┌──────────────┐ ┌──────────────┐ │ アプリ │ │ アプリ │ ← ただのプロセス ├──────────────┤ └──────┬───────┘ │ ゲスト OS │ ★もう1枚 │ namespace で視界を区切り │ （カーネル） │ カーネルが │ cgroup で資源を締め ├──────────────┤ 載る │ pivot_root で根を替えた │ 仮想ハード │ │ 「だけ」の状態 ├──────────────┤ ┌──────┴───────┐ │ ホスト OS │ │ ホスト OS │ ← カーネルは1つだけ ├──────────────┤ ├──────────────┤ │ ハードウェア │ │ ハードウェア │ └──────────────┘ └──────────────┘

ここが腑に落ちると、Docker まわりの不思議がまとめて説明できるようになります。なぜコンテナはミリ秒で起動するのか — 起動する OS が無いからです。ただプロセスを 1 つ fork して exec しているだけだからです。なぜ Linux のコンテナが Windows でネイティブに動かないのか — namespace も cgroup も Linux カーネルの機能そのものだからです。なぜコンテナの中で uname -r を打つとホストのカーネルバージョンが返るのか — 本当にホストのカーネルだからです。

逆に言うと、この教材で作るものは魔法ではありません。カーネルに既にある機能を、正しい順番で呼ぶだけです。難しいのは個々のシステムコールではなく、順番と後片付けです。それを間違えると、コンテナは静かに壊れます。壊れ方も含めて、全部この教材で踏みます。

では何なのか — 3つの細工をされたプロセス

コンテナが「ただのプロセス」なら、普通のプロセスと何が違うのでしょうか。答えは、起動する瞬間に3つの細工が施されている、それだけです。

1つめ、namespace（名前空間）で視界を区切る。 Linux のプロセスは、プロセス一覧・ホスト名・マウントの一覧・プロセス間通信の道具といった「見えるもの」を、既定ではシステム全体で共有しています。namespace は、この「見えるもの」の台帳をプロセスごとに別々に持たせる仕組みです。PID 名前空間を新しく作れば、そのプロセスは自分を PID 1 だと思い込みます。UTS 名前空間を作れば、ホスト名を勝手に変えてもホストに影響しません。隠しているのではなく、参照する台帳そのものが別になっています。

2つめ、cgroup（control group）で資源を締める。 視界を区切っただけでは、メモリを 100 GB 確保しにいってホストごと巻き込むことができてしまいます。cgroup は「このプロセス群はメモリを 10 MB までしか使ってはいけない」といった上限を、カーネルに強制させる仕組みです。上限を超えると、カーネルがそのプロセスを SIGKILL で殺します。お願いではなく、強制です。

3つめ、pivot_root で根を挿げ替える。 視界と資源を区切っても、ファイルシステムはホストのままです。コンテナの中で ls / と打ったときにホストの /etc が見えては、隔離とは言えません。pivot_root は、そのプロセスにとっての「/」を、別のディレクトリに丸ごと差し替えるシステムコールです。差し替えた先に alpine の中身を置けば、そのプロセスから見た世界は alpine そのものになります。

3つの細工 普通のプロセス コンテナ（＝細工されたプロセス） ───────────── ──────────────────────────── ps でホストの全プロセスが見える → namespace 自分しか見えない メモリは取り放題 → cgroup 10MB を超えたら殺される / はホストの / → pivot_root / は alpine の中身 細工は「起動の瞬間」に、この順で入る。順番を崩すと必ず壊れる。

この 3 つに、後半で「イメージをレジストリから取ってくる」「レイヤを重ねる」「実行中のコンテナを覚えておく」が加わります。Docker の本質的な部分は、この 6 つでほぼ説明がつきます。 残りは利便性のための膨大な作り込みです。この教材は本質的な 6 つを扱います。

Step 1完成品を 5 分だけ動かす（山頂を先に見る）

いきなり理屈から始めると、何を作っているのか分からないまま 3 章くらい進んでしまいます。ですので、先に完成品を見ます。ここではまだ手を動かさなくて構いません。実際に自分の環境で動かす準備は次の第00章でやります。今は「これがゴールなのか」と眺めるだけで十分です。

Step 2出力を 1 行ずつ読む

さらっと流してしまいがちですが、上の出力の 1 行 1 行が「細工が効いた証拠」です。順に見ていきます。

① ps に自分しか出ない — namespace が効いている

コンテナの中で ps を打つと、出てくるのは 2 行だけです。ヘッダと、PID 1 の /bin/sh。あとは ps 自身。同じ瞬間、ホスト側では 85 個のプロセスが動いています。sshd も、systemd 系のデーモンも、あなたのエディタも動いています。それが 1 つも見えません。

そして注目すべきは PID が 1 であることです。Linux で PID 1 は特別なプロセス、システム全体の親（init）です。普通のプログラムが PID 1 になることはありません。それがここでは /bin/sh になっています。このプロセスは「自分がこのシステムの最初のプロセスだ」と信じ込んでいます。 PID 名前空間が新しく作られ、その中で番号が 1 から振り直されているからです。これは第02章で作ります。

② hostname が mydocker — UTS 名前空間が効いている

ホスト側でホスト名を確認すると vm です。ところがコンテナの中では mydocker と返ってきます。コンテナの中で hostname を変更しても、ホストのホスト名は変わりません。ホスト名という「システムに 1 つしかないはずの設定」が、プロセスごとに別々の値を持てるようになっています。 これが UTS 名前空間です。これも第02章です。

③ ls / が alpine の中身 — pivot_root が効いている

bin dev etc home lib media mnt opt proc root run sbin srv sys tmp usr var。これは alpine linux 3.24.1 のルートディレクトリの中身です。ホストのルートには lost+found や boot や lib64 があるはずですが、ここには 1 つもありません。このプロセスにとっての「/」は、もうホストの / ではありません。

しかもこの alpine の中身は、事前にどこかからコピーしてきたものではありません。mydocker が自分でレジストリに HTTP でアクセスし、トークンを取り、マニフェストを読み、レイヤの tar.gz をダウンロードして展開したものです。第05章と第06章でこれを作ります。

⚠ 落とし穴 · 「見えない」と「隔離されている」は違う

この教材で作る mydocker は、ネットワーク名前空間だけは作っていません。つまりコンテナの中で ip addr を打つと、ホストの eth0 がそのまま見えます。IP アドレスもホストと同一です。

できていないことを「できたふり」で書かないために、この教材では第08章を「なぜネットワークの隔離が難しいのか・実装するなら何が必要か」を扱う地図の章にしてあります。作れなかったものを作れたことにするより、そのほうが読者の役に立つと判断しました。

Step 3数字で体感する

「軽い」という言葉は主観的です。数字で見ます。ここに挙げるのは、すべて実際にこの環境（Linux 6.18.5 / x86_64）で測った値です。

起動時間 — 12 ms 対 3 ms

キャッシュ済みの alpine で /bin/true を実行するだけのコンテナを 5 回起動して、かかった時間を測りました。

▸ 動かして確認

コンテナ起動 5 回分の実測値です。

15 ms / 13 ms / 12 ms / 12 ms / 12 ms

対照として、同じ /bin/true をホストで直接実行した場合は 3 ms でした。

差は 9〜12 ms。この差の中で、overlayfs のマウント、namespace の生成、cgroup ディレクトリの作成、pivot_root、/proc の貼り直し、そして後片付けが全部行われています。「プロセスを 1 つ起動する」ことに対する上乗せが、ミリ秒の桁で収まっているということです。

仮想マシンを 1 台起動すると、一般には数十秒かかり、ディスクイメージも数百 MB から数 GB になります。これは一般的に知られている事実として書いています。今回の環境では仮想マシンの起動時間を測っていないので、実測値としては提示しません。ただ、桁が 3 つも 4 つも違うという感覚は持っておいてください。そしてその差の理由が「起動する OS が無いから」であることは、もう分かるはずです。

この 85 対 1 という数字が、namespace が効いていることのいちばん分かりやすい証拠です。同じマシン、同じカーネル、同じ瞬間に、片方からは 85 個見えていて、もう片方からは 1 個しか見えていません。

⚠ 落とし穴 · 「1 個しか見えない」は自動的には手に入らない

PID 名前空間を作っただけでは、コンテナの中の ps はホストのプロセスを全部表示します。しかも実測では 87 個と、ホスト側の 85 個より多く出ました。名前空間は正しく効いているのに、です。

犯人は /proc です。ps は /proc を読んでプロセス一覧を作るので、/proc がホストのものを指したままだと、名前空間の中にいてもホストの情報が見えてしまいます。この「効いているのに見えない」問題は第03章の山場です。序章では「そういう罠がある」とだけ覚えておいてください。

道具箱 — これから断りなく使う言葉

ここから先、次の言葉は断りなく使います。今すべて理解する必要はありません。それぞれ担当の章で 1 つずつ丁寧に扱います。ここは「読んでいて詰まったら戻ってくる場所」として置いておきます。

用語ひとことで言うと扱う章
namespace
（名前空間）		プロセスから「見えるもの」の台帳を、プロセスごとに別々に持たせるカーネルの仕組み。PID・ホスト名・マウント・IPC など種類ごとに独立している。隠しているのではなく台帳が別。第02章
cgroup
（control group）		プロセス群に対して CPU・メモリ・プロセス数の上限をカーネルに強制させる仕組み。ディレクトリを作り、そこのファイルに数値を書き、cgroup.procs に PID を書くと効く。作っただけでは効かない。第04章
マウント
と伝播		ファイルシステムを「木のどこか」に接ぎ木すること。マウントには伝播（propagation）という性質があり、既定では自分のマウント操作が他へ伝わっていく。切らないとホストを汚す。第03章
rootfsコンテナにとって / になるディレクトリツリー。中身は bin etc lib …。カーネルは含まない。第03・06章
pivot_rootプロセスにとっての / を別のディレクトリに丸ごと差し替えるシステムコール。chroot より強い。chroot には破り方が知られている。第03章
レイヤイメージを構成する tar.gz の 1 枚。イメージは複数のレイヤの重ね合わせとして表現される。alpine は 1 枚。第05・06章
レジストリイメージを配る HTTP サーバ。Docker Registry API v2。トークン → マニフェスト → レイヤの 3 段でしか取れない。第05章
OverlayFS読み取り専用の下層（lowerdir）と書き込み用の上層（upperdir）を重ねて 1 つに見せるファイルシステム。書き込みは上層にだけ溜まる。捨てれば元通り。第06章
マニフェストイメージの目次にあたる JSON。どのレイヤをどの順で重ねるかが書いてある。⚠ 最初に返ってくるのはインデックス（マニフェストリスト）で、layers が入っていないことがある。第05章
re-exec自分自身のバイナリを /proc/self/exe 経由でもう一度起動する手法。名前空間を作りつつ Go のコードで初期化を書くための定石。第01章
ホワイトアウト「上のレイヤでこのファイルを消した」ことを表す印。tar の中では .wh. で始まるファイル名として現れる。overlay 形式へ翻訳が要る。第06章

もう 1 つ、断りなく使う略記があります。Must / Should / Could です。この教材では「絶対に作るもの（Must）」「作りたいもの（Should）」「余裕があれば（Could）」を最初に決めてから実装を始めました。namespace と cgroup が Must、イメージ取得と OverlayFS が Should、ネットワークが Could です。第00章では、その Must が本当に成立するかを実際に確かめるところから始めます。

層は下から積まれる — 飛ばせない

この教材はレシピ集ではありません。各章が一つの層で、下の層の上にしか次の層が立ちません。 「cgroup のところだけ読みたい」という読み方は、残念ながらできません。第04章は第01章で作った親子構造を前提にしているからです。

もっとはっきり言います。1 章飛ばすと次章は必ず分かりません。 これは脅しではなく構造上の事実です。第03章は第02章で「PID 名前空間を作ったのに ps がホストのプロセスを出す」という壊れ方を体験していることが前提ですし、第06章は第05章で取ってきたレイヤが手元にあることが前提です。

各章が何をする章なのかを、1 行ずつ書いておきます。

なぜ Go で、なぜ依存ライブラリを 1 つも使わないのか

言語の選択には理由があります。コンテナランタイムを書くのに向いている言語の条件は 3 つあります。システムコールを直接呼べること、1 つのバイナリに固まって配布できること、そして読みやすいことです。Go はこの 3 つを同時に満たします。C はシステムコールを呼べますが読みやすさで劣り、Python は読みやすいですがプロセスを fork して名前空間を作る部分で苦労します。実際、本物の Docker（moby / containerd / runc）もすべて Go で書かれています。

もう 1 つ、この教材には強い縛りがあります。外部ライブラリを 1 つも使いません。 go.mod の require ブロックは空のままです。使うのは Go の標準ライブラリだけ — syscall、os/exec、net/http、archive/tar、compress/gzip、encoding/json。この 6 つでコンテナランタイムが 1 本書けます。

なぜここまで縛るのか。ライブラリを使うと、いちばん学びたい部分がライブラリの中に隠れてしまうからです。libcontainer を使えばコンテナは 20 行で起動できます。ただ、その 20 行を書いても namespace のことは何も分かりません。分かるのは libcontainer の使い方だけです。この教材の目的は Docker を作ることではなく、Docker が何をしているかを理解することなので、そこは自分で書きます。

逆に言うと、この縛りがあるおかげで、この教材のコードは全部読めます。 行数にして数百行です。依存が無いので、ビルドもネットワーク無しで通ります。第00章で go build ./... を打つと、外部から何もダウンロードせずにバイナリができあがります。それが require が空であることの実感です。

この教材の書き方 — 素朴案が壊れるところから始める

各章は、だいたい同じ形をしています。まず素朴に考えて思いつく方法を試します。次にそれが壊れるところを実際に見ます。そのうえで、なぜ本物の実装がそういう形になっているのかを理解します。いきなり正解のコードを出すことはしません。

たとえば第03章は、こう進みます。「コンテナの / を変えたい。chroot というのがあるらしい」→ 実際に chroot で牢屋を作る → Python 10 行で牢屋から脱獄してみせる → だから pivot_root が要る。第02章はこうです。「名前空間を作った。ps を打とう」→ ホストより多い 87 個が出る → なぜだ → /proc だ。

この形にしているのは、「なぜ」が抜けた知識はすぐ消えるからです。「pivot_root を使いましょう」とだけ覚えても、半年後には忘れます。「chroot は fchdir で破れるのを自分の目で見た」なら、忘れません。少し遠回りに見えるかもしれませんが、こちらのほうが速いです。

そして各ステップの最後には「動かして確認」という関所を置いています。そこに書いてある出力が自分の画面に出るまでは、次に進まないでください。出ない場合は、その章のどこかに書いてある落とし穴を踏んでいます。落とし穴は読者が踏む前に警告する方針で書いていますが、それでも踏むときは踏みます。踏んだら、その章の「つまずき FAQ」を見てください。

必要なものは 2 つだけです。

必要ないものも、はっきり書いておきます。

  • Linux カーネルの知識は要りません。 namespace も cgroup も知らない前提で書いています。
  • Docker の内部知識も要りません。 docker run を使ったことがあれば十分で、無くても読めます。
  • C の知識も要りません。 システムコールは Go の syscall パッケージ越しに呼びます。

知らない概念が初めて出てくるところでは、その場で GO メモ または LINUX メモ という枠を挟んで補足します。形はこうです。

LINUX メモ · システムコール

プログラムがカーネルに仕事を頼むときの窓口がシステムコールです。ファイルを開く open、読む read、プロセスを複製する fork、別のプログラムに変身する execve — どれもシステムコールです。ユーザが書いたプログラムは、自分ではディスクにもメモリ管理にも触れません。必ずカーネルに頼みます。

この教材で使う unshare、mount、pivot_root、sethostname も、すべてシステムコールです。つまりコンテナを作るというのは、システムコールを正しい順番で呼ぶことに他なりません。

GO メモ · syscall パッケージ

Go の標準ライブラリには syscall というパッケージがあり、Linux のシステムコールをほぼそのまま呼べます。たとえば syscall.Sethostname([]byte("mydocker")) と書けば、C から sethostname() を呼ぶのと同じことが起きます。

「Go で低レベルなことをやるのは大変では?」と思うかもしれませんが、この教材の範囲ではむしろ C より書きやすいです。エラーが戻り値で返ってくるので errno を気にしなくて済みますし、os/exec が名前空間の指定まで面倒を見てくれます。C の知識は最後まで出てきません。

コードは常に src/ の実装と一字一句一致させています。教材のために簡略化した「説明用のコード」は 1 行もありません。省略するときは // …（後のステップで） と明示します。読んだコードがそのまま動くコードです。

⚠ Windows / macOS では動きません

⚠ 落とし穴 · ここが最初にして最大の関門

この教材のコードは、Windows でも macOS でもネイティブには一行も動きません。 namespace / cgroup / overlayfs / pivot_root は Linux カーネルの機能そのものだからです。「Go はクロスプラットフォームだから大丈夫」ではありません。Go は動きますが、呼ぶ相手のカーネルがいません。

さらに、Linux であっても特権（CAP_SYS_ADMIN など）が要ります。一般ユーザ権限では mount も pivot_root も /sys/fs/cgroup への書き込みも EPERM（Operation not permitted）で落ちます。

正直に言うと、この教材でいちばん多くの人がつまずくのは技術ではなく開発環境です。 第03章の pivot_root より、第00章の「特権 Linux をどう用意するか」のほうが脱落者が多い。だから第00章を独立した 1 章として立て、しかもそこそこの分量を割いています。

用意する方法は 2 つあります。案A: 特権付きの Docker コンテナを 1 つ立て、その中で開発する（推奨）。案B: WSL2 の Linux をそのまま使う。案A は「Docker を作るために Docker を使う」という愉快な入れ子になりますが、環境の差が出にくく、後片付けも楽です。詳しくは次の第00章で扱います。

そして第00章では、環境を用意したあとに疎通実験をします。namespace は作れるか。cgroup は書けるか。書けたとして本当に効くか。overlayfs はマウントできるか。レジストリに届くか。1 行も実装を書く前に、この 5 つを実際にコマンドを打って確かめます。 ここを飛ばすと、第04章まで進んでから「この環境では cgroup が効かない」と気づくことになります。

つまずき FAQ

Docker がもうあるのに、なぜ自分で作るんですか?

使うためではなく、理解するためです。この教材で作る mydocker は、本物の Docker の代わりにはなりません。ネットワークの隔離も無いし、イメージのビルドもできないし、セキュリティの絞り込みもしていません。

ただ、docker run が何をしているかを説明できるようになります。コンテナが起動しないとき、ログの前に /proc/<pid>/ns/ を見るという発想が出るようになります。「コンテナから抜け出せる脆弱性」というニュースを読んだときに、何が破られたのかが分かるようになります。ブラックボックスが 1 つ減るのが目的です。

「コンテナは軽量な VM ではない」と言われても、使う分には同じに見えます。何が変わりますか?

使う分には、たしかにほとんど同じに見えます。問題が起きたときに差が出ます。

たとえば、コンテナの中で free -m を打つとホストのメモリ量が返ってくることがあります。VM の比喩で考えていると意味が分かりませんが、「ただのプロセスで、/proc/meminfo はホストのものを見ている」と分かっていれば当然の結果です。コンテナの中の uname -r がホストのカーネルバージョンを返すのも同じ理由です。比喩で説明できない現象が出たとき、比喩を持っている人は詰みます。

Go を知らないと読めませんか? Python しか書いたことがありません。

読めます。この教材で使う Go は、ほぼ「型のある手続き型言語」の範囲です。func で関数を定義し、if err != nil { return err } でエラーを返し、defer で後片付けを予約する。この 3 つが分かれば 9 割は読めます。

むしろ難しいのは Go ではなく Linux 側です。そちらは前提知識ゼロで書いてあるので、Go の文法だけ都度調べれば追いつけます。なお疎通実験の一部と E2E テストは Python で書いてあるので、Python 経験は無駄になりません。

章を飛ばして、興味のある cgroup の章だけ読んではだめですか?

おすすめしません。第04章の cgroup は「第01章で作った親子構造の、子の PID を cgroup.procs に書く」という形で実装されているので、親子構造を知らないとコードの半分が宙に浮きます。

どうしても急ぐなら、第00章 → 第01章 → 第02章 → 第04章という最短経路はあります。ただし第03章を飛ばすと「ps が 87 個出る」という、この教材でいちばん面白い壊れ方を見逃します。もったいないです。

Mac で開発しています。詰みですか?

詰みではありません。Docker Desktop が動いていれば、その中で特権付きの Linux コンテナを立てられます。それが第00章の案Aです。「Docker を作るために Docker を使う」という入れ子になりますが、これは冗談ではなく実務でも普通に使われる手です。

ただし、macOS 上の Docker Desktop は内部で Linux VM を動かしているので、その VM のカーネル設定によっては cgroup まわりの挙動が変わることがあります。だからこそ第00章で「自分の環境で実際に何ができるか」を先に確かめます。前提にせず、確かめる。これがこの教材の姿勢です。

この教材のコードは、そのまま本番で使えますか?

使えません。使ってはいけません。理由を挙げます。

ネットワークが隔離されていないので、コンテナはホストのネットワークをそのまま共有します。user namespace を使っていないので、コンテナ内の root はホストの root です。seccomp も capabilities の絞り込みもしていないので、危険なシステムコールが素通りします。これらは「作り忘れ」ではなく、学習の焦点を絞るために意図的に外したものです。何を外したかは第09章で全部並べます。

外部ライブラリを使わないと言っていますが、それは意地を張っているだけでは?

実務なら意地です。学習ならそうではありません。libcontainer を import して 20 行でコンテナを起動しても、分かるのは libcontainer の API だけで、namespace のことは何も分かりません。

それに、この範囲では標準ライブラリだけで本当に足ります。syscall でシステムコールを呼び、os/exec で子プロセスを起こし、net/http でレジストリを叩き、archive/tar と compress/gzip でレイヤを展開する。無理をして避けているのではなく、素直に書いたら要らなかった、というのが実態です。

「動かして確認」の出力が自分の画面と違います。先に進んでいいですか?

進まないでください。この教材の出力はすべて実測で、想像で書いた行は 1 つもありません。違うということは、環境か手順のどちらかが違っています。

ただし、変わって当然のものもあります。PID の値（7 の部分）、コンテナ ID（a169666dadfc のような 12 桁）、起動時刻、ミリ秒の実測値です。これらは毎回変わります。変わってはいけないのは行数と構造です。ps が 3 行以上出たら、それは何かが効いていません。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。答えを見て「知っていた」と思うかどうかではなく、見る前に言葉にできたかで判定してください。

Q1. コンテナと仮想マシンの、いちばん本質的な違いは何ですか? 「軽い」以外の言葉で説明してください。

カーネルの枚数です。 仮想マシンはゲスト OS のカーネルをもう 1 枚積みます。コンテナは積みません。コンテナの中のプロセスはホストのカーネルに直接システムコールを投げています。

「軽い」はこの構造から出てくる結果であって、原因ではありません。起動する OS が無いから速く、カーネルを含まないからイメージが小さい。原因のほうを言えるようになってください。

Q2. コンテナの中で ps を打つと 2 行しか出ないのはなぜですか? ホスト側のプロセスはどこへ行ったのですか?

どこへも行っていません。85 個のプロセスは今この瞬間も同じマシンで動いています。 ただ、コンテナのプロセスが参照しているプロセス一覧の台帳（PID 名前空間）が別物なので、そこに載っていないだけです。

ここが「隠している」との決定的な違いです。フィルタしているのではなく、そもそも別の台帳を見ています。だからホスト側からは、コンテナの中のプロセスがちゃんと見えます（別の PID 番号で）。

Q3. コンテナの中の /bin/sh が PID 1 になっているのはなぜ重要なのですか?

PID 1 は Linux にとって特別な番号で、システム全体の親（init）です。それが /bin/sh になっているということは、このプロセスにとっての「システム全体」がコンテナの中だけになっていることを意味します。

実務的にも重要です。PID 1 はシグナルの扱いが特別（既定のシグナルハンドラが無効）なので、コンテナの PID 1 が SIGTERM を無視して docker stop が 10 秒待たされる、という現象がここから説明できます。

Q4. alpine のイメージは圧縮 3.67 MiB、展開後 8.7 MB、516 ファイルでした。カーネルはどこにありますか?

入っていません。 ホストのカーネルを使うからです。イメージに入っているのは /bin、/lib、/etc、/usr といったユーザ空間のファイルだけです。

これが「コンテナイメージは OS のイメージではない」ということの具体的な意味です。alpine のイメージは「alpine というディストリビューションのユーザ空間一式」であって、alpine のカーネルではありません。だからこの小ささで済みます。

Q5. この教材の章を飛ばせないのはなぜですか? 単に著者がそう決めただけではないのですか?

構造上の理由です。各章のコードが前章のコードの上に書かれています。第03章の pivotRoot は、第01章で作った「re-exec された子プロセス側」の中で呼ばれます。第04章の cgroup は、第01章の親側が子の PID を握っていることを前提にしています。

加えて、教材としての理由もあります。各章は「前章の作りかけが壊れている」ところから始まります。 第02章で名前空間を作った直後に ps が壊れて見え、その驚きが第03章の動機になります。飛ばすと、解決すべき問題を知らないまま解決策だけ読むことになり、記憶に残りません。

Q6. コンテナの起動が 12 ms、ホストでの直接実行が 3 ms でした。この 9 ms の差では何が起きていますか?

この教材で作るものに即して言うと、overlayfs のマウント、名前空間の生成、cgroup ディレクトリの作成と PID の登録、pivot_root、/proc の貼り直し、そして終了後の後片付けです。

大事なのは、ここにゲスト OS のブートが含まれていないことです。含まれていたら ms の桁では終わりません。9 ms は「プロセスを 1 つ起動する」ことへの上乗せであって、「OS を 1 つ起動する」時間ではありません。この差がコンテナの速さの正体です。

Q7. この教材が「実測にない数値は書かない」という縛りを置いているのはなぜだと思いますか?

技術文書でいちばん危ないのが、それらしい数字の捏造だからです。「起動は約 50 ms」と書いてあっても、測ったのか、どこかで読んだのか、なんとなくそう思っているのかは、読者には区別できません。

この教材では、貼ってある出力はすべて実際に取得したものです。だから ps が「87 個」というホストより多い変な値も、そのまま出てきます。都合の悪い値も含めて実測だけを載せる、というのはこの教材の姿勢そのものです。そして同じ姿勢を、あなたが実装するときにも要求します — 「上限を設定できた」ではなく「上限が効いた」を確かめる、というのが第00章と第04章の主題です。
