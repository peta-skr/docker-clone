Reexec— 自分自身を別の顔で呼ぶ

自分をもう一度起動する

コンテナの中で ps を打つと、いちばん上に PID 1 が座っています。あの 1 番は、いったい誰が、いつ、どうやって作ったのでしょうか。この章はその「1 番」を自分の手で生み出す章です。素直に書いたコードが素直に失敗するところから始めます。

◈ この章のゴール

internal/container/run.go の Run と internal/container/init.go の Init を読み切り、なぜ「自分自身をもう一度起動する」という一見おかしな手を使わなければならないのかを、自分の言葉で説明できるようになる。あわせて、親と子をつなぐ 1 本のパイプが何を守っているのかを理解する。仕上げに mydocker run alpine /bin/sh を打ち、コンテナの中の ps で 自分が PID 1 として並んでいることを確認する。

その「1 番」は誰なのか

序章で私たちは mydocker run を動かして、コンテナの中の ps がこう出るのを見ました。

/ # ps
PID   USER     TIME  COMMAND
    1 root      0:00 /bin/sh
    7 root      0:00 ps

これを見て、私は最初「ふーん」で流してしまいました。よく考えると変です。ホストの側では、番号 1 は init や systemd という、マシンが起動したときにいちばん最初に作られる特別なプロセスのものです。それ以外のプロセスが 1 番を名乗ることはできません。番号は先着順に配られるからです。

ところがコンテナの中では /bin/sh が堂々と 1 番に座っている。つまり 番号を配る台帳そのものが別になっているということです。この「台帳」が PID 名前空間（PID namespace）です。名前空間ごとに 1 から番号を配り直すので、同じ 1 番が世界に複数あってもぶつかりません。

番号の台帳が 2 冊ある ホストの台帳 コンテナの台帳 ───────────────── ───────────────── 1 systemd 1 /bin/sh ← 同じプロセスを … 7 ps 2 通りの番号で呼べる 23900 mydocker init … 23901 /bin/sh ←────────────┘

この図がこの章のすべてです。ホストから見れば PID 23900 番台のただのプロセス、コンテナの中から見れば PID 1。同じプロセスに 2 つの番号がついている。私たちがこれから書くコードは、この「2 冊目の台帳」を作り、そこに最初の 1 人を送り込む仕事をします。

そして、この章の主題はこう言い換えられます — 2 冊目の台帳の 1 番を、どうやって自分で作るか。

素朴案 — 「unshare して exec すればいい」

ここで一度、自分の頭で考えてみてください。名前空間を作るシステムコールに unshare(2) というものがあります（名前のとおり「共有をやめる」という意味です）。コマンドラインにも同名の unshare コマンドがあります。だとすれば、やることはこうではないでしょうか。

  1. 自分のプロセスの中で unshare(CLONE_NEWPID) を呼ぶ → 新しい PID 名前空間ができる
  2. 続けて exec で目的のコマンド（たとえば /bin/sh）に成り代わる
  3. 成り代わった /bin/sh は新しい名前空間の中にいるので、めでたく PID 1
素朴案（これは動かない） mydocker run alpine /bin/sh │ ├ unshare(CLONE_NEWPID) ← 名前空間そのものは、たしかに作られる │ └ exec /bin/sh ← ところが自分は PID 1 にならない （なぜかは Step 1 で実測する）

筋が通っているように見えます。私も最初はこれで書きました。そして動かず、半日溶かしました。この素朴案は原理的に成立しません。「実装が下手だったから」ではなく「カーネルがそういう作りだから」です。

まずはその破綻を、コードを書く前に、コマンド 2 つで自分の目で見ます。理屈を先に読むと「ふーん」で終わりますが、壊れる様子を見てからだと理屈が刺さります。

Step 1素朴案を試して、壊す

Go を書く前に、シェルで確かめます。unshare コマンドは、指定した名前空間を新しく作ってからコマンドを実行してくれる道具です。--pid を付ければ PID 名前空間を作ってくれます。

実行するコマンドは sh -c 'echo "自分の PID: $$"' にします。シェルの $$ は「このシェル自身の PID」です。素朴案が正しいなら、新しい PID 名前空間の中で最初に走るこのシェルは 1 と表示するはずです。

▸ 動かして確認

2 つ打ちます。違いは --fork が付いているかどうかだけです。まず 1 つ目だけを打って、出た番号を見てください。

$ unshare --pid sh -c 'echo "自分の PID: $$"'
自分の PID: 25171
$ unshare --pid --fork sh -c 'echo "自分の PID: $$"'
自分の PID: 1

（上の 25171 はこの環境で実際に出た番号です。あなたの手元では別の数字になりますが、1 ではないことが肝心なところです。）

1 つ目。--pid を付けて PID 名前空間を作ったのに、シェルは 25171 と答えました。ホストの番号のままです。名前空間の作成に失敗したのでしょうか。いいえ、成功しています。名前空間はちゃんと作られています。作られた名前空間が、その中にいるはずの自分に効いていないのです。

2 つ目。--fork を足しただけで 1 になりました。--fork は「unshare したあと、コマンドを直接 exec するのではなく、いったん子プロセスを作ってからその子で実行する」というオプションです。子を 1 つ挟んだ。それだけで結果がひっくり返りました。

⚠ 落とし穴 · PID 名前空間は「呼んだ本人」には効かない

PID 名前空間は、unshare を呼んだプロセス自身には適用されません。適用されるのは、その後に作られた子プロセスからです。つまり「自分が PID 1 になる」ことは、どんなに上手にコードを書いても原理的にできません。

理由を聞くと納得できます。プロセスの PID は、そのプロセスが生まれた瞬間に決まり、以後は変わらないものとして扱われます。走っている最中に自分の番号が 25171 から 1 に化けたら、その番号を握って kill したり wait したりしている親や兄弟が全員混乱します。だからカーネルは番号を途中で振り直さない。新しい台帳が適用されるのは、その台帳ができた後に生まれた者からだけです。

ここを知らないと、「名前空間を作ったのに ps の見え方が変わらない、実装のどこかにバグがある」と延々コードを疑うことになります。バグではありません。仕様です。

もうひとつ、Go 特有の事情があります。素朴案の「自分のプロセスの中で unshare を呼ぶ」は、Go では PID 以外の名前空間についても素直にいきません。Go のランタイムはマルチスレッドだからです。

Go は、あなたが goroutine を 1 つも作らなくても、ガベージコレクションやシステムコールの面倒を見るために裏で複数の OS スレッドを走らせています。ところが unshare(CLONE_NEWNS)（マウント名前空間）のような操作は、プロセス単位ではなくスレッド単位で効きます。「今このコードが動いているスレッド」だけが新しいマウント名前空間へ移り、残りのスレッドはホストに残る。しかも Go のスケジューラは goroutine をどのスレッドで走らせるかを自由に決めるので、「次の 1 行がどのスレッドで実行されるか」をこちらから保証できません。移った先のスレッドで続きが動く保証がないのです。

C で書くなら、fork の直後・スレッドを 1 本しか持たない状態で名前空間をいじる、という手が使えます。Go ではその「スレッドが 1 本だけの瞬間」がそもそも存在しません。

LINUX メモ · clone(2) と名前空間

Linux で新しいプロセスを作るシステムコールは clone(2) です（fork(2) も内部的にはこれの薄い皮です）。clone の引数にはフラグを渡せて、CLONE_NEWPID や CLONE_NEWNS を指定すると、子プロセスを作るのと同時に、その子のための新しい名前空間も作ることができます。

ここが unshare との決定的な違いです。

  • unshare(flags) … 今いる自分を新しい名前空間へ移す。PID 名前空間だけは例外的に「自分ではなく、以後の子に効く」という振る舞いになる
  • clone(flags) … これから生まれる子を、最初から新しい名前空間の中に置く。子は生まれながらにしてその中の住人

私たちが欲しいのは後者です。「あとから移す」のではなく「最初からそこに生む」。unshare --fork が動いたのも、内部で子を作ったからでした。Go から clone のフラグを指定する方法は Step 3 で出てきます。

LINUX メモ · 名前空間は 6 種類ある

この章では PID 名前空間ばかり話題にしていますが、名前空間は 1 種類ではありません。プロセス番号（PID）、マウント（MNT）、ホスト名（UTS）、プロセス間通信（IPC）、ネットワーク（NET）、ユーザー（USER）と、区切る対象ごとに独立して存在します。clone のフラグとしては CLONE_NEWPID、CLONE_NEWNS、CLONE_NEWUTS、CLONE_NEWIPC、CLONE_NEWNET、CLONE_NEWUSER という名前で並んでいます。

この章では「どれをいくつ作るか」は深追いしません。作る仕組みそのものを先に固めます。1 つずつ何が区切られるのかは第02章で扱います。

整理します。素朴案が壊れる理由は 2 つありました。

  1. PID 名前空間は呼んだ本人に効かない。自分が PID 1 になることはできない
  2. Go はマルチスレッドなので、スレッド単位の unshare を素直に扱えない

どちらも「子プロセスを 1 つ挟む」ことで解けます。子を clone で作り、そのときに名前空間も一緒に作ってしまえばいい。unshare --fork がやっていたのはまさにこれでした。

では、その子として何を起動すればいいでしょうか。ここで気の利いた答えが要ります。「自分自身」を起動するのです。

Step 2/proc/self/exe とは何か

「自分自身をもう一度起動する」と言われても、最初はぎょっとします。無限に増えるのでは、と。増えません。別の顔（＝別のサブコマンド）で起動するからです。

mydocker run alpine /bin/sh と打たれたとき、mydocker は自分自身を mydocker init <rootfs> <hostname> <workdir> /bin/sh という引数で起動します。同じ実行ファイルですが、渡す引数が違うので中で走る道筋がまったく違う。run の顔で走っているときは親の仕事を、init の顔で走っているときは子の仕事をします。1 つの実行ファイルが 2 つの役を演じるわけです。

1 つの実行ファイル、2 つの顔 /usr/local/bin/mydocker ├── 引数が run … → 親の顔。名前空間を作って子を起動し、片付ける └── 引数が init … → 子の顔。名前空間の中の PID 1 として地面を整える

そのとき困るのが、「自分自身の実行ファイルはどこにあるのか」という素朴な問題です。os.Args[0] を使えばいいでしょうか。あれは危ういのです。os.Args[0] は起動時に渡された文字列にすぎません。./mydocker のような相対パスかもしれず、その後にカレントディレクトリが変わっていたら辿れません。PATH 越しに mydocker とだけ書かれているかもしれず、その場合は探し直しになります。呼び出し側が argv[0] に嘘を入れることさえできます。

Linux にはもっと確実な答えがあります。/proc/self/exe です。

LINUX メモ · /proc/self/exe

/proc は、ディスク上のファイルではなくカーネルが今この瞬間の状態を見せてくれる窓です（procfs という特殊なファイルシステムです）。/proc/1234/ を覗けば PID 1234 のプロセスの情報が見えます。

/proc/self は「それを読んでいるプロセス自身」を指す特別な名前です。PID を調べてから /proc/<自分の PID> を組み立てなくても、/proc/self と書くだけで自分の分を見られます。

そして /proc/self/exe は、そのプロセスが今実行している実行ファイルを指すシンボリックリンクです。ls -l /proc/self/exe と打つと、そのとき /proc/self を読んでいるのは ls 自身なので、リンクは ls の実体（/usr/bin/ls など）を指しているのが見えます。「自分自身のパスを、自分で調べなくても手に入れられる」のがこのリンクの値打ちです。

さらにありがたい性質があります。このリンクはカーネルが管理している実体そのものへの参照なので、実行ファイルが起動後にリネームされても、削除されても、/proc/self/exe を exec すれば同じ中身が起動します。名前ではなく実体を掴んでいるからです。

▸ 動かして確認

手元で 1 度打ってみてください。ls のインストール場所は環境によって違うので、ここに出力は貼りません（この教材が貼る出力は実測したものだけ、という決まりです）。

$ ls -l /proc/self/exe

表示される矢印の先が ls コマンドの実体になっていれば、読み方は合っています。「自分自身を指す」の「自分」とは、そのリンクを読んだプロセスのことです。ls が読めば ls を指し、mydocker が読めば mydocker を指す。だから mydocker のコードの中に /proc/self/exe と書いておけば、それは常に mydocker 自身のことになります。

以上をまとめると、私たちが取る手はこうなります。

re-exec パターン ホストの名前空間 新しい名前空間 ───────────────────────── ─────────────────────── mydocker run alpine /bin/sh │ │ exec.Command("/proc/self/exe", │ "init", …) │ + Cloneflags で名前空間を要求 ↓ ├─── clone(2) ────────────────→ mydocker init … ← PID 1 │ │ │ │ ここから先が第03章の仕事 │ ↓ └─── cmd.Wait() で終了を待つ ←── syscall.Exec("/bin/sh") ← PID 1 のまま

肝は矢印の 1 本目です。名前空間は「子を作る操作」と同時に生まれ、子は生まれながらにして PID 1 になる。あとから移るのではないから、Step 1 の壁に当たりません。unshare --fork の --fork に相当するのが、この「/proc/self/exe を起動する」という一手です。

⚠ 落とし穴 · init は利用者が直接叩くものではない

この設計には代償があります。init という、利用者が絶対に叩かない入口が CLI に増えてしまうことです。放っておくと mydocker --help に init が並び、読んだ人が「初期化コマンドかな」と打ってしまいます。

そこで mydocker では 2 つ手を打っています。1 つ、--help の一覧に init を載せない。internal/cli/cli.go の usage 文字列に init の行はありません（ディスパッチの case "init": にだけコメントで「内部用」と書いてあります）。2 つ、src/README.md のコマンド表に「利用者が直接叩くものではない。親プロセスが /proc/self/exe を使って自分自身を再実行するための入口（re-exec パターン）」と明記する。

それでも手で叩かれたときのために、init は引数が足りなければ「init は mydocker が内部で使うサブコマンドです。直接実行しないでください」と言って止まります。引数が揃っていても、次の Step 4 で見る同期用の fd が無いので、そこで安全に止まります。隠すだけでなく、踏まれたときに壊れないようにしておくのが後始末です。

Step 3exec.Command に Cloneflags を渡す

ここからコードです。Go で外部コマンドを起動するときは exec.Command を使います。普段は exec.Command("ls", "-l") のように書いて Run() や Start() を呼ぶだけですが、私たちはこの起動に「ついでに新しい名前空間も作ってくれ」という注文を付けたい。それを担うのが SysProcAttr です。

まず Run の中で、実際に子を起動している部分だけを抜き出して見ます。前後は少し後で全文を読みます。

internal/container/run.go — Run の一部
	// --- 4. 自分自身を "init" という別の顔で起動する ---
	args := append([]string{"init", mnt.Merged, cfg.Hostname, orSlash(cfg.Workdir)}, cfg.Argv...)
	cmd := exec.Command("/proc/self/exe", args...)
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags: syscall.CLONE_NEWUTS | // ホスト名
			syscall.CLONE_NEWPID | // プロセス番号
			syscall.CLONE_NEWNS | // マウント
			syscall.CLONE_NEWIPC, // プロセス間通信
		// ⚠ これを忘れると、コンテナ内で行ったマウントがホスト側にも伝播する。
		//    pivot_root が EINVAL で落ちる原因にもなる。「なぜか動かない」の筆頭。
		Unshareflags: syscall.CLONE_NEWNS,
	}
	cmd.Stdin, cmd.Stdout, cmd.Stderr = os.Stdin, os.Stdout, os.Stderr
	cmd.Env = cfg.Env
	cmd.ExtraFiles = []*os.File{syncR} // 子から見て fd 3

1 行ずつ読みます。

args := append([]string{"init", …}, cfg.Argv...) — 子に渡す引数を組み立てています。先頭が init、続いて根にするディレクトリ（mnt.Merged。overlay で作った合成ディレクトリで、第06章の話です）、ホスト名、作業ディレクトリ、最後に利用者が打ったコマンド（cfg.Argv）。つまり mydocker run alpine /bin/sh は、内部的に mydocker init /var/lib/mydocker/containers/…/merged mydocker / /bin/sh という起動に化けます。

exec.Command("/proc/self/exe", args...) — Step 2 のリンクがここで効いてきます。mydocker の実行ファイルがどこに置かれていようと、この 1 行で自分自身を指せます。

cmd.SysProcAttr = &syscall.SysProcAttr{…} — ここが本丸です。SysProcAttr は「OS 固有の、プロセス起動時の細かい注文」を書く場所です。Linux 版の SysProcAttr には Cloneflags という欄があり、そこに書いたフラグが、子を作るときの clone(2) にそのまま渡されます。

Cloneflags: の 4 つは、|（ビット OR）で並べた名前空間の注文書です。ホスト名（UTS）、プロセス番号（PID）、マウント（NS）、プロセス間通信（IPC）。この 4 つを新しく作った状態で子を生んでくれ、という意味になります。この 1 か所がコンテナの「隔離」の実体で、たった 4 行です。何が起きるのかは第02章で 1 つずつ確かめます。

（気づいたかもしれません。ネットワーク CLONE_NEWNET がありません。これは意図的な未実装です。理由と、実装するなら何が要るのかは第08章でまるごと扱います。）

cmd.Stdin, cmd.Stdout, cmd.Stderr = os.Stdin, os.Stdout, os.Stderr — 子の標準入出力を、そのまま自分（＝端末）につなぎます。これがないと、コンテナの中の sh に文字が届かず、出力も見えません。名前空間を作っても、この 3 本のパイプは親から素直に引き継がれます。

cmd.ExtraFiles = []*os.File{syncR} — Step 4 の主役です。今は「余分に 1 本ファイルを渡している」とだけ見ておいてください。

GO メモ · exec.Command と SysProcAttr

exec.Command(name, args...) は *exec.Cmd という「これから起動するプロセスの設計図」を返します。この時点ではまだ何も起動していません。設計図のフィールドを埋めてから Start()（起動して戻る）か Run()（起動して終了まで待つ）を呼ぶと、はじめてプロセスが生まれます。

設計図の中でも SysProcAttr *syscall.SysProcAttr は特別で、OS ごとに中身が違います。Linux 版には Cloneflags、Unshareflags、Credential、Pdeathsig などが並び、macOS や Windows にはこれらがありません。だから Cloneflags を書いたコードは Linux でしかビルドが通りません。この教材が第00章で Linux 環境を用意することにこだわったのは、まさにこの一行のためです。

面白いのは、Go の標準ライブラリが clone(2) のフラグをそのまま素通しで渡してくれる点です。名前空間のために特別な API があるわけではありません。Go は「カーネルにこう頼め」と言う口を開けてくれているだけで、コンテナのことは何も知りません。知っているのは私たちの側です。

⚠ 落とし穴 · Unshareflags を忘れると、ホストのマウントが増えていく

コードの Unshareflags: syscall.CLONE_NEWNS は、Cloneflags に CLONE_NEWNS があるのだから重複しているように見えます。消してはいけません。この 1 行を落とすと、コンテナの中でやったマウントがホスト側にも伝播します。

マウントには「伝播（propagation）」という性質があります。多くのディストリビューションでは / 以下が shared という状態で、ここに繋がったマウント名前空間は、片方で行ったマウント／アンマウントがもう片方にも自動で伝わります。せっかく新しいマウント名前空間を作っても、その中身が「ホストと共有」の設定を引き継いだままだと、コンテナが /proc を貼ったり rootfs を bind mount したりするたびに、ホストのマウント表が増えていきます。コンテナを 10 回起動したらホストに残骸が 10 個。mount の出力がどんどん汚れ、最後には「なぜかディスクが外せない」状態になります。

Unshareflags: syscall.CLONE_NEWNS を書くと、Go は子プロセスの中で unshare(CLONE_NEWNS) を追加で呼び、マウント名前空間をホストから切り離した状態にしてくれます。つまり Cloneflags が「新しい部屋を作れ」、Unshareflags が「作った部屋の壁に穴が残っていないか確かめろ」に当たります。

被害はもう 1 つあります。この設定が抜けていると、第03章で使う pivot_root が EINVAL（引数が不正）で落ちます。pivot_root は新しい root が shared なマウントの上にあることを許さないからです。エラーメッセージは「invalid argument」としか言ってくれないので、原因に辿り着くのは至難です。この教材で「なぜか動かない」の筆頭がこれです。だから先に警告しておきます。

ちゃんと効いていることは、あとで機械的に確かめられます。E2E テストの終わりにはこの項目が入っています — OK テスト全体を通してホストのマウント数が元に戻る（開始 22 → 終了 22）。開始も終了も 22 のまま。漏れていません。

ここまでで、名前空間を持った子を起動する部分は書けました。実際に mydocker run を打つと、この子の中で ps が自分だけを見ます。

Step 4親子の同期パイプ — 合図が来るまで一歩も動かない

ここは、コードを見ただけでは絶対に必要性がわからない部分です。逆に言えば、ここを理解すると「並行するプロセスを扱う」という仕事の勘所が掴めます。

問題はこうです。親には、子を起動したあとにやることが残っています。

  1. 子の PID を cgroup（資源の上限をかける仕組み）に登録する
  2. コンテナの記録（state.json）を保存する

1 番が厄介です。cgroup は「このディレクトリに PID を書き込むと、そのプロセスに上限がかかる」という仕組みで、PID がわからないと登録できません。PID がわかるのは子を起動した後です。順番が決まってしまっています。

ところが cmd.Start() は、子を起動したらすぐに戻ってきます。待ってはくれません。つまり親が cgroup のファイルに書き込んでいる数ミリ秒のあいだ、子はもう走り出しています。

同期が無いとどうなるか（時間は左から右へ） 親 ─ Start() ─┬─ cgroup に PID を書く ─ state.json を保存 ─ Wait() … │ ↑ここが数ミリ秒 │ 子 └─ exec /bin/sh ─ メモリを確保しはじめる … ↑上限がまだ効いていない！

数ミリ秒くらい、と思うでしょうか。私も思いました。ところが第00章で測ったように、コンテナの起動そのものが 12〜15 ms です。同じ桁の話をしています。実際、この同期を入れる前は「メモリ上限 10MB を指定したのに 100MB 確保できてしまう」テストが、通ったり落ちたりしました。走らせるたびに結果が変わる。いちばん嫌な種類のバグです。原因が自分のコードなのか環境なのかも判断できません。

解き方はいくつか考えられます。実装ログに残した検討はこうでした。

そこで C。子に「待て」を教えるのです。子は起動した直後、決められた合図が届くまで一歩も動かない。親は準備を全部終えてから合図を送る。合図の届け方として、Unix にはうってつけの道具があります。パイプです。

同期パイプの流れ 親 子（init） ────────────────────────── ───────────────────────── syncR, syncW := os.Pipe() cmd.ExtraFiles = []*os.File{syncR} cmd.Start() ────── clone ─────→ 起動（PID 1） syncR.Close()（親側では使わない） waitForParent() fd 3 を読む → まだ空 cg.Apply(pid) ← cgroup に登録 ‥‥ 止まって待つ ‥‥ st.Save() ← 記録を保存 ‥‥ 止まって待つ ‥‥ syncW.WriteString("OK") syncW.Close() ───── 合図 ───→ "OK" を読み切って前進 pivot_root → mount → exec cmd.Wait() ←──── 終了を待つ ───── /bin/sh として走る

パイプというのは、片方に書いた内容がもう片方から読める 1 方向の管です。シェルの | と同じものです。ここでは通信の中身よりも、「読もうとすると、誰かが書くまでブロックする」という性質を使います。子はパイプを読もうとして止まる。親が書くまで、子は絶対に前へ進めない。これで順序が保証されます。

子側のコードを見ましょう。init.go の先頭に置かれた 2 つの定数と、待つ関数の全文です。

// syncFD は親から「準備ができた」合図を受け取るためのファイルディスクリプタ。
//
// なぜ必要か: 親は子を起動してから cgroup に PID を入れる。その間に子が走り出すと、
// **上限が効く前にメモリを確保してしまう**。それでは「上限を超えたら死ぬ」テストが
// 気まぐれに通ったり落ちたりする。そこで子はここで一度止まり、親の合図を待つ。

// syncReady は親が送る合図。これ以外が来たら（＝親が失敗したら）子は何もせず終わる。

// waitForParent は fd 3 から親の合図を読む。
// 親が合図を送らずに閉じた（＝準備に失敗した）場合はエラーにする。
func waitForParent() error {
	f := os.NewFile(uintptr(syncFD), "sync")
	if f == nil {
		return fmt.Errorf("親との同期用ディスクリプタがありません（init は直接実行できません）")
	}
	defer f.Close()
	b, err := io.ReadAll(f)
	if err != nil {
		return fmt.Errorf("親からの合図を読めませんでした: %w", err)
	}
	if strings.TrimSpace(string(b)) != syncReady {
		return fmt.Errorf("親の準備が失敗したため中止します")
	}
	return nil
}

短いですが、詰まっているものが多い関数です。順に見ます。

os.NewFile(uintptr(syncFD), "sync") — syncFD は 3 です。番号 3 のファイルディスクリプタを、Go の *os.File として扱えるようにしています。ここで新しくファイルを開いているのではありません。親から引き継いだ、すでに開いている管に名前を付けているだけです。

なぜ 3 なのか。プロセスが持つ fd には昔からの約束があり、0 が標準入力、1 が標準出力、2 が標準エラーです。exec.Cmd の ExtraFiles に渡したファイルは、この 3 本の次から順に子へ引き継がれます。1 本だけ渡したので 3 番。2 本渡せば 3 番と 4 番になります。親の ExtraFiles の並び順と、子の syncFD = 3 という定数は、コードのどこにも書かれていない暗黙の約束で結ばれています。片方だけ直すと静かに壊れる箇所なので、両方に理由をコメントで残してあります。

io.ReadAll(f) — ここが「待つ」の正体です。ReadAll は相手が書き終えて管を閉じるまで読み続けます。親がまだ何も書いていなければ、この行で止まります。goroutine も time.Sleep もポーリングも要りません。カーネルがプロセスを眠らせ、書き込みが来たら起こしてくれます。Unix の道具立てで待つと、待つコードは 1 行になります。

strings.TrimSpace(string(b)) != syncReady — 読み取った中身が "OK" かどうかを確かめます。ここが二重の意味を持っています。

LINUX メモ · パイプは「閉じた」ことも伝えられる

パイプの読み側は、書き側がすべて閉じられた時点で「もう来ない（EOF）」を返します。ここが単なる通信路との違いです。

つまり親には 2 通りの意思表示ができます。

  • "OK" を書いてから閉じる → 子は "OK" を読む → 準備できた。進め
  • 何も書かずに閉じる → 子は空っぽを読む → 親が失敗した。何もせず終われ

異常を伝えるために別の連絡路を用意する必要がありません。「黙って閉じる」がそのままエラー通知になっています。親のコードでは、失敗の分岐で syncW.Close() の隣にはっきり // 合図を送らずに閉じる → 子は何もせず終了する と書いてあります。

おまけの効能もあります。mydocker init … を人間が手で叩いた場合、fd 3 は開いていないか、まったく別のものです。合図が "OK" にならないので、子は pivot_root に手をつける前に止まります。危険な操作の手前に関所がある、という形になっています。

親側の対応する部分も見ておきます。Run の中の、パイプを作るところと合図を送るところです。

internal/container/run.go — Run の一部
	// --- 3. 子と同期するためのパイプ ---
	// 親が cgroup に PID を入れ終えるまで、子は走り出してはいけない。
	syncR, syncW, err := os.Pipe()
	if err != nil {
		_ = cleanup(cg)
		return 1, err
	}

	// …（Cloneflags の設定は Step 3 で読んだ）

	if err := cmd.Start(); err != nil {
		syncR.Close()
		syncW.Close()
		_ = cleanup(cg)
		return 1, fmt.Errorf("コンテナの起動に失敗しました: %w", err)
	}
	syncR.Close() // 親側では使わない

	pid := cmd.Process.Pid
	st.PID = pid
	st.StartTime = ReadStartTime(pid)

	// --- 5. cgroup に入れてから、子に合図を送る ---
	startErr := func() error {
		if cg != nil {
			if err := cg.Apply(pid); err != nil {
				return err
			}
		}
		return st.Save()
	}()
	if startErr != nil {
		syncW.Close() // 合図を送らずに閉じる → 子は何もせず終了する
		_ = cmd.Wait()
		_ = cleanup(cg)
		return 1, startErr
	}
	if _, err := syncW.WriteString(syncReady); err != nil {
		syncW.Close()
		_ = cmd.Wait()
		_ = cleanup(cg)
		return 1, err
	}
	syncW.Close()

os.Pipe() は読み側 syncR と書き側 syncW の 2 本を返します。読み側を ExtraFiles で子に渡し、書き側は親が握る。子を起動したら、親は自分の手元の読み側をすぐ閉じます（syncR.Close()）。これは行儀の問題ではありません。読み側が親の手元にも残っていると、パイプの参加者が増えたままになり、閉じたことが正しく伝わらなくなります。使わない口は閉じる。パイプを扱うときの鉄則です。

そのあとの流れは、まさに「順序を守るために書かれたコード」です。cg.Apply(pid) で cgroup に登録し、st.Save() で記録を保存し、それが全部成功してはじめて syncW.WriteString(syncReady) で "OK" を送ります。途中で失敗したら、合図を送らずに閉じて、子の終了を待ち（cmd.Wait()）、後片付けをして戻ります。「上限を指定したのに黙って無視して走らせる」という、いちばん最悪の結果を避けるための造りです。

GO メモ · 即時実行される無名関数で「まとめて失敗を捕まえる」

親のコードに startErr := func() error { … }() という書き方が出てきました。関数を定義してすぐ () で呼んでいます。見慣れないと戸惑いますが、狙いははっきりしています。

cgroup への登録と記録の保存という2 つの処理をひとまとめにし、どちらが失敗しても同じ 1 つの後始末（合図を送らずに閉じる）へ合流させたいのです。素直に書くと同じ 4 行の後始末が 2 か所に並び、片方だけ直して壊すことになります。defer で書く手もありますが、ここは「失敗したら子に合図を送らない」という 1 点に集約したいので、この形が読みやすいと判断しました。

親の全体像 — Run の全文

部分ばかり見てきたので、ここで Run を頭から終わりまで通して読みます。長いですが、番号付きのコメント（1〜7）が地図になっています。今の時点で全部わからなくて構いません。overlay（1 の部分）は第06章、cgroup（2 の部分）は第04章、後片付け（7 の部分）は第07章で扱います。この章で追いかけるのは 3・4・5 です。

internal/container/run.go
// Run はコンテナを1つ起動し、終了まで待って終了コードを返す。
//
// ★この教材でいちばん説明の要る箇所が、次の re-exec パターンである。
//
// 素朴に考えると「unshare して、そのあと目的のコマンドを exec すればいい」と思える。ところが:
//
//   - PID 名前空間は unshare を呼んだプロセス自身には適用されない。
//     適用されるのは **その後に作られた子プロセス** から。「自分が PID 1 になる」ことはできない
//   - Go のランタイムはマルチスレッドなので、プロセス内でスレッド単位の unshare を素直に扱えない
//
// そこで /proc/self/exe（＝自分自身の実行ファイル）を "init" という別の顔で起動する。
// 新しい名前空間はこの起動と同時に生まれ、子は生まれながらにして PID 1 になる。
func Run(cfg Config) (int, error) {
	id := NewID()
	base := stateDir(id)
	if err := os.MkdirAll(base, 0o755); err != nil {
		return 1, err
	}

	// --- 1. 根になるファイルシステムを用意する（レイヤの重ね合わせ）---
	mnt, err := overlay.New(base, cfg.Lowers)
	if err != nil {
		_ = os.RemoveAll(base)
		return 1, err
	}

	st := &State{
		ID:        id,
		Image:     cfg.Image,
		Command:   cfg.Argv,
		Hostname:  cfg.Hostname,
		Workdir:   cfg.Workdir,
		CreatedAt: time.Now(),
		Merged:    mnt.Merged,
	}

	// 後片付けは1か所にまとめる。途中でどこで失敗しても必ずここを通す。
	cleanup := func(cg *cgroup.Cgroup) error {
		var firstErr error
		if cg != nil {
			if err := cg.Destroy(); err != nil {
				firstErr = err
			}
		}
		// ⚠ アンマウントの成否を確かめずに削除へ進んではいけない。
		//    失敗したまま RemoveAll すると、マウント越しに lowerdir（＝イメージの実体）まで消える。
		if err := mnt.Unmount(); err != nil {
			if firstErr == nil {
				firstErr = err
			}
			// ★削除には進まない。状態ファイルも残して、人間が調べられるようにする。
			return firstErr
		}
		if err := RemoveRecord(st); err != nil && firstErr == nil {
			firstErr = err
		}
		return firstErr
	}

	// --- 2. 資源の上限を用意する（プロセスはまだ入れない）---
	var cg *cgroup.Cgroup
	if !cfg.Limits.IsZero() {
		cg, err = cgroup.New(id, cfg.Limits)
		if err != nil {
			// ⚠ 上限を指定したのに黙って無視して走らせるのが最悪の結果。必ず止める。
			_ = cleanup(nil)
			return 1, err
		}
		st.CgroupDirs = cg.Dirs()
		st.CgroupVersion = cg.Version()
	}

	// --- 3. 子と同期するためのパイプ ---
	// 親が cgroup に PID を入れ終えるまで、子は走り出してはいけない。
	syncR, syncW, err := os.Pipe()
	if err != nil {
		_ = cleanup(cg)
		return 1, err
	}

	// --- 4. 自分自身を "init" という別の顔で起動する ---
	args := append([]string{"init", mnt.Merged, cfg.Hostname, orSlash(cfg.Workdir)}, cfg.Argv...)
	cmd := exec.Command("/proc/self/exe", args...)
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags: syscall.CLONE_NEWUTS | // ホスト名
			syscall.CLONE_NEWPID | // プロセス番号
			syscall.CLONE_NEWNS | // マウント
			syscall.CLONE_NEWIPC, // プロセス間通信
		// ⚠ これを忘れると、コンテナ内で行ったマウントがホスト側にも伝播する。
		//    pivot_root が EINVAL で落ちる原因にもなる。「なぜか動かない」の筆頭。
		Unshareflags: syscall.CLONE_NEWNS,
	}
	cmd.Stdin, cmd.Stdout, cmd.Stderr = os.Stdin, os.Stdout, os.Stderr
	cmd.Env = cfg.Env
	cmd.ExtraFiles = []*os.File{syncR} // 子から見て fd 3

	if err := cmd.Start(); err != nil {
		syncR.Close()
		syncW.Close()
		_ = cleanup(cg)
		return 1, fmt.Errorf("コンテナの起動に失敗しました: %w", err)
	}
	syncR.Close() // 親側では使わない

	pid := cmd.Process.Pid
	st.PID = pid
	st.StartTime = ReadStartTime(pid)

	// --- 5. cgroup に入れてから、子に合図を送る ---
	startErr := func() error {
		if cg != nil {
			if err := cg.Apply(pid); err != nil {
				return err
			}
		}
		return st.Save()
	}()
	if startErr != nil {
		syncW.Close() // 合図を送らずに閉じる → 子は何もせず終了する
		_ = cmd.Wait()
		_ = cleanup(cg)
		return 1, startErr
	}
	if _, err := syncW.WriteString(syncReady); err != nil {
		syncW.Close()
		_ = cmd.Wait()
		_ = cleanup(cg)
		return 1, err
	}
	syncW.Close()

	if !cfg.Quiet {
		fmt.Fprintf(os.Stderr, "コンテナ %s を起動しました (PID %d)\n", id, pid)
	}

	// --- 6. 終了を待つ ---
	// Ctrl-C は端末から子にも届く。親がここで死ぬと後片付けが走らないので、
	// 親は明示的にシグナルを受け流し、子の終了を待ってから片付ける。
	sig := make(chan os.Signal, 4)
	signal.Notify(sig, syscall.SIGINT, syscall.SIGTERM, syscall.SIGHUP)
	defer signal.Stop(sig)
	go func() {
		for range sig {
		}
	}()

	waitErr := cmd.Wait()
	code := exitCode(waitErr)

	// --- 7. 後片付け（★ここを落とすと静かに壊れる）---
	if err := cleanup(cg); err != nil {
		return code, err
	}
	return code, nil
}

いま読めるようになった箇所を確かめてください。3 でパイプを作り、4 で /proc/self/exe を init の顔で・名前空間付きで起動し、5 で cgroup に入れてから "OK" を送る。この章の内容がそのまま並んでいます。

ついでに 6 にも触れておきます。Ctrl-C を押すと、端末はそのグループのプロセス全員にシグナルを送ります。親も子も一緒に殺されます。そこで親は signal.Notify でシグナルを受け取り、go func(){ for range sig {} }() という「受け取って何もしない」goroutine に流し込んでいます。親は勝手に死なない。子が終わるのを cmd.Wait() で見届けて、後片付け（7）まで責任を持つ。ここを省くと、コンテナを Ctrl-C で止めるたびに overlay のマウントがホストに残ります。第07章で扱う「残骸」の話につながる部分です。

ここまでずっと親の話でした。最後に、生まれたばかりの子（＝コンテナの PID 1）が何をするのかを見ます。この章では 5 つの手順のうち 1 と 5 だけを深く読み、2〜4 は「次章以降で開く箱」として置いておきます。一度に全部やると必ず溺れます。

まず、子が受け取る引数の定義です。

そして本体です。

internal/container/init.go
// Init は新しい名前空間の中（＝コンテナの PID 1）で走る処理である。
//
// ここに来た時点で、親が Cloneflags で作った namespace の中にいる。
// あとは「地面を入れ替えて、目的のコマンドに成り代わる」だけ。
//
//  1. 親の合図を待つ（cgroup に入れてもらうまで動かない）
//  2. ホスト名を変える（UTS 名前空間の効果を目に見える形にする）
//  3. pivot_root で root を挿げ替える
//  4. /proc /sys /dev を貼り直す
//  5. syscall.Exec で目的のコマンドに成り代わる（★戻ってこない）
func Init(args InitArgs) error {
	if err := waitForParent(); err != nil {
		return err
	}

	if args.Hostname != "" {
		if err := syscall.Sethostname([]byte(args.Hostname)); err != nil {
			return fmt.Errorf("ホスト名を設定できませんでした: %w", err)
		}
	}

	if err := pivotRoot(args.Rootfs); err != nil {
		return err
	}
	if err := mountSpecialFilesystems(); err != nil {
		return err
	}

	// 実行するコマンドを新しい root の中から探す。
	// ⚠ ここは pivot_root の **後** でなければならない。前に探すとホスト側の
	//    /bin/sh を掴んでしまい、「コンテナの中なのにホストのバイナリが動く」ことになる。
	env := args.Env
	if len(env) == 0 {
		env = []string{"PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin", "HOME=/root", "TERM=xterm"}
	}
	if err := os.Setenv("PATH", envValue(env, "PATH")); err != nil {
		return err
	}

	// イメージが WorkingDir を指定していればそこへ移る。
	// 無ければ / のまま。存在しないディレクトリを指していても起動は止めない。
	if args.Workdir != "" && args.Workdir != "/" {
		if err := syscall.Chdir(args.Workdir); err != nil {
			fmt.Fprintf(os.Stderr, "警告: 作業ディレクトリ %s へ移れませんでした: %v\n", args.Workdir, err)
		}
	}
	path, err := exec.LookPath(args.Argv[0])
	if err != nil {
		return fmt.Errorf("コマンドが見つかりません: %s", args.Argv[0])
	}

	// ★syscall.Exec はプロセスを置き換える。成功すればこの行から先は実行されない。
	//   fork ではないので、コンテナの PID 1 はこのまま目的のコマンドそのものになる。
	if err := syscall.Exec(path, args.Argv, env); err != nil {
		return fmt.Errorf("%s の実行に失敗しました: %w", path, err)
	}
	return nil // 到達しない
}

この関数の形を、まず遠くから眺めてください。やることが上から下へ一直線に並んでいます。分岐らしい分岐がありません。「合図を待つ → ホスト名 → 根を替える → 特殊なファイルシステム → 目的のコマンドに成り代わる」。コンテナを起動するというのは、結局これだけのことなのです。

1. waitForParent() — Step 4 で読んだ関所です。Init のいちばん最初にあることが重要です。ホスト名を変えるより前、root を挿げ替えるより前。まだ何も壊していない段階で止まれるようにしてあります。

2. syscall.Sethostname — ホスト名を変えます。ふつう、走っているプログラムがホスト名を書き換えたらマシン全体のホスト名が変わってしまい、大惨事です。ところが私たちは CLONE_NEWUTS で UTS 名前空間を新しく作っているので、この変更はこの名前空間の中だけに閉じます。序章のデモで hostname が mydocker と答えたのに、あなたのホストの名前は変わっていない — その仕掛けがこの 1 行です。名前空間が効いていることを目で見られる、いちばん手軽な証拠でもあります。第02章で詳しく扱います。

3. pivotRoot(args.Rootfs) と 4. mountSpecialFilesystems() — この章では中身を開きません。「地面を入れ替える」「/proc などを貼り直す」という 2 つの仕事があることだけ覚えてください。ここは順序を 1 つ間違えるだけで失敗する、この教材でいちばん神経を使う場所で、まるごと第03章に取ってあります。

5. syscall.Exec(path, args.Argv, env) — 締めくくりです。ここが、この章の最初に置いた問い「PID 1 は誰か」への最終的な答えになります。

GO メモ · syscall.Exec はプロセスを置き換える

exec.Command(...).Run() は新しいプロセスを作って実行します。対して syscall.Exec は違います。今走っているプロセスの中身を、指定した実行ファイルで丸ごと上書きします。新しいプロセスは生まれません。PID も変わりません。

器はそのまま、中身だけが入れ替わる。だからコードにはこう書いてあります — 成功すればこの行から先は実行されない。最後の return nil には // 到達しない というコメントが付いています（Go の型検査を通すために書いてあるだけの行です）。

これが決定的に効きます。fork して子で /bin/sh を動かしたなら、PID 1 は mydocker init のままで、/bin/sh は PID 2 あたりの子になっていたはずです。ps にも mydocker init が居座って見えたでしょう。syscall.Exec で置き換えるので、コンテナの PID 1 はそのまま /bin/sh そのものになります。

実際、序章のデモの ps にはこう出ていました — 1 root 0:00 /bin/sh -c ps; echo ---; …。1 番の名前が mydocker ではなく利用者が打ったコマンドそのもの。mydocker init という顔は、役目を終えて消えたのです。

つまずき FAQ

自分自身を再実行するって、無限ループになりませんか?

なりません。起動するときの引数が違うからです。run の引数で呼ばれたときだけ Run（＝また自分を起動する側）が走り、init の引数で呼ばれたときは Init が走ります。Init の中には「自分をもう一度起動する」処理はありません。だから深さは常に 2 段で止まります。

分岐しているのは internal/cli/cli.go の switch 1 か所だけです。case "run": と case "init": が並んでいて、そこで道が分かれます。同じバイナリの中に親の道と子の道が同居している、というだけの話です。

/proc/self/exe ではなく os.Args[0] ではだめなんですか?

動くこともありますが、壊れる条件が多すぎます。os.Args[0] は起動時に渡された文字列にすぎません。./mydocker のような相対パスなら、カレントディレクトリが変わった後には辿れません。PATH 経由で mydocker とだけ渡っていたら、探し直しが必要です。そもそも呼び出し側は argv[0] に好きな文字列を入れられるので、信用に足りません。

/proc/self/exe はカーネルが握っている実行ファイルの実体への参照です。名前の綴りに依存しないので、起動後にファイルがリネームされても削除されても、正しく同じ中身を起動できます。「自分」を確実に指せる唯一の方法だと思ってよいです。

子を作らずに、親自身が名前空間に入る方法は本当に無いんですか?

PID 名前空間については本当にありません。Step 1 の実測がその証拠です。unshare --pid だけでは 25171、--fork を足して初めて 1。プロセスの PID は生まれた瞬間に決まり、途中で振り直されないためです。振り直したら、その PID を握っている親や兄弟が全員おかしくなります。

ただし、PID 以外の名前空間（マウント・UTS・IPC など）については、unshare で自分自身を移すことはできます。「入れない」わけではないのです。それでも Go でそれをやらないのは、マウント名前空間の unshare がスレッド単位の操作で、マルチスレッドの Go ランタイムでは「移った先のスレッドで続きが動く」保証が取れないからです。理由が 2 つ重なっている、と整理しておくと混乱しません。

Cloneflags と Unshareflags に同じ CLONE_NEWNS が書いてあります。片方は消していいのでは?

消すと壊れます。役割が違うからです。Cloneflags は「新しいマウント名前空間を作れ」という注文。Unshareflags は「作った名前空間を、ホストから伝播しない状態にしておけ」という追加の注文です。

後者が抜けると、部屋は新しくなったのに壁に穴が空いたままになります。コンテナの中で /proc を貼るたび、rootfs を bind mount するたび、その操作がホストのマウント表にも現れる。起動のたびにホストにゴミが積もり、しかも第03章の pivot_root は EINVAL で落ちます。エラーメッセージからは絶対に原因がわからない種類の失敗なので、先に警告しておきました。

同期パイプが無いとどうなるのか、いまいち実感が湧きません。数ミリ秒ですよね?

その数ミリ秒が致命的な領域なんです。コンテナの起動そのものが 12〜15 ms（ホストで /bin/true を直に実行すると 3 ms）です。子が exec を終えてメモリを触り始めるまでの時間と、親が cgroup のファイルに書き込む時間は、同じ桁で競争しています。

結果として何が起きるかというと、テストが気まぐれに通ったり落ちたりします。--memory 10m を付けたのに 100MB 確保できてしまう回が混じる。10 回に 1 回落ちるテストは、原因を突き止めるのがいちばん難しい種類のバグです。しかも「たまたま通った」ときに人はそれを信じてしまいます。

パイプを 1 本入れれば、この競争そのものが消えます。速くしたのではなく、順序を決めたのです。並行するものを相手にするときは、速さで殴らず順序で押さえる、と覚えておくと応用が利きます。

誤って mydocker init を手で打ってしまいました。ホストが壊れたりしませんか?

大丈夫です。二段構えで止まります。まず引数が 4 つ未満なら「init は mydocker が内部で使うサブコマンドです。直接実行しないでください」と表示して終わります。引数を無理やり揃えたとしても、Init の最初の waitForParent() で fd 3 を読みにいきます。手で起動したプロセスに親からのパイプは繋がっていないので、"OK" は届かず「親の準備が失敗したため中止します」で止まります。

大事なのは、止まる位置が pivotRoot より前だということです。root を挿げ替えたりマウントしたりする前に引き返すので、ホストには何も残りません。危ない操作の手前に関所を置く、という設計になっています。

ネットワークの名前空間（CLONE_NEWNET）が入っていないのはなぜですか?

実装していないからです。素直に書くと Cloneflags に syscall.CLONE_NEWNET を足すだけに見えますが、それだけだとコンテナから外に一切出られなくなります。新しいネットワーク名前空間には lo しかなく、外へ繋ぐには veth のペアを作り、ブリッジを立て、IP を配り、NAT を設定し…という一式が要ります。手を出すなら中途半端にはできません。

この教材は「できていないことをできたように書かない」を方針にしているので、現状では CLONE_NEWNET を入れていません。その結果、コンテナはホストのネットワークをそのまま共有しています（実測でも、コンテナの中の eth0 にホストと同じアドレスが見えています）。なぜ難しいのか・何が必要なのかは第08章でまるごと扱います。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。答えを見て「知っていた」と思うかどうかではなく、口に出して説明できたかで判定してください。

Q1. unshare --pid sh -c 'echo $$' が 1 ではない番号を出すのはなぜ? 何を足すと 1 になりますか?

PID 名前空間は unshare を呼んだプロセス自身には適用されず、その後に作られた子プロセスから効くからです。sh は unshare した本人（の後継）なので、ホストの番号（実測では 25171）のままになります。

--fork を足すと、unshare のあとに子を 1 つ作ってからコマンドを実行するので、その子は新しい名前空間の最初の住人となり 1 になります。mydocker における「/proc/self/exe を init の顔で起動する」が、この --fork に相当します。

Q2. /proc/self/exe は何を指していますか? 「self」とは誰のことですか?

そのリンクを読んだプロセス自身が今実行している実行ファイルを指すシンボリックリンクです。ls -l /proc/self/exe なら ls の実体を、mydocker のコードから辿れば mydocker の実体を指します。

ポイントは、これがカーネルの持つ実体への参照であって、名前（パス文字列）への依存が無いことです。だから os.Args[0] のように相対パスや PATH 解決の事情に振り回されません。

Q3. Cloneflags に名前空間のフラグを並べるだけでなく、Unshareflags: syscall.CLONE_NEWNS も要るのはなぜ?

新しいマウント名前空間を作っても、そのままだとホストとのマウントの伝播（shared subtree）が残り、コンテナ内のマウントがホスト側にも現れてしまうからです。Unshareflags を指定すると、子の中で追加の unshare(CLONE_NEWNS) が行われ、ホストから切り離された状態になります。

これを忘れると、①起動のたびにホストのマウントが増える、②第03章の pivot_root が EINVAL で落ちる、の 2 つが起きます。効いていることは E2E の「ホストのマウント数が元に戻る（開始 22 → 終了 22）」で機械的に確認しています。

Q4. 子は起動直後に何をして待っていますか? 待たせないと何が起きますか?

Init の先頭で waitForParent() を呼び、fd 3（親から ExtraFiles で渡されたパイプの読み側）を io.ReadAll で読み切るまで止まっています。親が "OK" を書いて閉じるまで、1 行も先へ進みません。

待たせないと、親が cgroup に PID を登録し終える前に子が走り出し、上限が効く前にメモリを確保してしまいます。結果、上限のテストが気まぐれに通ったり落ちたりします。順序を保証するための 1 本のパイプです。

Q5. 親が準備に失敗したことを、子にはどうやって伝えていますか?

合図を書かずにパイプを閉じます。子の io.ReadAll は空のデータを受け取って戻り、"OK" と一致しないので「親の準備が失敗したため中止します」というエラーで終了します。

パイプは「閉じられた」こと自体が読み側に伝わるので、異常通知のための別の連絡路が要りません。Run の失敗分岐に syncW.Close() // 合図を送らずに閉じる → 子は何もせず終了する と書かれているのがそれです。

Q6. syscall.Exec と exec.Command(...).Run() の違いは? なぜ前者でなければならないのですか?

exec.Command(...).Run() は新しい子プロセスを作って実行します。syscall.Exec は今のプロセスの中身を置き換えます。新しいプロセスは生まれず、PID も変わりません。

もし子を作る方を使ったら、コンテナの PID 1 は mydocker init のままで、利用者のコマンドはその子になってしまいます。syscall.Exec で置き換えるからこそ、PID 1 がそのまま /bin/sh になる。実測の ps の 1 行目が /bin/sh であることがその証拠です。

あわせて、次の 3 つを声に出して説明できるか試してください。①なぜ unshare だけでは PID 1 になれないのか、②/proc/self/exe は何を指しているのか、③fd 3 のパイプは何を守っているのか。詰まったところが、この章のもう一度読む場所です。

まとめ — 次の層へ

この章で、私たちはコンテナのいちばん最初の一歩を手に入れました。素朴案（unshare してから exec）が原理的に成立しないことを実測で確かめ、そこから re-exec パターンの必然を導きました。/proc/self/exe で自分自身を確実に指し、Cloneflags で名前空間を注文しながら子を生み、Unshareflags でホストとの伝播を断ち、fd 3 の同期パイプで「cgroup が効く前に走り出す」競争を消し、最後に syscall.Exec で中身を入れ替えて PID 1 を目的のコマンドそのものにする。Run と Init という 2 つの顔が、1 つの実行ファイルの中で親子として噛み合う仕組みができました。

ただし、いま手元にあるのは入れ物だけです。名前空間という箱は作れましたが、その箱で何が区切られているのかを、私たちはまだ 1 つも確かめていません。CLONE_NEWUTS と CLONE_NEWPID と CLONE_NEWNS と CLONE_NEWIPC を並べて書いただけで、それぞれが何を隠し、何を隠さないのかは手つかずです。ホスト名が変わることだけは見えましたが、たとえば「コンテナの中の ps はどこまでホストを見せるのか」は説明できません。実際、この段階のコンテナには奇妙な症状が残っています。PID 名前空間は確実に効いているのに、ps がホストのプロセスをずらりと並べてしまうのです。箱は作った、けれど中の見え方はまだ制御できていない。

次章では、この箱の中身を 1 つずつ開けます。名前空間 6 種類（PID・MNT・UTS・IPC・NET・USER）を順に取り上げ、それぞれが何を区切るのかを、動く実験で 1 つずつ確かめていきます。そして最後に、あの謎に正面から出会います — 名前空間は効いているのに、ps はホストを見せ続ける。実測ではホスト側 85 個に対して、コンテナの中は 87 個。区切ったはずなのにホストより多いのです。この矛盾の犯人を突き止めることが、第03章で「根を挿げ替える」動機になります。
