Namespace— 視界に壁を立てる

見える世界を区切る

前章で、私たちは自分自身をもう一度起動できるようになりました。けれど生まれた子プロセスは、まだホストと同じ世界を見ています。この章では、その子に 「あなたの世界はここまで」 という壁を4枚立てます。ホスト名、プロセス番号、マウント、プロセス間通信。壁を立て終えたところで、1つだけどうしても壁を越えてくるものに出会います。そこが次章の入口です。

◈ この章のゴール

internal/container/run.go の Cloneflags に並ぶ4つのフラグが、それぞれ何を区切っているのかを自分の言葉で説明できるようになる。Unshareflags がなぜ別に要るのかも言えるようにする。仕上げに、コンテナの中で hostname を打つとホストと違う名前が返ることを確認し、そのうえで ps だけがまだホストのプロセスを見せてしまうという「謎」を自分の目で見る。

名前空間とは、カーネルが持っている「見え方の台帳」

まず言葉を1つだけ引き受けてください。名前空間（namespace）です。難しそうな名前ですが、やっていることはとても素朴です。

Linux カーネルの中には、「今このマシンのホスト名は何か」「今動いているプロセスは何番と何番か」「今どこに何がマウントされているか」といった台帳がいくつも置かれています。ふつう、この台帳はマシンに1冊ずつしかありません。誰がどこから読んでも同じ内容が返る。だから hostname はどのプロセスから打っても同じ答えを返しますし、ps はどのプロセスから打っても同じ一覧を返します。

名前空間というのは、この台帳を複数冊に増やして、「このプロセスはこっちの台帳を読む」と割り当てられるようにした仕組みです。それだけです。仮想マシンのようにハードウェアを真似しているわけでもなければ、カーネルをもう1つ動かしているわけでもありません。カーネルは1つのまま、台帳だけが枝分かれします。

名前空間がないとき（台帳は1冊） プロセス A ──┐ プロセス B ──┼──▶ 【ホスト名の台帳】 "vm" プロセス C ──┘ 名前空間があるとき（台帳が2冊になり、C だけ別の冊子を見る） プロセス A ──┐ プロセス B ──┴──▶ 【ホスト名の台帳 その1】 "vm" プロセス C ─────▶ 【ホスト名の台帳 その2】 "mydocker" C が "mydocker" と書き換えても、A と B の見る台帳は "vm" のまま。 カーネルは1つ。動いている CPU も1つ。増えたのは台帳だけ。

この「台帳が枝分かれする」という感覚を掴んでしまえば、この章の残りはただの各論です。区切れる台帳が6種類あって、私たちはそのうち4種類を使う、というだけの話になります。

そして大事なことを1つ。台帳は種類ごとに独立して枝分かれします。 ホスト名の台帳だけ分けて、プロセス番号の台帳は共有する、ということができる。逆もできる。この「選べる」性質が、後で私たちを助けもし、悩ませもします。

6種類の名前空間 — 何を区切るのか、どれを使うのか

Linux が用意している名前空間のうち、コンテナを作るときに関係してくるのは次の6種類です。この教材で使うものと使わないものを、最初に正直に並べておきます。

名前空間何を区切るかこの教材で使うか
UTSホスト名・ドメイン名✅ 使う（CLONE_NEWUTS）
PIDプロセス番号✅ 使う（CLONE_NEWPID）
MNTマウントの見え方✅ 使う（CLONE_NEWNS）
IPCプロセス間通信（共有メモリ・セマフォ）✅ 使う（CLONE_NEWIPC）
NETネットワーク機器・アドレス・ルーティング❌ 使わない（第08章で理由を書く）
USERユーザ ID / グループ ID の対応付け❌ 使わない（第09章の発展課題）

下の2行に ❌ が並んでいるのが見えたと思います。ここでごまかしません。この教材の mydocker は、ネットワークもユーザ ID も隔離していません。 4枚の壁は立ちますが、6枚ではありません。

「使っていないなら書かなければいいのに」と思うかもしれません。逆です。使っていないことを知らずに使うほうが危ないからです。とくにネットワークは、隔離できていないことが目に見えにくい。実際に mydocker の中でネットワーク機器の一覧を打ってみると、こうなります。

▸ 動かして確認 · 隔離できていないものを見ておく

コンテナの中から ip -o addr を打ちます。-o は1機器を1行にまとめる指定です。

$ mydocker run --quiet alpine /bin/sh -c 'ip -o addr'
1: lo    inet 127.0.0.1/8 scope host lo\       valid_lft forever preferred_lft forever
2: eth0    inet 192.0.2.2/24 brd 192.0.2.255 scope global eth0\       valid_lft forever preferred_lft forever

この eth0 の 192.0.2.2/24 は、ホストのアドレスそのものです。コンテナ専用の仮想的なアドレスではありません。つまりコンテナは、ホストのネットワークをそのまま覗いています。ホスト名は違うのにアドレスは同じ、という中途半端な状態です。

これは壊れているのではなく、私たちが CLONE_NEWNET を渡していないからそうなっています。なぜ渡さなかったのか、渡すと何を追加で作らなければならなくなるのかは、第08章でまるごと1章使って扱います。

USER 名前空間のほうも同じです。使っていません。私たちのコンテナの中の root は、ホストの root と同じ root です。ID を付け替えていないのだから当然で、これは「コンテナの中で root を取れたらホストの root も取れる」という、セキュリティ上いちばん大きな穴です。教材としてどこまで踏み込むかの線引きと、実装するとしたら何をするのかは第09章に置きました。

できていないことを「できたふり」で書かない。教材が読者に対して払える最低限の敬意は、たぶんこれだけです。この教材の方針
LINUX メモ · 名前空間はプロセスの属性である

名前空間は「箱」や「入れ物」ではありません。プロセスに貼られた属性です。ls -l /proc/<pid>/ns/ を見ると、そのプロセスが今どの名前空間に属しているかがシンボリックリンクとして並んでいます。uts、pid、mnt、ipc、net、user… といった名前のリンクです。

リンクの先は uts:[4026531838] のような、番号の付いた擬似的な名前になっています。この番号が台帳の識別子です。2つのプロセスの同じ種類のリンクが同じ番号を指していれば、その2つは同じ台帳を見ている。違う番号なら別の台帳を見ている。判定はそれだけです。

この「リンクとして触れる」性質は飾りではありません。ファイルとして開けるということは、開いたまま持ち回れるということです。あとで mydocker exec（実行中のコンテナにもう1つコマンドを送り込む機能）を作るとき、私たちはまさにこのリンクを os.Open で開いて、その fd を setns というシステムコールに渡します。「あの台帳に、私も加えてくれ」という頼み方です。Step 4 で実物のコードを見ます。

もう1つ。名前空間には明示的な破棄がありません。参照するプロセスが1つもいなくなり、開いたままのリンクも無くなった時点で、カーネルが黙って回収します。だから私たちのコードには「名前空間を閉じる」処理がどこにも出てきません。free の要らないメモリのようなものだと思ってください。

どこから手を付けるか — いちばん確かめやすい壁から

4枚の壁を立てるにあたって、順番には意味があります。効いたかどうかが一目で分かるものからやります。

この方針は趣味ではありません。カーネルの機能をいじるときの一般的な護身術です。名前空間のような機能は、効いていないのにエラーも出さないことがあります。フラグを1つ書き忘れても、プログラムは何食わぬ顔で走ってしまう。だから「効いた／効いていない」を1コマンドで判定できる足場を、最初に確保しておきます。

その足場に最適なのが UTS です。hostname と打つだけで答えが返る。ホストで打った答えとコンテナで打った答えが違えば、壁は立っている。それだけです。

この章で立てる壁と、効いたことの確かめ方 Step 1 UTS ホスト名 → hostname が違う答えを返す ★いちばん明快 Step 2 PID プロセス番号 → 自分の PID が 1 になる Step 3 MNT マウントの見え方 → ホスト側のマウント数が増えない Step 4 IPC 共有メモリ等 → （目には見えにくい。理屈で押さえる） ──────────────────────────────────────────────────────────── Step 6 ??? ps の一覧 → ★ここだけ、壁を立てても直らない

Step 1UTS から始める — hostname を打つだけで違いが見える

UTS という名前は UNIX Time-sharing System の頭文字です。由来は歴史的なもので、意味を追っても得るものはありません。区切られるのはホスト名とドメイン名の2つだけだと覚えてしまってください。6種類のなかでいちばん守備範囲が狭く、いちばん理解しやすい名前空間です。

守備範囲が狭いことは弱点ではなく利点です。1つの台帳に1つの文字列しか載っていないので、枝分かれしたかどうかが文字列の比較で分かる。まずホスト側で名前を確認しておきます。

▸ 動かして確認 · ホスト側のホスト名
$ hostname
vm

この環境のホスト名は vm です。あなたの環境では別の文字列が返るはずですが、それで構いません。大事なのは「ホスト側では これ が返る」という基準線を持つことです。

ホスト名を変えるシステムコール

次に、コンテナの中でホスト名を変える側のコードを見ます。internal/container/init.go の Init 関数です。この関数は新しい名前空間の中で走ることに注意してください。前章で作った re-exec の、その「子」の側です。

internal/container/init.go
// Init は新しい名前空間の中（＝コンテナの PID 1）で走る処理である。
//
// ここに来た時点で、親が Cloneflags で作った namespace の中にいる。
// あとは「地面を入れ替えて、目的のコマンドに成り代わる」だけ。
//
//  1. 親の合図を待つ（cgroup に入れてもらうまで動かない）
//  2. ホスト名を変える（UTS 名前空間の効果を目に見える形にする）
//  3. pivot_root で root を挿げ替える
//  4. /proc /sys /dev を貼り直す
//  5. syscall.Exec で目的のコマンドに成り代わる（★戻ってこない）
func Init(args InitArgs) error {
	if err := waitForParent(); err != nil {
		return err
	}

	if args.Hostname != "" {
		if err := syscall.Sethostname([]byte(args.Hostname)); err != nil {
			return fmt.Errorf("ホスト名を設定できませんでした: %w", err)
		}
	}

	// …（3〜5 は第03章で読む）
}

ホスト名を変えている部分は、たった5行です。逐行で見ます。

  • args.Hostname != "" — 空文字なら何もしません。ホスト名を指定せずに起動する道も残しておくためです。
  • syscall.Sethostname([]byte(args.Hostname)) — これが本体です。sethostname(2) というシステムコールを直接呼んでいます。Go の syscall パッケージは、こういうカーネルの入口をほぼそのままの名前で持っています。引数が string ではなく []byte なのは、システムコール側がバイト列と長さを受け取る形をしているからです。
  • 失敗したらエラーを返して起動を止めます。ホスト名が変えられないということは UTS 名前空間が効いていない可能性が高く、黙って続けると「壁が立っていないコンテナ」ができあがってしまいます。

ここで一度、立ち止まって考えてほしいことがあります。この Sethostname は、名前空間とは何の関係もない、ただの普通のシステムコールです。 昔からある、マシンのホスト名を変える呼び出しです。

ではなぜ、これを呼んでもホスト側のホスト名が変わらないのか。このプロセスが読み書きする台帳が、すでに枝分かれしているからです。同じシステムコールが、属している名前空間によって別の台帳を書き換える。アプリケーション側のコードは何も変わらないのに、効果の及ぶ範囲だけが変わる。これが名前空間という仕組みのいちばん美しいところだと私は思っています。

⚠ 落とし穴 · UTS 名前空間なしで Sethostname を呼ぶとどうなるか

もし Cloneflags から CLONE_NEWUTS を落としたまま、このコードを動かしたらどうなるでしょうか。

答えは 「成功して、ホスト側のホスト名が変わる」 です。エラーは出ません。root で走っているので権限も足ります。カーネルは言われたとおり、ホストの台帳を書き換えます。あなたのターミナルのプロンプトが、次にログインしたときから mydocker になっているかもしれません。

怖いのは「エラーにならない」ことです。名前空間まわりのバグは、たいていこの形をしています。失敗ではなく、範囲の取り違えとして現れる。 だからこそ Step 1 で「ホスト側で hostname を打っておく」という基準線を取ったのでした。壁を立てたあとで、ホスト側がまだ vm のままであることを、必ず確かめてください。

実際に、違う答えが返る

完成した mydocker で確かめます。実装はまだ途中ですが、この章の終わりに何が手に入るのかを先に見ておきましょう。

▸ 動かして確認 · コンテナの中のホスト名
$ mydocker run alpine /bin/sh
/ # hostname
mydocker

そしてコンテナを抜けて、ホストで同じコマンドを打ちます。

$ hostname
vm

台帳が2冊に分かれています。 コンテナの中で書き換えた mydocker は、ホスト側の台帳には1文字も届いていません。壁の1枚目が立ちました。

たった1行の文字列が違うだけですが、これは決定的な一歩です。「同じカーネルの上で、プロセスによって世界の見え方が違う」という現象を、あなたは今、自分の手で起こしました。残りの3枚は、区切る対象が変わるだけで、原理はこれと完全に同じです。

Step 2PID 名前空間 — 自分が 1 番になる

2枚目の壁はプロセス番号です。ここが名前空間のなかでいちばん面白く、いちばん誤解されやすいところです。

ふつう、Linux のプロセス番号（PID）はマシン全体で一意です。1 番は起動時に最初に立ち上がるプロセス（init や systemd）で、あとは順に大きな番号が振られていく。同じ番号のプロセスが2つ存在することはありません。

PID 名前空間は、この番号の台帳を枝分かれさせます。枝分かれした先では、番号がまた 1 から振り直されます。つまりコンテナの中で最初に走るプロセスが、そのコンテナにとっての PID 1 になる。

まず素朴に試して、失敗する

いきなりコードを書く前に、unshare というコマンドで手触りを掴みます。これは「新しい名前空間を作って、その中でコマンドを走らせる」ためのコマンドラインツールです。私たちがこれから Go で書こうとしていることを、コマンド1つでやってくれます。

素朴に考えると、こう打てば PID 1 になれそうです。$$ はシェルが自分自身の PID に展開する記法です。

▸ 動かして確認 · 素朴な試み
$ unshare --pid sh -c 'echo "自分の PID: $$"'
自分の PID: 25171

1 ではありません。 25171 という、いかにもホスト側の連番らしい数字が返ってきました。--pid を渡したのに、PID 名前空間が効いていないように見えます。

ここで「unshare が壊れている」と結論づけないでください。効いています。効いているのに 1 にならない。この食い違いには、はっきりした理由があります。

PID 名前空間は、それを作ったプロセス自身には適用されません。

理由を考えると納得できます。すでに走っているプロセスの番号を途中で 1 に付け替えたら、そのプロセスを wait している親や、PID を握っている他のプロセスとの辻褄が合わなくなります。番号は生まれたときに1回だけ決まるもので、後から変えられるものではない。だからカーネルは、こう振る舞います。

PID 名前空間が「誰に」効くのか unshare --pid sh ──────────────── ① unshare が新しい PID 台帳を作る └─ ただし unshare 自身の番号は、古い台帳のまま（25171 など） ② その後 fork で生まれた子から、新しい台帳の番号が付く └─ 最初に生まれた子が PID 1 つまり「作った本人」ではなく「作ったあとに生まれた子」が 1 番になる。 --fork は「もう1段 fork してから実行する」という指定。これで1番が取れる。

unshare には、まさにこのための --fork というオプションがあります。付けてみます。

▸ 動かして確認 · --fork を足す
$ unshare --pid --fork sh -c 'echo "自分の PID: $$"'
自分の PID: 1

1 になりました。 フラグは何も変えていません。変えたのは「誰が実行するか」だけです。

この 25171 と 1 の対比は、この章でいちばん覚えて帰ってほしい実験です。名前空間は「作る」だけでは不十分で、「作ってから生まれる」必要がある。

そして、これはあなたが前章でさんざん苦労した re-exec パターンが、なぜあの形をしていたかの答えでもあります。run.go のコメントにも同じことが書いてあります。

internal/container/run.go
// 素朴に考えると「unshare して、そのあと目的のコマンドを exec すればいい」と思える。ところが:
//
//   - PID 名前空間は unshare を呼んだプロセス自身には適用されない。
//     適用されるのは **その後に作られた子プロセス** から。「自分が PID 1 になる」ことはできない
//   - Go のランタイムはマルチスレッドなので、プロセス内でスレッド単位の unshare を素直に扱えない
//
// そこで /proc/self/exe（＝自分自身の実行ファイル）を "init" という別の顔で起動する。
// 新しい名前空間はこの起動と同時に生まれ、子は生まれながらにして PID 1 になる。

「生まれながらにして PID 1」。これが re-exec の存在理由です。私たちは unshare --fork の --fork の部分を、Go で自前でやっているのです。

★同じプロセスが、番号を2つ持つ

ここから先が、PID 名前空間でいちばん頭がねじれるところです。ゆっくり行きます。

コンテナの中のプロセスが PID 1 になったからといって、ホスト側からそのプロセスが見えなくなるわけではありません。 ホストの台帳にも、ちゃんと載っています。載っているけれど、別の番号で載っています。

実測で見ます。sleep 20 を動かすコンテナを起動して、ホスト側の一覧（mydocker ps）と、コンテナの中の一覧（mydocker exec 経由で ps）を並べます。

▸ 動かして確認 · 外から見た番号と、中から見た番号

まずホスト側から。mydocker ps は、実行中のコンテナをホスト側の PID つきで並べます。

$ mydocker ps
CONTAINER ID   IMAGE                                 COMMAND    PID     STATUS   CREATED
0c1be9ad663a   mirror.gcr.io/library/alpine:latest   sleep 20   16144   Up       0s
合計 1 件

ホストから見ると、この sleep 20 は 16144 番です。次に、同じコンテナの中に入って ps を打ちます。

$ mydocker exec 0c1be9ad663a /bin/sh -c 'hostname; ps'
mydocker
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 20
    8 root      0:00 /bin/sh -c hostname; ps
   15 root      0:00 ps

中から見ると、同じ sleep 20 が 1 番です。

16144 と 1。これは2つのプロセスではありません。1つのプロセスです。メモリ上に task_struct は1つしかなく、CPU 時間も1つ分しか消費していません。ただ、読む台帳によって振られている番号が違うだけです。

同じ1つの sleep 20 が、番号を2つ持っている 【ホストの PID 名前空間】 【コンテナの PID 名前空間】 PID 1 systemd （この台帳は空から始まった） PID … （ホストのいろいろ） PID 16144 sleep 20 ←── 同一のプロセス ──→ PID 1 sleep 20 PID 8 /bin/sh -c hostname; ps PID 15 ps ・ホスト側からは 16144 として見え、kill もできる（親は子を殺せる） ・コンテナの中からは 1 としてしか見えない。16144 という番号は存在すらしない ・逆にコンテナの中からホストの systemd(1) を kill することはできない。 そもそも番号が割り振られていないので、指し示す手段がない ★入れ子は一方通行。親の台帳は子を見られるが、子の台帳は親を見られない。

この一方通行の関係が、PID 名前空間の隔離の本質です。コンテナからホストのプロセスを触れないのは、権限で禁じているからではありません。番号として存在しないから、指し示す言葉がないのです。 鍵をかけているのではなく、住所が書けない。

ついでに、上の ps の出力をよく見てください。1 の次が 8 で、その次が 15 です。1、2、3 と続いていません。コンテナの中でも番号は消費されており、シェルが内部で使った番号などが飛んでいます。コンテナの中の PID も、ただの連番だということです。特別なことは何もしていません。

LINUX メモ · PID 1 という特別な役目

PID 1 は、Linux では特別扱いされます。教材の範囲を越えますが、知っておくと後で困りません。

1つめ。PID 1 が終了すると、その PID 名前空間の中の全プロセスが道連れで終了させられます。 カーネルが SIGKILL を配ります。だから docker run したコンテナは、指定したコマンドが終わると中で何が動いていようと丸ごと終わる。これは実装の都合ではなく、カーネルの規則です。

2つめ。PID 1 は、シグナルのデフォルト動作が効きません。 ふつうのプロセスは SIGTERM を受けると、ハンドラを書いていなくても終了します。PID 1 はハンドラを登録していないシグナルを無視します。うっかり init を殺してシステムを止めないための保護です。コンテナで「Ctrl-C が効かない」という現象の多くはこれが原因です。

3つめ。親を失ったプロセス（孤児）は PID 1 に引き取られます。 引き取ったプロセスは、その子の終了を wait で回収する責任を負います。回収しないとゾンビが溜まる。本物の init はこの仕事を淡々とやりますが、私たちが PID 1 に据えるのは /bin/sh や sleep です。ゾンビの回収まではしてくれません。この教材ではそこまで踏み込みませんが、「docker run --init というオプションが何のためにあるのか」の答えがこれです。

Step 3MNT 名前空間 — マウントの見え方を区切る

3枚目はマウントです。区切られる台帳は「どこに何がマウントされているか」の一覧、いわゆるマウント表です。

フラグの名前だけ注意してください。他は CLONE_NEWUTS、CLONE_NEWPID と綺麗に揃っているのに、マウントだけ CLONE_NEWNS です。NEWMNT ではありません。NS は namespace の略で、これはいちばん最初に実装された名前空間だからです。当時は他に名前空間がなく、「名前空間といえばマウントのこと」だったので、区別のための接尾辞が付きませんでした。歴史的事故です。覚えるしかありません。

ホスト側のマウント表を見ておきます。/proc/mounts が現在のマウント一覧で、1行が1マウントです。

この環境では 22 行でした。これも Step 1 の hostname と同じ、基準線です。この章の実験を全部やり終えたあとで、もう一度数えて 22 に戻っていれば「漏れていない」。増えていたら「漏れた」。判定はこれだけです。

なぜマウントを区切る必要があるのか。理由は次章の予告にもなります。私たちはこれから、コンテナの中でたくさんマウントします。イメージを重ねた overlay を根として貼り、/proc を貼り、/sys を貼り、/dev に tmpfs を敷きます。これらが全部ホストのマウント表に載ったら、コンテナを1つ起動するたびにホストのマウント表が数行ずつ伸びていくことになります。

MNT 名前空間なし / あり 【なし】コンテナが増えるたびにホストのマウント表が伸びる ホストのマウント表: 22 行 → コンテナ起動 : 26 行 （overlay, proc, sys, dev が載る） → もう1つ起動 : 30 行 → 異常終了で残る : 30 行のまま ★誰も片付けない → 数日後 : 数百行 ★df も mount もまともに読めない 【あり】枝分かれしたマウント表の上で好きなだけマウントする ホストのマウント表 : 22 行 ────────────── 22 行（変わらない） └─ 枝分かれ ─▶ コンテナのマウント表 overlay を根に、proc, sys, dev を追加 プロセスが全部終わると台帳ごと消える

右側の 「台帳ごと消える」 が効きます。名前空間には明示的な破棄がなく、参照するプロセスが消えれば回収される。つまりコンテナの中でやったマウントは、コンテナが終わった時点で自動的に片付きます。 私たちが umount を書いて回る必要がない。これは実装量の削減であると同時に、異常終了しても散らからないという信頼性でもあります。

フラグを1つ書くだけでは足りない

GO メモ · syscall.SysProcAttr の Cloneflags と Unshareflags の違い

syscall.SysProcAttr は、Go の os/exec で子プロセスを起動するときに「OS 固有の細かい注文」を書くための構造体です。Linux 版にはたくさんフィールドがありますが、この教材で使うのは2つだけです。

Cloneflags は、clone(2) システムコールに渡すフラグです。clone は「プロセスを作る」システムコールで、fork の細かい版だと思ってください。ここにフラグを並べると、子プロセスが生まれるまさにその瞬間に、新しい名前空間が一緒に作られます。「生まれながらにして」を実現しているのはこのフィールドです。

Unshareflags は違います。こちらは Go のランタイムが、子プロセス側で、目的のプログラムを exec する直前に unshare(2) を呼んでくれるという指定です。clone と同時ではなく、生まれたあとにもう1回名前空間を分ける。

では、なぜ CLONE_NEWNS だけ両方に要るのか。Cloneflags だけでも、マウント名前空間そのものは確かに新しく作られます。ところが、新しく作られたマウント名前空間は、親のマウント表を「複製」した状態で始まり、しかも複製元との間に「伝播」の関係が残っているのです。伝播が残っていると、子でマウントしたものが親にも伝わってしまう。Unshareflags でもう一度 unshare することで、この伝播の関係を確実に断ち切ります。

「なぜ2回やる必要があるのか、1回で済まないのか」と思うのは正しい感覚です。厳密に言えば、伝播を切る方法は他にもあります（次の LINUX メモを読んでください）。ただ Unshareflags を書いておくのが、Go から扱ううえでいちばん確実で、いちばん短い。runc をはじめ実運用のコンテナランタイムも、形は違えど同じ「2段構え」をしています。

⚠ 落とし穴 · Unshareflags を忘れると、ホストのマウントが増えていく

Unshareflags: syscall.CLONE_NEWNS の1行を落としても、プログラムはエラーを出しません。コンテナは起動し、コマンドは走り、終了します。何も起きていないように見えます。

起きているのはホスト側です。コンテナの中で貼った overlay や /proc が、伝播の関係を通ってホストのマウント表にも載ります。そしてコンテナが終わっても、ホスト側に載ったぶんは消えません。コンテナを起動するたびに、ホストのマウント表が伸び続けます。

症状は忘れた頃に出ます。mount や df の出力が数百行になって読めなくなる。overlay の lowerdir（＝イメージの実体）が掴まれたままになって消せなくなる。さらに悪いことに、伝播が残ったままだと pivot_root が EINVAL で落ちます。第03章でいちばん最初にぶつかるエラーがこれです。

だから run.go のコメントには「『なぜか動かない』の筆頭」と書いてあります。この1行は、書き忘れても叱ってくれない種類の1行です。

確かめ方は簡単です。実験の前後で wc -l < /proc/mounts を打ち、数が戻っていることを見る。この教材の E2E テストにも同じ項目が入っています。「テスト全体を通してホストのマウント数が元に戻る（開始 22 → 終了 22）」という検査です。

LINUX メモ · マウントの伝播（shared subtree）

いま「伝播」と言ったものの正体を、もう少しだけ開けておきます。第03章でこれを自分で切ることになるので、名前だけでも通しておくと楽です。

Linux のマウントには、伝播タイプという属性が付いています。「このマウントポイントの下で起きたマウント／アンマウントを、他のマウント名前空間にも伝えるかどうか」を決める設定です。主なものは4つ。

  • shared — 双方向に伝わる。こちらでマウントすると向こうにも現れ、向こうでマウントするとこちらにも現れる
  • slave — 一方向。親から子へは伝わるが、子から親へは伝わらない
  • private — どちらにも伝わらない。完全に独立
  • unbindable — private に加えて、bind mount の元にすることも禁止される

問題は、現代の Linux ディストリビューションの多くが、/ を shared にして起動することです（systemd がそうします）。shared は便利だからです。たとえば USB メモリを挿したとき、その自動マウントが全部の名前空間に伝わってほしい、という要求は自然です。

ところが私たちにとっては、これがそのまま漏れ口になります。CLONE_NEWNS で新しいマウント名前空間を作っても、複製されたマウント表の各エントリは shared の関係を引き継いでいます。子でマウントすると、shared の線を伝って親にも現れる。名前空間は分かれているのに、内容が同期してしまう。

切り方は2つあります。1つは Unshareflags（この Step で見たもの）。もう1つは、子プロセスの中から明示的に / を private に付け替えることです。私たちのコードは両方やっています。init.go の pivotRoot の1行目が後者で、syscall.Mount("", "/", "", syscall.MS_PRIVATE|syscall.MS_REC, "") という呼び出しです。MS_REC は「配下のマウント全部に再帰的に」という指定。第03章で逐行に読みます。

「両方やるのは冗長では」と思うかもしれません。冗長です。そして冗長にしておくべき箇所です。ここが破れたときの症状（ホストのマウント表がじわじわ伸びる）は、発見が遅れるほど回復が面倒になる種類のものだからです。

Step 4IPC 名前空間 — 地味だが要る 4 枚目の壁

4枚目は IPC、プロセス間通信です。正直に言って、この章でいちばん地味です。動かして「おおっ」となる瞬間がありません。それでも入れる理由を書きます。

IPC 名前空間が区切るのは、System V IPC と呼ばれる古い仕組みの3点セットと、POSIX メッセージキューです。

仕組み何をするもの
共有メモリ（shared memory）複数プロセスが同じメモリ領域を直接読み書きする。いちばん速いプロセス間通信
セマフォ（semaphore）「今この資源を使っているのは誰か」を数で管理する。排他制御の道具
メッセージキュー（message queue）プロセス間で構造化されたメッセージを送り合う待ち行列

この3つには共通の特徴があります。ファイルシステムの外に住んでいるということです。共有メモリの領域は /tmp/xxx のようなパスを持ちません。カーネルの中の、パスとは別の名前空間（この文脈では「識別子の一覧」くらいの意味）に、キーと ID だけで登録されています。

なぜ IPC だけ別の壁が要るのか ファイルを介した通信 System V IPC ───────────────────── ───────────────── プロセス A ──▶ /tmp/sock ◀── B プロセス A ──▶ key 0x1234 ◀── B ↑ ↑ パスがある → MNT の壁で隠せる パスがない → MNT の壁は無力 ↓ IPC 名前空間が要る ★MNT / PID / UTS の壁を3枚立てても、この経路だけは素通しのまま残る。

つまり、こういうことです。MNT 名前空間でファイルシステムをどれだけ隔離しても、共有メモリの経路は塞がりません。 パスを持たないものは、パスの見え方を変えても隠れないからです。

具体的に何が困るか。3つ挙げます。

  • 意図しない通信路が残る。 コンテナの中のプロセスと、ホストのプロセスが、共有メモリ越しに繋がってしまう可能性があります。ファイルは1つも共有していないのに、です。「隔離したつもり」がいちばん危ない状態です。
  • キーの衝突が起きる。 System V IPC のキーは、アプリケーションが決め打ちの数値を使うことが珍しくありません。同じイメージから2つコンテナを起動したら、両方が同じキーを取りに行って、片方が「すでに存在します」で起動に失敗する。コンテナが増えると再現する、たちの悪いバグです。
  • 片付かない。 System V IPC のオブジェクトは、作ったプロセスが死んでも残ります。明示的に消すまでカーネルに居座る。名前空間で囲っておけば、名前空間ごと消えるときに一緒に回収されます。ファイルの後始末と同じ話が、ここでも効いてきます。

3つめの理由は、Step 3 の「台帳ごと消える」とまったく同じ形をしています。名前空間で囲うと、後始末が自動になる。 隔離のためだけでなく、掃除のために壁を立てる、という見方をしておくと、この先の章でも見通しが良くなります。

フラグは CLONE_NEWIPC。Cloneflags に | で足すだけです。追加のコードは1行も要りません。コストがほぼゼロで、塞げる穴が1つ増える。 入れない理由がありません。

名前空間を「開いて、参加する」— setns

UTS・PID・IPC が揃ったところで、これらを実際にファイルとして開いて使っているコードを見ておきます。mydocker exec、つまり実行中のコンテナにもう1つコマンドを送り込む機能の中身です。

この機能は、新しい名前空間を作るのではなく、既存の名前空間に参加します。「LINUX メモ · 名前空間はプロセスの属性である」で予告した /proc/<pid>/ns/ のリンクが、ここで実物として登場します。

internal/container/run.go
	// pid 名前空間への setns は「呼び出し元自身」ではなく「これから作る子」に効く。
	// つまりこの後の cmd.Start() で生まれる子が、コンテナの PID 名前空間に入る。
	for _, ns := range []struct {
		name string
		flag int
	}{
		{"uts", syscall.CLONE_NEWUTS},
		{"ipc", syscall.CLONE_NEWIPC},
		{"pid", syscall.CLONE_NEWPID},
	} {
		path := filepath.Join("/proc", fmt.Sprint(st.PID), "ns", ns.name)
		f, err := os.Open(path)
		if err != nil {
			return 1, fmt.Errorf("%s を開けませんでした: %w", path, err)
		}
		_, _, errno := syscall.Syscall(sysSetns, f.Fd(), uintptr(ns.flag), 0)
		f.Close()
		if errno != 0 {
			return 1, fmt.Errorf("%s 名前空間に参加できませんでした: %v", ns.name, errno)
		}
	}

読みどころは3つです。

  • filepath.Join("/proc", fmt.Sprint(st.PID), "ns", ns.name) — 組み立てているのは /proc/16144/ns/uts のようなパスです。st.PID は、状態ファイルに記録しておいたホスト側の PID。中から見た 1 ではなく、外から見た 16144 のほうを使っています。ホスト側で走っているコードなので当然です。
  • os.Open(path) — 名前空間をファイルとして開いています。 ここが気持ちのいいところです。カーネルの中の抽象的な「台帳」に、ファイルディスクリプタという普通のハンドルで手が届く。Linux の「すべてはファイル」という思想が、こんなところにも通っています。
  • syscall.Syscall(sysSetns, f.Fd(), uintptr(ns.flag), 0) — setns(2) を直接呼び出しています。「この fd が指す名前空間に参加させてくれ」という頼み方です。第2引数のフラグは「参加させようとしているのが確かに UTS 名前空間であること」をカーネルに検算させるための安全装置で、種類が違えばエラーになります。

そして、リストに mnt が入っていないことに気づいたでしょうか。UTS・IPC・PID の3つだけです。これには理由があり、しかも妥協です。run.go の Exec のコメントが、その妥協をそのまま書いています。マウント名前空間への setns は呼び出し元がシングルスレッドでないと通らず、Go のランタイムは常にマルチスレッドなので満たせない——だから exec ではマウント名前空間だけは新しく作り、同じ merged ディレクトリを根にすることで見えるファイルを一致させています。第07章で改めて扱います。

  • exec.Command("/proc/self/exe", args...) — /proc/self/exe は「今走っている自分自身の実行ファイル」を指す特別なパスです。自分をもう一度、init という別の顔で起動する。これが re-exec でした。
  • args の先頭が "init" — 起動された側は、この第1引数を見て「あ、自分は init として呼ばれたのだな」と判断し、Step 1 で読んだ Init 関数へ進みます。
  • cmd.ExtraFiles = []*os.File{syncR} — 親が「準備できた」と合図を送るためのパイプです。子は fd 3 でこれを受け取り、合図が来るまで走り出しません。第04章の cgroup が効く前に子がメモリを掴んでしまわないための同期です。

そしてこの cmd.Start() が呼ばれた瞬間に、4つの名前空間が同時に生まれ、子はその中で生まれます。生まれながらにして PID 1、生まれながらにして別のホスト名の台帳、生まれながらにして自前のマウント表。順番に設定していくのではなく、誕生と同時に全部決まる。ここが名前空間の作りのきれいなところです。

数えます。ps -e は全プロセスの一覧、--no-headers は見出し行を落とす指定、wc -l は行数を数えるコマンドです。

⚠ 落とし穴 · 「ps がホストを見せる = 名前空間が壊れている」という誤診

この症状を見て「PID 名前空間が効いていない」と診断するのは、間違いです。効いています。私たちはそれをすでに証明しました。

まったく同じ unshare --pid --fork の中で、シェルは自分が 1 番だと答えています。カーネルが返すこの答えに嘘はありません。PID 名前空間は間違いなく枝分かれしています。

にもかかわらず ps はホストのプロセスを並べる。つまり、ps が見ているものと、カーネルが $$ に返す番号とは、出どころが別だということになります。

ここを取り違えると、直っているものを直そうとして何時間も溶かします。症状から原因へ飛ばないでください。 「PID 名前空間が効いていない」ではなく「ps の情報源が壁の外にある」と読むのが正しい診断です。

87 という数字そのものにも意味があります。ホストが 85 なのに、なぜ増えるのか。

答えは「この実験自体がプロセスを増やしているから」です。unshare があり、--fork で分かれた sh があり、ps があり、wc があります。それらがホストの一覧に上乗せされて 87 になっています。裏を返せば、コンテナの中の ps がホストの全プロセスを数え上げたうえで、自分たちのぶんまで足しているということです。隔離が効いていないどころではなく、完全に素通しです。

なお、ホスト側の 85 という数字は測るたびに少し揺れます（この環境では 85〜87 の範囲でした）。1 や 2 の差に意味はありません。意味があるのは桁です。数十なのか、数個なのか。 ここだけ見てください。

つまずき FAQ

名前空間って、要するに軽い仮想マシンということですか?

いいえ、根本的に別物です。ここを混同すると、この先ずっと足を取られます。

仮想マシンはハードウェアを真似します。CPU も、メモリも、ディスクも、ネットワークカードも、偽物を用意して、その上でゲスト OS のカーネルをもう1つ起動します。だからカーネルが2つ動きます。Linux の上で Windows を動かせるのは、この方式だからです。

名前空間はハードウェアを何も真似しません。カーネルは1つのままです。増えるのは、この章で言い続けた「台帳」だけ。コンテナの中のプロセスは、ホストのプロセスとまったく同じカーネルの上で、まったく同じように実行されています。だから起動が速い（この教材の実測で 12〜15 ms、ホストで直接 /bin/true を実行した 3 ms と比べても、桁が同じです)。

そして同じ理由で、コンテナの中で別の OS のカーネル機能は使えません。「Linux の上で Windows のコンテナ」は原理的に無理です。ここが仮想マシンとの決定的な差で、コンテナの速さと制約は、同じ1つの事実の裏表です。

unshare --pid だけだと PID が 1 にならないのに、--fork を足すと 1 になるのはなぜですか?

PID 名前空間が「作った本人」には適用されないからです。適用されるのは、作ったあとに生まれた子プロセスからです。

すでに走っているプロセスの番号を途中で 1 に変えてしまうと、そのプロセスを wait している親や、PID を握って通信している他のプロセスとの辻褄が合わなくなります。番号は生まれたときに1回だけ決まるもので、後から変えられるものではない。だからカーネルは「次の世代から」という設計にしました。

--fork は、unshare に「名前空間を作ったあと、もう1段 fork してから目的のコマンドを実行しろ」と指示するオプションです。その1段の fork で生まれた子が、新しい台帳の最初の住人になり、1 番を取ります。

私たちの mydocker は、この --fork に当たる部分を re-exec（/proc/self/exe を init として起動する）で自前でやっています。前章でやったことと、この章の話は、同じ1つの制約から出ています。

Cloneflags に CLONE_NEWNET も足せば、ネットワークも隔離できるんじゃないですか?

足すこと自体はできます。1行足せば、コンテナは確かに独立したネットワーク名前空間を持ちます。

問題はその後です。新しく作られたネットワーク名前空間は、完全に空っぽです。入っているのは、上がってすらいないループバックデバイスだけ。eth0 はありません。IP アドレスもありません。ルーティングテーブルも空です。つまり、コンテナから外に一切出られなくなります。ping も curl も apk add も、全部沈黙します。

使える状態にするには、追加で全部自分で作らなければなりません。仮想イーサネットのペアを作り、片方をコンテナ側の名前空間に押し込み、ホスト側にブリッジを立て、そこに繋ぎ、IP を振り、ルートを足し、外に出るための NAT 規則を iptables に入れる。1行のフラグに対して、数百行の付き添いが要ります。

この教材はそこを実装していません。中途半端に CLONE_NEWNET だけ足して「ネットワークも隔離しました」と書くほうが、よほど不誠実だと考えました。第08章を、この判断の説明と、実装するなら何をどの順で作るかの地図に使っています。

Unshareflags を書かなくても、手元では普通に動いてしまいました。何が問題なんですか?

「普通に動く」のが、この落とし穴のいちばん厄介なところです。エラーは出ません。コンテナは起動し、コマンドは走り、終了します。

壊れているのはホスト側です。コンテナの中で貼ったマウントが、伝播の関係を通ってホストのマウント表にも載り、コンテナが終わっても消えません。1回では気づきません。100 回起動して初めて、mount の出力が数百行になっていることに気づきます。

確かめ方はあります。実験の前後で wc -l < /proc/mounts を打って、数が戻っているかを見てください。この環境では 22 でした。1回コンテナを起動して、終了後に 22 に戻っていれば漏れていません。増えていたら漏れています。

もう1つ、もっと早く症状が出る経路もあります。伝播が残ったままだと、次章の pivot_root が EINVAL で落ちます。「第03章でいきなりエラーになった」という人は、まずこの1行を疑ってください。

IPC 名前空間って、無くても動きますよね? 本当に要りますか?

動きます。落としても、この教材の範囲でエラーになる場面はたぶん出てきません。それでも入れています。理由は3つです。

1つめ。塞がない限り、通信路として残ります。 共有メモリやセマフォはパスを持たないので、MNT 名前空間でファイルシステムをどれだけ隔離しても隠れません。「ファイルは1つも共有していないのに繋がっている」という状態は、隔離としては失格です。

2つめ。キーの衝突が起きます。 System V IPC のキーは決め打ちの数値であることが多く、同じイメージから2つコンテナを起動すると、両方が同じキーを取りに行って片方が起動に失敗します。コンテナが増えたときにだけ再現する、原因の分かりにくいバグです。

3つめ。後始末が自動になります。 System V IPC のオブジェクトは、作ったプロセスが死んでも残ります。名前空間で囲っておけば、名前空間ごと回収されるときに一緒に消えます。

そのうえで、コストは | syscall.CLONE_NEWIPC という1行です。追加のコードも設定も要りません。入れない理由が見つかりませんでした。

コンテナの中で hostname mynew と打ったら、ホストのホスト名も変わってしまいますか?

変わりません。それがまさに、この章で CLONE_NEWUTS を渡した理由です。

コンテナの中の hostname コマンドも、私たちの syscall.Sethostname も、呼んでいるシステムコールは同じ sethostname(2) です。違うのはそのプロセスがどの台帳に属しているかだけ。コンテナの中のプロセスは枝分かれした台帳を見ているので、書き込みもそちらに行きます。ホスト側の台帳は vm のまま無傷です。

逆に言うと、CLONE_NEWUTS を渡し忘れていた場合は、本当にホストのホスト名が変わります。エラーも警告も出ずに、成功して変わります。Step 1 の落とし穴ボックスに書いたとおりです。この章で最初に hostname を打って基準線を取ったのは、この事故に後から気づけるようにするためでした。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。答え合わせより、先に自分で言葉にすることのほうが大事です。

Q1. UTS 名前空間を作らずに syscall.Sethostname を呼ぶと、何が起きますか?

成功して、ホスト側のホスト名が変わります。 エラーにはなりません。

Sethostname は名前空間とは無関係の、昔からある普通のシステムコールです。カーネルは、呼んだプロセスが属している UTS 名前空間の台帳を書き換えます。枝分かれさせていなければ、その台帳はホストのものです。

ここから引き出すべき一般則: 名前空間まわりの間違いは、多くの場合エラーではなく「効果の及ぶ範囲の取り違え」として現れる。だからテストは「成功したか」ではなく「ホスト側が変わっていないか」を見なければなりません。

Q2. unshare --pid sh -c 'echo $$' が 1 を返さない理由を説明してください。

PID 名前空間は作ったプロセス自身には適用されず、その後に生まれる子プロセスから適用されるからです。unshare 自身も、--fork なしで直接実行される sh も、古い台帳の番号（実測では 25171）を持ったままです。

設計としてこうなっている理由は、すでに走っているプロセスの番号を途中で変えると、そのプロセスを wait している親や、PID を握って通信している他のプロセスとの辻褄が合わなくなるからです。番号は生まれたときに1回だけ決まります。

--fork を足すと、unshare がもう1段 fork してからコマンドを実行するため、その子が新しい台帳の 1 番になります（実測で 1）。私たちの mydocker は、この1段を re-exec で自前でやっています。

Q3. Cloneflags と Unshareflags の違いは何ですか? なぜ CLONE_NEWNS だけ両方に書いてあるのですか?

Cloneflags は clone(2) に渡すフラグです。子プロセスが生まれるまさにその瞬間に、新しい名前空間が一緒に作られます。「生まれながらにして PID 1」を実現しているのはこちらです。

Unshareflags は、Go のランタイムが子プロセスの中で、目的のプログラムを exec する直前に unshare(2) を呼ぶという指定です。生まれたあとに、もう一度分けます。

CLONE_NEWNS が両方にあるのは、Cloneflags だけではマウントの伝播（shared subtree）の関係が残ってしまうからです。新しいマウント名前空間は親のマウント表を複製した状態で始まり、多くのディストリビューションでは / が shared なので、子でマウントしたものが親にも伝わります。Unshareflags でもう一度分けることで、この線を確実に断ちます。

なお私たちのコードは、これに加えて init.go の pivotRoot の1行目で MS_PRIVATE|MS_REC による付け替えもしています。冗長ですが、ここは冗長にしておくべき箇所です。

Q4. コンテナの中の PID 1 は、ホストから見ると何番ですか? 番号は1つですか、2つですか?

番号は2つあります。同じ1つのプロセスに、名前空間ごとの番号が付いています。

実測で言えば、sleep 20 を動かしたコンテナは、ホストの mydocker ps からは 16144 番として見え、コンテナの中の ps からは 1 番として見えました。プロセスは1つです。メモリ上の実体も1つ、消費する CPU 時間も1つ分です。

関係は一方通行です。ホスト側からはコンテナの中のプロセスが見え、kill もできます。逆に、コンテナの中からホストのプロセスを触ることはできません。権限で禁じられているからではなく、コンテナ側の台帳にその番号が存在しないから、指し示す手段がないのです。

Q5. unshare --pid --fork の中で ps -e がホストより多い 87 を返しました。名前空間は壊れていますか? そう判断する根拠は?

壊れていません。 根拠は、まったく同じ unshare --pid --fork の中で echo $$ が 1 を返すことです。カーネルがそのプロセスに 1 番を割り当てているのだから、PID 名前空間は間違いなく枝分かれしています。

したがって、ps が読んでいる情報源が、カーネルが $$ に返す番号とは別のところにあると読むのが正しい診断です。実際、--mount-proc というオプションを1つ足すだけで、PID まわりのフラグを一切変えずに答えが 87 から 3 に変わります。

87 がホストの 85 より多いのは、実験そのものが増やしたプロセス（unshare、sh、ps、wc）が上乗せされているからです。なお 85 という数字自体は測るたびに 85〜87 の範囲で揺れます。見るべきは 1 や 2 の差ではなく、数十なのか数個なのかという桁です。

Q6. NET 名前空間を使っていないと、コンテナの中で ip -o addr を打つと何が見えますか?

ホストのネットワーク機器とアドレスが、そのまま見えます。 実測ではこうでした。

$ mydocker run --quiet alpine /bin/sh -c 'ip -o addr'
1: lo    inet 127.0.0.1/8 scope host lo\       valid_lft forever preferred_lft forever
2: eth0    inet 192.0.2.2/24 brd 192.0.2.255 scope global eth0\       valid_lft forever preferred_lft forever

eth0 の 192.0.2.2/24 は、コンテナ用に作られた仮想的なアドレスではなくホストのアドレスそのものです。コンテナはホストのネットワーク名前空間をそのまま共有しています。

これは CLONE_NEWNET を渡していないことの直接の帰結です。壊れているのではなく、実装していない。この状態が何を意味するのか、実装するとしたら何を作らなければならないのかは 第08章で扱います。

2つめ。PID 名前空間が効いているのに ps がホストを見せる、という現象を自分の目で見て、それを「壊れている」と誤診しないこと。

$ unshare --pid --fork sh -c 'echo "自分の PID: $$"'
自分の PID: 1
$ unshare --pid --fork sh -c 'ps -e --no-headers | wc -l'
87
$ unshare --pid --fork --mount-proc sh -c 'ps -e --no-headers | wc -l'
3

この3行が並んだ状態を見て、「壁は立っている。壁の外に情報源が残っているだけだ」と言えれば、次章の準備は万端です。

まとめ — 次の層へ

この章で、私たちは4枚の壁を立てました。UTS でホスト名の台帳を、PID でプロセス番号の台帳を、MNT でマウント表を、IPC で共有メモリとセマフォの一覧を、それぞれホストから枝分かれさせました。書いたコードは Cloneflags の4行と Unshareflags の1行だけです。仮想マシンも、デーモンも、設定ファイルも要りませんでした。カーネルが元から持っている機能に、正しい名前で頼んだだけです。同時に、使っていない壁が2枚あることも正直に確認しました。ネットワーク（NET）は隔離しておらず、コンテナの中から ip -o addr を打てばホストの eth0 が 192.0.2.2/24 のまま見えます。ユーザ ID（USER）も隔離していないので、中の root は外の root と同じ root です。この2つは、それぞれ第08章と第09章で正面から扱います。

それでも、まだ ps がホストのプロセスを見せます。PID 名前空間は確かに効いていて、echo $$ は 1 と答えるのに、ps -e は 87 行を並べる。ホストの 85 より多い。壁を1枚足せば直る問題ではありませんでした。--mount-proc というオプションを1つ足すだけで答えが 3 に変わったことが、犯人の居場所を教えています。ps はカーネルに直接聞いているのではなく、どこか別の場所を読んでいる。そしてその場所は、私たちがまだホストのものを踏んだままの「地面」の上にある。 視界を区切っただけでは足りなかったのです。立っている足元そのものが、まだホストのものだからです。

次章では、その地面を入れ替えます。pivot_root という、根そのものを挿げ替えるシステムコールを使って、コンテナの / をイメージの中身に取り替えます。素朴に思いつく chroot がなぜ足りないのかを、実際に牢屋を破って見せるところから始めます。そして --mount-proc が何をしていたのか——なぜ /proc を貼り直すと ps の答えが変わるのか——その正体を、次章の最初のページで開けます。謎はもう目の前に置いてあります。あとは蓋を取るだけです。
