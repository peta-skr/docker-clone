はっきり言います。この教材の最大のリスクは、技術ではなく開発環境です。 pivot_root より、namespace より、cgroup より、「特権付きの Linux をどう用意するか」でつまずく人のほうが多い。だからこの章を独立した 1 章として立てました。地面をならし、そのうえで実装を 1 行も書く前に、この環境で何ができて何ができないかを実際にコマンドを打って確かめます。

なぜ環境が最大のリスクなのか

序章で「コンテナはただのプロセスだ」と書きました。裏を返すと、コンテナを作る道具はすべて Linux カーネルの中にあるということです。namespace も、cgroup も、overlayfs も、pivot_root も、カーネルが提供している機能そのものです。ライブラリでも、フレームワークでも、エミュレータでもありません。

ということは、Linux カーネルが無いところでは 1 行も動きません。 Windows でも macOS でも、ネイティブには動きません。「Go はクロスプラットフォームだから」は関係ありません。Go のコードはコンパイルできますが、syscall.Mount を呼んだ相手がいません。

しかも、Linux ならどこでも同じというわけでもありません。ここが厄介です。

  • 特権が要ります。 mount、pivot_root、/sys/fs/cgroup への書き込みは、いずれも CAP_SYS_ADMIN 相当を必要とします。一般ユーザ権限だと EPERM（Operation not permitted）で落ちます。
  • cgroup には v1 と v2 があります。 どちらが有効かは環境で違います。しかも混在している環境（hybrid 構成）もあります。実際、この教材を書いた環境がそれでした。
  • v2 が動いていても、使いたいコントローラが v2 側にあるとは限りません。 これは Step 3 で実際に踏みます。
  • ネットワークの出口が塞がれていることがあります。 会社や学校のネットワークでは、レジストリのレイヤ配信ドメインだけが通らない、ということが実際に起きます。これも踏みました。
この教材が要求するもの ┌────────────────────────────────────────────┐ │ Linux カーネル │ ← 必須。エミュレータ不可 │ + 特権（CAP_SYS_ADMIN 相当） │ ← 必須。無いと全部 EPERM │ + cgroup（v2 または v1） │ ← 04章。どちらでもよい │ + overlayfs │ ← 06章。無ければ縮退できる │ + レジストリへの HTTPS │ ← 05章。無ければ縮退できる └────────────────────────────────────────────┘ 上2つが無いと教材が成立しない。下3つは無くても迂回路がある。 ★どれが有るかを「前提にせず、確かめる」のがこの章の仕事。

この章の姿勢を一言で書くと、「前提にせず、確かめる」です。ドキュメントに「cgroup v2 が使えます」と書いてあっても信じません。実際にディレクトリを作り、値を書き、超過させて殺されるところまで見ます。ここを飛ばすと、第04章まで進んでから「この環境では上限が効かない」と気づくことになります。そのときの手戻りは、この章に費やす 2〜3 時間よりずっと大きくなります。

「Docker を作るために Docker を使う」

さて、Windows や macOS を使っている読者はどうするか。答えは愉快です。Docker で特権付きの Linux コンテナを 1 つ立てて、その中で開発します。

読み返してください。Docker を作るために Docker を使うのです。しかもその中で、さらにコンテナを起動します。三重の入れ子です。

入れ子の構造 ┌─ あなたの PC（Windows / macOS / Linux）────────────┐ │ │ │ ┌─ Docker Desktop の Linux ─────────────────────┐ │ │ │ │ │ │ │ ┌─ 特権コンテナ「dev」（golang:1.24-bookworm）─┐ │ │ │ │ │ ここで開発・ビルド・テストをする │ │ │ │ │ │ │ │ │ │ │ │ ┌─ mydocker が起動するコンテナ ─────────┐ │ │ │ │ │ │ │ 自作ランタイムが作った alpine │ │ │ │ │ │ │ └──────────────────────────────────────┘ │ │ │ │ │ └────────────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────┘ │ └────────────────────────────────────────────────────┘ ★内側の2枚は、どちらも「namespace で区切られたプロセス」でしかない。

ふざけているように見えますが、これは実務でも普通に使われる手です。ビルド環境をコンテナに閉じ込めておくと、「自分の PC では動くのに」問題が起きません。golang:1.24-bookworm という公式イメージを使えば、Go のバージョンまで全員そろいます。

そして教育的にも良い入れ子です。いちばん外側の「dev コンテナ」も、いちばん内側の「mydocker が起動したコンテナ」も、原理はまったく同じだからです。どちらも namespace で区切られ、cgroup で締められ、根を挿げ替えられたプロセスです。違いは、片方を Docker が作り、もう片方をあなたが作る、というだけです。この章の終わりには、外側の箱の中身が全部見えるようになっています。

LINUX メモ · 特権（privileged）とは何を意味するか

Linux では root の権限が capability という単位に細分化されています。CAP_SYS_ADMIN（mount や pivot_root ができる）、CAP_NET_ADMIN（ネットワーク設定ができる）、CAP_SYS_BOOT（再起動できる）など、40 個ほどあります。

通常の Docker コンテナには、この一部しか与えられません。だから docker run ubuntu mount ... は失敗します。--privileged（compose では privileged: true）を付けるとほぼ全部が与えられ、ホストとほぼ同等の権限になります。便利ですが、コンテナの隔離はほぼ無くなります。開発用途に限って使ってください。本番で --privileged を見かけたら、それは事故です。

案A（特権 Docker）と案B（WSL2）

環境の用意には 2 つの道があります。案A を推奨しますが、理由も含めて比べます。

観点案A · 特権 Docker コンテナ（推奨）案B · WSL2 の Linux を直接使う
使える OSWindows / macOS / Linux。Docker が動けばどこでもWindows のみ
用意の手間docker compose run --rm dev の 1 行WSL2 と Go の導入が別途必要
Go のバージョンgolang:1.24-bookworm で固定される自分で入れる。ディストリの都合でずれることがある
cgroupcgroup: host でホストの階層をそのまま使う⚠ 環境によって v2 の有効/無効も、使えるコントローラも違う
実験で汚したときの復旧コンテナを捨てれば終わり自分の Linux が汚れる。rmdir し忘れが残る
ホストへの影響マウントの伝播を切っていれば基本的に無い直接触るので影響が出うる
速度macOS / Windows では VM 越しになるぶん遅いネイティブに近く、速い
⚠ 落とし穴 · 案B は「たぶん v2 が使える」で始めてはいけない

WSL2 の cgroup まわりは、Windows のバージョン、WSL のカーネル、/etc/wsl.conf や .wslconfig の設定によって有効なバージョンもコントローラも変わります。「WSL2 は cgroup v2 です」と書いてある記事を読んで前提にすると、第04章で静かに失敗します。

案B を選ぶなら、この章の Step 3 と Step 4 を必ず自分の環境で走らせてください。 走らせて答えが出れば、それが v1 でも v2 でも問題ありません。この教材の実装は両方に対応しています。困るのは「確かめずに前提にすること」だけです。

なお、すでに Linux マシンを root で使えるなら、案A の中身をそのまま自分の Linux で実行しても構いません。実際、この教材の実測はそうやって取りました。作業していた環境がすでに特権付きの Linux コンテナの中で、unshare も mount -t overlay も mkdir /sys/fs/cgroup/... もそのまま通ったからです。つまり案A が要求する条件を最初から満たしていました。それでも読者が同じ環境を再現できるように、案A そのものである docker-compose.yml を成果物として用意してあります。この章の後半で全文を読みます。

Step 1カーネルと cgroup のバージョンを見る

環境に入ったら、最初にやることは自己紹介です。カーネルは何か、自分は root か、cgroup はどのバージョンか。3 行で済みます。

▸ 動かして確認

この 3 つを打ってください。値はあなたの環境で違って構いません。大事なのは「見た」ことです。

$ uname -r
6.18.5
$ stat -fc %T /sys/fs/cgroup/
tmpfs
$ id
uid=0(root) gid=0(root) groups=0(root)

1 行目、カーネルは 6.18.5。namespace も cgroup v2 も overlayfs も、とっくに入っている世代です。3 行目、uid=0(root)。root です。ここが root でなければ、この先ほぼ全部 EPERM で落ちるので、環境の用意に戻ってください。

問題は 2 行目です。stat -fc %T /sys/fs/cgroup/ が tmpfs を返しました。

LINUX メモ · stat -fc %T が何を答えているか

stat -f は、指定したパスがどのファイルシステムの上に載っているかを調べます。%T はその種別を人間が読める名前で出す指定です。

cgroup v2 が素直に有効な環境では、/sys/fs/cgroup は cgroup2 ファイルシステムそのものなので cgroup2fs と返ります。v1 だけの環境では、/sys/fs/cgroup 自体は単なる置き場（tmpfs）で、その下にコントローラごとのディレクトリが別々にマウントされるので tmpfs と返ります。

つまりこの 1 行は「v2 か、そうでないか」の目安になります。目安です。断定ではありません。その理由を Step 3 で見ます。

素直に読むと「この環境は cgroup v2 ではない」となります。多くの手順書はここで「v2 が使えないので cgroup 機能は諦める」という分岐に倒れます。しかしこれで結論を出すのは早すぎます。 実際この環境は、v1 と v2 が同時に存在する hybrid 構成でした。Step 3 で掘ります。

ついでに、これから使う道具のバージョンも見ておきます。

▸ 動かして確認
$ go version
go version go1.24.7 linux/amd64
$ python3 --version
Python 3.11.15

Go は実装に、Python は疎通実験と E2E テストに使います。Python は標準ライブラリしか使いません。

Step 2namespace が作れるか（生命線）

ここが生命線です。namespace が作れなければ、この教材は 1 章目から成立しません。 逆にここさえ通れば、あとは全部なんとかなります。

いきなり Go を書く必要はありません。unshare というコマンドが最初から入っていて、これが「新しい名前空間を作ってからコマンドを実行する」道具です。まず PID 名前空間だけを作ってみます。

▸ 動かして確認

まず --fork を付けずに。$$ はシェルが自分の PID に展開します。

$ unshare --pid sh -c 'echo "自分の PID: $$"'
自分の PID: 25171

次に --fork を付けて。

$ unshare --pid --fork sh -c 'echo "自分の PID: $$"'
自分の PID: 1

PID が 1 になりました。 名前空間が効いています。そして --fork の有無で結果が変わったことに注目してください。ここが PID 名前空間の独特なところです。

LINUX メモ · PID 名前空間は「次の子」から効く

unshare(CLONE_NEWPID) を呼んだプロセス自身は、新しい PID 名前空間には移りません。移るのはそのあとに作られる子プロセスです。だから --fork 無しだと、呼んだ本人は元の名前空間に残ったままで、PID は 25171 のような普通の値になります。

--fork を付けると unshare が自分で fork し、その子の中でコマンドを実行します。この子は新しい名前空間の最初の住人なので、PID 1 を名乗ります。

この癖は第01章で正面から効いてきます。 Go で名前空間を作るときも「自分を作り直す」必要があり、それが /proc/self/exe による re-exec という手法につながります。今は「PID 名前空間は次の子から効く」とだけ覚えてください。

では、その名前空間の中でプロセス一覧を見てみます。ここでこの章でいちばん驚く結果が出ます。

▸ 動かして確認

PID 名前空間の中で、プロセスの個数を数えます。ホスト側と比べてください。

$ unshare --pid --fork sh -c 'ps -e --no-headers | wc -l'
87
$ ps -e --no-headers | wc -l
85
⚠ 落とし穴 · 隔離したのに、ホストより多い

名前空間の中で 87 個、ホスト側で 85 個。隔離したはずが増えました。「隔離に失敗している」ように見えますが、そうではありません。名前空間は正しく作られています。

犯人は /proc です。ps は /proc 以下のディレクトリを読んでプロセス一覧を作ります。unshare --pid は PID 名前空間を作りますが、/proc は貼り替えません。だから ps はホストの /proc を読み、ホストのプロセスを列挙します。増えているのは unshare 自身と sh が加わったぶんです。

これがこの教材でいちばん重要な壊れ方です。 第03章で正面から扱います。「名前空間が効いていないのではなく、/proc が古い」という切り分けができるかどうかが、この教材の中盤の分かれ目になります。

解決策も先に見ておきます。--mount-proc を付けると、unshare が新しいマウント名前空間の中で /proc を貼り直してくれます。

▸ 動かして確認
$ unshare --pid --fork --mount-proc sh -c 'ps -e --no-headers | wc -l'
3
$ unshare --pid --fork --mount-proc ps aux
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root           1  0.0  0.0   7900  3932 ?        R    22:14   0:00 ps aux

通りました。 ps aux が、自分自身を PID 1 として 1 行だけ表示しています。85 個のプロセスが動いている同じマシンで、です。視界が区切られていることが目で見えました。

→ namespace による隔離は Must のまま進められます。この教材が成立します。

Step 3cgroup の正体を暴く（hybrid 構成の発見）

Step 1 で stat が tmpfs を返しました。素直に v2 を見にいって、そこから掘っていきます。この Step は推理小説のように進みますので、順番に読んでください。

3.1 まず素直に v2 を見る（→ 失敗）

cgroup v2 では、/sys/fs/cgroup/cgroup.controllers に「この階層で使えるコントローラ」が一覧されます。まずそれを読みます。

▸ 動かして確認
$ cat /sys/fs/cgroup/cgroup.controllers
cat: /sys/fs/cgroup/cgroup.controllers: No such file or directory
$ cat /sys/fs/cgroup/cgroup.subtree_control
cat: /sys/fs/cgroup/cgroup.subtree_control: No such file or directory

そもそもファイルがありません。/sys/fs/cgroup が cgroup2fs ではなく tmpfs だからです。ここで「v2 は無い」と結論して先へ進みたくなります。まだです。

3.2 何がマウントされているのか調べる

/sys/fs/cgroup が tmpfs なら、その下に何か置かれているはずです。見ます。

▸ 動かして確認
$ ls -la /sys/fs/cgroup/

drwxr-xr-x 11 root root   0 Aug  2 07:26 ..

コントローラの名前がディレクトリとして並んでいます。そして最後に unified という見慣れないものがあります。マウントの一覧を見ると正体が分かります。

$ mount | grep cgroup

謎が解けました。/sys/fs/cgroup は tmpfs の「置き場」で、その下に v1 のコントローラが 1 つずつ別々にマウントされ、さらに unified/ に cgroup2 も同時にマウントされています。 v1 と v2 が同居しています。これが典型的な hybrid 構成です。

この環境の cgroup 配置 /sys/fs/cgroup/ ← tmpfs（ただの置き場。cgroup ではない） ├─ cpu/ ← cgroup v1 ├─ cpuacct/ ← cgroup v1 ├─ memory/ ← cgroup v1 ★上限を書けるのはここ ├─ devices/ ← cgroup v1 ├─ freezer/ ← cgroup v1 ├─ blkio/ ← cgroup v1 ├─ pids/ ← cgroup v1 └─ unified/ ← cgroup2 v2 ★あるが memory は見えない stat -fc %T /sys/fs/cgroup/ は一番上の tmpfs だけを見ている。 → 「v2 が無い」ようにも「v2 がある」ようにも見えない。だから掘る。

/proc/self/cgroup を読むと、同じことがプロセスの側から見えます。

▸ 動かして確認
$ cat /proc/self/cgroup
7:pids:/
6:blkio:/
5:freezer:/
4:devices:/
3:memory:/process_api/019fc9b0-aeea-7122-9c35-01e1302d5859
2:cpuacct:/
1:cpu:/
0::/

数字付きの行が v1、0::/ の行が v2 です。両方あります。

LINUX メモ · cgroup v1 と v2 の違い、そして hybrid

v1 は「コントローラごとに独立した階層」を作ります。memory の木、cpu の木、pids の木がそれぞれ別にあり、1 つのプロセスが木ごとに違う位置にいられます。柔軟ですが、整合を取るのが大変でした。

v2 は「階層は 1 本（統一階層 / unified hierarchy）、その各ノードで使うコントローラを選ぶ」形に整理されました。ファイル名も memory.max、cpu.max、pids.max と揃っています。

hybrid は移行期の構成で、両方が同時にマウントされています。ここで重要なのが次の一文です — 1 つのコントローラは、v1 か v2 のどちらか一方にしか結び付けられません。 memory を v1 が握っていたら、v2 側からは memory は見えません。次でこれを確かめます。

3.3 v2 側で memory / cpu / pids が使えるか（→ 使えない）

unified/ に cgroup2 があるなら、そこで memory.max を使えばよさそうです。使えるコントローラの一覧を読みます。

▸ 動かして確認
$ cat /sys/fs/cgroup/unified/cgroup.controllers
cpuset hugetlb

念のため、自分で新しい cgroup2 をマウントして同じか確かめます。

$ mkdir -p /tmp/cg2 && mount -t cgroup2 none /tmp/cg2
$ cat /tmp/cg2/cgroup.controllers
cpuset hugetlb
⚠ 落とし穴 · cgroup2 がマウントできても memory が使えるとは限らない

この章でいちばん重要な発見です。 cgroup2 自体はマウントできます。cgroup.controllers も読めます。しかし中身は cpuset hugetlb の 2 つだけで、memory も cpu も pids も v2 側には見えません。

理由は上の LINUX メモのとおりです。この環境では memory / cpu / pids が v1 に取られているので、v2 からは使えません。

怖いのは失敗の仕方です。v2 だけを前提に書いた実装は、この環境では例外を投げません。mkdir は成功し、しかし memory.max というファイルがそもそも作られないので、書き込もうとした時点で初めて気づきます。あるいは、書き込みエラーを握りつぶしていると「上限を設定したつもりで、まったく効いていないコンテナ」ができあがります。静かな失敗です。

Step 4上限は「書けた」ではなく「効く」か

ここがこの章でいちばん大事な Step です。

cat memory.limit_in_bytes が 10485760 を返すことは、上限が効いている証拠にはなりません。 それは「ファイルに値が書かれた」ことの証拠にすぎません。カーネルが本当にその上限で殺しにくるかどうかは、別の話です。

確かめる方法は 1 つしかありません。超過させて、殺されるところを見ることです。10 MB 制限の cgroup に自分を入れて、200 MB 確保しにいく Python を書きます。

/tmp/hog.py
import os
open("/sys/fs/cgroup/memory/smoketest/cgroup.procs","w").write(str(os.getpid()))
b = bytearray()
for i in range(200):
    b += bytearray(1024*1024)
print("allocated", len(b))

ポイントは 2 つです。①自分の PID を cgroup.procs に書くこと。これをしないと、いくら上限を設定しても自分には関係ありません。②最後に print すること。上限が効いていれば、この行には到達しません。

▸ 動かして確認

exit=137
$ cat /sys/fs/cgroup/memory/smoketest/memory.failcnt
37

効きました。 読み取るべきことが 3 つあります。

  • allocated ... が印字されていません。 200 MB 確保しきる前に殺されました。
  • Killed / exit=137。 137 は 128 + 9、つまり SIGKILL で殺されたという意味です。カーネルの OOM killer が仕事をしました。お願いではなく強制である、というのがこの数字です。
  • memory.failcnt が 37。 上限に当たった回数がカーネル側にも記録されています。プロセスの外側からも「効いた」ことが確認できます。
LINUX メモ · 終了コード 137 の読み方

シグナルで終了したプロセスの終了コードは、シェルの慣習で 128 + シグナル番号になります。SIGKILL は 9 番なので 128 + 9 = 137。SIGTERM（15 番）なら 143 です。

この 137 は第04章でもう一度出てきます。mydocker run --memory 10m で起動したコンテナが上限を超えると、mydocker の終了コードも 137 になります。E2E テストは「設定値が読めること」ではなく「exit 137 になること」で合格を判定します。 同じ思想です。

⚠ 落とし穴 · cat が期待値を返しても、効いている証明にはならない

もう一度書きます。cat memory.limit_in_bytes が 10485760 を返しても、それは値が書かれたことの証拠にすぎません。

実際、次のどれか 1 つでも欠けていると、値は読めるのに上限は効きません。①cgroup.procs に PID を書き忘れている／②親の cgroup で subtree_control にコントローラを有効化していない（v2）／③そもそもそのコントローラが別バージョンに取られている（Step 3.3）。

だから第04章の実装でも、E2E テストでも、この教材は一貫して「超過させて殺されるか」で判定します。設定値の読み返しでは済ませません。

→ cgroup による資源制限は Must のまま進められます。ただし、この環境では v1 で。

⚠ 落とし穴 · umount の成否を確かめずに rm -rf を続けてはいけない

これはこの教材で最も危険な操作です。順に説明します。

/tmp/ovl/merged には overlay がマウントされています。もし umount が何らかの理由で失敗し（プロセスがそのディレクトリを開いたまま、など）、それに気づかずに rm -rf /tmp/ovl を実行すると、マウント越しに lower の実体まで削除されます。overlay の merged は下層の中身が「見えている」だけで、削除操作は下層の実ファイルに届くからです。

今回は /tmp の実験用ディレクトリなので笑い話で済みます。しかし第06章以降では、lowerdir にダウンロードして展開したイメージのレイヤが入ります。同じことをすれば、共有しているレイヤのキャッシュが消えます。他のコンテナも巻き添えになります。

ですから、umount したら mountpoint -q で外れたことを確認し、外れていたときだけ削除に進みます。 この「確認してから消す」という型は、第06章の Unmount と第07章の rm にそのまま実装されています。

▸ 動かして確認

overlay の後片付け。アンマウントが成功したときだけ削除します。

$ umount /tmp/ovl/merged
$ if mountpoint -q /tmp/ovl/merged; then
>     echo "!! まだマウントされている。削除しない。"
> else
>     rm -rf /tmp/ovl
> fi

⚠ 落とし穴 · cgroup のディレクトリは rm -rf では消えない

/sys/fs/cgroup の下にあるものは、普通のディレクトリのように見えて、カーネルが管理している仮想的なファイルシステムです。中のファイル（memory.limit_in_bytes など）は個別に削除できません。だから rm -rf は「中のファイルが消せない」と言って失敗します。

正しくは rmdir です。ディレクトリを直接消すと、カーネルがその cgroup を解体します。中のファイルは自動的に消えます。

そして rmdir は、その cgroup にまだプロセスが residing していると EBUSY で失敗します。これは正しい挙動です。「まだ誰か使っている cgroup を壊すな」というカーネルの主張です。第07章の後片付け実装では、この EBUSY を正面から扱います。

▸ 動かして確認
$ rmdir /sys/fs/cgroup/unified/smoketest
$ rmdir /sys/fs/cgroup/memory/smoketest
$ rmdir /sys/fs/cgroup/pids/smoketest

今回、memory.failcnt が 37 まで上がっていた smoketest は、中のプロセスが既に OOM で死んでいたので rmdir が素直に成功しました。もしプロセスが生きていれば EBUSY になります。

順に見ます。

image: golang:1.24-bookworm

Go の公式イメージです。Debian bookworm ベースで、Go 1.24 が入っています。自分で Go を入れる手間が消え、全員のバージョンが揃います。 実測環境の go version は go1.24.7 linux/amd64 でした。go.mod の go 1.24 と合っています。

privileged: true — 無いと全部 EPERM

ここが要です。 これが無いと、この章の実験のほとんどが EPERM（Operation not permitted）で落ちます。具体的には mount も、pivot_root も、/sys/fs/cgroup への書き込みも、unshare の一部も通りません。

通常の Docker コンテナには capability の一部しか与えられていません。privileged: true はほぼ全部を与えます。ホストとほぼ同じ権限です。裏を返すとコンテナとしての隔離はほとんど無くなります。開発用途に限って使ってください。

GO メモ · EPERM に出会ったときの読み方

Go で syscall.Mount(...) が失敗すると、返ってくるエラーは operation not permitted という文字列になります。これが EPERM です。

この教材で EPERM が出たら、疑うべきはコードではなく権限です。順に確認してください — ①id で root か／②privileged: true が効いているか（docker compose の設定を変えたあとコンテナを作り直したか）／③そもそもホストが Linux か。この 3 つで大半は解決します。EPERM は「コードが間違っている」ではなく「そもそも許されていない」というサインです。

cgroup: host — 書き込める cgroup 階層を得る

cgroup の階層をホストと共有し、書き込み可能にする指定です。これが無いと、/sys/fs/cgroup が読み取り専用でマウントされ、その配下にディレクトリを作れません。Step 3.4 でやった mkdir /sys/fs/cgroup/memory/smoketest が通らなくなります。

ここは第04章に直結します。mydocker がコンテナごとに cgroup を作れなければ、資源の上限はかけられません。

volumes — リポジトリ全体と、状態の置き場

2 つマウントしています。

  • ../..:/work — リポジトリ全体をコンテナの /work にマウントします。src/ だけでなく docs/ も見えます。ホスト側のエディタで編集した内容が、そのままコンテナの中に反映されます。
  • mydocker-state:/var/lib/mydocker — 名前付きボリュームです。mydocker が状態（展開済みレイヤ、マニフェストのキャッシュ、実行中コンテナの記録、overlay の作業ディレクトリ）を置く場所を、ホストのファイルシステムから切り離しています。

tmpfs: /run — マウントの伝播を private にする

コンテナの中で行ったマウント操作が、ホスト側へ伝わってしまうことがあります。これがマウントの伝播（propagation）です。既定の shared のままだと、コンテナ内のマウントがホストへ漏れます。漏れると、コンテナを消してもホストにマウントが残ります。

この伝播という性質は、第03章で pivot_root をやるときに正面から扱います。MS_PRIVATE|MS_REC で伝播を切ることが、根を挿げ替える 5 手順の 1 番目になります。今は「マウントには伝わる性質があり、切らないとホストを汚す」とだけ覚えてください。

environment: GOCACHE — 毎回フルビルドを避ける

GOCACHE=/var/lib/mydocker/.gocache。Go のビルドキャッシュの置き場を、名前付きボリュームの中に指定しています。

docker compose run --rm dev は --rm なので、シェルを抜けるとコンテナが消えます。キャッシュがコンテナの中に置かれていると、毎回一緒に消えて、毎回フルビルドになります。ボリュームに置けば残ります。地味ですが、この教材のように何十回もビルドし直す作業では効きます。

GO メモ · go.mod と require ブロック

go.mod は Go のモジュール定義ファイルで、module（このモジュールの名前）、go（言語バージョン）、require（依存する外部モジュールとそのバージョン）を書きます。

外部パッケージを 1 つでも import して go mod tidy を打つと、require ブロックが自動的に生えます。逆に言えば、require が空のままだということは、標準ライブラリ以外を 1 つも import していないことの機械的な証明になります。人間の宣言ではなく、ツールが保証してくれます。

おまけとして、go.sum も要りませんし、go build がネットワーク無しで通ります。第00章でビルドを試すとき、外部から何もダウンロードされないことを確かめてみてください。

なぜここまで縛るのか。序章でも触れましたが、もう一度書きます。ライブラリを使うと、いちばん学びたい部分がライブラリの中に隠れるからです。libcontainer を import すればコンテナは 20 行で起動しますが、その 20 行を書いても namespace のことは何も分かりません。分かるのは libcontainer の API だけです。

そして実際、標準ライブラリだけで足ります。使うのは syscall（名前空間とマウント）、os/exec（子プロセスの起動）、net/http（レジストリ通信）、archive/tar と compress/gzip（レイヤの展開）、encoding/json（マニフェストの解析）。この 6 つです。無理をして避けているのではなく、素直に書いたら要らなかった、というのが実態です。

つまずき FAQ

Docker Desktop が入っていません。他に方法はありますか?

あります。Linux マシン（クラウドの VM でも構いません）に root で入れるなら、docker-compose.yml の中身を読み替えて直接その Linux で作業できます。必要なのは「Linux + 特権」だけで、Docker は必須ではありません。

Windows なら WSL2（案B）も選べます。ただし比較表と落とし穴ボックスに書いたとおり、cgroup の構成が環境ごとに違うので、Step 3 と Step 4 は必ず自分で走らせてください。答えが v1 でも v2 でも問題ありません。困るのは、確かめずに前提にすることだけです。

mkdir /sys/fs/cgroup/memory/smoketest が Permission denied になります。

3 つ確認してください。

①root ですか? id で uid=0(root) を確認します。②privileged: true は効いていますか? compose ファイルを編集したあとにコンテナを作り直していないと、古い設定のまま動いています。一度抜けて run --rm dev し直してください。③cgroup: host は付いていますか? これが無いと /sys/fs/cgroup が読み取り専用でマウントされます。mount | grep cgroup の出力に ro, が入っていたらこれです。

stat -fc %T /sys/fs/cgroup/ が cgroup2fs でした。この教材のとおりに進みませんが大丈夫ですか?

まったく問題ありません。むしろ素直な環境です。cgroup2fs なら、/sys/fs/cgroup/cgroup.controllers が読めるはずなので、そこに memory cpu pids が並んでいるか確認してください。並んでいれば v2 でそのまま進めます。

その場合、Step 3.4 の代わりに mkdir /sys/fs/cgroup/smoketest して memory.max に 10485760 を書きます。Step 4（超過させて殺されるか）は必ずやってください。 v2 でも「親の cgroup.subtree_control に memory を有効化していないと子で使えない」という別の落とし穴があるので、効くかどうかは確かめる必要があります。

hybrid 構成って、そんなに珍しくないんですか? 自分の環境も気にしたほうがいい?

珍しくありません。cgroup v2 は 2016 年に入りましたが、v1 を前提にした既存のソフトウェアが多かったので、長い移行期間がありました。その名残で、v1 と v2 が同時にマウントされている環境は今でも普通に見かけます。特にクラウドの実行基盤やコンテナの中のコンテナでは、よく起きます。

気にしたほうがいいかというと、「気にする」のではなく「確かめる」のが答えです。mount | grep cgroup を打てば 3 秒で分かります。この教材の実装が起動時に自動判定しているのも、同じ理由です。

memory.failcnt が 37 でした。この数字に意味はありますか?

「上限に当たった回数」です。今回は 1 MB ずつ確保していったので、10 MB の壁に何度もぶつかりながら、カーネルがページを回収したり再試行したりして、37 回目あたりで諦めて SIGKILL を投げた、という経緯を表しています。

値そのものに深い意味はありません。大事なのは「0 ではない」ことです。 0 なら一度も上限に触れていない、つまり上限が効いていないか、そもそも超過していないということになります。プロセスが死んだ理由が本当に cgroup なのかを、プロセスの外側から裏取りできる数字です。

後片付けの節、そんなに大事ですか? /tmp なんだから残っても困りません。

この章の /tmp は困りません。困るのは第06章以降です。

そこでは lowerdir にダウンロードして展開したレイヤが入ります。umount の成否を確かめずに rm -rf すると、マウント越しに共有レイヤの実体が消えます。他のコンテナも巻き添えです。そして厄介なことに、この事故はエラーを出しません。次に別のコンテナを起動したときに、原因不明の「ファイルが無い」で気づきます。

もう 1 つ。第07章の E2E テストは「10 回起動しても overlay のマウント数が増えないこと（前 0 件 → 後 0 件）」「テスト全体を通してホストのマウント数が元に戻ること（開始 22 → 終了 22）」を実数で検査します。後片付けは、この教材では検査対象の機能そのものです。

Step 6 でレイヤの取得だけが失敗します。ネットワークの問題ですか?

おそらくそうです。この教材を書いた環境でも同じことが起きました。トークンもマニフェストも取れるのに、レイヤ配信ドメイン production.cloudfront.docker.com への CONNECT が 403 で弾かれました。組織の egress ポリシーです。

切り分け方は簡単で、トークンとマニフェストが取れているかどうかを見ます。そこまで取れていれば、認証もレジストリ API も理解できているということなので、あとは届くレジストリに替えるだけです。この教材の実測は mirror.gcr.io/library/alpine で取りました。中身は同一で、同じ digest sha256:79ff19e9084a… を指します。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。答えを見て「知っていた」と思うかではなく、見る前に言葉にできたかで判定してください。

Q1. stat -fc %T /sys/fs/cgroup/ が tmpfs を返したとき、「この環境に cgroup v2 は無い」と結論してよいですか?

いけません。 それは /sys/fs/cgroup という 1 点が tmpfs だという事実にすぎません。hybrid 構成では、その tmpfs の下に v1 のコントローラが個別にマウントされ、さらに unified/ に cgroup2 も同時にマウントされます。

結論を出すには mount | grep cgroup まで見る必要があります。実際、この教材の環境では cgroup2 on /sys/fs/cgroup/unified type cgroup2 という行がちゃんとありました。1 つの指標で断定しない、というのがこの Step の教訓です。

Q2. cgroup2 がマウントできているのに memory.max が使えませんでした。なぜですか?

1 つのコントローラは v1 か v2 のどちらか一方にしか結び付けられないからです。この環境では memory / cpu / pids が v1 に取られていたので、v2 側の cgroup.controllers には cpuset hugetlb しか出ませんでした。

確かめ方は cat <v2のマウント先>/cgroup.controllers です。自分で新しく mount -t cgroup2 none /tmp/cg2 しても結果は同じでした。マウントの問題ではなく、コントローラの所属の問題だからです。

Q3. cat memory.limit_in_bytes が 10485760 を返しました。上限は効いていますか?

分かりません。 それは「ファイルに値が書かれた」ことの証拠でしかありません。

効いていることを確かめるには、超過させて殺されるところを見ます。この章では 10 MB 制限の中で 200 MB 確保しにいって、Killed / exit=137（= 128 + SIGKILL）を得ました。memory.failcnt も 37 に増えていました。

加えて、cgroup.procs に PID を書いていなければ、誰にも効いていません。ディレクトリを作って値を書くのは準備であって、適用ではありません。

Q4. umount のあと mountpoint -q で確認せずに rm -rf すると何が起きますか?

umount が失敗していた場合、マウント越しに lower の実体まで削除されます。overlay の merged は下層の中身が見えているだけなので、削除操作は下層の実ファイルに届きます。

第06章以降の lowerdir にはダウンロードして展開したレイヤが入るので、これは共有キャッシュの破壊を意味します。しかも即座にはエラーになりません。次に別のコンテナを起動したときに、原因不明の「ファイルが無い」として現れます。

だから型は「umount → mountpoint -q で確認 → 外れていたときだけ削除」です。外れていないなら、消さずに止まるほうが安全です。

Q5. cgroup のディレクトリを rm -rf で消してはいけないのはなぜですか? EBUSY が返ったらどうしますか?

cgroup のディレクトリはカーネルが管理する仮想ファイルシステムで、中のファイル（memory.limit_in_bytes など）を個別に削除することはできません。だから rm -rf は失敗します。正しくは rmdir で、ディレクトリを消すとカーネルがその cgroup を解体します。

EBUSY が返るのは、その cgroup にまだプロセスが入っているときです。これは正しい挙動なので、力ずくで消そうとしてはいけません。中のプロセスを終了させる（あるいは終了を待つ）のが正解です。第07章の rm 実装では、実行中のコンテナを消そうとすると mydocker: コンテナ … はまだ実行中です。先に終了させてください と拒否する形になっています。

Q6. docker-compose.yml から privileged: true を消すと、最初にどこで壊れますか?

ほぼ全部で壊れますが、この章の順番でいうと Step 3.4 の mkdir /sys/fs/cgroup/memory/smoketest か、Step 5 の mount -t overlay が最初です。どちらも EPERM（Operation not permitted）になります。

実装を書き始めてからだと、第02章の名前空間生成、第03章の mount と pivot_root、第04章の cgroup 書き込みが軒並み落ちます。EPERM を見たら、まずコードではなく権限を疑ってください。

Q7. go.mod の require が空であることは、何を保証していますか?

標準ライブラリ以外を 1 つも import していないことを、機械的に保証しています。外部パッケージを 1 つでも使えば go mod tidy で require が生えるので、空のままだということは使っていないということです。人間の宣言ではなく、ツールによる証明です。

教材としての意味は、「この教材のコードは全部読める」ということです。libcontainer の中で何が起きているかを追う必要がありません。目の前の数百行が全部です。おまけに、go build がネットワーク無しで通ります。
