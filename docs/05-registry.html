Registry— docker pull の中身を開ける

イメージを取ってくる

ここまでの章で、コンテナを閉じ込める箱はほぼ出来ました。ただ、その箱に入れる中身を、私たちはまだ手で用意していません。docker pull と打つと何かが降ってくる、あの「何か」の正体をこの章で開けます。docker は一切呼びません。使うのは net/http だけです。

◈ この章のゴール

internal/image/registry.go をほぼ全文読み切り、Docker Registry HTTP API v2 の3回のやりとり（トークン → マニフェスト → レイヤ）を自分の言葉で説明できるようになる。途中で必ず踏む4つの罠（Accept 忘れ・マニフェストリスト・attestation・取得回数制限）を、踏む前に見分けられるようになる。仕上げに、mydocker pull で alpine を自力で取ってきて、2回目がネットワークに触らないことを確認する。

docker pull は、実は HTTP を3回叩いているだけ

最初に身も蓋もない結論を置いておきます。この章を読み終わったあなたが持ち帰るのは、次の一文です。

イメージとは、tar.gz の列と JSON である。internal/image/registry.go の冒頭コメント

それ以上でも以下でもありません。docker pull alpine と打ったとき、Docker が裏でやっているのは HTTP GET を3回（正確にはもう少し多いですが、種類としては3つ）です。魔法の独自プロトコルもバイナリの秘密の握手もありません。ブラウザで URL を開くのと同じ HTTP です。

docker pull alpine の中身 — HTTP を3種類叩くだけ ① トークン ② マニフェスト ③ レイヤ（blob） auth.docker.io registry-1.docker.io registry-1.docker.io /token?scope=repository: /v2/library/alpine /v2/library/alpine library/alpine:pull /manifests/latest /blobs/sha256:55af… │ │ │ │ JWT が返る │ JSON の目録が返る │ tar.gz が返る └──────► Authorization: Bearer eyJhbGci… ─────────────────►┘ ①で得た鍵を、②と③の全部のリクエストに付ける。それだけ。

ここで「なんだ、簡単じゃないか」と思ったなら、それは半分正しくて半分は罠です。3回の GET のあいだに、初見では必ず引っかかる段差が4つあります。この章はその4つを順番に踏み抜いていく章でもあります。先に名前だけ出しておきます。Accept ヘッダ、マニフェストリスト、attestation、取得回数制限。どれも「なぜか動かない」という形でやってきます。

イメージの中身は、二段の目録になっている

docker images で見える「alpine:latest」という1個のものは、実際には目録の目録から始まります。latest というタグを引くと、まず「どの CPU アーキテクチャ向けの版がありますか」という一覧が返ってきて、その中から自分に合う1件を選んで、もう一度取りに行く。この二段構造が、初見で最も戸惑うところです。

マニフェストは二段になっている GET /v2/library/alpine/manifests/latest └─ マニフェストリスト（OCI インデックス）… layers が無い! ├─ platform linux/amd64 digest 79ff19e9084a… ← これを選ぶ ├─ platform unknown/unknown attestation-manifest ← 署名の付随物。罠 └─ …（他のアーキテクチャ向けの版が並ぶ） │ 選んだ digest で、もう一度 GET ▼ GET /v2/library/alpine/manifests/sha256:79ff19e9084a… └─ マニフェスト本体 ├─ config digest d529dd0c6e55… 611 バイト → Env / Cmd / Entrypoint └─ layers[0] digest 55afa1ecc21d… 3.67 MiB → tar.gz の実体（1枚だけ）

alpine の場合、下の段まで降りてようやく layers が見えます。そして中身はたった1枚の tar.gz です。圧縮 3.67 MiB、展開すると 8.7 MB・516 ファイル。これが「Linux ディストリビューション1個ぶん」です。

取ってきたものを、どこに置くか

降ってきた tar.gz を毎回どこかに散らかすわけにはいきません。置き場を先に決めます。/var/lib/mydocker の下に3つのディレクトリを掘ります。ここには後で効いてくる仕掛けが1つ埋まっているので、図をよく見てください。

ローカルの置き場 /var/lib/mydocker /var/lib/mydocker/ ├─ manifests/ │ └─ mirror.gcr.io_library_alpine_latest.json ← 参照名 → 目録 ├─ configs/ │ └─ sha256_d529dd0c6e55….json ← Env / Cmd / Entrypoint └─ layers/ ├─ sha256_55afa1ecc21d…/ ← 展開済みの中身（516 ファイル） └─ sha256_55afa1ecc21d….complete ← 「最後まで終わった」印 ★ layers/ の名前は digest（＝中身の SHA-256）そのもの。 名前が同じなら中身も同じ。だから存在確認だけでキャッシュとして成立する。

ディレクトリ名がハッシュ値になっているのが仕掛けです。ふつうファイル名は人間が付けますが、ここでは中身がファイル名を決めます。この性質を content-addressable（内容アドレス指定）と呼びます。後の Step 7 でじっくり効いてきます。

Step 1まず curl で手で叩く — 匿名なのにトークンが要る

コードを書く前に、手で叩きます。相手が何を返してくるか分からないまま Go を書き始めると、必ず「どこで間違えたか分からない」状態になります。まず curl です。

素朴に考えれば、公開イメージなのだから https://registry-1.docker.io/v2/library/alpine/manifests/latest をそのまま GET すれば取れそうです。ところが取れません。401 Unauthorized が返ります。ログインしていないどころか、アカウントすら要らない公開イメージなのに、です。

Docker Hub の作法はこうです。匿名にも匿名用のトークンを発行する。認証サーバに「このリポジトリを pull したい」と申告すると、その用途に限った鍵をくれます。ユーザ名もパスワードも要りません。ただ「くださいと言う」手続きだけが要ります。

▸ 動かして確認

認証サーバに、alpine を pull する権限だけを申告してみます。head -c 200 で先頭 200 バイトだけ見ます（全体は 2658 文字あります）。

$ curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/alpine:pull" | head -c 200
{"token":"eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsIng1YyI6WyJNSUlFRmpDQ0F2NmdBd0lCQWdJVU9yTFd5UVpxMmFuZXd6WnhYN1JLbHQ3bDVUTXdEUVlKS29aSWh2Y05BUUVMQlFBd2dZWXhDekFKQmdOVkJBWVRBbFZUTVJNd0VRWURWUVFJRXdwRFlXeH

返ってきた文字列を見てください。eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCI… で始まっています。この eyJ という始まりは JWT（JSON Web Token）の目印です。JWT は「JSON を Base64 で符号化して署名を付けたもの」なので、頭を Base64 で戻すと {"alg":"RS256","typ":"JWT",… という JSON が出てきます。中身が読めるのがポイントで、暗号化されているのではなく署名されているだけです。書き換えると署名が合わなくなるので偽造はできませんが、覗くことはできます。

URL のクエリを分解しておきます。

  • service=registry.docker.io — 「どのサービス向けの鍵か」。この鍵は Docker Hub のレジストリでしか通りません
  • scope=repository:library/alpine:pull — 「library/alpine というリポジトリを pull する権限だけください」。書式は repository:<リポジトリ名>:<動作>

つまりこのトークンは、alpine を読むことしかできません。他のイメージを取ろうとすれば拒否されますし、push もできません。用途を申告した本人が、自分の権限を最小に絞っている形です。この形式は Docker 独自ではなく、OCI Distribution Specification として標準化されていて、GitHub の ghcr.io でも Google の mirror.gcr.io でも同じ考え方が通じます（取りに行く URL だけが違い、それは Step 9 で解決します）。

ここまでを Go にします。

internal/image/registry.go
const (
	defaultRegistry = "registry-1.docker.io"
	dockerAuthURL   = "https://auth.docker.io/token"
	dockerService   = "registry.docker.io"
)
internal/image/registry.go
// fetchToken は pull 用のトークンを取る。
//
// Docker Hub は決まった URL で取れる。それ以外のレジストリは、まず /v2/ を叩いて
// 401 と一緒に返ってくる WWW-Authenticate ヘッダ（＝どこへ取りに行けばよいかの案内）を読む。
func (s *Store) fetchToken(client *http.Client, ref Ref) (string, error) {
	authURL := ""
	if ref.Registry == defaultRegistry {
		authURL = fmt.Sprintf("%s?service=%s&scope=repository:%s:pull", dockerAuthURL, dockerService, ref.Repository)
	} else {
		realm, service, err := discoverAuth(client, ref)
		if err != nil {
			return "", err
		}
		if realm == "" {
			return "", nil // 認証不要のレジストリ
		}
		authURL = fmt.Sprintf("%s?scope=repository:%s:pull", realm, ref.Repository)
		if service != "" {
			authURL += "&service=" + service
		}
	}

	resp, err := client.Get(authURL)
	if err != nil {
		return "", fmt.Errorf("トークンの取得に失敗しました: %w", err)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		body, _ := io.ReadAll(io.LimitReader(resp.Body, 512))
		return "", fmt.Errorf("トークンの取得に失敗しました (HTTP %d): %s", resp.StatusCode, strings.TrimSpace(string(body)))
	}
	var tok struct {
		Token       string `json:"token"`
		AccessToken string `json:"access_token"`
	}
	if err := json.NewDecoder(resp.Body).Decode(&tok); err != nil {
		return "", fmt.Errorf("トークンの JSON を読めませんでした: %w", err)
	}
	if tok.Token != "" {
		return tok.Token, nil
	}
	return tok.AccessToken, nil
}

上から追います。Docker Hub なら URL は決め打ちで組み立てます。さっき curl で叩いたのと一字一句同じ URL です。else の側は他のレジストリ向けで、これは Step 9 まで置いておきます（discoverAuth が「どこへ取りに行けばよいか」を調べてくれます）。

面白いのは最後の6行です。トークンの入っているフィールド名がレジストリによって違います。Docker Hub は token、他所は access_token を使うことがあります。どちらも受けられるように構造体に両方書いておいて、token が空なら access_token を返す。仕様の揺れをここで吸収しています。

io.LimitReader(resp.Body, 512) も地味ですが大事です。エラー時に相手が何を返してくるか分かりません。HTML のエラーページが数百 KB 返ってくることもあります。それを全部エラーメッセージに載せると端末が埋まるので、先頭 512 バイトで打ち切る。エラー処理でこそ、相手を信用しないコードを書きます。

GO メモ · net/http のヘッダと 401 の扱い

Go の net/http は、HTTP のステータスコードをエラーとして扱いません。404 でも 401 でも 500 でも、通信そのものが成立していれば err は nil です。ここが最初にハマるところで、client.Get() のエラーだけ見ていると「取れた気になって空の JSON をパースする」ことになります。だから必ず resp.StatusCode を自分で見ます。err != nil は「相手に届かなかった」、StatusCode != 200 は「届いたが断られた」。この2つは別の事故です。

ヘッダは req.Header.Set("Authorization", "Bearer "+token) のように付けます。Set は同名ヘッダを置き換え、Add は追加します。認証は必ず Set です。なお client.Get() はヘッダを付けられない簡易版なので、ヘッダが要るときは http.NewRequest でリクエストを組み立ててから client.Do(req) を呼びます。この章のコードで両方が出てくるのはそのためです。

defer resp.Body.Close() は必ず書きます。忘れると接続が返却されず、繰り返すうちにファイルディスクリプタを食い潰します。&tok の & はアドレス演算子で、Decode に「ここへ書き込んでくれ」と渡しています。

Step 2マニフェストを取る — Accept ヘッダを忘れない

鍵は手に入りました。次は目録です。URL の形は素直で、https://<レジストリ>/v2/<リポジトリ>/manifests/<タグまたは digest> です。alpine なら https://registry-1.docker.io/v2/library/alpine/manifests/latest。ここに Authorization: Bearer … を付けて GET します。

ここで最初の大きな段差が来ます。Accept ヘッダを付けないと、古い形式が返ってきます。

⚠ 落とし穴 · Accept を付けないと schema 1 が返ってくる

レジストリは「相手が読める形式」を Accept ヘッダで判断します。付けないと、いちばん古くて誰でも読める形式——manifest schema 1——を返してきます。schema 1 には layers 配列が存在しません（代わりに fsLayers という別物が入っています）。

すると何が起きるか。JSON のパースは成功します。Go の encoding/json は知らないフィールドを黙って捨て、無いフィールドはゼロ値のままにするからです。エラーは出ません。ただ len(man.Layers) == 0 になる。「200 が返ってきて、JSON も読めて、なぜかレイヤだけが0枚」という、いちばん原因の見えない詰まり方をします。

だから Accept を明示します。しかも1つではなく、4つ並べます。

internal/image/registry.go
// acceptManifest は Accept ヘッダに並べるメディアタイプ。
//
// ⚠ これを付けないと、レジストリは古い形式（schema 1）を返してくる。
// schema 1 には layers 配列が無いので「取れた JSON に layers が無い」と悩むことになる。
var acceptManifest = strings.Join([]string{
	"application/vnd.docker.distribution.manifest.v2+json",
	"application/vnd.docker.distribution.manifest.list.v2+json",
	"application/vnd.oci.image.manifest.v1+json",
	"application/vnd.oci.image.index.v1+json",
}, ",")

4つある理由は、2×2 だからです。

単体（マニフェスト本体）リスト（インデックス）
Docker 形式…docker.distribution.manifest.v2+json…docker.distribution.manifest.list.v2+json
OCI 形式…oci.image.manifest.v1+json…oci.image.index.v1+json

縦軸が方言です。Docker が先に作った形式（vnd.docker.…）と、それを業界標準として整理し直した OCI 形式（vnd.oci.…）。中身の構造はほぼ同じで、名前だけが違います。イメージがいつビルドされたかで、どちらが返るかが変わります。実際、この章で扱う alpine は OCI 形式で返ってきます。

横軸が段です。単体のマニフェスト本体なのか、アーキテクチャ別の入り口であるリストなのか。タグを引くと、たいていリストが返ってきます。

この4つを全部「読めます」と申告しておけば、相手がどれを持っていても最新の形式で返してくれます。strings.Join でカンマ区切りにしているのは、HTTP の Accept ヘッダがカンマ区切りだからです。

取得の本体はこうです。

internal/image/registry.go
func (s *Store) fetchManifest(client *http.Client, ref Ref, token, reference string) (*manifest, error) {
	url := fmt.Sprintf("https://%s/v2/%s/manifests/%s", ref.Registry, ref.Repository, reference)
	body, err := s.get(client, url, token, acceptManifest)
	if err != nil {
		return nil, err
	}
	var man manifest
	if err := json.Unmarshal(body, &man); err != nil {
		return nil, fmt.Errorf("マニフェストの JSON を読めませんでした: %w", err)
	}
	return &man, nil
}

引数の reference に注目してください。タグでも digest でも同じ関数で取れます。URL の最後に入るのが latest なのか sha256:79ff19e9084a… なのかの違いだけで、レジストリはどちらも受け付けます。この設計のおかげで、Step 3 で「リストだったのでもう一度取り直す」処理が同じ関数の呼び直しで済みます。

実際の HTTP は s.get という共通の小道具に任せています。ここに、この章で踏む最後の罠の対策も入っています。

internal/image/registry.go
func (s *Store) get(client *http.Client, url, token, accept string) ([]byte, error) {
	req, _ := http.NewRequest(http.MethodGet, url, nil)
	if token != "" {
		req.Header.Set("Authorization", "Bearer "+token)
	}
	req.Header.Set("Accept", accept)
	resp, err := client.Do(req)
	if err != nil {
		return nil, fmt.Errorf("%s の取得に失敗しました: %w", url, err)
	}
	defer resp.Body.Close()
	if resp.StatusCode == http.StatusNotFound {
		return nil, fmt.Errorf("見つかりませんでした (HTTP 404): %s", url)
	}
	if resp.StatusCode == http.StatusTooManyRequests {
		return nil, fmt.Errorf("取得回数の上限に達しました (HTTP 429)。しばらく待つか、キャッシュ済みのイメージを使ってください")
	}
	if resp.StatusCode != http.StatusOK {
		body, _ := io.ReadAll(io.LimitReader(resp.Body, 512))
		return nil, fmt.Errorf("取得に失敗しました (HTTP %d): %s", resp.StatusCode, strings.TrimSpace(string(body)))
	}
	return io.ReadAll(resp.Body)
}

ステータスコードを3段階で見ています。404 は「そんなイメージは無い」、429 は「引きすぎ」（Step 7 で詳しく）、その他の非 200 は本文を 512 バイトだけ添えて返す。エラーメッセージを読んだだけで次に何をすればいいか分かることを狙っています。「取得に失敗しました」だけのメッセージは、あとで自分を苦しめます。

token != "" のときだけ Authorization を付けているのも意図があります。認証を要求しないレジストリでは fetchToken が空文字列を返します。そのとき空の Bearer ヘッダを付けると、逆に断られるレジストリがあります。付けないほうが通るケースがあるのです。

Step 3layers が無い! — 返ってきたのはリストだった

さて、Accept も付けた、トークンも付けた、200 も返ってきた。JSON も読めた。それなのに layers が空です。ここが二番目の段差です。

実際に返ってきたものを見てください。これは実測した応答の先頭です（長いので途中で切れています）。

なぜこんな二段構えなのか。理由はCPU アーキテクチャです。alpine:latest という1つのタグが、x86_64（amd64）でも ARM（arm64）でも動いてほしい。しかし中身のバイナリはアーキテクチャごとに完全に別物です。そこで「タグ → アーキテクチャ別マニフェストの一覧」という段を1つ挟み、取りに来た側が自分に合う版を選ぶことにした。あなたのラップトップが Apple Silicon でも、サーバが Intel でも、同じ docker pull alpine で正しいものが降ってくるのは、この段のおかげです。

この二種類の JSON を、Go でどう受けるか。ここに面白い工夫があります。

internal/image/registry.go
// descriptor はマニフェスト中の1項目（レイヤや設定への参照）。
type descriptor struct {
	MediaType string `json:"mediaType"`
	Digest    string `json:"digest"`
	Size      int64  `json:"size"`
	Platform  *struct {
		Architecture string `json:"architecture"`
		OS           string `json:"os"`
	} `json:"platform,omitempty"`
}

// manifest は「マニフェスト」と「マニフェストリスト（インデックス）」の両方を受けられる形。
// manifests が非 nil ならリスト、layers が非 nil なら本体である。
type manifest struct {
	SchemaVersion int          `json:"schemaVersion"`
	MediaType     string       `json:"mediaType"`
	Manifests     []descriptor `json:"manifests"` // インデックスのとき
	Config        descriptor   `json:"config"`    // 本体のとき
	Layers        []descriptor `json:"layers"`    // 本体のとき
}

1つの構造体に、リスト用のフィールドと本体用のフィールドを両方持たせています。どちらが来ても同じ型で受けて、あとから中身を見て判断する。JSON にそのキーが無ければ、対応するスライスは nil（長さ0）のまま残ります。だから len(man.Manifests) > 0 ならリスト、len(man.Layers) > 0 なら本体、と判定できます。

descriptor が「レイヤ」でも「config」でも「別のマニフェストへの案内」でも使い回せるのも、この形式のうまさです。どれも「メディアタイプ・digest・サイズ」の3点で表せる。だから layers の中身も config も manifests の中身も、全部同じ descriptor 型です。

GO メモ · encoding/json で「どちらの形かわからない JSON」を受ける

Go の encoding/json は、構造体に無いキーを黙って捨て、JSON に無いキーはゼロ値のままにします。この寛容さが、ここでは武器になります。リストが来れば Manifests だけが埋まり Layers は nil、本体が来れば逆になる。どちらもエラーになりません。

判定は スライスが nil かどうかで行います。MediaType フィールドを見て分岐する手もありますが、これは当てになりません。実際にこの alpine の応答には、いちばん外側に mediaType が入っていないことがあります（上の実測 JSON を見てください、manifests がいきなり来ています）。「あると書いてあるフィールド」より「実際に埋まったフィールド」を信じるほうが頑丈です。

Platform がポインタ（*struct{…}）になっているのも意図的です。値型にすると「platform キーが無い」と「platform が空だった」を区別できません。ポインタなら、キーが無いときは nil のままです。Step 4 の pickPlatform は、この nil チェックから始まります。

もう1つ。もし「キーの有無を後で調べたい」ならば map[string]json.RawMessage で受けて生のバイト列を保持しておく手もあります。ただ今回は必要なフィールドが分かっているので、素直な構造体で足ります。

そして、リストだったら取り直す。Pull の中のこの部分です。

⚠ 落とし穴 · マニフェストは一段深いところにある

タグを引いて返ってきた JSON に layers が無いのは、異常ではなく通常です。公式イメージはほぼ確実にマニフェストリストを返します。「layers が無い＝エラー」と決めつけて例外を投げる実装は、いちばん普通のケースで落ちます。

正しい対応は「リストなら1件選んで、その digest でもう一度取る」。取り直しは 同じ fetchManifest に digest を渡すだけで、新しい関数は要りません。

Step 4さらに罠 — 「最初の項目」を取ると確実に壊れる

リストから1件選べばいい。ではどう選ぶか。素朴に考えれば「1件目でいいのでは」となります。実測 JSON の1件目はちょうど linux/amd64 ですし、動いてしまいそうです。

これは確実に壊れます。2件目を見てください。

リストの2件目（実測 JSON の抜粋を読み下したもの） digest : sha256:f21951a6120df0f5… mediaType : application/vnd.oci.image.manifest.v1+json platform : { "architecture": "unknown", "os": "unknown" } ★ annotations : { "vnd.docker.reference.type": "attestation-manifest", ★ "vnd.docker.reference.digest": "sha256:79ff19e9084a…" } size : 838 ★ これはイメージではない。1件目のイメージに対する「署名の付随物」。 掴むと、layers の無いマニフェストを引く。

これは attestation（証明） です。「このイメージは誰が・どういう手順でビルドしたか」を記録した付属文書で、サプライチェーンの検証に使われます。イメージそのものではありません。だから platform.architecture が "unknown" になっています。「どの CPU 向けでもない」という意味です。

並び順は保証されていません。attestation が先に来ることもあれば、arm64 が先のこともあります。順番に依存した実装は、いつか静かに壊れます。しかも壊れ方が意地悪です。attestation の digest を引くと HTTP 200 で正しい JSON が返り、ただ layers だけが無い。Step 3 で見たのと同じ「原因の見えない詰まり方」に戻ってしまいます。

だから、選び方を明示します。

internal/image/registry.go
// pickPlatform はマニフェストリストから、この環境で動く1件を選ぶ。
//
// ⚠ 「最初の項目を取る」実装は確実に壊れる。
// リストには architecture が "unknown" の attestation（署名の付随物）が混ざっており、
// それを掴むと layers の無いマニフェストを引いてしまう。
func pickPlatform(list []descriptor) (descriptor, error) {
	for _, d := range list {
		if d.Platform == nil {
			continue
		}
		if d.Platform.OS == runtime.GOOS && d.Platform.Architecture == runtime.GOARCH {
			return d, nil
		}
	}
	var have []string
	for _, d := range list {
		if d.Platform != nil {
			have = append(have, d.Platform.OS+"/"+d.Platform.Architecture)
		}
	}
	return descriptor{}, fmt.Errorf("このイメージに %s/%s 向けの版がありません（あるのは: %s）",
		runtime.GOOS, runtime.GOARCH, strings.Join(have, ", "))
}

前半のループが本体です。runtime.GOOS と runtime.GOARCH は、この Go プログラムがビルドされたときの OS と CPU アーキテクチャを表す定数です。この環境では linux と amd64（go version go1.24.7 linux/amd64 でしたね）。文字列として "linux" と "amd64" が入っているので、JSON の値とそのまま比較できます。OCI の仕様が Go の慣習に合わせて作られたので、この2つはきれいに一致します。

d.Platform == nil の continue は、platform キーそのものが無い項目を飛ばすためです。attestation は "unknown" という値を持っているのでここでは弾かれず、次の行の == runtime.GOARCH の比較で落ちます。二重の網です。

後半の have を集めるループが、この関数のもう一つの主張です。見つからなかったときに、あるものの一覧を添えてエラーにする。 たとえば ARM の Mac で amd64 専用イメージを引いてしまったとき、

  • 悪い例: マニフェストが見つかりません — 何を調べればいいか分からない
  • この実装: このイメージに linux/arm64 向けの版がありません（あるのは: linux/amd64, unknown/unknown） — その場で理解できて、次の一手が決まる

エラーメッセージは、失敗したときにしか読まれません。だからこそ、失敗した人がいちばん知りたい情報を載せます。「無い」だけでなく「代わりに何があったか」を。

⚠ 落とし穴 · attestation を掴むと、200 なのに layers が無い

マニフェストリストの中には、イメージではない項目が混ざっています。vnd.docker.reference.type: attestation-manifest という注釈が付き、platform は unknown/unknown。これを掴んでも HTTP は 200 で成功します。ただ layers が無いだけです。

「最初の項目を取る」「platform を見ずに mediaType だけで選ぶ」実装は、いずれこれを引きます。必ず platform.os と platform.architecture の両方を、自分の runtime.GOOS / runtime.GOARCH と突き合わせて選んでください。

Step 5設定 JSON を取る — Env と Cmd はここにある

取り直したマニフェスト本体には、layers のほかに config という項目が1つあります。これも digest で指された blob です。中身は JSON で、コンテナをどう起動すべきかが書いてあります。

ここは意外と見落とされる部分です。docker run alpine と打ったとき、何もコマンドを指定していないのに /bin/sh が動きます。echo $PATH を打つとちゃんと値が入っています。あの既定値は、カーネルでもランタイムでもなく、この config JSON から来ています。

私たちが要るのは4つだけです。

JSON タグの大文字に注意してください。"Env"、"Cmd"、"Entrypoint" と、頭が大文字です。マニフェストのほうは "mediaType"、"digest" と小文字始まりでした。同じイメージ仕様の中で命名規則が食い違っています。config JSON は Docker が昔から使ってきた形式がそのまま残っているためで、歴史的経緯としか言いようがありません。タグを小文字で書くと黙って空になりますので、ここは仕様書どおりに写します。

外側に config というキーがもう一段あるのも見落としやすい点です。JSON は {"config":{"Env":[…],"Cmd":[…]}} という入れ子で、だから Go 側も匿名の構造体を1段ネストさせています。

取得の関数はこうです。ここで初めてキャッシュが顔を出します。

internal/image/registry.go
func (s *Store) fetchConfig(client *http.Client, ref Ref, token string, d descriptor) (*imageConfig, error) {
	var cfg imageConfig
	path := s.configPath(d.Digest)
	if err := loadJSON(path, &cfg); err == nil {
		return &cfg, nil
	}
	url := fmt.Sprintf("https://%s/v2/%s/blobs/%s", ref.Registry, ref.Repository, d.Digest)
	body, err := s.get(client, url, token, "*/*")
	if err != nil {
		return nil, err
	}
	if err := json.Unmarshal(body, &cfg); err != nil {
		return nil, fmt.Errorf("イメージ設定の JSON を読めませんでした: %w", err)
	}
	if err := os.MkdirAll(filepath.Dir(path), 0o755); err != nil {
		return nil, err
	}
	if err := os.WriteFile(path, body, 0o644); err != nil {
		return nil, err
	}
	return &cfg, nil
}

最初の3行が「もうローカルにあるなら、それを読んで即座に返す」です。ファイル名は digest から作るので（configPath）、同じ digest なら中身は同じ。読めたら通信しません。読めなければ（ファイルが無ければ）落としに行き、成功したら次回のために書いておきます。

URL の形が /manifests/ ではなく /blobs/ になっていることに注意してください。マニフェストは「目録」、blob は「中身」です。config JSON もレイヤの tar.gz も、レジストリから見ればどちらも同じ blob で、同じエンドポイントで配られます。

Accept に "*/*" を渡しているのは、blob は形式の交渉が要らないからです。digest で名指しした時点で中身は一意に決まっています。ここで acceptManifest を渡してしまうと、逆に「その形式では配れない」と断られることがあります。

ちなみに alpine の config は 611 バイトしかありません。展開後 8.7 MB のファイルシステム全体に対して、起動の作法を記述した部分はたったこれだけです。

Step 6レイヤを落とす — 落としながらハッシュを取る

ようやく実体です。layers の各項目の digest を /blobs/ に投げれば、tar.gz がそのまま降ってきます。alpine の場合、レイヤは1枚だけ、mediaType は application/vnd.oci.image.layer.v1.tar+gzip、圧縮 3.67 MiB です。

素朴に書くなら「全部ダウンロードして一時ファイルに保存 → ハッシュを検算 → 展開」でしょう。3段階です。しかしこれは、3.67 MiB を2回読むことになります（検算で1回、展開で1回）。しかも一時ファイルの置き場所も要ります。

もっといい方法があります。流しながら、同時に両方やるのです。

io.TeeReader — 読みながら、同じバイト列を別の場所にも流す ┌──────────────────────────────► ExtractLayer │ （tar.gz を解いて展開） layers/sha256_55af….tmp/ resp.Body ──► TeeReader │ └──────────────────────────────► sha256 ハッシュ計算器 （1バイトも余分に読まずに） 最後に digest と照合 読み取りは1回だけ。ネットワークから来たバイトが、展開器とハッシュ計算器の 両方を同時に通り抜ける。一時ファイルは要らない。

実装を見てください。

internal/image/registry.go
// fetchLayer はレイヤ1枚を落として dir に展開する。
//
// 途中で失敗したディレクトリを「取得済み」と誤認しないよう、
// 展開が最後まで終わったときにだけ .complete という印を置く。
func (s *Store) fetchLayer(client *http.Client, ref Ref, token string, d descriptor, dir string) error {
	url := fmt.Sprintf("https://%s/v2/%s/blobs/%s", ref.Registry, ref.Repository, d.Digest)
	req, _ := http.NewRequest(http.MethodGet, url, nil)
	if token != "" {
		req.Header.Set("Authorization", "Bearer "+token)
	}
	resp, err := client.Do(req)
	if err != nil {
		return fmt.Errorf("レイヤの取得に失敗しました: %w", err)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		return fmt.Errorf("レイヤの取得に失敗しました (HTTP %d): %s", resp.StatusCode, shortDigest(d.Digest))
	}

	// 落としながら同時にハッシュを計算する。digest は中身のハッシュなので、
	// 一致しなければ「途中で壊れた」か「別物を掴んだ」ことになる。
	hasher := sha256.New()
	body := io.TeeReader(resp.Body, hasher)

	tmp := dir + ".tmp"
	_ = os.RemoveAll(tmp)
	if _, err := ExtractLayer(body, tmp); err != nil {
		_ = os.RemoveAll(tmp)
		return fmt.Errorf("レイヤ %s の展開に失敗しました: %w", shortDigest(d.Digest), err)
	}
	// 本体を読み切ってからでないとハッシュが完成しない
	if _, err := io.Copy(io.Discard, body); err != nil {
		_ = os.RemoveAll(tmp)
		return err
	}
	got := "sha256:" + hex.EncodeToString(hasher.Sum(nil))
	if !strings.EqualFold(got, d.Digest) {
		_ = os.RemoveAll(tmp)
		return fmt.Errorf("レイヤの digest が一致しません: 期待 %s / 実際 %s", d.Digest, got)
	}

	_ = os.RemoveAll(dir)
	if err := os.MkdirAll(filepath.Dir(dir), 0o755); err != nil {
		return err
	}
	if err := os.Rename(tmp, dir); err != nil {
		return err
	}
	return os.WriteFile(dir+".complete", []byte(d.Digest), 0o644)
}

中心は2行です。

hasher := sha256.New() でハッシュ計算器を作り、body := io.TeeReader(resp.Body, hasher) で「body から読むと、読まれたぶんが自動的に hasher にも流れる」読み取り口を作ります。あとは body を ExtractLayer に渡すだけ。展開器はハッシュのことを何も知りませんし、知る必要もありません。

GO メモ · io.TeeReader

io.TeeReader(r, w) は「r から読んだバイトを、そのまま w にも書きながら返す io.Reader」を作ります。名前は UNIX の tee コマンド（標準出力に流しつつファイルにも保存するあれ）から来ています。

ありがたいのはメモリを食わないことです。3.67 MiB のレイヤでも 3 GB のレイヤでも、使うメモリは内部バッファのぶんだけ。全体をメモリに載せる必要も、一時ファイルに落とす必要もありません。ネットワークから来たバイトが、通り過ぎざまにハッシュを更新していきます。

ここで押さえておくべき性質が1つ。hasher が正しい値になるのは、body を最後の1バイトまで読み切ったときだけです。読まれなかったバイトはハッシュにも入りません。だから io.Copy(io.Discard, body) が要ります。ExtractLayer は gzip ストリームを解きますが、tar の終端に達した時点で読むのをやめるので、末尾に数バイト残ることがあるのです。io.Discard は「書き込まれたものを捨てる io.Writer」で、この io.Copy は「残りを読み捨てて hasher を完成させる」ためだけに存在します。捨てるために読むという一見無駄な行に、ちゃんと役目があります。

ハッシュの照合が終わったら、.tmp を本番の名前に os.Rename します。ここが原子的（アトミック）であることが肝です。同じファイルシステム内の rename はカーネルが一瞬で行うので、「半分だけ名前が変わった状態」は存在しません。展開中の中途半端なディレクトリが本番の名前を名乗る瞬間が無い、ということです。

そして最後の1行、.complete の印。これは Step 7 の主題なので、そこで扱います。

LINUX メモ · digest（content-addressable）

sha256:55afa1ecc21d… という名前は、そのデータ自体を SHA-256 に通した結果です。ファイル名を人間が決めるのではなく、中身が自分の名前を決めています。これを content-addressable（内容アドレス指定）と言います。

この一点から、いくつもの性質が自動的に付いてきます。同じ名前なら中身は必ず同じ（SHA-256 が衝突しない限り）。だから「もう持っているか」の判定が名前の比較だけで済み、キャッシュが自然に成立します。逆に中身が1バイトでも違えば名前も違うので、上書きや世代管理という概念そのものが要りません。新しい中身は新しい名前で置かれるだけです。

そして検証もタダで付いてきます。落としたものを SHA-256 に通して名前と一致すれば、途中で壊れていないことも、別物を掴んでいないことも同時に確かめられます。fetchLayer の照合はまさにこれです。HTTPS で守られているのは「通信路」であって「中身」ではありません。レジストリの中で壊れていたり、キャッシュサーバが古いものを返したりする可能性は HTTPS では消えません。digest の照合は、相手が誰であっても中身が正しいことを自分で確かめる手段です。

Git のコミットハッシュ、IPFS の CID、Nix のストアパス。みな同じ考え方の上に建っています。/var/lib/mydocker/layers/sha256_55afa… という長い名前は、その一員です。

Step 7キャッシュ — digest をディレクトリ名にする

ここまでで機能としては動きます。しかし開発中にこのまま進めると、遠くない未来に必ず止まります。

⚠ 落とし穴 · Docker Hub には匿名アクセスの取得回数制限がある

Docker Hub は、匿名（未ログイン）でのイメージ取得に回数の上限を設けています。上限に達すると HTTP 429 Too Many Requests が返り、しばらく何も取れなくなります。

これは本番運用の話ではありません。開発中がいちばん危ないのです。「動くかな」と go run を10回、テストで20回、うっかりループで数十回。イメージの中身は1バイトも変わっていないのに、同じものを何度も引きに行く。ある回から突然エラーになり、しかもコードは何も変えていないので原因が分かりません。

この実装では s.get が 429 を専用に検知して 取得回数の上限に達しました (HTTP 429)。しばらく待つか、キャッシュ済みのイメージを使ってください と返します。だがそもそも、2回目を引かないのが正解です。

では、どうやって「もう持っている」を判定するか。ここで Step 6 の digest が効いてきます。ディレクトリ名を digest にしておけば、名前の存在確認がそのままキャッシュの判定になります。「同じ名前＝同じ中身」が保証されているからです。中身を比べる必要も、更新日時を見る必要も、バージョンを管理する必要もありません。

置き場を決める部分を見ます。

internal/image/registry.go
// Store はイメージのローカル置き場。
//
// ⚠ Docker Hub には匿名アクセスの取得回数制限がある。開発中に何度も引くと止まる。
// レイヤは digest をディレクトリ名にして保存する。digest は中身のハッシュなので、

safeDigest は sha256:55afa… の : を _ に置き換えるだけの関数です（Step 8 でまとめて見ます）。コロンはファイル名に使えない環境があるので、機械的に潰しています。

Log io.Writer という設計も見ておいてください。進捗を fmt.Println で直に出さず、書き込み先を外から渡せるようにしてあります。nil なら何も出さない。これで mydocker run --quiet のときに黙らせることができますし、テストでは出力を捕まえて検証できます。ライブラリが標準出力を勝手に汚さないための小さな作法です。

次に、「取得済み」の判定です。ここに、初見では思いつきにくい工夫が入っています。

internal/image/registry.go
func isComplete(dir string) bool {
	if _, err := os.Stat(dir + ".complete"); err != nil {
		return false
	}
	fi, err := os.Stat(dir)
	return err == nil && fi.IsDir()
}

なぜ「ディレクトリが存在するか」だけで判定しないのか。途中で失敗したディレクトリを「取得済み」と誤認しないためです。

考えてみてください。3.67 MiB を展開している途中で、ネットワークが切れた、電源が落ちた、Ctrl-C を押した。すると layers/sha256_55afa… には中途半端に展開されたファイル群が残ります。ディレクトリは存在します。でも中身は半分です。次に起動したとき「ディレクトリがあるから取得済み」と判断すると、ファイルが欠けたイメージでコンテナを起動してしまいます。しかも一度そうなると、以後ずっとそのままです。

そこで、印を分けます。展開が最後まで終わり、ハッシュの照合も通り、rename も済んだ——その全部が終わった後にだけ、.complete という別のファイルを置く。判定はこの印を見ます。途中で死んだら印は置かれないので、次回はきちんと取り直します。

「取得済み」の印を、中身とは別のファイルにする理由 途中で失敗したとき 最後まで成功したとき ───────────────── ───────────────── layers/sha256_55af….tmp/ ← 中途半端 layers/sha256_55af…/ ← 完全な中身 （.complete は無い） layers/sha256_55af….complete ← 印 isComplete() は .complete だけを見る。 → 中途半端なディレクトリを「持っている」と誤認しない。 → 展開 → ハッシュ照合 → rename → 印、の順序が守られている証明にもなる。

この「本体を書き終えてから印を置く」という順序は、あらゆる場所で使える型です。データベースのコミットログも、ビルドシステムのスタンプファイルも、考え方は同じです。作業の完了は、作業とは別に記録する。

さらにもう一段。マニフェストも保存してしまえば、2回目は HTTP を1回も叩かずに済みます。

// fromCache は保存済みのマニフェストとレイヤだけでイメージを組み立てられるか試す。
func (s *Store) fromCache(ref Ref) (*Image, bool) {
	var man manifest
	if err := loadJSON(s.manifestPath(ref), &man); err != nil {
		return nil, false
	}

		return nil, false
	}

		dir := s.layerDir(l.Digest)

			return nil, false
		}

	}

	if err := loadJSON(s.configPath(man.Config.Digest), &cfg); err != nil {
		return nil, false
	}
	return &Image{

この関数の構造をよく見てください。「揃っていなければ、いつでも false を返して諦める」という一本道です。マニフェストが読めない、レイヤが0枚、どれか1枚でも .complete が無い、config が読めない——どこで転んでも (nil, false)。そして呼び出し側は、false なら普通に通信して取りに行くだけです。

キャッシュのコードで怖いのは「壊れたキャッシュを使ってしまう」ことです。それを防ぐには、疑わしきは使わないを徹底するのがいちばん簡単です。この関数はエラーを一切上に投げません。エラーは全部「キャッシュは使えなかった」という意味に変換されます。最悪でも通信が1回増えるだけで、間違った中身でコンテナが起動することはありません。

internal/image/registry.go
// Pull はイメージを取得して展開し、使える状態にして返す。
// すべてキャッシュに揃っていればネットワークには一切アクセスしない。
func (s *Store) Pull(refStr string) (*Image, error) {
	ref, err := ParseRef(refStr)
	if err != nil {
		return nil, err
	}

	// --- キャッシュだけで済むなら、そもそも通信しない ---
	if img, ok := s.fromCache(ref); ok {
		s.logf("キャッシュ: %s（ネットワークにはアクセスしません）", ref)
		return img, nil
	}

	client := &http.Client{Timeout: 120 * time.Second}

	// ① トークン
	token, err := s.fetchToken(client, ref)
	if err != nil {
		return nil, err
	}

	// ② マニフェスト
	man, err := s.fetchManifest(client, ref, token, ref.Tag)
	if err != nil {
		return nil, err
	}

	// ⚠ 返ってきたのがマニフェストリスト（インデックス）のことがある。
	//    複数 CPU アーキテクチャの入り口なので、amd64/linux の項目を選んで digest で取り直す。
	if len(man.Layers) == 0 && len(man.Manifests) > 0 {
		target, err := pickPlatform(man.Manifests)
		if err != nil {
			return nil, err
		}
		s.logf("マニフェストリストでした。%s/%s の %s を取り直します", runtime.GOOS, runtime.GOARCH, shortDigest(target.Digest))
		man, err = s.fetchManifest(client, ref, token, target.Digest)
		if err != nil {
			return nil, err
		}
	}
	if len(man.Layers) == 0 {
		return nil, fmt.Errorf("%s: マニフェストに layers がありません（schema 1 が返っている可能性があります）", ref)
	}

	// 設定 JSON（Env / Cmd を拾う）
	cfg, err := s.fetchConfig(client, ref, token, man.Config)
	if err != nil {
		return nil, err
	}

	// ③ レイヤ
	var dirs []string
	for i, layer := range man.Layers {
		dir := s.layerDir(layer.Digest)
		if isComplete(dir) {
			s.logf("レイヤ %d/%d %s: キャッシュ済み", i+1, len(man.Layers), shortDigest(layer.Digest))
		} else {
			s.logf("レイヤ %d/%d %s: 取得中 (%.1f MiB)", i+1, len(man.Layers), shortDigest(layer.Digest), float64(layer.Size)/(1<<20))
			if err := s.fetchLayer(client, ref, token, layer, dir); err != nil {
				return nil, err
			}
		}
		dirs = append(dirs, dir)
	}

	// マニフェストを保存しておけば、次回は通信そのものが要らなくなる
	if err := saveJSON(s.manifestPath(ref), man); err != nil {
		return nil, err
	}

	return &Image{
		Ref:        ref,
		LayerDirs:  dirs,
		Env:        cfg.Config.Env,
		Cmd:        cfg.Config.Cmd,
		Entrypoint: cfg.Config.Entrypoint,
		WorkingDir: cfg.Config.WorkingDir,
	}, nil
}

Step 8イメージ参照の分解 — alpine とは何の略か

ここまで ref.Registry や ref.Repository を当たり前のように使ってきましたが、利用者が実際に打つのは alpine の6文字だけです。これを組み立て直す必要があります。

docker pull alpine が実際に取りに行っているのは registry-1.docker.io/library/alpine:latest です。省略されているものが3つあります。レジストリ名・名前空間（library/）・タグ（:latest）。この省略の展開規則を実装するのがこの Step です。

受け皿の型から。

internal/image/registry.go
// Ref は "alpine" や "ghcr.io/foo/bar:1.2" のようなイメージ参照を分解したもの。
type Ref struct {
	Registry   string // 例: registry-1.docker.io
	Repository string // 例: library/alpine
	Tag        string // 例: latest
}

func (r Ref) String() string { return r.Registry + "/" + r.Repository + ":" + r.Tag }

// cacheKey はキャッシュのファイル名に使える形にした参照。
func (r Ref) cacheKey() string {
	s := r.Registry + "_" + r.Repository + "_" + r.Tag
	return strings.NewReplacer("/", "_", ":", "_").Replace(s)
}

String() を定義してあるので、fmt.Errorf("%s: …", ref) と書くだけで mirror.gcr.io/library/alpine:latest という完全な形で出ます。エラーメッセージが親切になるのは、こういう地味な定義のおかげです。

本体です。

internal/image/registry.go
// ParseRef は利用者が打った文字列を Ref に分解する。
//
//	alpine              → registry-1.docker.io / library/alpine : latest
//	alpine:3.20         → registry-1.docker.io / library/alpine : 3.20
//	library/alpine      → registry-1.docker.io / library/alpine : latest
//	ghcr.io/foo/bar:1.2 → ghcr.io             / foo/bar        : 1.2
func ParseRef(s string) (Ref, error) {
	s = strings.TrimSpace(s)
	if s == "" {
		return Ref{}, fmt.Errorf("イメージ名が空です")
	}
	ref := Ref{Registry: defaultRegistry, Tag: "latest"}

	name := s
	// 先頭の要素にドットかコロンがあれば、それはレジストリのホスト名である。
	// （"alpine" と "ghcr.io/x" を見分けるための、レジストリ界隈の慣習）
	if i := strings.Index(name, "/"); i >= 0 {
		head := name[:i]
		if strings.ContainsAny(head, ".:") || head == "localhost" {
			ref.Registry = head
			name = name[i+1:]
		}
	}
	// タグの切り出し。ポート番号入りホスト名と混同しないよう、最後の "/" より後ろだけを見る。
	if i := strings.LastIndex(name, ":"); i >= 0 && !strings.Contains(name[i:], "/") {
		ref.Tag = name[i+1:]
		name = name[:i]
	}
	if name == "" {
		return Ref{}, fmt.Errorf("イメージ名が空です: %q", s)
	}
	// Docker Hub の公式イメージは library/ 名前空間に居る
	if ref.Registry == defaultRegistry && !strings.Contains(name, "/") {
		name = "library/" + name
	}
	ref.Repository = name
	return ref, nil
}

4段階です。順番に踏みます。

1. レジストリ名の判定。 ここが一番の勘所です。ghcr.io/foo/bar の ghcr.io はホスト名ですが、library/alpine の library は名前空間です。形の上では区別が付きません。どちらも「/ の前の文字列」です。

⚠ 落とし穴 · レジストリ名かどうかは「ドットかコロンがあるか」で決めている

この判定に厳密な定義はありません。「先頭の要素にドット . かコロン : が含まれていればホスト名とみなす」という、レジストリ界隈の慣習です。ghcr.io にはドットがある、localhost:5000 にはコロンがある、library にはどちらも無い。それだけの理由で振り分けています。

だから例外を1つ手で足す必要があります。localhost です。ドットもコロンも無いのにホスト名。だからコードに || head == "localhost" という特例が書いてあります。この1行は、慣習で決めた規則にはこういうほころびが出る、という証拠です。Docker 本家の実装にも同じ特例が入っています。

2. タグの切り出し。 ここにもう1つの罠があります。素朴に「: で分割する」と書くと、localhost:5000/myimage で壊れます。5000/myimage がタグになってしまうからです。

タグの切り出しで、ポート番号と混同しない工夫 入力: localhost:5000/myimage ↑ここのコロンはポート番号 ① 先にレジストリを剥がす → name = "myimage"（コロンはもう無い） ② それでも残るケースに備え、LastIndex で「最後のコロン」を見る さらに !strings.Contains(name[i:], "/") で 「そのコロンより後ろに / が無い」ことを確認する 例: foo/bar:1.2 → 最後の ":" の後ろは "1.2"。/ が無い → タグである ✔ host:5000/bar → 最後の ":" の後ろは "5000/bar"。/ がある → タグではない ✘

LastIndex（最後の :）と「その後ろに / が無いこと」の二段構えです。タグはイメージ参照のいちばん末尾に来るので、タグを表すコロンの後ろにスラッシュが現れることはありえない。この性質を使って区別しています。

3. 空チェック。 alpine: のような入力（コロンの後ろが空）を弾きます。エラーメッセージの %q は、Go の書式指定で「引用符付きで出す」の意味です。イメージ名が空です: " " のように、空白文字が見える形で出るので原因が分かります。

4. library/ の補完。 Docker Hub の公式イメージは library という名前空間の下にいます。alpine の正体は library/alpine です。ただしこの補完をするのは Docker Hub のときだけ。ghcr.io/alpine に library/ を足したら、存在しないパスになってしまいます。条件に ref.Registry == defaultRegistry が入っているのはそのためです。

	return strings.NewReplacer(":", "_", "/", "_").Replace(d)

func shortDigest(d string) string {
	if i := strings.Index(d, ":"); i >= 0 && len(d) > i+13 {
		return d[i+1 : i+13]
	}
	return d
}

func saveJSON(path string, v any) error {
	if err := os.MkdirAll(filepath.Dir(path), 0o755); err != nil {
		return err
	}
	b, err := json.MarshalIndent(v, "", "  ")
	if err != nil {
		return err
	}
	return os.WriteFile(path, b, 0o644)
}

func loadJSON(path string, v any) error {
	b, err := os.ReadFile(path)
	if err != nil {
		return err
	}
	return json.Unmarshal(b, v)
}

shortDigest は sha256:55afa1ecc21d2bb5e… から 55afa1ecc21d（12文字）だけを切り出します。ログに 64 文字のハッシュを全部出すと読めたものではないので、人間向けの短縮形です。len(d) > i+13 の境界チェックがあるので、短すぎる文字列を渡してもパニックせず、そのまま返します。ログ用の関数が例外を投げて本体を落とすのは最悪なので、ここは臆病に書きます。

saveJSON の json.MarshalIndent(v, "", " ") は、整形して（インデント2スペース）保存するという意味です。1バイトも節約になりませんが、/var/lib/mydocker/manifests/*.json を cat したときに人間が読めます。デバッグしている自分に対する親切です。

Step 9他のレジストリ — 401 が道を教えてくれる

最後の部品です。Docker Hub 以外のレジストリでは、トークンの取得先 URL が違います。ghcr.io なら https://ghcr.io/token、mirror.gcr.io ならまた別。これを全部ハードコードして回るのは無理です。

幸い、HTTP がちゃんと考えられています。401 を返すとき、サーバは「どこへ鍵を取りに行けばいいか」を一緒に教えてくれます。 WWW-Authenticate というヘッダです。だから、まず何も付けずに /v2/ を叩いて、断られ方を読めばいい。

401 が道を教えてくれる ① GET https://ghcr.io/v2/ （鍵は付けない。わざと断られに行く） ↓ HTTP/1.1 401 Unauthorized WWW-Authenticate: Bearer realm="https://ghcr.io/token",service="ghcr.io" └─ 取りに行く先 ─┘ └─ 名乗る相手 ─┘ ↓ ② realm + "?scope=repository:foo/bar:pull" + "&service=" + service を GET ↓ トークンが返る → あとは Docker Hub と同じ手順 ★ 401 が返らなかった（＝いきなり 200 だった）なら、認証不要のレジストリ。 その場合はトークン無しで進む。

実装です。

internal/image/registry.go
// discoverAuth は /v2/ の 401 応答から認証サーバの場所を読み取る。
func discoverAuth(client *http.Client, ref Ref) (realm, service string, err error) {
	resp, err := client.Get("https://" + ref.Registry + "/v2/")
	if err != nil {
		return "", "", fmt.Errorf("レジストリ %s に接続できませんでした: %w", ref.Registry, err)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusUnauthorized {
		return "", "", nil
	}
	h := resp.Header.Get("WWW-Authenticate")
	if !strings.HasPrefix(h, "Bearer ") {
		return "", "", nil
	}
	for _, part := range strings.Split(strings.TrimPrefix(h, "Bearer "), ",") {
		kv := strings.SplitN(strings.TrimSpace(part), "=", 2)
		if len(kv) != 2 {
			continue
		}
		v := strings.Trim(kv[1], `"`)
		switch kv[0] {
		case "realm":
			realm = v
		case "service":
			service = v
		}
	}
	return realm, service, nil
}

/v2/ という何も指定しないパスを叩くのが定石です。OCI Distribution Spec で「API のバージョン確認用エンドポイント」として決められていて、認証が要るレジストリはここで 401 を返します。

解析は素朴な文字列処理です。Bearer を剥がして、カンマで割って、それぞれを = で2つに割って、値の引用符を取る。SplitN(…, "=", 2) の 2 が効いています。realm="https://ghcr.io/token" の値の中に = が入っていても（クエリ文字列付きの realm もあります）、最初の = でだけ割るので壊れません。

そして 401 が返らなかった場合、("", "", nil) を返します。エラーではありません。fetchToken 側で realm == "" なら空トークンを返し、s.get は空トークンなら Authorization ヘッダを付けません。認証の要らないレジストリでは、認証の話が全部消える。条件分岐が3か所に散っているように見えますが、それぞれが「知らないことは付けない」という一貫した態度で書かれています。

⚠ 正直に書いておく · この環境では Docker Hub からレイヤを落とせなかった

この教材を書いた環境には、組織の egress ポリシー（外向き通信の制限）が掛かっています。そして Docker Hub のレイヤ配信ドメイン production.cloudfront.docker.com に出られませんでした（CONNECT が 403 で拒否される）。

症状が独特です。トークンは取れる。マニフェストも取れる。レイヤの取得だけが失敗する。Docker Hub は blob の配信を CDN の別ドメインに委ねているため、registry-1.docker.io は通っても CDN は通らない、という状態が起こりえます。Step 1・2 の curl が成功したのに Step 6 で落ちる場合、コードではなくネットワークを疑ってください。

ここで取った方針を明記します。回避策を実装に埋め込みませんでした。プロキシ設定やドメインの読み替えをコードに入れると、この環境でしか意味のない汚れが恒久的に残ります。代わりに、届くレジストリを利用者が指定できるという既にある性質（Step 8 の ParseRef）を使い、mirror.gcr.io/library/alpine を指定して進めました。この章の実測出力が全部 mirror.gcr.io/… になっているのはそのためです。取得できる中身は同一で、同じ digest sha256:79ff19e9084a… を指しています。

この「別のレジストリを指定して回避できた」という事実自体が、Step 8 と Step 9 を作った価値の証明になっています。レジストリ名をハードコードしていたら、この教材はここで止まっていました。

つまずき FAQ

公開イメージなのに、なぜトークンが要るんですか? 誰も認証していないのに。

「認証」と「認可」を分けて考えると腑に落ちます。Docker Hub がトークンで管理しているのは、あなたが誰かではなく何をどれだけしていいかです。匿名のトークンには「library/alpine を pull する権限だけ」が入っていて、有効期限も付いています。

実利もあります。トークンには発行の記録が残るので、取得回数を数えられます。Step 7 で触れた匿名アクセスの回数制限は、この仕組みの上に乗っています。またレジストリ本体は「有効な鍵か」を確かめるだけでよく、認証サーバと配信サーバを分離できます。だから auth.docker.io と registry-1.docker.io は別のホストなのです。

Accept ヘッダを付け忘れると、具体的に何が返ってくるんですか?

manifest schema 1 という、Docker の初期からある古い形式です。中身の構造がまるごと違い、layers ではなく fsLayers という配列にレイヤが入っています（順序も逆向きです）。

厄介なのはエラーにならないことです。HTTP は 200、JSON も正しい JSON なのでパースも通る。Go の encoding/json は知らないキーを黙って捨てるので、man.Layers は nil のまま。「なぜかレイヤが0枚」という結果だけが残ります。この実装が「schema 1 が返っている可能性があります」というエラーメッセージを持っているのは、まさにこの状態を後から見分けるためです。

マニフェストリストから自分で選ぶのは面倒です。docker は自動でやってくれますよね?

やってくれます。ただ、やっていることは pickPlatform と同じです。docker も自分の GOOS/GOARCH（正確にはビルド時のプラットフォーム情報）と platform を突き合わせて1件選んでいます。docker pull --platform linux/arm64 というオプションがあるのは、その選択を手動で上書きするためです。

つまり「自動」というのは「あなたの代わりに誰かが同じコードを書いた」という意味でしかありません。この章でやったのは、その誰かの仕事を自分の手でやり直すことです。一度自分で書くと、--platform が何をするオプションなのかが完全に分かります。

digest の照合って、そこまで必要ですか? HTTPS で取ってきているのに。

HTTPS が守るのは通信路であって中身ではありません。「registry-1.docker.io と名乗るサーバと確かに話した」「途中で誰にも書き換えられていない」ことは保証されますが、「そのサーバが渡してきたものが正しい中身か」は保証しません。

実際に起こりうるのは、CDN のキャッシュが壊れている、ミラーが古い、レジストリ側のストレージでビット反転が起きている、といったケースです。どれも HTTPS では検出できません。digest の照合は相手が誰であっても中身が正しいことを自分で確かめるための、独立した安全網です。

それに、この照合はほとんどタダです。io.TeeReader のおかげで読み取り回数は増えず、追加コストは SHA-256 の計算だけ。3.67 MiB なら一瞬です。安いのだからやる、で十分な理由になります。

.complete というファイルを置くのはなぜですか? ディレクトリの有無で判定してはだめですか?

だめです。理由は「ディレクトリが存在する」と「中身が完全である」が別のことだからです。

展開の途中で Ctrl-C を押したり、ネットワークが切れたり、ディスクが一杯になったりすると、中途半端に展開されたディレクトリが残ります。ディレクトリは存在します。ファイルもいくつか入っています。でも 516 ファイルのうち 200 ファイルしかありません。これを「取得済み」と判定すると、欠けたイメージでコンテナが起動し、しかも次回以降ずっとそのままです。

だから、すべてが終わった後にだけ置かれる別の印を使います。展開して、ハッシュを照合して、rename して、そこでようやく .complete を書く。この順序が守られている限り、印があることは中身が完全であることの証明になります。ちなみに展開先が dir + ".tmp" という別名なのも同じ理由で、本番の名前は完成品しか名乗れないようにしてあります。

Docker Hub からレイヤが落とせません。私の環境でも起きますか?

起きるかもしれません。この教材を書いた環境では実際に起きました。組織の egress ポリシーで production.cloudfront.docker.com（Docker Hub が blob 配信に使う CDN）への接続が 403 で拒否されたためです。

見分け方は簡単です。Step 1 の curl（トークン）と Step 2 のマニフェスト取得は成功するのに、レイヤの取得だけが失敗するなら、まずこれを疑ってください。コードのバグではありません。Docker Hub は目録と中身を別のドメインで配っているので、片方だけ通るという状態が成立します。

回避は、届くレジストリを指定することです。mydocker pull mirror.gcr.io/library/alpine のように書けます。ParseRef が先頭要素のドットを見てレジストリ名だと判断し、discoverAuth がそのレジストリの認証方式を自分で調べてくれるので、コードを1行も変えずに切り替えられます。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。

Q1. Accept ヘッダを付けずにマニフェストを取ると何が返ってきて、その結果コードのどこで詰まりますか?

manifest schema 1 という古い形式が返ってきます。HTTP は 200 で、JSON のパースも成功します。ただし schema 1 には layers というキーが無い（fsLayers という別のキーになっている）ので、manifest 構造体の Layers は nil のままになります。

詰まるのは Pull の if len(man.Layers) == 0 { return nil, fmt.Errorf("…マニフェストに layers がありません（schema 1 が返っている可能性があります）") } の行です。エラーメッセージ自体が原因を名指ししているので、ここに来たら Accept を疑います。

Q2. マニフェストリストの「最初の項目」を選ぶ実装は、なぜ確実に壊れるのですか?

リストには、イメージではない項目——attestation（署名の付随物）——が混ざっているからです。platform が {"architecture":"unknown","os":"unknown"}、注釈に vnd.docker.reference.type: attestation-manifest が付いた項目です。

並び順は保証されていないので、いつ先頭に来るか分かりません。そして掴んでしまったときの壊れ方が悪質です。HTTP 200 で正しい JSON が返り、ただ layers だけが無い。Q1 と同じ症状になり、原因が Accept なのか選択ミスなのか分からなくなります。

正しくは pickPlatform のように、d.Platform.OS == runtime.GOOS && d.Platform.Architecture == runtime.GOARCH で明示的に絞ります。

Q3. レイヤの保存先ディレクトリ名に digest を使うと、なぜそれだけでキャッシュになるのですか?

digest は中身そのものの SHA-256 だからです。名前が中身によって決まっているので、「同じ名前なら中身も同じ」が保証されます（content-addressable）。

この性質があると、キャッシュの判定が名前の存在確認だけで済みます。中身を比較する必要も、更新日時を見る必要も、世代を管理する必要もありません。中身が変われば名前も変わるので、上書きという概念すら不要です。isComplete(s.layerDir(layer.Digest)) という1行が、キャッシュ機構の全部です。

Q4. fetchLayer で io.Copy(io.Discard, body) を呼んでいるのはなぜですか? 展開はもう終わっているのに。

ハッシュを完成させるためです。

io.TeeReader は「読まれたぶんだけ」ハッシュ計算器に流します。逆に言えば、読まれなかったバイトはハッシュに反映されません。ExtractLayer は gzip ストリームを解きながら tar を読みますが、tar の終端に達した時点で読むのをやめるので、ストリームの末尾に数バイト残ることがあります。

その状態で hasher.Sum(nil) を呼ぶと、途中までのハッシュが出てきて digest と一致しません。展開は成功しているのに検証で落ちる、という理不尽なエラーになります。io.Copy(io.Discard, body) は残りを読み捨てて、TeeReader に最後まで流させるためだけの行です。「捨てるために読む」——目的はハッシュのほうにあります。

Q5. ParseRef("localhost:5000/foo:1.0") はどう分解されますか? ポート番号のコロンと混同しないのはなぜですか?

Registry: "localhost:5000"、Repository: "foo"、Tag: "1.0" になります。

順序が効いています。先にレジストリを剥がすので、タグを切り出す段階で見ているのは foo:1.0 だけです。先頭要素 localhost:5000 にはコロンが含まれるため strings.ContainsAny(head, ".:") が真になり、ホスト名と判定されます。

さらに二重の保険が掛かっています。タグの切り出しは strings.LastIndex(name, ":")（最後のコロン）を使い、かつ !strings.Contains(name[i:], "/")——そのコロンより後ろにスラッシュが無いこと——を確認します。タグは参照の末尾に来るので、タグを表すコロンの後ろにスラッシュが現れることはありえません。host:5000/bar なら最後のコロンの後ろが 5000/bar でスラッシュを含むため、タグとは判定されません。

ちなみに library/ の補完はされません。Docker Hub 以外だからです（ref.Registry == defaultRegistry の条件）。

Q6. 2回目の mydocker pull が通信を1回もしないのはなぜですか? 何が揃っていればそうなりますか?

Pull のいちばん先頭で s.fromCache(ref) を呼び、成功したらそこで return しているからです。http.Client を作るコードより前にあるので、トークンすら取りに行きません。

fromCache が成功する条件は4つ全部です。①manifests/<参照名>.json が読めること ②そのマニフェストの layers が1枚以上あること ③すべてのレイヤに .complete の印があること ④configs/<config の digest>.json が読めること。1つでも欠ければ false を返し、通常どおり通信して取りに行きます。

この「疑わしきは使わない」設計のおかげで、キャッシュが壊れていても最悪 HTTP が1往復増えるだけで、間違った中身でコンテナが起動することはありません。

まとめ — 次の層へ

docker pull の中身が、全部見えました。トークンを取り、マニフェストを取り、リストだったので digest で取り直し、config を読み、tar.gz を落として展開する。使ったのは net/http と encoding/json と crypto/sha256、全部 Go の標準ライブラリです。そして分かったのは、イメージとは tar.gz の列と JSON でしかないという身も蓋もない事実でした。alpine の正体は、圧縮 3.67 MiB の tar.gz 1枚と、611 バイトの JSON です。魔法はどこにもありませんでした。あるのは、初見で必ず踏む4つの段差——Accept 忘れ、マニフェストリスト、attestation、取得回数制限——だけで、それも全部踏み終えました。

しかし、今できているのはtar.gz を1枚ずつ展開しただけです。alpine はレイヤが1枚だったので、これで足りているように見えます。でも Image.LayerDirs が配列であることを思い出してください。実用的なイメージはレイヤが何枚もあります。そして私たちは、複数枚をどう重ねるかをまだ知りません。素朴に上から順に上書きコピーすればいい、と思うかもしれませんが、それでは足りないのです。上の層で「削除した」ファイルが、下の層にはまだ残っています。単純なコピーでは、消したはずのファイルが復活してしまいます。しかも、コンテナを起動するたびに 516 ファイルを全部コピーするのでは、起動が 12 ms で終わるはずがありません。

次章は OverlayFS です。カーネルに「この複数のディレクトリを、1つのディレクトリとして見せてくれ」と頼む仕組みで、重ね順も、削除の表現（whiteout）も、書き込みの行き先も、全部カーネルが面倒を見てくれます。そして——ここが本題ですが——コンテナの「使い捨て」の正体がここで分かります。なぜコンテナを消すと中で書いたファイルが消えるのか、なぜ同じイメージから 10 個のコンテナを立ち上げてもディスクが 10 倍にならないのか。LayerDirs のコメントにあった「★下から上の順（先頭が最下層）」という一言が、次章で効いてきます。
