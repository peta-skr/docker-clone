前章の宿題 — 名前空間は効いていた。それなのに

前章で私たちは Cloneflags に CLONE_NEWUTS、CLONE_NEWPID、CLONE_NEWNS、CLONE_NEWIPC の4枚を並べました。ホスト名は変わりました。$$（自分の PID）も 1 になりました。ところが ps を打つと、ホストで動いているプロセスがずらずらと出てきます。

ここで多くの人が「名前空間の作り方を間違えたのだろう」と考えます。私も最初はそう思って Cloneflags を何度も見直しました。しかしフラグは正しかったのです。この章の Step 5 で、その種明かしをします。先に結論だけ言っておくと、犯人は名前空間ではなくファイルシステムでした。つまり、コンテナが立っている「地面」の方です。

だから、この章のテーマは「地面の入れ替え」になります。順番としてもここが正しい。名前空間で見え方を区切っただけでは、コンテナはまだホストと同じディレクトリツリーの上に立っています。同じ /etc、同じ /usr、同じ /root。これでは「別の世界」とは呼べません。

「マウント名前空間は分けたのに、なぜ同じ / を見ているの?」という疑問はもっともです。マウント名前空間を分けると、マウントの一覧が複製されて、以後の変更が互いに伝わらなくなるだけで、複製された時点の中身は元と同じです。分身を作っただけで、まだ何も入れ替えていない。ここから先が本章の仕事になります。

「地面を入れ替える」とは何をすることか

Linux のファイルシステムは / を頂点とした1本の木です。/usr/bin/ls というパスは、/ から usr → bin → ls と降りていく道順を書いたものにすぎません。ということは、その / が別のものに差し替わってしまえば、同じパスを書いても全く別の場所に着くわけです。

私たちの手元には、これから使いたい「別の世界の中身」があります。alpine のイメージを展開したディレクトリ（この本ではこれを rootfs と呼びます）です。中には bin、etc、lib、usr といった、いかにも root らしい顔ぶれが入っています。ただし、今のところそれはホストから見ればただの一つのディレクトリです。

やりたいこと 【今】 【したい】 / ← ホストの root / ← rootfs が root になる |- bin |- bin |- etc |- etc |- usr |- lib |- root |- usr +- var +- var +- lib +- mydocker +- .../merged ← rootfs (ホストの / はどこにも見えない) |- bin |- etc +- usr

この「差し替え」をやってくれるシステムコールが2つあります。chroot と pivot_root です。名前からすると chroot（change root）の方が素直に見えます。実際、まずはそちらを試すべきです。試して、破れることを自分の目で見てから pivot_root に進む。それがこの章の進み方です。

Step 1まず chroot を試して、破ってみる

素朴な案から始めます。chroot("/tmp/jail") を呼べば、そのプロセスにとって /tmp/jail が / になります。牢屋（jail）という呼び方が定着しているくらいで、いかにも閉じ込められそうです。

実験用に /tmp/jail を作り、中に bin と inner という2つのディレクトリだけを置いておきました。ここに chroot したプロセスからは、世界にこの2つしか無いように見えるはずです。そして実際そう見えます。問題はその後です。

次の Python スクリプトを読んでください。Go ではなく Python なのは、os.chroot が標準ライブラリにあって短く書けるからです。やっていることに言語は関係ありません。

escape.py（この章だけの実験用。実装には含まれない）
import os
fd = os.open("/", os.O_RDONLY)      # ★chroot する前に、外の / を掴んでおく
os.chroot("/tmp/jail")              # 牢に入る
os.chdir("/")
print("chroot 直後の ls / :", sorted(os.listdir("/")))
os.fchdir(fd)                       # 掴んでおいた外のディレクトリへ戻る
for _ in range(64):
    os.chdir("..")                  # 上へ登り切る
os.chroot(".")                      # 牢を「今いる場所」に付け替える
print("脱獄後の  ls / :", sorted(os.listdir("/"))[:12])

手口は4手です。順に見ます。

  1. chroot する前に、外側のディレクトリを open しておく。 これで、そのプロセスは「外の / を指すファイルディスクリプタ」を1本、手に握った状態になります。
  2. chroot する。 ここでプロセスから見た / は /tmp/jail になります。ls / をすれば bin と inner しか出ません。牢は閉まったように見えます。
  3. fchdir(fd) で、掴んでおいた場所へ移動する。 ここが要です。fchdir はパス名を辿りません。ディスクリプタが直接指している場所へ、一瞬で移るのです。パスを辿らないのだから / がどこに付け替えられていようと関係ありません。
  4. .. を登り切ってから chroot(".")。 今いる場所は牢の外なので、そこから .. を繰り返せば本物の / に着きます（64 回も登れば十分です）。そして今いる場所を新しい root として chroot し直せば、牢は消えます。
chroot が変えるもの / 変えないもの プロセスが持っている情報 ------------------------------------------------ fs->root = /tmp/jail ← chroot が書き換えるのはここだけ fs->pwd = /tmp/jail ← chdir("/") でここに来る fd[3] = (chroot 前の /) ← 誰も無効化してくれない ★ここが穴 fchdir(3) でいつでも戻れる

2行目に boot や etc、home が並んでいます。これはホストの / です。 牢の中から、たった数行で外に出てしまいました。

LINUX メモ · chroot は「見え方」しか変えない

chroot がやることは、カーネルの中にあるそのプロセスの情報のうち「root はここ」という1項目を書き換えることだけです。パス名を / から解決するとき、その項目が起点として使われます。だから /etc/passwd と書けば /tmp/jail/etc/passwd が開きます。

問題は、プロセスが既に持っている参照には手を触れないことです。開いてあるファイルディスクリプタ、現在の作業ディレクトリ、他のプロセスから受け取ったディスクリプタ——これらは「パス名で辿る」ものではなく「もう掴んでいる」ものなので、root の付け替えの影響を受けません。上の実験は、その性質をそのまま突いています。

ここから導かれる教訓は「chroot は間違っている」ではなく、「chroot はセキュリティ境界として設計されていない」です。もともとはビルド環境を切り替えるための道具でした。隔離のために使うなら、別の道具が要ります。

ではどうするか。穴の正体が「外側への参照が生き残ること」なら、対策は一つしかありません。外側そのものを、マウント木から消してしまうことです。参照先が木から切り離されていれば、そこへ fchdir で戻ったところで、そこから上へ登る道がありません。

それをやるのが pivot_root です。pivot_root(new_root, put_old) は、マウント名前空間の root を new_root に付け替えると同時に、古い root を put_old の位置へ「押し出し」ます。押し出されたものは普通のマウントとして put_old にぶら下がっているだけなので、後から umount で切り離せます。切り離せば、参照ごと消えます。

Step 2伝播を切る — なぜ最初にこれが要るのか

最初のブロックは、一見すると何もしていないように見えます。

internal/container/init.go
	// 1. マウントの伝播をホストから切る。
	//    これをやらないと、この後の bind mount や /proc のマウントがホスト側に漏れる。
	if err := syscall.Mount("", "/", "", syscall.MS_PRIVATE|syscall.MS_REC, ""); err != nil {
		return fmt.Errorf("マウントの伝播を切れませんでした: %w", err)
	}

第1引数（source）は空文字、第3引数（fstype）も空文字、最後のデータも空文字。実質的に指定しているのは「/ に対して MS_PRIVATE|MS_REC という属性を設定する」ことだけです。何かを新しくマウントしているわけではありません。マウントの性質を変える呼び出しです。

では、変えている性質とは何か。「伝播」です。

LINUX メモ · マウントの伝播（shared subtree）

マウントには「伝播」という性質があります。ある名前空間でマウントを追加したとき、それを他の名前空間にも自動で反映するかどうかを決める設定です。既定値は多くのディストリビューションで shared（共有）になっています。理由はもっともで、たとえば USB メモリを挿したとき、システム中のあらゆる名前空間からそれが見えてほしいからです。

主な種類は3つです。shared は双方向に伝わる。slave は親から子へは伝わるが逆は伝わらない。private はどちらにも伝わらない。コンテナが欲しいのは private です。コンテナの中で /proc を貼り直したからといって、ホストの /proc まで貼り替わっては困ります。

MS_REC（recursive）は「/ の下にぶら下がっているすべてのマウントにも同じ設定を及ぼす」という意味です。ホストには /proc、/sys、/dev、/run など多くのマウントがあり、この環境では合計 22 個ありました。1つでも shared のまま取り残すと、そこから漏れます。だから再帰なのです。

伝播を切る前と後 【切る前】shared 【切った後】private ホストのマウント木 ホストのマウント木 | | | 双方向に伝わる X 伝わらない | | コンテナのマウント木 コンテナのマウント木 | | +- ここで mount すると +- ここで何をしても ホストにも同じものが増える ホストは 22 個のまま

「マウント名前空間を分けたのに、まだ伝わるのか?」と思うかもしれません。私も同じところで引っかかりました。名前空間を分けることと、伝播を切ることは別の操作です。 名前空間を分けるのは「マウント一覧の写しを作る」こと。伝播はその写しと元の間に張られたパイプで、写しを作っただけではパイプは残っています。MS_PRIVATE はそのパイプを外す操作です。

実は前章の run.go にも、この件に関する仕込みが1行入っていました。

internal/container/run.go（第02章で見た箇所）
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags: syscall.CLONE_NEWUTS | // ホスト名
			syscall.CLONE_NEWPID | // プロセス番号
			syscall.CLONE_NEWNS | // マウント
			syscall.CLONE_NEWIPC, // プロセス間通信
		// ⚠ これを忘れると、コンテナ内で行ったマウントがホスト側にも伝播する。
		//    pivot_root が EINVAL で落ちる原因にもなる。「なぜか動かない」の筆頭。
		Unshareflags: syscall.CLONE_NEWNS,
	}

Unshareflags は Go の os/exec が用意している仕掛けで、子プロセスを起動する直前に unshare(2) を呼ばせるものです。Cloneflags にも CLONE_NEWNS があるのに二重に見えますが、この2行はホスト側で先に伝播の縁を切っておくために効いてきます。そして子の側では、いま見た MS_PRIVATE|MS_REC でもう一度、確実に切ります。ベルトと吊りひもの両方を着けているわけです。

⚠ 落とし穴 · 伝播を切らないと、ホストのマウントが増えていく

この1ブロックを省いても、コンテナはしばらく普通に動いてしまいます。だから気付きにくい。しかし裏では、コンテナを起動するたびにホストのマウント一覧に overlay や bind mount が積み上がっていきます。何十回か起動したあとにホストが妙に遅くなり、mount の出力が画面に収まらなくなって、ようやく気付く——という壊れ方をします。

さらに悪いことに、この状態では pivot_root 自体が EINVAL で落ちることがあります。pivot_root は「新しい root が shared なマウントであってはならない」という条件を持っているためです。「pivot_root が EINVAL」と出たら、まず伝播を疑う。 これは覚えておく価値のある対応関係です。

Step 3rootfs を自分自身に bind mount する

2つめのブロックは、初めて見ると一番わけが分からない箇所です。同じパスを2回書いています。

internal/container/init.go
	// 2. ⚠ 新しい root は「マウントポイント」でなければならない。
	//    普通のディレクトリを渡すと pivot_root は EINVAL で落ちる。
	//    自分自身に bind mount することでマウントポイントの条件を満たす。
	if err := syscall.Mount(rootfs, rootfs, "", syscall.MS_BIND|syscall.MS_REC, ""); err != nil {
		return fmt.Errorf("rootfs を自分自身に bind mount できませんでした (%s): %w", rootfs, err)
	}

syscall.Mount(rootfs, rootfs, ...)。source も target も同じ rootfs です。何も移動していないのだから、実行後にファイルの見え方は1バイトも変わりません。それなのに、この行が無いと pivot_root は動きません。

理由は pivot_root(2) の規則にあります。新しい root に渡せるのは「マウントポイント」だけで、ただのディレクトリは受け付けてくれません。ところが私たちの rootfs は、イメージを展開しただけの普通のディレクトリです（第06章で overlayfs を導入すると merged は本物のマウントポイントになりますが、それでもこの行は残しておきます。理由は後述します）。

そこで MS_BIND の出番です。bind mount は「あるディレクトリを、別の場所にもう一度生やす」マウントで、行き先を自分自身にすることもできます。自分の上に自分を重ねると、見え方は変わらないまま、そのパスは「マウントポイントである」という資格を得ます。カーネルのマウント一覧に1行増えるからです。まさに、規則を満たすためだけの操作です。

bind mount 前と後（見え方は同じ、資格だけが変わる） 【前】カーネルのマウント一覧 rootfs は… / on / ext4 ただのディレクトリ /proc on /proc proc → pivot_root は EINVAL ... (全 22 行) 【後】カーネルのマウント一覧 rootfs は… / on / ext4 マウントポイント /proc on /proc proc → pivot_root の条件を満たす ... (全 22 行) ROOTFS on ROOTFS bind ← この1行が増えただけ
LINUX メモ · pivot_root(2) の規則

pivot_root(new_root, put_old) には、満たさなければならない条件がいくつもあります。実装で効いてくるのは次の3つです。

(1) new_root はマウントポイントでなければならない。 普通のディレクトリでは EINVAL。Step 3 の bind mount はこれを満たすためのものです。

(2) put_old は new_root の配下（下の階層）でなければならない。 古い root を新しい root の外に置くことはできません。「押し出した先」が新しい世界から見えないと、後で umount できないからです。本実装が rootfs/.old_root を作るのはこの規則のためです。

(3) new_root も現在の root も、伝播が shared であってはならない。 Step 2 の MS_PRIVATE はこれを満たすためのものでもあります。3つの条件が「Step 2 → Step 3 → Step 4」という順序を決めているわけです。

ちなみに MS_REC を付けているのは、rootfs の下に既に何かがマウントされていた場合に、それも一緒に持っていくためです。イメージを展開しただけの状態では下に何もありませんが、付けておいて損はありません。

⚠ 落とし穴 · EINVAL は「引数が不正」としか言ってくれない

pivot_root が失敗したときのエラーは、多くの場合 invalid argument の一言です。5つある条件のどれを破ったのかは教えてくれません。私はここで半日溶かしました。落ちたときに疑う順番を決めておくと早いです。

  1. Step 2 を省いていないか（伝播が shared のまま）
  2. Step 3 を省いていないか（new_root がただのディレクトリ）
  3. put_old が new_root の中にあるか（/tmp/old のような外側の場所を渡していないか）
  4. そもそもマウント名前空間の中にいるか（CLONE_NEWNS を付け忘れていないか）

この4つを上から順に見れば、まず当たります。

Step 4根を挿げ替える — pivot_root を呼ぶ

下ごしらえが済みました。ここが山場です。3つのブロックが続きます。

GO メモ · syscall.PivotRoot と syscall.Mount の引数

Go の syscall パッケージは、Linux のシステムコールをほぼそのままの形で公開しています。だから man 2 pivot_root と見比べながら読めます。

syscall.PivotRoot(newroot, putold string) error — C の pivot_root(2) そのままです。返り値が int と errno ではなく error になっているのが Go らしいところで、失敗すると syscall.Errno 型の値が返ります。これは error インターフェースを満たすので、そのまま %w で包めます。

internal/container/init.go
// pivotRoot は rootfs をコンテナの新しい / にする。
//
// ⚠ この順序を崩すと必ず失敗する。1つずつ理由がある。
//
// chroot ではなく pivot_root を使うのは、chroot には抜け出す既知の手口があり、
// 古い root のマウントも残るため。pivot_root は古い root を完全に切り離せる。
func pivotRoot(rootfs string) error {
	// 1. マウントの伝播をホストから切る。
	//    これをやらないと、この後の bind mount や /proc のマウントがホスト側に漏れる。
	if err := syscall.Mount("", "/", "", syscall.MS_PRIVATE|syscall.MS_REC, ""); err != nil {
		return fmt.Errorf("マウントの伝播を切れませんでした: %w", err)
	}

	// 2. ⚠ 新しい root は「マウントポイント」でなければならない。
	//    普通のディレクトリを渡すと pivot_root は EINVAL で落ちる。
	//    自分自身に bind mount することでマウントポイントの条件を満たす。
	if err := syscall.Mount(rootfs, rootfs, "", syscall.MS_BIND|syscall.MS_REC, ""); err != nil {
		return fmt.Errorf("rootfs を自分自身に bind mount できませんでした (%s): %w", rootfs, err)
	}

	// 3. 古い root の置き場を新しい root の中に用意する。
	//    ⚠ put_old は new_root の配下でなければならない。これも規則。
	putOld := filepath.Join(rootfs, oldRoot)
	if err := os.MkdirAll(putOld, 0o700); err != nil {
		return fmt.Errorf("古い root の置き場を作れませんでした: %w", err)
	}

	// 4. 根の挿げ替え。ここで / が入れ替わる。
	if err := syscall.PivotRoot(rootfs, putOld); err != nil {
		return fmt.Errorf("pivot_root に失敗しました: %w", err)
	}

	// 5. 作業ディレクトリは古い root を指したままなので、新しい / に移る。
	if err := syscall.Chdir("/"); err != nil {
		return fmt.Errorf("新しい / へ移動できませんでした: %w", err)
	}
	return nil
}

⚠ 落とし穴 · 「namespace が壊れている」と誤診する

この症状に出会ったとき、9割の人は名前空間のフラグを疑います。CLONE_NEWPID のスペルを確かめ、Cloneflags の | を数え直し、カーネルのバージョンを調べ始めます。そこには何の問題もありません。

診断の決め手は echo $$ です。$$ が 1 なのに ps がホストを出すなら、名前空間は効いていて /proc だけが古い——この組み合わせを覚えておけば、二度と半日を失いません。

なぜ /proc なのか

種明かしをします。ps はプロセスの一覧をカーネルに問い合わせているわけではありません。 /proc の下にあるディレクトリを読んでいるだけです。/proc/1、/proc/42、/proc/1337——数字の名前が付いたディレクトリを片っ端から開き、その中の stat や cmdline を読んで表を作っています。ps は、言ってしまえば ls /proc の親戚です。

そして /proc は procfs という特別なファイルシステムで、マウントされたその瞬間の PID 名前空間に結び付けられます。ホストで起動時にマウントされた /proc は、ホストの PID 名前空間を映す鏡です。コンテナがその鏡をそのまま覗いていれば、映るのはホストの世界です。

/proc がどこを指しているか 【貼り直す前】 コンテナのプロセス | | ps が読む v /proc ────────→ ホストの PID 名前空間 ← 起動時にホストがマウントした鏡 (85 個のプロセス) ※ PID 名前空間そのものは分かれている。$$ はちゃんと 1 になる。 分かれていないのは「鏡」の方。 【貼り直した後】 コンテナのプロセス | | ps が読む v /proc ────────→ コンテナの PID 名前空間 ← 自分でマウントし直した鏡 (1 個のプロセス)

だから正しい言い方はこうなります。PID 名前空間は効いていた。見えていたのは /proc の中身であって、名前空間の中身ではなかった。 私たちは名前空間を疑っていたのに、実際には「古い鏡を見続けていた」だけだったのです。

LINUX メモ · procfs は「ファイルに見せかけたカーネルの窓口」

/proc の下にあるものはディスク上に存在しません。読もうとした瞬間にカーネルがその場で内容を作って返します。/proc/self/status を cat するたびに値が変わるのはそのためです。

この「その場で作る」性質があるから、マウントするときにどの名前空間に結び付けるかが決まるのです。ファイルの実体を移動しているのではなく、窓口をどこに向けるかを決めている。/proc を貼り直すという操作は、実体のコピーではなく宛先の変更だと考えると腑に落ちます。

ついでに言うと、/proc/self/exe を使って自分自身を起動する第01章の re-exec も、/proc/<pid>/ns/pid を開いて名前空間に参加する第07章の exec も、すべてこの窓口の上に成り立っています。/proc が無いコンテナは、道具箱を持たずに現場に来たようなものです。

Step 6古い root を捨てる — MNT_DETACH

Step 4 の図を思い出してください。ホストの root はまだ /.old_root にぶら下がっています。このままでは、Step 1 の脱獄と同じ理屈で外へ出られます。というより、cd /.old_root と打つだけで出られます。捨てなければ意味がありません。

internal/container/init.go
// dropOldRoot は古い root を切り離して捨てる。
// ⚠ /proc を貼り直した後に呼ぶこと。順序を逆にすると /proc のマウントで古い root を掴む。
func dropOldRoot() error {
	// MNT_DETACH は遅延アンマウント。まだ参照が残っていても切り離せる。
	if err := syscall.Unmount(oldRoot, syscall.MNT_DETACH); err != nil {
		return fmt.Errorf("古い root を切り離せませんでした: %w", err)
	}
	if err := os.Remove(oldRoot); err != nil && !os.IsNotExist(err) {
		return fmt.Errorf("古い root の置き場を消せませんでした: %w", err)
	}
	return nil
}

2段構えです。まず syscall.Unmount でマウント木から切り離し、次に os.Remove で空になったディレクトリを消します。切り離した後の /.old_root は、中身が空の普通のディレクトリに戻っています。だから os.Remove（空ディレクトリしか消せない安全な方）で足ります。os.RemoveAll ではありません。順序を間違えて Remove を先にしたら、マウント越しにホストのファイルを消しにいくことになります。

!os.IsNotExist(err) の条件は「既に無いなら、それは成功と同じ」という意味です。冪等（何度やっても同じ結果）にしておくと、後片付けの処理は書きやすくなります。

古い root が切り離される様子 【pivot_root 直後】 【dropOldRoot の後】 / / |- bin |- bin |- etc |- etc |- proc ← Step 5 で貼った |- proc +- .old_root ← ホストの root が (.old_root は消滅) |- bin まるごと見えている |- etc ホストへ戻る道は |- home マウント木から消えた +- var
LINUX メモ · MNT_DETACH（遅延アンマウント）

普通の umount は、そのファイルシステムを誰かが使っていると EBUSY（デバイスが使用中）で失敗します。誰かが開いているファイル、誰かの作業ディレクトリ——1つでもあれば断られます。

MNT_DETACH はこの制約を外します。マウント木からの切り離しだけを直ちに行い、実際の解放は最後の参照が消えるまで待つという動きです。「遅延アンマウント」と呼ばれます。umount -l の -l（lazy）がこれです。

私たちの場面ではこれが理想的に働きます。切り離した瞬間から、新しく /.old_root を辿ってホストへ行くことはできなくなる。まだ古い参照を握っているプロセスがいたとしても、その参照は木から浮いた孤島を指しているだけで、そこから上へは登れません。chroot の穴が、ここで塞がります。

裏返しの注意もあります。MNT_DETACH は失敗しにくいぶん、「切れたつもり」で先に進みやすい。第07章で後片付けを書くときには、umount の結果を無視して rm -rf に進む実装がイメージの実体まで消すという事故につながります。そちらでは MNT_DETACH に頼らず、エラーを見て止まる作りにしています。

さて、この関数をどこから呼ぶかが本題です。mountSpecialFilesystems の中、/proc をマウントした直後です。

internal/container/init.go
	if err := syscall.Mount("proc", "/proc", "proc", 0, ""); err != nil {
		return fmt.Errorf("/proc をマウントできませんでした: %w", err)
	}

	// ここまで来れば古い root はもう要らない。
	// ⚠ /proc より先に捨てると、/proc のマウントが古い root を掴んで失敗することがある。
	if err := dropOldRoot(); err != nil {
		return err
	}
⚠ 落とし穴 · /proc より先に古い root を捨てると失敗する

直感的には「危ないものは早く捨てたい」ので、pivot_root の直後に dropOldRoot を呼びたくなります。実際、私は最初そう書きました。そして /proc のマウントが失敗しました。

理由はこうです。pivot_root の直後、プロセスはまだ古い root に紐づいた状態をいくつも引きずっています。その状態で古い root を切り離してしまうと、続く mount の処理が足場を失って転びます。/proc を先に貼って足場を作り、それから古い足場を蹴る。 順序はこれで固定です。

2つの「⚠」がコード中で向かい合っているのはそのためです。dropOldRoot のコメントは「/proc を貼り直した後に呼ぶこと」、呼び出し側のコメントは「/proc より先に捨てると失敗する」。同じ規則を、書く側と呼ぶ側の両方から釘を刺してあります。

Step 7/sys と /dev を用意する

残りは2つです。どちらも /proc ほど死活的ではありませんが、無いと不便な場面が出ます。

			syscall.MS_NOSUID|syscall.MS_NOEXEC|syscall.MS_NODEV|syscall.MS_RDONLY, ""); err != nil {

}

/sys のマウントには4つのフラグが並んでいます。読み方は素直です。MS_NOSUID（setuid ビットを無視する）、MS_NOEXEC（このファイルシステム上のバイナリを実行させない）、MS_NODEV（デバイスファイルとして扱わない）、MS_RDONLY（読み取り専用）。sysfs はカーネルの設定を書き換えられる窓口なので、コンテナからは読むだけにしておきます。

そして /proc と違うのは、失敗してもエラーを返さない点です。fmt.Fprintf(os.Stderr, ...) で警告を出すだけで先に進みます。/proc が無ければ ps すら動かないので致命的ですが、/sys が無くてもシェルは普通に使えます。どこを致命扱いにし、どこを警告で流すかは設計判断で、この判断はコメントに書き残してあります。

/dev を自分で組み立てる

/dev は、この章で唯一「借りてこない」場所です。ホストの /dev を bind mount すれば1行で済むのに、そうしていません。 なぜか。

⚠ 落とし穴 · ホストの /dev を bind mount するとホストのディスクに手が届く

/dev にあるのはファイルの形をしたデバイスへの入口です。/dev/sda や /dev/nvme0n1 はホストのディスクそのもので、root 権限で開いて書き込めば、ファイルシステムを飛び越えて生のブロックを書き換えられます。パーティションテーブルを壊すことも、他のファイルを直接読み出すこともできます。

コンテナの中は（この実装では）root です。そこにホストの /dev をそのまま見せるということは、隔離のためにここまで積み上げてきたものを、最後の1行で全部無効にするということです。pivot_root でホストのファイルツリーを消したのに、/dev/sda 経由でその中身に手が届いてしまう。

だから /dev だけは、借りずに自分で組み立てます。空の tmpfs を敷いて、そこに本当に必要なノードだけを mknod で作る。作らなかったものは存在しません。

/dev の作り方の違い 【bind mount する案】 【tmpfs + mknod の案（採用）】 /dev ──→ ホストの /dev /dev = tmpfs (64k, mode=755) |- null |- null 1:3 |- zero |- zero 1:5 |- sda ★ホストのディスク |- full 1:7 |- nvme0n1 ★ホストのディスク |- random 1:8 |- kmsg |- urandom 1:9 +- ... (数百) |- tty 5:0 |- fd -> /proc/self/fd |- stdin -> /proc/self/fd/0 |- stdout -> /proc/self/fd/1 +- stderr -> /proc/self/fd/2 1行で済むが穴が空く 書く量は増えるが、無いものは触れない

実装を全文見ます。まず、作りたいノードを表すための小さな型があります。

internal/container/init.go
// devNode は最小限のデバイスノード定義。
type devNode struct {
	path  string
	mode  uint32
	major uint32
	minor uint32
}

func mountDev() error {
	if err := os.MkdirAll("/dev", 0o755); err != nil {
		return err
	}
	if err := syscall.Mount("tmpfs", "/dev", "tmpfs", syscall.MS_NOSUID, "mode=755,size=64k"); err != nil {
		return err
	}
	nodes := []devNode{
		{"/dev/null", syscall.S_IFCHR | 0o666, 1, 3},
		{"/dev/zero", syscall.S_IFCHR | 0o666, 1, 5},
		{"/dev/full", syscall.S_IFCHR | 0o666, 1, 7},
		{"/dev/random", syscall.S_IFCHR | 0o666, 1, 8},
		{"/dev/urandom", syscall.S_IFCHR | 0o666, 1, 9},
		{"/dev/tty", syscall.S_IFCHR | 0o666, 5, 0},
	}
	for _, n := range nodes {
		if err := syscall.Mknod(n.path, n.mode, int(mkdev(n.major, n.minor))); err != nil {
			fmt.Fprintf(os.Stderr, "警告: %s を作れませんでした: %v\n", n.path, err)
		}
	}
	// 標準入出力へのシンボリックリンク。シェルが期待することがある。
	_ = os.Symlink("/proc/self/fd", "/dev/fd")
	_ = os.Symlink("/proc/self/fd/0", "/dev/stdin")
	_ = os.Symlink("/proc/self/fd/1", "/dev/stdout")
	_ = os.Symlink("/proc/self/fd/2", "/dev/stderr")
	return nil
}

順に読みます。

tmpfs を size=64k で敷く。 デバイスノードは実体を持たない（番号の組を書いたエントリがあるだけ）ので、64 キロバイトもあれば十分すぎます。小さく取ることで、コンテナが /dev にファイルを書き込んでホストのメモリを食い潰す道も塞いでいます。mode=755 は /dev 自体のパーミッション、MS_NOSUID はここでも setuid 封じです。

6つのノードを作る。 それぞれ「メジャー番号:マイナー番号」の組でカーネル内のドライバに結び付いています。1:3 が null、1:5 が zero、1:8 が random——これらは Linux で固定された番号です。syscall.S_IFCHR は「キャラクタデバイスである」という印で、0o666（誰でも読み書き可）と OR して mode にします。ディスクのようなブロックデバイス（S_IFBLK）は1つも作っていません。 これがこの設計の要点です。

失敗しても警告だけ。 Mknod がエラーでもループは止まりません。たとえば /dev/tty が作れなくても、多くのコマンドは動きます。全部か無かにしない、というのはここでも同じ方針です。

4本のシンボリックリンク。 /dev/stdout に書けば標準出力に流れる、という約束をシェルやツールが期待することがあります。実体は /proc/self/fd/1 なので、リンクを張るだけで済みます。Step 5 で /proc を貼っていなければ、このリンクは全部壊れたリンクになります。 順序がここでも効いています。返り値を _ で捨てているのは、失敗しても構わないという意思表示です。

最後に、デバイス番号を1つの数値にまとめる関数です。ビット演算だけの小さな関数ですが、載せておきます。

internal/container/init.go
func mkdev(major, minor uint32) uint64 {
	return uint64(minor&0xff) | (uint64(major&0xfff) << 8) |
		((uint64(minor) &^ 0xff) << 12) | ((uint64(major) &^ 0xfff) << 32)
}

mknod(2) は major と minor を別々ではなく、1つの整数に詰めた形で受け取ります。詰め方が歴史的な事情でこの通り歪んでいて、下位 8 ビットに minor の下位、その上に major の下位 12 ビット、さらに上へ残りを追い出す、という配置になっています。&^ は Go 独特の演算子（AND NOT、ビットクリア）で、uint64(minor) &^ 0xff は「minor の下位 8 ビットを落とした残り」を意味します。この関数は暗記するものではありません。 C のマクロ makedev() と同じことをしている、と分かれば十分です。

GO メモ · エラーを返すか、警告で流すか

この章のコードには2つの流儀が混在しています。return fmt.Errorf(...) で止めるものと、fmt.Fprintf(os.Stderr, "警告: ...") で先に進むものです。使い分けの基準は「それが無いとコンテナが目的を果たせないか」の一点です。

止めるのは pivot_root の5ブロックと /proc。これらが欠けたコンテナは、隔離されていないか、ps すら動かないので、動かす意味がありません。

流すのは /sys と /dev、それに個々のデバイスノード。無くても大半の用は足ります。ここで止めてしまうと、環境の些細な違いで起動しないコンテナランタイムになります。

大事なのは黙って流さないことです。標準エラーに1行出しておけば、後で「なぜか /dev/tty が無い」と悩んだときに手がかりが残ります。_ = os.Symlink(...) のように完全に捨てているのは、失敗しても実害がほぼ無いと判断した箇所だけです。

ここまでで mountSpecialFilesystems は完成です。全文を通して読むと、Step 5・6・7 が1本の流れになっているのが分かります。

internal/container/init.go
// mountSpecialFilesystems は /proc /sys /dev を新しい root に貼り直す。
//
// ⚠ /proc を貼り直さないと PID 名前空間が効いていないように見える。
// 実際には効いているのに、/proc がホストのものを指したままなので
// ps がホストの全プロセスを出す。「namespace が壊れている」と誤診する典型である。
func mountSpecialFilesystems() error {
	// /proc は必須。ps が動くための最低条件。
	if err := os.MkdirAll("/proc", 0o555); err != nil {
		return err
	}
	if err := syscall.Mount("proc", "/proc", "proc", 0, ""); err != nil {
		return fmt.Errorf("/proc をマウントできませんでした: %w", err)
	}

	// ここまで来れば古い root はもう要らない。
	// ⚠ /proc より先に捨てると、/proc のマウントが古い root を掴んで失敗することがある。
	if err := dropOldRoot(); err != nil {
		return err
	}

	// /sys は無くても ps は動く。失敗しても致命ではないので警告に留める。
	if err := os.MkdirAll("/sys", 0o555); err == nil {
		if err := syscall.Mount("sysfs", "/sys", "sysfs",
			syscall.MS_NOSUID|syscall.MS_NOEXEC|syscall.MS_NODEV|syscall.MS_RDONLY, ""); err != nil {
			fmt.Fprintf(os.Stderr, "警告: /sys をマウントできませんでした: %v\n", err)
		}
	}

	// /dev は tmpfs を敷いて、必要な最小限のデバイスノードだけを自分で作る。
	// ホストの /dev をそのまま見せるとコンテナからホストのディスクが触れてしまう。
	if err := mountDev(); err != nil {
		fmt.Fprintf(os.Stderr, "警告: /dev を用意できませんでした: %v\n", err)
	}
	return nil
}

つまずき FAQ

chroot ではだめなんですか? 実際に動いてはいますよね。

動きます。ただ、抜け出す方法が知られています。Step 1 で実際に破ってみせたとおり、chroot する前にディレクトリのファイルディスクリプタを掴んでおけば、fchdir でそこへ戻れてしまいます。chroot はパス名の起点を付け替えるだけで、既に握られている参照には触らないからです。

これは chroot のバグではありません。chroot(2) はもともとビルド環境を切り替えるための道具で、敵対的なプロセスを閉じ込める目的で設計されていないのです。man ページにも「セキュリティ機構として意図されていない」という趣旨のことが書かれています。

pivot_root を選ぶ理由は2つあります。(1) 古い root を put_old に押し出してマウント木ごと切り離せるので、戻る道自体が消える。(2) 古い root にぶら下がっていたマウントも一緒に片付くので、後始末が確実になる。第03章の実装がこの順序で書かれているのは、この2点のためです。

pivot_root したのに、なぜ /proc を貼り直さないと ps が壊れるんですか? root は入れ替わったのに。

pivot_root が入れ替えるのはマウント木の根であって、既にマウントされているものの中身ではありません。ホストの /proc は、ホスト起動時に「ホストの PID 名前空間を映す鏡」としてマウントされたもので、pivot_root の後もその性質のままです。

ただし本実装では、pivot_root の直後にコンテナの /proc は空のディレクトリです（イメージの中の /proc は空だから）。だから貼り直さないと ps は何も読めません。unshare --pid --fork で 87 と出たのは、pivot_root をしていないためにホストの /proc をそのまま見ていたケースです。

いずれにせよ結論は同じで、「PID 名前空間を作ったら、その中で /proc を新しくマウントする」がワンセットです。片方だけでは成立しません。

MS_PRIVATE と MS_REC の違いが分かりません。両方要るんですか?

役割が別なので両方要ります。

MS_PRIVATE は「何をするか」です。伝播の種類を private（どちらにも伝えない）にします。shared のままだと、コンテナ内のマウントがホストに漏れ、ホストのマウント一覧が起動のたびに増えます。

MS_REC は「どこまでやるか」です。指定したディレクトリの下にぶら下がっている全マウントにも同じ処理を及ぼします。/ だけを private にしても、その下の /proc、/sys、/run などが shared のまま残ってしまい、そこから漏れます。この環境ではホストに 22 個のマウントがありました。1つ残らず切るために再帰が要ります。

覚え方としては「private が動詞、rec が範囲」です。MS_BIND|MS_REC の MS_REC も同じで、「bind するのは分かった、で、下も一緒に持っていくのか?」に答えています。

pivot_root が EINVAL で落ちます。何を疑えばいいですか?

EINVAL は「引数が不正」としか言わないので、条件を上から潰します。頻度順に4つです。

(1) 伝播を切っていない。 Step 2 の Mount("", "/", "", MS_PRIVATE|MS_REC, "") が抜けていないか。親側の Unshareflags: syscall.CLONE_NEWNS も確認してください。init.go と run.go の両方に警告コメントがあるのは、ここが最頻出だからです。

(2) new_root がマウントポイントでない。 Step 3 の自分自身への bind mount が抜けていないか。イメージを展開しただけのディレクトリは、そのままでは条件を満たしません。

(3) put_old が new_root の外にある。 /tmp/old のような場所を渡していないか。本実装は filepath.Join(rootfs, "/.old_root") で必ず内側になるようにしています。

(4) マウント名前空間の中にいない。 CLONE_NEWNS を付け忘れていないか。名前空間の外で pivot_root を呼ぶのは、ホストの root を挿げ替えるということなので、当然拒まれます。

/dev はホストのを bind mount した方が早いのでは? わざわざ mknod する意味がありますか?

早いです。そしてそこまでの隔離が全部無駄になります。

ホストの /dev には /dev/sda のようなブロックデバイスが並んでいます。これはホストのディスクへの生の入口で、root なら開いて書けます。ファイルシステムを介さないので、pivot_root でホストのファイルツリーを見えなくしたことは何の防御にもなりません。ディスクの中身を直接読み書きできてしまいます。

だから本実装は、/dev に size=64k の tmpfs を敷き、null・zero・full・random・urandom・tty の6つだけを mknod で作ります。すべてキャラクタデバイスで、ブロックデバイスは1つもありません。 作らなかったものはコンテナから見て存在しないので、触りようがありません。

「無いものは壊せない」という考え方は、この本を通して何度も出てきます。許可リストを短く保つのが、いちばん安上がりな防御です。

.old_root を消し忘れたらどうなりますか? 見えているだけなら害は無い気もしますが。

害しかありません。/.old_root はホストの root がそのままぶら下がっている場所なので、コンテナの中で cd /.old_root と打つだけで、ホストの /etc も /root も読めます。Step 1 で見た脱獄の、もっと簡単な版が成立します。

加えて、切り離していないと古い root のマウントが掴まれたままになり、コンテナ終了後の後片付け（第07章）で umount が EBUSY で失敗する原因にもなります。「見えている」だけでなく「掴んでいる」のが問題なのです。

本実装では dropOldRoot が MNT_DETACH で切り離し、空になったディレクトリを os.Remove で消します。消えていることは実測で確認できます — コンテナの中で ls /.old_root と打つと No such file or directory が返ります。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。すらすら言えなければ、対応するステップに戻ると効率がいいです。

Q1. rootfs を自分自身に bind mount するのはなぜ? これをしないと何が起きますか?

pivot_root(2) には「new_root はマウントポイントでなければならない」という規則があります。イメージを展開しただけの rootfs はただのディレクトリなので、この条件を満たしません。自分自身に bind mount すると、見え方は1バイトも変わらないままカーネルのマウント一覧に1行増え、「マウントポイントである」という資格だけが得られます。

これをしないと pivot_root は EINVAL（invalid argument）で落ちます。エラーメッセージは理由を教えてくれないので、原因に辿り着くのに時間がかかる部類の失敗です。

Q2. 02章の時点で PID 名前空間は正しく作れていた。それなのに ps がホストのプロセスを表示したのはなぜですか?

ps はカーネルに問い合わせているのではなく、/proc の下の数字ディレクトリを読んでいるだけだからです。そして /proc（procfs）は、マウントされた時点の PID 名前空間に結び付けられます。ホスト起動時にマウントされた /proc は、ホストの PID 名前空間を映す鏡のままです。

つまり、PID 名前空間は効いていた。見えていたのは /proc の中身であって、名前空間の中身ではなかったのです。実測でも、unshare --pid --fork の中で数えると 87 個（ホストの 85 個より多い!）、--mount-proc を足すと 3 個になりました。名前空間のフラグは1文字も変えていません。

診断の決め手は echo $$ です。$$ が 1 なら名前空間は効いています。そのうえで ps がホストを出すなら、犯人は /proc です。

Q3. chroot から抜け出す手口を、3行で説明してください。

(1) chroot する前にディレクトリを open して、外側を指すファイルディスクリプタを掴んでおく。

(2) chroot の後、fchdir(fd) でそこへ移る。fchdir はパス名を辿らないので、/ がどこに付け替えられていようと関係ない。

(3) .. を登り切って本物の / に着いたら、chroot(".") で牢を今いる場所に付け替える。以上で外に出られます。

本質は「chroot はパス解決の起点を変えるだけで、既に持っている参照を無効化しない」ことです。pivot_root + MNT_DETACH は参照先そのものをマウント木から切り離すので、同じ手が通りません。

Q4. dropOldRoot を /proc のマウントより先に呼ぶと何が起きますか?

/proc のマウントが失敗することがあります。pivot_root の直後、プロセスはまだ古い root に紐づいた状態を引きずっており、その足場を先に蹴ってしまうと、続くマウント処理が転びます。init.go にも「⚠ /proc より先に捨てると、/proc のマウントが古い root を掴んで失敗することがある」と書いてあります。

正しい順序は「/proc を貼って新しい足場を作る → 古い足場を捨てる」です。dropOldRoot の関数コメントと呼び出し側のコメントの両方に同じ規則が書かれているのは、どちらから読んでも間違えないようにするためです。

Q5. mount("", "/", "", MS_PRIVATE|MS_REC, "") を省くと、ホスト側に何が起きますか?

マウントの伝播が shared のまま残るので、コンテナの中で行ったマウントがホスト側にも現れます。コンテナを起動するたびにホストのマウント一覧が増えていき、この環境なら 22 個から静かに膨らんでいきます。すぐには壊れないので気付きにくいのが厄介です。

さらに、pivot_root には「new_root も現在の root も shared であってはならない」という条件があるため、pivot_root 自体が EINVAL で落ちることもあります。「pivot_root が EINVAL」→「まず伝播を疑う」という対応関係を覚えておくと早いです。

正しく切れていれば、テストの前後でホストのマウント数は変わりません（開始 22 → 終了 22）。

Q6. /dev を tmpfs + mknod で作るのはなぜ? ホストの /dev を bind mount した場合と何が違いますか?

ホストの /dev を bind mount すると、/dev/sda のようなブロックデバイスがコンテナから見えます。これはホストのディスクへの生の入口で、root なら開いて書き込めます。ファイルシステムを経由しないので、pivot_root でホストのファイルツリーを隠したことがまったく防御になりません。

本実装は size=64k の tmpfs を敷き、null(1:3)・zero(1:5)・full(1:7)・random(1:8)・urandom(1:9)・tty(5:0) の6つだけを mknod で作ります。すべて S_IFCHR、つまりキャラクタデバイスで、ブロックデバイスは1つもありません。

加えて /dev/fd・/dev/stdin・/dev/stdout・/dev/stderr を /proc/self/fd 系へのシンボリックリンクとして張ります。これは Step 5 で /proc を貼った後でなければ意味を持ちません。

まとめ — 次の層へ

コンテナは、ようやく「別の世界」になりました。第02章までは、名前空間で見え方を区切っただけで、地面はホストと同じものを踏んでいました。この章で pivot_root を通し、古い root を MNT_DETACH で切り離したことで、コンテナの中からホストのファイルへ辿り着く道はマウント木から消えました。chroot を実際に破ってみたのは、この「切り離す」という一手が飾りではないと納得するためです。そして /proc を貼り直したことで、前章から持ち越した謎も解けました——PID 名前空間は最初から効いていて、私たちが古い鏡を覗いていただけでした。

しかし、この世界には底がありません。中で動くプロセスは、メモリを好きなだけ確保できます。CPU を独占できます。プロセスをいくらでも生やせます。ホストのファイルは見えないのに、ホストの資源は無制限に食えるのです。試しにコンテナの中でメモリを確保し続けるプログラムを走らせれば、ホストごと巻き添えにできます。隔離とは「見えないこと」だけではなく「他人の分を奪えないこと」でもあった、というのが次に突き当たる壁です。1つのコンテナが暴走してホスト全体を道連れにできるうちは、まだ道具として使えません。

次章では、この世界に上限を設けます。使う仕組みは cgroup（control group）です。名前がいかにも難しそうで、私も最初は身構えました。ところが正体は拍子抜けするほど素直で、ディレクトリを作り、ファイルに数字を書き、別のファイルにプロセス番号を書く——それだけです。新しいシステムコールは1つも出てきません。しかも「設定できた」ことと「実際に効いた」ことは別物なので、10MB の上限をかけたコンテナで 100MB を確保しにいって、本当に殺されるところまで確かめます。
