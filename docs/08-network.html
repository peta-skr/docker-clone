外とつながる

ここまでの 7 章は、書いたコードを動かし、動いたことを実測で確かめて進んできました。この章だけは違います。ネットワークは実装していません。だからこの章は、動くコードの解説ではなく、なぜ手を出さなかったのか・実装するなら何が必要になるのか・どこで転ぶのかを渡す地図です。地図は歩いた道の記録ではありませんが、これから歩く人にとっては、たぶん記録より役に立ちます。

■ 先に正直に言っておくこと

この章には実装がありません。src/internal/network/ というディレクトリは存在せず、ネットワークを設定する関数も型も 1 つも書いていません。したがって、この章に Go のコードは 1 行も出てきません。存在しないコードを載せることになるからです。

代わりに出てくるのは、ip / iptables / sysctl といった シェルコマンドと、図と、概念の説明です。そしてそのシェルコマンドも、「実装するとこういう操作になる」という設計の説明として書いてあります。私が打って出力を採ったものではありません。

この章で「実際に打って、出力を採った」ものはただ 1 つ、いまのコンテナが外をどう見ているかを確かめる 1 コマンドだけです。それは次の節にそのまま貼ります。

まず現状を見る — ここだけは実測

第 02 章で、私たちは名前空間を 4 つ作りました。internal/container/run.go の Cloneflags に並んでいるのは CLONE_NEWUTS（ホスト名）・CLONE_NEWPID（プロセス番号）・CLONE_NEWNS（マウント）・CLONE_NEWIPC（プロセス間通信）の 4 つです。第 02 章で名前空間を 6 種類並べたとき、私は「このうち NET はこの教材では作らない」と断りました。その断り書きが、ここで効いてきます。

CLONE_NEWNET が無いということは、コンテナはホストのネットワーク名前空間をそのまま共有しているということです。理屈で言われても実感が湧かないので、まずコンテナの中から自分の住所を聞いてみます。

▸ 動かして確認

コンテナの中で ip -o addr を打ちます。-o は「1 つのインタフェースを 1 行にまとめて出す」という意味で、見比べるときに便利です。

$ mydocker run --quiet alpine /bin/sh -c 'ip -o addr'
1: lo    inet 127.0.0.1/8 scope host lo\       valid_lft forever preferred_lft forever
2: eth0    inet 192.0.2.2/24 brd 192.0.2.255 scope global eth0\       valid_lft forever preferred_lft forever

2 行目の eth0 の 192.0.2.2/24。これは ホストのアドレスそのものです。コンテナ用に新しく振られたアドレスではありません。lo（ループバック）も同じで、ホストの lo です。

第 03 章で ls / を打ったときは、ホストのファイルは 1 つも見えませんでした。第 02 章で ps を打ったときも、ホストのプロセスは 1 つも出ませんでした。ところが ip -o addr だけは、ホストのものが素通しで見えている。箱の壁に、ここだけ穴が空いているわけです。

いまの mydocker — NET だけ隔離していない host netns +------------------------------------+ | lo 127.0.0.1/8 | | eth0 192.0.2.2/24 ---> outside | | | | +----------------------------+ | | | mydocker container | | ← UTS / PID / MNT / IPC は別の箱 | | (uses the SAME lo/eth0) | | ← NET だけホストと同じ部屋のまま | +----------------------------+ | +------------------------------------+

この状態には、良いことと悪いことが両方あります。

良いこと — 通信は「できる」

コンテナの中から外へ出る通信は普通にできます。ホストとまったく同じ経路・同じ住所を使うので、ホストで通るものはコンテナでも通ります。第 05 章でイメージを取ってくるとき、通信の設定を何もしなかったのに動いていたのは、そもそも隔離していなかったからです。

つまり「外とつながる」という機能要件だけを見れば、すでに満たされているように見えます。ここが厄介なところで、動いているように見えるので問題に気づきにくい。

悪いこと — 「隔離されていない」

問題は、通信がホストと区別できないことです。具体的には次のことが起きます。

  • ポートがホストのポートである。コンテナの中で 8080 番を開くと、それはホストの 8080 番です。ブラウザから localhost:8080 で直接届きます。「ポートを公開する」という概念がそもそも存在しません（すでに全部公開されているので）。
  • ポートが衝突する。同じイメージのコンテナを 2 つ動かして、両方が 8080 番を開こうとすると、後から起動したほうが「アドレスが使用中です」で失敗します。ホストで何かが 8080 番を使っていても同じです。
  • コンテナ同士を区切れない。コンテナ A とコンテナ B は同じネットワークにいるので、互いに 127.0.0.1 で通じてしまいます。「この 2 つは通信させたくない」を表現する手段がありません。
  • ホストのネットワーク設定に手を出せてしまう。コンテナの中は root です。ホストの netns を共有しているということは、そこで ip コマンドを打てばホストの経路表を書き換えられるということでもあります。

要件定義の §3.2 には「コンテナ間およびコンテナ・外部間のネットワーク通信」がはっきりとスコープ外として書いてあります。つまりこれは事故ではなく、最初から外すと決めていたものです。ただ、決めていたからといって「無かったこと」にはできません。今の mydocker はネットワークについては隔離されていない道具であり、それを知って使うのと知らずに使うのとでは、まったく話が違います。

LINUX メモ · ネットワーク名前空間（network namespace）

ネットワーク名前空間は、ネットワークに関する持ち物一式をまるごと 1 セット複製する仕組みです。ここでいう「持ち物一式」には次のものが含まれます。

ネットワークインタフェース（lo や eth0）、IP アドレス、経路表（どの宛先をどこへ流すか）、ARP テーブル、ポート番号の空間、そしてファイアウォール（iptables）のルール。これらが名前空間ごとにまるごと別になります。

ここで大事なのは、新しく作った netns はほとんど空っぽだという点です。作った直後にあるのは、電源の入っていない lo ただ 1 つ。外へ出る線は 1 本もありません。第 03 章で新しい / を用意したときと同じで、箱を作ることと、箱に中身を入れることは別の作業です。そして後者のほうがずっと大変だ、というのがこの章の主題です。

ちなみに「ポート番号の空間が別になる」というのが、Docker で -p 8080:80 と書ける理由です。コンテナの 80 番とホストの 8080 番は別の名簿に載った別の 80 番・8080 番なので、対応づけという概念が成り立ちます。名簿が 1 冊しかない今の mydocker では、対応づけようがありません。

なぜ最後まで手を出さなかったのか

ここは言い訳の節ではなく、判断の記録の節です。「時間が足りなかった」で済ませると何も学べないので、何をどう秤にかけたのかを書きます。

1. Must と Should を、検証込みで仕上げることを優先した

要件を優先度で並べたとき、絶対に落とせない Must は 3 つでした — 隔離（名前空間）、根の挿げ替え（pivot_root）、資源制限（cgroup）。この 3 つが揃って初めて「コンテナ」と呼べるものになります。次の Should が、イメージの取得・層の重ね合わせ・ps・exec。ここまでで「使える道具」になります。ネットワークは Could、つまり「あればなお良い」の段でした。

そしてこの教材の方針として、「実装した」と書けるのは検証まで通したものだけと決めていました。第 04 章でメモリ上限を確かめるとき、設定ファイルに数値が書き込めたことでは満足せず、実際に上限を超える確保をさせて exit=137 で殺されるところまで見ましたね。あれを全機能でやると、実装そのものと同じくらいの時間がかかります。

限られた時間の使い道は 2 つありました。

  • A. Must と Should を、検証込みで完全に仕上げる
  • B. Must と Should の検証を薄くして、ネットワークにも着手する

選んだのは A です。理由は次の 2 つ目に続きます。

2. ネットワークは「単体で数時間」かつ「失敗が分かりにくい」

これが決定的でした。この章のあとで見る 4 つの部品——bridge を作る、veth を渡す、経路を引く、NAT をかける——は、どれか 1 つでも欠けると通信できません。しかもそのとき出るエラーが、ほぼ全部同じ顔をしています。

4 つの部品と、欠けたときの見え方 bridge が無い → そもそも線がつながらない veth を渡していない → コンテナ内に eth0 が無い 経路を引いていない → 「Network is unreachable」 NAT をかけていない → 何も言わずに、ただ黙る（応答が返ってこない） 最後のやつが、いちばん時間を溶かす。 「送れている」のに「返ってこない」ので、送信側だけ見ても何も分からない。

プログラムのバグなら、スタックトレースが出るか、少なくとも例外が飛びます。ネットワークの設定漏れは沈黙で表れます。パケットは正しく出ていって、正しく相手に届いて、相手も正しく返事をして、その返事だけがどこかへ消える。この状態を切り分けるには、少なくとも「どこまで届いているか」を見る道具（tcpdump のような）と、それを読む力が要ります。それはこの教材が扱う範囲を明らかに超えていました。

3. 動かない実装は資産にならない

いちばん避けたかったのは、次の結末です。

ネットワークに手を出したせいで時間が溶け、その結果ネットワークは中途半端に動くだけで終わり、しかも他の章の検証まで薄くなった。 — 最悪のシナリオ

コードは書いた量ではなく、信頼できる量で測るべきです。「たぶん動くはずのネットワーク実装」は、後から誰か（未来の自分を含む）が触るときに、資産ではなく負債になります。「これは動くと確認した」「これは着手していない」がはっきり分かれているほうが、どちらの立場から見ても扱いやすい。

だから mydocker のネットワーク機能は、中途半端に存在するのではなく、はっきり存在しません。そして代わりに、この地図の章があります。

⚠ ここで身につけてほしい態度

「やらなかった」と「できなかった」と「やらないと決めた」は、まったく別のことです。3 つ目だけが、判断として記録に値します。

そして記録するときに書くべきなのは、やらなかった理由ではなく何を優先したかです。「時間が無かった」は理由に見えて何も言っていません。「Must の検証を優先し、Could を落とした」なら、次に時間ができたときに何から手をつけるかまで決まります。

■ これ以降のコマンドの読み方

Step 1 以降に出てくるコマンドには、プロンプト記号（$）も出力も付けていません。私が実行して結果を採ったものではないからです。付けてしまうと「動かした記録」に見えてしまいます。

Step 1bridge を作る

最初に作るのは bridge、日本語なら仮想的なスイッチです。これはコンテナがまだ 1 つも無くても作れます。というより、コンテナより先に無いと困るものです。コンテナは起動のたびに現れて消えますが、ぶら下がる先のスイッチは居続けてもらわないといけません。

名前は mydocker0 にします。末尾の 0 は「1 本目」という慣習で、Docker の docker0 も同じ流儀です。

# 1. スイッチの本体を作る（この時点では何も挿さっていない）
ip link add mydocker0 type bridge

# 2. スイッチ自身に住所を与える
#    この住所が、コンテナから見た「ゲートウェイ」になる
ip addr add 172.30.0.1/16 dev mydocker0

# 3. 電源を入れる（これを忘れると、線を挿しても何も流れない）
ip link set mydocker0 up

3 行それぞれに役割があります。

  • 1 行目で箱そのものを作ります。type bridge がスイッチであることの宣言です。この時点では、ポートが全部空いているハブが机の上に置かれただけの状態です。
  • 2 行目でスイッチ自身に IP を振ります。ここが少し不思議に感じるところで、「スイッチに住所が要るのか?」と思うかもしれません。要ります。というのも、この bridge はただのスイッチであると同時に、ホスト側のインタフェースでもあるからです。コンテナから見ると、この 172.30.0.1 が「外へ出るときにまず渡す相手」——つまりゲートウェイになります。
  • 3 行目で電源を入れます。Linux のインタフェースは作った直後は DOWN で、明示的に up にするまで一切のパケットを通しません。これは「作ったのに動かない」の定番の原因です。

172.30.0.0/16 という範囲を選んだのは、これがプライベートアドレス（インターネットには出ていかない、組織内で自由に使ってよい範囲）だからです。/16 は「上位 16 ビットが同じものは同じネットワーク」という意味で、172.30.0.1 から 172.30.255.254 までの約 6 万 5 千個を使えます。コンテナを 6 万個立てる予定は無いので十分です。

LINUX メモ · bridge（仮想スイッチ）

bridge は、複数のネットワークインタフェースを束ねて1 つのスイッチのように振る舞わせるカーネルの機能です。物理的なスイッチングハブがやっていることを、そのままソフトウェアでやります。

スイッチの仕事は単純です。ある口からフレームが入ってきたら、宛先の MAC アドレスを見て、その相手がぶら下がっている口だけへ流す。相手がどの口にいるか知らなければ、とりあえず全部の口へ流して、返事が来た口を覚える。これだけです。IP アドレスのことは何も知りません——スイッチは 1 つ下の階層（データリンク層）の道具だからです。

ではなぜ Step 1 の 2 行目で IP を振ったのか。それは mydocker0 がスイッチであると同時に、ホスト自身がそのスイッチにつないだ 1 本の線でもあるからです。ホストは「スイッチに参加している 1 台」として住所を持ち、その住所がコンテナ側のゲートウェイになります。この二重の役割が、bridge がいちばん理解しにくい点だと思います。

◇ 自分で確かめるなら

この Step の内容は、コンテナが 1 つも無くても確かめられます。壊してよい Linux で ip link add ... type bridge を打ってから ip link の一覧を見ると、作ったばかりの mydocker0 が DOWN で並んでいるはずです。up にする前後で状態表示がどう変わるかを見ておくと、Step 2 以降で「なぜか流れない」に当たったときに、まずここを疑えるようになります。

後片付けは ip link del mydocker0 です。作ったら消す——第 07 章でさんざんやったことが、ここでもそのまま必要になります。

Step 2veth ペアで名前空間をまたぐ

スイッチができました。次はコンテナをそこへつなぐ線が要ります。ここで使うのが veth ペアです。

veth の性質でいちばん大事なのは、必ず 2 本 1 組で生まれることです。単体では作れません。そして片方に入れたパケットは、必ずもう片方から出てきます。ケーブルとまったく同じ振る舞いです。

# 1. ケーブルを 1 本作る（両端に veth0 / veth1 という名前が付く）
ip link add veth0 type veth peer name veth1

# 2. 片端をスイッチに挿す
ip link set veth0 master mydocker0

# 3. ホスト側の端に電源を入れる
ip link set veth0 up

# 4. もう片端を、コンテナのネットワーク名前空間へ引っ越させる
#    <pid> はコンテナの中の PID 1 の、ホストから見た PID
ip link set veth1 netns <pid>

4 行目が、この章でいちばん面白いところです。インタフェースを名前空間ごと引っ越させるという操作が存在します。ファイルを移動するのと同じ感覚で、ネットワークインタフェースを別の部屋へ移せる。

veth ペア — 1 本のケーブルの両端 作った直後（両端ともホストの netns にいる） host netns +-------------------------------------+ | veth0 ==================== veth1 | +-------------------------------------+ 片端だけ引っ越した後 host netns container netns +--------------------+ +--------------------+ | veth0 ============|========|=== veth1 | +--------------------+ +--------------------+ ↑ ↑ bridge に挿す eth0 に改名して IP を振る ホスト側からはもう見えない

ここで <pid> と書いたのは、コンテナのホストから見た PID です。第 01 章でやったことを思い出してください——コンテナの中では PID 1 でも、ホストから見れば普通の番号を持ったプロセスです。ip link set ... netns <pid> は「この PID のプロセスが属している netns へ移せ」という指定なので、ホスト側の番号を渡します。internal/container/run.go の Run は、子プロセスを起動した直後にこの PID を掴んでいます（st.PID = pid の行です）。実装するなら、その直後がこの操作を差し込む場所になります。

⚠ 落とし穴 · 引っ越した veth は、元の部屋から「消えたように見える」

ip link set veth1 netns <pid> を打った直後にホストで ip link を見ると、veth1 がどこにもありません。消えたのではなく、別の部屋に移っただけです。しかし初めて見ると「コマンドが失敗してインタフェースが壊れた」ようにしか見えません。

この「消えたように見える」性質は、順序を間違えたときにも牙を剥きます。たとえば veth1 に IP を振ってから引っ越させようとすると、その後の操作をホスト側から続けられません。引っ越しは、その端に対する最後のホスト側操作だと考えてください。それ以降は、コンテナの netns の中から触ることになります。

もっと厄介なのは、引っ越し先の netns が消滅したときです。netns はその中にプロセスが 1 つもいなくなると消えます。コンテナが終了すると netns も消え、その中にいた veth1 も一緒に消えます。ここは救いで、ペアの片方が消えるともう片方も自動的に消えます。つまり通常終了ならホスト側の veth0 の後始末は要りません。ただし「通常終了なら」です。

LINUX メモ · veth ペア

veth は virtual Ethernet の略で、常に 2 本 1 組で作られる仮想インタフェースです。単体では存在できません。ip link add veth0 type veth peer name veth1 の peer が「相方」の意味で、この 1 コマンドで 2 本同時に生まれます。

動作はきわめて素直です。veth0 へ送信されたフレームは、そのまま veth1 の受信として現れます。逆も同じ。中身を見ることも、書き換えることもしません。ただの直結ケーブルです。

「ただの直結ケーブル」が価値を持つのは、両端を別々の名前空間に置けるからです。名前空間は壁ですが、veth はその壁を貫通して置ける唯一の線になります。第 03 章で pivot_root をやったとき、コンテナの中からホストのファイルへ手が届かないことを確かめました。ネットワークの世界における「その壁に開ける穴」が veth です。穴の開け方が明示的であることがポイントで、意図せず穴が空くことはありません。

なお、コンテナ側の端を eth0 と名付けるのは単なる慣習です。カーネルは名前を気にしません。ただ、中で動くアプリケーションが「eth0 があるのが普通」と思っていることが多いので、慣習に従っておくと余計な問題を踏みません。

Step 3コンテナ側の住所と道順

線はつながりました。しかし、コンテナ側の端はまだ名前も住所も無い、電源も入っていないケーブルです。ここに 3 つのことをします——名前を付ける、住所を振る、道順を教える。

操作の場所が変わることに注意してください。ここからはコンテナの netns の中で打つコマンドです。ホストからそれをやる方法として ip netns exec という仕組みがありますが、mydocker のようにコンテナを自前で起動している場合は、対象の netns を /proc/<pid>/ns/net として指定して同じことをします。第 07 章の Exec で /proc/<pid>/ns/uts のようなパスを開いて setns したのと、まったく同じ考え方です。

# --- ここからはコンテナの netns の中での操作 ---

# 1. ループバックを起こす（意外と忘れる。中のアプリが localhost を使うと詰む）
ip link set lo up

# 2. 引っ越してきた端を eth0 に改名する（慣習に合わせるだけ）
ip link set veth1 name eth0

# 3. 住所を振る
ip addr add 172.30.0.2/16 dev eth0

# 4. 電源を入れる
ip link set eth0 up

# 5. 道順を教える — 「知らない宛先はすべて bridge へ渡せ」
ip route add default via 172.30.0.1

5 行目の デフォルトルートが肝です。これが無いと、コンテナは 172.30.x.x 宛（つまり同じ bridge にぶら下がった相手）としか話せません。それ以外の宛先について、パケットをどこへ出せばいいか分からないからです。「知らない宛先は全部 172.30.0.1 に渡す」と教えることで、初めて外の世界へ向かう道ができます。

ここまでやると、コンテナ ↔ ホストは通じるようになります。コンテナから 172.30.0.1 へ、ホストから 172.30.0.2 へ、どちらも届きます。コンテナ A ↔ コンテナ B も、同じ bridge にぶら下がっているので通じます。

⚠ ここで「できた」と思うと、必ず転ぶ

Step 3 まで終わった時点で、コンテナからホストへ ping が通ります。ここで「よし、ネットワークができた」と思うのが、この一連の作業でいちばんよくある勘違いです。

まだ外の世界へは 1 バイトも出られません。通じているのは「同じ bridge にぶら下がっている者同士」と「ホスト自身」だけです。外へ出るには、あと 2 つ——転送の許可と、送信元アドレスの書き換え——が要ります。それが Step 4 です。

◇ 考えてみる

Step 4 を読む前に、少しだけ考えてみてください。いまコンテナが 172.30.0.2 という送信元アドレスでパケットを外へ出したら、返事はどこへ返ってくるでしょうか?

ヒント: 172.30.0.0/16 はプライベートアドレスです。つまり、インターネットのどこにも「そこへの行き方」を知っている機械はありません。この 1 点から、Step 4 で何をしなければならないかが導けます。

Step 4転送と NAT — ここを忘れると必ず詰まる

さっきの問いの答えです。返事はどこへも返ってきません。

コンテナが送信元 172.30.0.2 でパケットを出す。それはホストを通って外の相手に届く（ここまでは行けます）。相手は律儀に返事を作り、宛先に 172.30.0.2 と書く。ところが 172.30.0.2 はこの家の中でしか通用しない住所なので、世界中のどのルータもそこへの行き方を知りません。返事は途中で捨てられます。

NAT を忘れると起きること コンテナ ホスト 外の相手 172.30.0.2 ─────→ そのまま通す ─────→ 受け取る 「172.30.0.2 へ返信」 │ ？ ←─────────────────── │ どのルータも 172.30.0.2 を知らない → 返事は途中で消える 送信側から見ると「送れているのに黙っている」ようにしか見えない。 これが「ping は出るのに応答が返らない」の正体。

だから、外へ出るときに送信元アドレスをホストのものに書き換える必要があります。これが NAT（Network Address Translation）です。そして帰ってきた返事を、書き換える前のコンテナのアドレスへ戻す必要もあります。この 2 つは同じ仕組みの表と裏です。

# 1. カーネルに「自分宛でないパケットを転送してよい」と許可する
#    既定では 0（転送しない）。ここが 0 のままだと bridge 止まりになる
sysctl -w net.ipv4.ip_forward=1

# 2. 172.30.0.0/16 から出ていくパケットの送信元を、出口のアドレスに書き換える
#    「! -o mydocker0」= bridge の内側へ戻る通信は書き換えない、の意味
iptables -t nat -A POSTROUTING -s 172.30.0.0/16 ! -o mydocker0 -j MASQUERADE

1 行目は通行許可です。Linux は既定では「自分宛でないパケットは黙って捨てる」設定になっています。これは安全側に倒した既定値で、うっかりルータとして振る舞ってしまわないための配慮です。コンテナのパケットを外へ流すというのは、まさにルータとして振る舞うことなので、明示的に許可が要ります。

2 行目が NAT の設定です。読み解くと次のようになります。

断片意味
-t natアドレス書き換え用の表を触る（フィルタ用の表とは別）
-A POSTROUTING「行き先を決めた後、実際に送り出す直前」の段に規則を足す
-s 172.30.0.0/16送信元がコンテナの範囲のものだけを対象にする
! -o mydocker0ただし出口が bridge 自身のものは除く（＝コンテナ同士の通信は書き換えない）
-j MASQUERADE送信元アドレスを「出ていくインタフェースのアドレス」に書き換える

! -o mydocker0 の ! は否定です。これが無いと、コンテナ A からコンテナ B への通信まで書き換えてしまい、B から見た送信元が全部ホストになってしまいます。外へ出るときだけ書き換えるのが要点です。

NAT がヘッダを書き換える様子 行き（コンテナ → 外） コンテナが作った時点 ホストを出る時点 +----------------------+ +----------------------+ | src 172.30.0.2:50001 | → | src 192.0.2.2:41000 | ← 書き換わる | dst OUTSIDE:443 | | dst OUTSIDE:443 | +----------------------+ +----------------------+ （この対応を表に控えておく） 帰り（外 → コンテナ） ホストに届いた時点 コンテナへ渡す時点 +----------------------+ +----------------------+ | dst 192.0.2.2:41000 | → | dst 172.30.0.2:50001 | ← 元に戻す +----------------------+ +----------------------+ （控えた表を引いて宛先を復元する）

図の右下の「控えた表」が、NAT がステートフル（状態を持つ）である理由です。書き換えっぱなしでは帰り道が分からないので、誰の通信をどう書き換えたかを覚えている必要があります。この表はカーネルが持っていて、通信が終われば消えます。

LINUX メモ · NAT / MASQUERADE

NAT はパケットのヘッダに書かれたアドレスを書き換える技術の総称です。家庭用のルータが当たり前にやっていることと同じで、家の中の複数の機械が 1 つのグローバルアドレスを共有できるのはこの仕組みのおかげです。

MASQUERADE は NAT の一種で、「書き換え先を固定で指定せず、出ていくインタフェースのアドレスを自動で使う」という意味です。似たものに SNAT があり、こちらは書き換え先のアドレスを明示します。ホストのアドレスが DHCP で変わりうる環境では MASQUERADE のほうが安全で、代わりに毎回アドレスを引く分だけわずかに遅い、というのが両者の違いです。

ポート番号も一緒に書き換わることに注目してください。図では 50001 が 41000 になっています。なぜかというと、複数のコンテナが同時に外と通信したとき、送信元アドレスを全部ホストのものにしてしまうと、返事が誰宛か分からなくなるからです。ポート番号を振り分けることで区別しています。だから正確には NAPT（アドレスとポートの変換）と呼ぶべきものですが、実務では区別せず NAT と呼ぶことがほとんどです。

⚠ 落とし穴 · NAT を忘れると「ping は出るのに応答が返らない」

これがこの章で最大の落とし穴です。症状はこうです——コンテナから外へ ping を打つ。エラーは出ない。パケットは確かに出ていく。ただ、いつまでも応答が返ってこない。タイムアウトするだけで、何が悪いのかを示す情報が一切出ません。

原因は上で見たとおり、送信元アドレスが外から見て到達不能だからです。返事の宛先が世界のどこにも存在しないので、返事そのものが作られても捨てられる。送信側だけをいくら調べても分かりません。

切り分けの手掛かりは「どこまでは届くか」を段階的に確かめることです。bridge のアドレス（172.30.0.1）へは届くか。ホストの物理インタフェースのアドレスへは届くか。外の相手へは届くか。届かなくなった境目が、設定が欠けている場所です。この地道な切り分けが必要になることこそ、私がネットワークを MVP から外した理由そのものです。

⚠ 落とし穴 · ip_forward が 0 のままだと bridge 止まりになる

NAT を正しく書いても、net.ipv4.ip_forward が 0 のままなら外へは出られません。カーネルが「自分宛でないパケット」を転送する前に捨てるからです。

症状は NAT 忘れとよく似ていて、やはり沈黙します。違いは「bridge のアドレスまでは届くが、その先へ 1 ホップも進まない」こと。ここでも切り分けは「どこまで届くか」を刻んで確かめるしかありません。

もう 1 つ厄介なのが、sysctl -w での設定は再起動すると消えることです。「昨日は動いたのに今日動かない」の典型的な原因になります。恒久化するには設定ファイルに書く必要があり、つまり mydocker がホストの永続設定に手を出すかどうかという設計判断が発生します。これも見えにくいコストです。

Step 5名前解決 — いちばん分かりにくい壊れ方

ここまでで、コンテナは IP アドレスを指定すれば外と通信できるようになりました。しかし、まだ 1 つ足りません。

/etc/resolv.conf です。これはコンテナの中のファイルで、「ホスト名を IP アドレスに翻訳してくれるサーバはどこか」を書いておく場所です。第 06 章でやった overlay の上に、このファイルを置いてやる必要があります。

# コンテナの rootfs の中に、名前解決の宛先を書いておく
# （実際にはホストの /etc/resolv.conf をそのまま写すことが多い）
echo "nameserver 8.8.8.8" > /path/to/merged/etc/resolv.conf

これを忘れたときの壊れ方が、この章でいちばん意地悪です。

resolv.conf を忘れたときの症状 ping 1.1.1.1 → 通る ← IP を直に指定すれば動く curl 93.x.x.x → 通る ← これも動く curl example.com → 失敗 ← 名前を使った瞬間だけ落ちる 「ネットワークは繋がっている」ことが確認できてしまうので、 ネットワークの問題だと思わない。アプリのバグを疑い始める。

IP 直打ちは通るのです。だから「ネットワークは動いている」という確信が持ててしまう。その状態で curl example.com だけが失敗するので、疑う先がアプリケーション側へ逸れます。実際には、名前解決だけが別の経路——DNS サーバへの問い合わせ——を通っていて、その宛先が書かれていないだけです。

名前解決は、他のネットワーク機能とは層が違うということを覚えておいてください。Step 1〜4 はカーネルの機能でした。名前解決はユーザ空間のライブラリがファイルを読んで行うことなので、カーネルの設定がどれだけ完璧でも、ファイルが無ければ動きません。

⚠ 落とし穴 · resolv.conf を忘れると、名前解決だけが失敗する

症状: ping 1.1.1.1 は通るのに curl example.com が失敗する。あるいは「一部のアプリだけ動かない」という報告になる。

原因: 名前解決だけが DNS という別の仕組みを通っており、その宛先を書いた /etc/resolv.conf がコンテナの rootfs に無い。

気づきにくさ: 他のすべてが正常に見えるため。ネットワーク疎通の確認を IP アドレスで行っていると、100% 成功します。確認は必ず名前でも行ってください。

さらに厄介なこと: ホストの /etc/resolv.conf をそのまま写すと、そこに 127.0.0.53 のようなループバックのアドレスが書いてあることがあります（ホスト上でローカルの DNS キャッシュが動いている場合）。コンテナの netns の中の 127.0.0.1 はホストのループバックではないので、写しただけでは動きません。「写せばいい」で済まないのが、この部品の面倒なところです。

Go から実装するとどうなるか — 設計の見取り図

ここまでのコマンドを、mydocker の中からどうやって実行するか。これは実装の話に見えて、実は方針の話です。そして着手する前に決めておくべきだったのが、まさにこの部分でした。

この教材は「コンテナ関連のライブラリを使わず、カーネルの機能を直接扱う」という縛りで書いています。第 04 章では cgroup のファイルに直接数値を書き、第 05 章ではレジストリの HTTP API を自分で叩き、第 06 章では mount(2) を直接呼びました。同じ方針をネットワークに当てはめると、道は 2 つに分かれます。

道 A · netlink のソケットを自分で組み立てる

ip コマンドがやっていることは、突き詰めると netlink という専用のソケットを開いて、決められた形式のバイト列をカーネルへ送ることです。カーネルとユーザ空間がネットワーク設定をやりとりするための、専用の通信路だと思ってください。

これを Go の標準ライブラリだけでやるのは、できます。syscall パッケージには netlink 用のソケットを開く機能があります。ただし、その先が長い。「bridge を 1 つ作る」というたった 1 つの操作のために、メッセージのヘッダを組み、属性を入れ子で詰め、長さフィールドを計算し、境界を 4 バイトに揃え、返ってきたバイト列を解釈してエラーかどうかを判定する——という作業が続きます。しかも失敗したときに返ってくるのは数値のエラーコードだけです。

これは第 05 章でレジストリの API を自分で叩いたときとは、難しさの質が違います。あちらは HTTP と JSON という、読める形式でした。netlink は読めないバイト列です。デバッグの体験がまるで別物になります。

道 B · ip コマンドを外部プロセスとして呼ぶ

もう 1 つの道は、os/exec で ip コマンドをそのまま呼ぶことです。Step 1〜4 のコマンドを文字列で組み立てて実行する。これなら実装は圧倒的に短く、エラーメッセージも人間が読める形で返ってきます。

問題は建前です。「ライブラリを使わずにカーネルの機能を直接扱う」と言いながら、外部コマンドに頼るのは一貫しているのか? ——ここに線を引かないといけません。

ちなみに mydocker は、この線を完全には引ききっていません。第 06 章で見たとおり overlay のマウントは syscall.Mount を直接呼んでいますが、教材の中では mount コマンドを使った説明もしています。「学習のために手で確かめるのは外部コマンド、実装は直接呼び出し」という使い分けです。ネットワークにも同じ線が引けるなら、道 A が筋ということになります。

そして、この判断こそ先に決めるべきだった

私がネットワークに着手しなかった理由を、もう 1 段掘り下げるとここに行き着きます。方針が決まっていなかったのです。

  • 道 A を選べば、実装コストは Step 1〜5 の設定そのものより、netlink のバイト列を組む作業のほうが大きくなる
  • 道 B を選べば実装は数時間で終わるが、教材の一貫性に穴が空く。そして読者は「なぜここだけ外部コマンドなのか」と正当に疑問を持つ
  • どちらを選んでも、Step 1〜5 の 4 つの部品の切り分けコストは変わらない

着手してから悩み始めていたら、悩んでいる時間そのものが Must の検証時間を食っていたはずです。「作るか作らないか」を決める前に、「作るならどう作るか」の見通しを立てる。見通しが立たないなら、それは着手すべきタイミングではない——これがこの章から持ち帰ってほしい、いちばん実務的な教訓かもしれません。

LINUX メモ · netlink

netlink は、ユーザ空間のプログラムとカーネルがやりとりするための、ソケット型の通信路です。AF_NETLINK という種別のソケットを開いて使います。

ネットワーク設定に netlink が使われているのは歴史的な理由があります。昔は ioctl という仕組みで設定していたのですが、こちらは 1 回の呼び出しで渡せる情報の形が固定で、IPv6 のように後から増えた概念を表現しきれませんでした。netlink は可変長の属性を入れ子で詰められる設計なので、拡張に強い。その柔軟さの代償が、組み立ての面倒さです。

ちなみに ip コマンドと、それより古い ifconfig の違いもここにあります。ifconfig は ioctl の時代の道具なので、新しい機能——複数アドレスの割り当てや、名前空間の操作——を表現できません。ネットワークの操作は ip コマンドを使う、というのが現在の標準的な作法です。

難所の地図

この章で出てきた落とし穴を、1 つの表にまとめます。実装するときは、この表を横に置いておくと切り分けの時間がだいぶ減るはずです。

難所症状原因
NAT 忘れping は出るのに応答が返らない送信元アドレスが外から到達不能
IP フォワード無効bridge までは届くが外へ出ないカーネルが転送しない
resolv.conf 忘れIP 直打ちは通るのに名前で失敗名前解決だけが別経路
netns へ veth を入れる順序インタフェースが消えたように見える移動後は元の netns から見えない
コンテナ終了後の掃除veth と iptables ルールが溜まり続ける後片付けの対象が増える

最後の行が、第 07 章の話とそのままつながります。第 07 章で私たちは「終わったら何も残さない」ことに強くこだわりました。overlay をアンマウントし、cgroup のディレクトリを消し、状態ファイルを片付ける。E2E テストでは 10 回起動しても overlay のマウント数が増えないことと、テスト全体でホストのマウント数が元に戻ることまで確かめました。

ネットワークを実装すると、この「片付けるべきものリスト」に 2 種類が加わります。

  • veth インタフェース。通常終了ならペアの相方が消えると自動的に消えます。しかし mydocker 自身が SIGKILL で殺されたら? 第 07 章で見たとおり、そのときは overlay のマウントが残りました。同じことが veth でも起きえます。
  • iptables のルール。これは自動では消えません。コンテナごとにルールを足す設計にすると、起動のたびにルールが 1 行ずつ増えていくことになります。10 回起動して 10 行残っていたら、それは第 07 章の基準では明確な失敗です。

つまりネットワークは、実装コストだけでなく後片付けの設計コストも持ち込みます。第 07 章で Cleanup に組み込んだ「アンマウントが失敗したら削除に進まない」のような慎重な設計を、ネットワークの片付けにも設計し直す必要がある。これも、着手前には見えていなかったコストです。

つまずき FAQ

実装しなかったのに章を作る意味はあるんですか?

率直な問いなので、率直に答えます。意味はある、と私は思っています。ただし理由は「章数を揃えたいから」ではありません。

1 つ目の理由。読者が今の mydocker を誤解しないためです。この章が無ければ、読者は「7 章まで読んだから、コンテナの隔離は全部分かった」と思って終わります。実際にはネットワークだけ穴が空いている。それを知らずに「自作コンテナで隔離できた」と考えるのは、この教材が生み出せる最悪の誤解です。

2 つ目の理由。やらないと決める判断も技術の一部だからです。実務で書くコードのうち、何を書かないかを決めることは、何を書くかを決めることと同じくらい重要です。にもかかわらず、教材でそれを扱うものはほとんどありません。全部作った話しか載らないからです。この章は「作らなかったものの話」を残す場所です。

3 つ目の理由。実際、これから作る人には地図が要るから。Step 1〜5 と難所の表は、私が読んで調べて整理したものです。これから実装する人が同じ調査を最初からやる必要はありません。

ネットワークが隔離されていないのに「コンテナ」と呼んでいいんですか?

呼んでいいと思いますが、注釈が要ります。

実は Docker にも --network host というオプションがあって、まさに今の mydocker と同じ状態——ホストの netns をそのまま使う——でコンテナを起動できます。性能が要る場面や、ホストのネットワークをそのまま見たい場面で実際に使われます。つまり「ネットワークを隔離しないコンテナ」という形態は、実運用にも存在します。

違いは、Docker ではそれが選択肢であるのに対し、mydocker ではそれしかないことです。選べるのと選べないのとでは、道具としての性質が違います。

正確に書くならこうなります——mydocker は、UTS・PID・マウント・IPC を隔離し、資源を制限し、イメージの層を重ねられるコンテナランタイムであり、ネットワークの隔離だけを持たない。この一行が書ければ、呼び方の問題は解決します。

Cloneflags に CLONE_NEWNET を足すだけではだめなんですか?

足すだけなら 1 行です。そして足した瞬間、コンテナは外とまったく通信できなくなります。

理由は「LINUX メモ · ネットワーク名前空間」で書いたとおりで、新しく作った netns は空っぽだからです。中にあるのは電源の入っていない lo だけ。外へ出る線が 1 本もありません。

つまり CLONE_NEWNET を足すというのは、Step 1〜5 を全部やることとセットです。片方だけやると、今より確実に悪くなります（今は少なくとも通信できるので）。「隔離されていないが通信はできる」状態と「隔離されているが通信できない」状態のどちらがマシかと言えば、道具としては前者です。

これも、私が中途半端に着手しなかった理由の 1 つです。途中まで実装した状態は、実装しない状態より悪いという、珍しい性質を持った機能なのです。

第 05 章でイメージを取ってこられたのは、ネットワークがあったからですよね?

鋭い質問です。答えは「ネットワークがあったから」ではなく、「ネットワークを隔離していないから」です。

もう少し丁寧に言うと、第 05 章のレジストリからの取得は、コンテナの中ではなくホスト側で走っています。mydocker pull はコンテナを起動しません。ホスト上のただのプロセスとして HTTPS を喋り、取ってきたレイヤを /var/lib/mydocker/layers/ に置くだけです。だから、そもそもコンテナのネットワークとは無関係でした。

では mydocker run がイメージを取ってくる場合は? これも同じで、コンテナを起動する前にホスト側で取得を済ませ、そのあとで overlay を組んで起動します。順序としてはネットワークが要る場面が先に終わっています。

ただし、コンテナの中で apk add のようなコマンドを打った場合は話が別で、それはコンテナのネットワーク（＝今はホストのもの）を使います。ここが動いているのは、まさに隔離していないおかげです。

4 つの部品のうち、どれか 1 つだけ先に作って試すことはできますか?

できますし、実装するならその順序を強くおすすめします。ただし「試す」の意味を段階ごとに変える必要があります。

Step 1（bridge）まで: コンテナが無くても、ホストで ip link を見て存在を確認できます。ここは独立して検証できる、いちばん安全な一歩です。

Step 2（veth）まで: コンテナの中に eth0 が現れることを確認できます。まだ IP は無いので通信はできません。

Step 3（IP と経路）まで: コンテナ ↔ ホストの疎通が確認できます。ここが最初の「通った!」の瞬間です。ただしここで満足してはいけないことは Step 3 の hazard で書いたとおりです。

Step 4（転送と NAT）まで: ようやく外と通信できます。ここまで来て初めて「ネットワークができた」と言えます。

Step 5（resolv.conf）まで: 名前で通信できます。実用上、ここまでやらないと使い物になりません。

段階ごとに「何が確認できるようになるか」を先に決めておくのが、この手の作業を切り分ける唯一の方法です。逆に言うと、これを決めずに 5 つ全部書いてから動かすと、どこが悪いか分からない状態から始まることになります。

コンテナ同士を通信させないようにしたい場合は、どこをいじるんですか?

今の mydocker では不可能です。全コンテナがホストの netns を共有しているので、区切る単位が存在しません。

Step 1〜5 を実装したとしても、あの構成では全コンテナが同じ bridge にぶら下がるので、やはり互いに通信できます。区切りたいなら、次のどちらかが要ります。

1 つは bridge を複数用意する方法。mydocker0 / mydocker1 のように分け、通信させたくないコンテナは別の bridge にぶら下げます。Docker の「ユーザ定義ネットワーク」がおおむねこの発想です。

もう 1 つは iptables のフィルタ規則で止める方法。同じ bridge のままで、特定の組み合わせだけを落とすルールを書きます。柔軟ですが、ルールの管理が一気に難しくなります。

どちらにせよ、この章の Step 1〜5 ができてからの話です。地図の外側、と思ってください。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。この章はコードが無いぶん、言葉で説明できるかどうかがそのまま理解度になります。

Q1. いまのコンテナで ip -o addr を打つと、なぜホストと同じアドレスが出るのですか?

internal/container/run.go の Cloneflags に CLONE_NEWNET が含まれていないからです。名前空間は明示的に指定したものだけが新しく作られ、指定しなかったものは親（＝ホスト）のものをそのまま共有します。

指定しているのは UTS・PID・マウント・IPC の 4 つ。ネットワークは指定していないので、コンテナはホストのネットワーク名前空間の中にいます。したがって、そこから見えるインタフェースもアドレスも経路表も、すべてホストのものです。

ここで大事なのは、これはバグではないということです。指定しなかったものが共有されるのは名前空間の設計どおりの振る舞いで、要件定義でもネットワークはスコープ外と明記してあります。

Q2. veth ペアが「必ず 2 本 1 組」であることは、なぜ重要なのですか?

名前空間という壁を貫通させるためです。

名前空間は、中と外を完全に分けます。分けたままでは通信できないので、どこかに穴が必要です。veth は 2 本 1 組で、片方に入れたものが必ずもう片方から出るという性質を持っているので、両端を別々の名前空間に置くと、そのまま壁を貫通する 1 本の線になります。

もし veth が単体で作れる（相方のいない）インタフェースだったら、パケットの行き先が定義できません。「片端に入れたら必ずもう片端から出る」という保証があるからこそ、線として使えます。

さらに言えば、この設計は穴が明示的であることも保証しています。veth を作って引っ越させるという操作をしない限り、名前空間の壁に穴は空きません。うっかり漏れるということが起きない設計です。

Q3. Step 3 まで終わった時点で「ネットワークができた」と言えないのはなぜですか?

通じているのが同じ bridge の内側だけだからです。

Step 3 までで確立するのは、コンテナ ↔ ホスト（bridge のアドレス）と、コンテナ ↔ コンテナの疎通です。これは 172.30.0.0/16 という閉じた範囲の中の話で、その外へは 1 バイトも出ていません。

外へ出るには 2 つ足りません。1 つはカーネルの転送許可（net.ipv4.ip_forward=1）で、これが無いと自分宛でないパケットは捨てられます。もう 1 つが NAT で、これが無いと出ていけても返事が返ってきません。

そして厄介なのは、Step 3 の時点で ping が通ってしまうので、できた気になれてしまうことです。この「部分的な成功が誤解を生む」構造こそが、この作業の難しさの本体です。

Q4. 「ping は出るのに応答が返らない」とき、まず何を疑いますか? そしてなぜその症状になるのですか?

まず疑うのは NAT（MASQUERADE）の設定漏れです。

症状の理屈はこうです。コンテナが送信元 172.30.0.2 でパケットを出す。ホストがそれを転送する。相手に届く。相手は返事を作り、宛先に 172.30.0.2 と書く。ところが 172.30.0.2 はプライベートアドレスなので、インターネット上のどのルータもそこへの経路を知りません。返事は途中で捨てられます。

だから送信側から見ると「送れているのに黙っている」状態になります。エラーは出ません——エラーを出す相手がいないからです。

NAT はこの問題を、出ていくパケットの送信元をホストのアドレスに書き換えることで解決します。書き換えた対応を表に控えておき、返事が来たら元のアドレスに戻す。この表を持っているからこそ、返事を正しいコンテナへ配れます。

Q5. resolv.conf の忘れが「いちばん分かりにくい壊れ方」と言われるのはなぜですか?

他のすべてが正常に動いて見えるからです。

ping 1.1.1.1 は通ります。IP アドレスを直に指定した通信は全部通ります。つまり、ネットワークの疎通確認を IP で行うかぎり 100% 成功します。この状態で「ネットワークは正常」と結論づけるのは、極めて自然な判断です。

ところが curl example.com だけが失敗する。ここで疑いの矛先はアプリケーション側や、相手のサーバへ向かいます。実際の原因はネットワーク設定なのに、ネットワークは無罪だと確認してしまっている。この「無罪の証明を先に取ってしまう」構造が、切り分けを狂わせます。

層が違うことも理由です。Step 1〜4 はカーネルの機能でしたが、名前解決はユーザ空間のライブラリが /etc/resolv.conf というファイルを読んで行う処理です。カーネル側の設定をいくら見直しても出てきません。

予防策は単純で、疎通確認を必ず名前でも行うことです。

Q6. ネットワークを MVP から外した判断を、一言で説明してください。

模範解答の一例: 「4 つの部品のどれか 1 つ欠けても通信できず、しかも失敗が沈黙として現れるため切り分けコストが読めない。その不確実な作業に時間を割くより、Must と Should を検証込みで仕上げることを優先した」。

ここで避けたい答えが「時間が無かったから」です。これは理由の形をしていますが、何も説明していません。時間はいつでも足りないので、本当に言うべきなのは何を優先したかです。

もう 1 段付け足せると、さらに良い答えになります。「途中まで実装した状態が、実装しない状態より悪くなる機能だった」——CLONE_NEWNET だけ足すと、隔離はされるが通信ができなくなる。今は隔離されていないが通信はできる。道具としては後者のほうが使えます。だから「少しだけ着手する」という選択肢が存在しませんでした。

✓ 完了の合図

この章には実装がないので、確認するのは「作ったものが動くこと」ではありません。いまの状態を自分の目で確かめることが、この章の完了の合図です。

コンテナの中で ip -o addr を打ってください。そこにホストと同じアドレスがそのまま見えていれば、この章は完了です。

$ mydocker run --quiet alpine /bin/sh -c 'ip -o addr'
1: lo    inet 127.0.0.1/8 scope host lo\       valid_lft forever preferred_lft forever
2: eth0    inet 192.0.2.2/24 brd 192.0.2.255 scope global eth0\       valid_lft forever preferred_lft forever

この 2 行を見て「あ、これはホストのアドレスだ。ネットワーク名前空間を作っていないからだ」と即座に言えれば、この章の目的は達成されています。7 章かけて積み上げた隔離の壁に、ここだけ穴が空いている——その事実を、誤解なく持って次へ進んでください。

まとめ — 次の層へ

この章で分かったのは、コンテナのネットワークが 4 つの部品でできているということでした。仮想的なスイッチ（bridge）を立て、壁を貫通する 1 本のケーブル（veth ペア）を渡し、コンテナ側に住所と道順（IP とデフォルトルート）を与え、外へ出るときに送信元を書き換える（転送許可と NAT）。そこに名前解決のファイルを 1 つ置いて、ようやく「使えるネットワーク」になります。そして、この 4 つはどれか 1 つ欠けても通信できず、しかも欠けたときの症状がほとんど沈黙で表れる。だから切り分けの時間が読めない。それが、この機能を Must の後ろに置いた理由でした。「時間が無かった」ではなく「何を優先したか」で説明できる判断として、記録しておく価値のあるものだと思っています。

そして、いまの mydocker はネットワークだけ隔離されていません。コンテナの eth0 はホストの eth0 そのもので、開いたポートはホストのポート、コンテナ同士は素通しでつながります。この状態でも通信は普通にできてしまうので、放っておけば気づかないまま使い続けることになります。だからこの章を置きました。それを知っていて使うのと、知らずに使うのとは、まったく別のことです。知っていれば「このコンテナでサーバを立てるならポートの衝突に気をつける」と判断できます。知らなければ、衝突したときに原因にたどり着けません。第 00 章から一貫して言ってきた「壊れたときに原因にたどり着けること」は、実装した機能だけでなく、実装しなかった機能についても成り立たなければいけません。

次の第 09 章は、この教材の最後の章です。ここまでで作ったものを一度全部並べ、そのうえで何が足りないかを正直に並べます。ネットワークだけではありません——rootless 実行、権限の絞り込み、イメージのビルド、ボリューム、複数コンテナの取りまとめ。どれも「本物のコンテナランタイム」には当たり前にあって、mydocker には無いものです。それらを 1 つずつ、なぜ無いのか・作るなら何が要るのかという形で並べ、最後に docker run の一行の中で何が起きているかを、もう一度最初から通しで見ます。作ったものの総括と、作らなかったものの一覧——その両方を持って、この本を閉じます。
