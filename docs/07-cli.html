道具にする

ここまでの 6 章で、コンテナは「起動して、終わる」ところまで来ました。けれど今できるのは run だけです。今いくつ動いているのかも分からず、動いているものの中を覗くこともできず、そして——これが本当の問題なのですが——片付け損ねたマウントが、誰にも気づかれないままホストに溜まっていきます。この章で run を「道具」に変えます。

◈ この章のゴール

cmd/mydocker/main.go・internal/cli/cli.go・internal/container/state.go を読み切り、実行中のコンテナをどこに、何を、なぜ記録するのかを自分の言葉で説明できるようになる。そのうえで internal/container/run.go の Cleanup を読み、「アンマウント → 削除」の順序を崩すと何が消えるのかを理解する。仕上げに、コンテナを 10 回起動しても overlay のマウント数が増えていないことを、数えて確かめる。

「動く」と「道具になっている」の間

前章の終わりで、私たちはこう打てるようになりました。

$ mydocker run alpine /bin/sh

これは確かに動きます。動きますが、道具ではありません。試しに、こういう場面を想像してみてください。あなたはこのコンテナを起動したまま、別の端末を開きました。さて——今どのコンテナが動いていますか? 答えられません。どこにも書いていないからです。

コンテナの中でファイルがおかしいので中を覗きたい。覗けません。そのコンテナの名前空間に入る手段がないからです。

さらに悪いことがあります。コンテナを起動するたびに、ホストのマウント表に overlay のマウントが 1 行増えます。正常に終われば消えます。けれど ホストを再起動せずに 100 回起動して 3 回だけ片付けに失敗していたら、そのことに誰も気づきません。マウントは目に見えないところに積み上がり、ある日ディスクが埋まるか、アンマウントできないディレクトリの山になって現れます。

「動く」と「道具になっている」の距離 ここまで（第01〜06章） この章で足すもの ───────────────────── ────────────────────────── run できる run に加えて ps … 今何が動いているか 終わったら消える（はず） exec … 動いているものの中に入る ↑ rm … 残骸を安全に回収する └ 「はず」を確かめる手段が info … この環境で何が使えるか 1つも無かった ＋ overlay の件数を実数で つまり足すのは「機能」ではなく ★状態を持つこと と ★状態を後始末すること

この章で足すものの正体は、突き詰めると 2 つだけです。実行中のコンテナの記録を持つことと、その記録と実体を安全に消すこと。ps も exec も rm も、この 2 つの上に乗った薄い皮にすぎません。

そして厄介なのは後者です。「消す」というのは、プログラムが行う操作のなかでいちばん取り返しがつかないものだからです。この章の後半では、順序をひとつ間違えるだけで イメージの実体が丸ごと消える という実話を扱います。

状態はどこに置くのか

「実行中のコンテナを記録する」と言ったとき、置き場所の候補はいくつかあります。メモリの中（＝プロセスが死んだら消える）、データベース、ファイル。mydocker はいちばん素朴なファイルを選びました。理由は 2 つあります。

1 つ目。mydocker ps は mydocker run とは別のプロセスです。別の端末から打たれます。メモリの中に持っていては、そもそも読めません。プロセスをまたいで残るものが要ります。

2 つ目。人間が読めるほうがいいからです。何かがおかしくなったとき、cat で開いて中身を確かめられることには実用上とても大きな価値があります。実際、この章の後半で出てくる E2E テストは、整形された mydocker ps の出力ではなく この JSON を直接読んで PID を取り出しています。

Step 1入り口を薄く保つ

まず main 関数から見ます。ここは驚くほど短くしてあります。短くしてあることに意味があるので、先に全文を貼ります。

cmd/mydocker/main.go（全文）
// mydocker — 自作コンテナランタイム（学習用）の入り口。
//
// ここは薄く保つ。引数を internal/cli に渡し、終了コードを整えるだけ。
//
// ⚠ このプログラムは自分自身を再実行する（/proc/self/exe を "init" という顔で起動する）。
// 詳しくは internal/container/run.go の Run を読むこと。
package main

import (
	"errors"
	"fmt"
	"os"

	"mydocker/internal/cli"
)

func main() {
	err := cli.Run(os.Args[1:])
	if err == nil {
		return
	}

	// 「メッセージは出し終わっているので、この終了コードで終われ」という合図。
	// コンテナの中のコマンドの終了コードを、そのまま利用者に返すために使う。
	var ee *cli.ExitError
	if errors.As(err, &ee) {
		os.Exit(ee.Code)
	}

	fmt.Fprintf(os.Stderr, "mydocker: %v\n", err)
	os.Exit(1)
}

やっていることは 3 つです。cli.Run に引数を丸投げする。エラーが無ければ黙って終わる。エラーがあれば、その種類によって振る舞いを変える。

最後の「種類によって」が肝心なところです。ここには 2 種類のエラーが流れてきます。

  1. 普通のエラー — 「イメージ名を指定してください」「コンテナが見つかりません」のような、まだ利用者に何も伝えていない失敗。これは mydocker: ... という形で標準エラーに出してから、終了コード 1 で終わる
  2. ExitError — 「メッセージはもう出し終わった。あとはこの終了コードで終わってくれ」という合図。何も表示せずに、指定された番号で終わる

2 つ目が要る理由は、mydocker run の役目を考えると分かります。

$ mydocker run --quiet --memory 10m alpine /bin/sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1'
$ echo $?
137

この 137 は コンテナの中で走ったコマンドの終了コードです（第04章でメモリ上限に当たって殺されたときの値でした）。mydocker 自身は失敗していません。mydocker は正しく仕事をして、その結果として中のコマンドが 137 で終わった、という事実を伝えているだけです。

だからここで mydocker: exit status 137 などと余計なメッセージを出してはいけません。docker run も出しません。透明であること——シェルスクリプトの中に mydocker run を書いたとき、それが素の dd と同じように振る舞うこと——が、道具としての最低条件です。

その「メッセージを出さずに、この番号で終わりたい」を Go の型で表したのが ExitError です。定義は cli パッケージの冒頭にあります。

internal/cli/cli.go（冒頭）
// ExitError は「メッセージは既に出したので、この終了コードで終わってほしい」を表す。
type ExitError struct{ Code int }

func (e *ExitError) Error() string { return fmt.Sprintf("exit status %d", e.Code) }

Error() string メソッドを持っているので、これは Go の error インタフェースを満たします。つまり普通のエラーと同じ経路（return err）で運べる。運ばれた先の main で、型を見て「あ、これは特別な合図だ」と気づく。エラーを「文字列」ではなく「値」として設計する、というのが Go の作法です。

GO メモ · errors.As でエラーの型を見る

errors.As(err, &ee) は、「err、またはそれに包まれている元のエラーのどれかが *cli.ExitError 型なら、それを ee に入れて true を返す」という関数です。

なぜ単純な型アサーション（ee, ok := err.(*cli.ExitError)）ではないのでしょうか。Go では fmt.Errorf("... : %w", err) という書き方でエラーを包むことができます。包まれると外側の型は変わってしまうので、素朴な型アサーションは中身を見逃します。errors.As は %w で包まれた層を順にほどきながら探してくれます。

兄弟に errors.Is があります。こちらは「特定の値と等しいか」（errors.Is(err, os.ErrNotExist) など）を見るもの。型で分岐したいときは As、値で分岐したいときは Is と覚えてください。この mydocker では、ExitError が 付随データ（終了コード）を持つので As のほうを使っています。

もうひとつ細かい話を。var ee *cli.ExitError は「*cli.ExitError 型のポインタ変数」を nil で宣言しています。errors.As にはそのアドレス（&ee、つまり **cli.ExitError）を渡します。「見つかったらここに入れてくれ」という受け皿を渡しているわけです。ポインタのポインタが出てくるとぎょっとしますが、やっていることは json.Unmarshal(b, &s) と同じ「書き込み先を渡す」だけです。

入り口が薄いことにはもうひとつ効用があります。テストしやすいのです。cli.Run は []string を受け取って error を返すただの関数なので、os.Exit を呼ばずに何度でも呼べます。os.Exit はプロセスを即座に終わらせてしまう乱暴な関数で、defer も走りません。これを main の中だけに閉じ込めておくと、残り全部が普通の Go のコードになります。

Step 2サブコマンドの振り分け

次は cli.Run。mydocker がどんなコマンドを持っているかは、この関数を読めば全部分かります。

internal/cli/cli.go — usage と Run
const usage = `mydocker — 自作コンテナランタイム（学習用）

使い方:
  mydocker run [オプション] <イメージ> [コマンド...]   コンテナを起動する
  mydocker ps                                          実行中のコンテナを一覧する
  mydocker exec <ID> <コマンド...>                     実行中のコンテナでコマンドを実行する
  mydocker rm <ID>                                     終了したコンテナの痕跡を片付ける
  mydocker pull <イメージ>                             イメージを取得だけする
  mydocker info                                        この環境で何が使えるかを表示する

run のオプション:
  --memory <量>     メモリ上限（例: 10m, 512k, 1g）
  --cpus <数>       CPU の上限（例: 0.5 で 0.5 コア分）
  --pids <数>       プロセス数の上限
  --hostname <名>   コンテナのホスト名（既定: mydocker）
  --rootfs <パス>   イメージの代わりにローカルのディレクトリを根として使う
  --layer <パス>    重ねるレイヤを直接指定する（下から順に複数回指定できる）
  --quiet           起動時のメッセージを出さない

例:
  mydocker run alpine /bin/sh
  mydocker run --memory 10m alpine sh -c 'echo hello'
  mydocker run --rootfs /var/lib/mydocker/layers/xxxx /bin/sh
`

// Run はコマンドラインを処理する。
func Run(args []string) error {
	if len(args) == 0 {
		fmt.Print(usage)
		return &ExitError{Code: 2}
	}
	switch args[0] {
	case "run":
		return cmdRun(args[1:])
	case "init":
		// ★内部用。利用者が直接叩くものではないので --help には出さない。
		//   親プロセスが /proc/self/exe を使って自分自身を再実行するための入口である。
		return cmdInit(args[1:])
	case "ps":
		return cmdPS(args[1:])
	case "exec":
		return cmdExec(args[1:])
	case "rm":
		return cmdRM(args[1:])
	case "pull":
		return cmdPull(args[1:])
	case "unpack":
		// 内部用（検査用）。tar の展開だけを単体で走らせる。
		return cmdUnpack(args[1:])
	case "info":
		return cmdInfo(args[1:])
	case "help", "-h", "--help":
		fmt.Print(usage)
		return nil
	default:
		fmt.Fprintf(os.Stderr, "知らないコマンドです: %s\n\n", args[0])
		fmt.Fprint(os.Stderr, usage)
		return &ExitError{Code: 2}
	}
}

ただの switch です。それ以上のことは何もしていません。パッケージのコメントにもそう書いてあります——「ここは薄く保つ。実際の仕事は internal/container・internal/cgroup・internal/image が持つ」。

この薄さは意図したものです。CLI の層に仕事をさせ始めると、run と exec で微妙に違う後片付けが書かれ、片方だけ直して片方を忘れる、というのが必ず起きます。後片付けのような「絶対に間違えてはいけない処理」は、1 か所にしか書かない。この方針は Step 7 でもう一度出てきます。

サブコマンドの振り分け（cli.Run の switch） 利用者が打つもの 内部用（--help に出さない） ───────────────────────── ────────────────────────────── run → cmdRun init → cmdInit ps → cmdPS └ 親が /proc/self/exe を exec → cmdExec 再実行するときの入口 rm → cmdRM unpack → cmdUnpack pull → cmdPull └ tar の展開だけを単体で走らせる info → cmdInfo （E2E が細工した tar を投入する） help / -h / --help → usage を表示 知らないコマンド → usage を標準エラーに出して ExitError{2}

なぜ init を --help に出さないのか

上の usage 文字列をもう一度見てください。init の行がありません。unpack もありません。switch にはちゃんと case があるのに、です。

init は第01章で作った re-exec パターンの受け口でした。mydocker run の親プロセスが /proc/self/exe を init という顔で起動する。そのための入口です。利用者が直接叩くものではありません。

ところが CLI というのは「並んでいるものは打たれる」ものです。--help に init と書いてあれば、必ず誰かが「初期化コマンドかな」と思って打ちます。打たれた結果が「よく分からないエラー」であれば、その人はバグを報告してくるでしょう。設計上あり得ない使い方を、道具の側が誘発しているわけです。

そこで mydocker は 3 段構えにしています。

  1. usage に載せない。目に触れさせない
  2. src/README.md のコマンド表では別の節に分ける。「内部用サブコマンド（--help に出していない）」という見出しを立て、init には「利用者が直接叩くものではない」と太字で書いてある。隠すのではなく、役割が違うことを明示する
  3. それでも叩かれたときに、意味の分かるメッセージで止まる。

3 番目がこれです。

internal/cli/cli.go — cmdInit
func cmdInit(args []string) error {
	if len(args) < 4 {
		return errors.New("init は mydocker が内部で使うサブコマンドです。直接実行しないでください")
	}
	return container.Init(container.InitArgs{
		Rootfs:   args[0],
		Hostname: args[1],
		Workdir:  args[2],
		Argv:     args[3:],
		Env:      os.Environ(),
	})
}

引数が 4 つ未満なら、はっきりと「直接実行しないでください」と言って止まります。仮に引数を 4 つ揃えて叩いたとしても、第01章で見た親との同期用ディスクリプタ（fd 3）が無いので、そこで安全に止まります。隠すだけでなく、踏まれても壊れないようにしておく。これが「内部用」の正しい扱い方です。

unpack のほうも同じ考え方ですが、こちらは存在理由が少し違います。

internal/cli/cli.go — cmdUnpack
func cmdUnpack(args []string) error {
	if len(args) != 2 {
		return errors.New("使い方: mydocker unpack <tar または tar.gz> <展開先>（内部用）")
	}
	f, err := os.Open(args[0])
	if err != nil {
		return err
	}
	defer f.Close()
	n, err := image.ExtractLayer(f, args[1])
	if err != nil {
		return err
	}
	fmt.Printf("%d 件のエントリを展開しました\n", n)
	return nil
}

これは検査のための入口です。第06章で ExtractLayer は「展開先の外にファイルを作らせない」検証（safeJoin）を持っていました。この検証が本当に効いているかを確かめるには、悪意のある tar を自分で作って投入するしかありません。.. を含むパスや絶対パスを仕込んだ tar を用意し、それを展開させて、外にファイルができないことを確認する。

そのとき、レジストリから本物のイメージを取ってきていては話になりません。tar の展開だけを単体で走らせる口が要る。それがこの unpack です。E2E テストの「== 5. 取得したイメージの安全な展開 (FR-6) ==」の節は、この口から細工した tar を投入しています。

テストのためだけに存在する入口を持つのは、悪いことではありません。悪いのは、それを利用者向けの機能のような顔で --help に並べることです。

run のオプションはどう受けるか

		quiet    = fs.Bool("quiet", false, "起動メッセージを出さない")
	)
	fs.Var(&layers, "layer", "重ねるレイヤ（下から順に複数回指定できる）")
	fs.Usage = func() { fmt.Fprint(os.Stderr, usage) }
	if err := fs.Parse(args); err != nil {
		return &ExitError{Code: 2}
	}
	rest := fs.Args()
	// …（以降はイメージの解決とコンテナ設定の組み立て。第05・06章で見た通り）
}
GO メモ · flag パッケージと繰り返し指定できるオプション

Go の標準ライブラリ flag は、fs.String("memory", "", "...") のように書くと *string を返します。ポインタなのは、パースは後から起きるからです。宣言した時点では値がまだ決まっておらず、fs.Parse(args) が走ったあとで中身が埋まる。だから使うときは *memory とデリファレンスします。

問題は --layer です。これは --layer /a --layer /b --layer /c のように何度も指定できるようにしたい。ところが fs.String は最後の 1 個で上書きされてしまいます。

そこで flag.Value インタフェースの出番です。定義はたった 2 メソッド。

type Value interface {
	String() string
	Set(string) error
}

Set はオプションが現れるたびに 1 回ずつ呼ばれます。だから Set の中で append すれば、指定された順に全部溜まる。それが stringList の正体です。String() のほうは --help に既定値を表示するために使われるもので、ここでは中身をカンマでつないで返しています。

登録は fs.Var(&layers, "layer", "...")。fs.String のように値を返すのではなく、自分で用意した受け皿のアドレスを渡す形になります。メソッドがポインタレシーバ（func (s *stringList) Set(...)）なのは、append の結果を元のスライスに書き戻す必要があるからです。値レシーバにすると、追加したものがどこにも残りません。

もうひとつ。flag.ContinueOnError を指定しているのは、パース失敗時に flag が勝手に os.Exit することを避けるためです（既定は flag.ExitOnError）。ここで勝手に終わられると、この章の主題である後片付けが走らなくなります。mydocker では失敗を &ExitError{Code: 2} に変換して、いつもの経路で返しています。

ちなみに fs.Args() はオプションを取り除いた残りの引数です。mydocker run --memory 10m alpine /bin/sh なら ["alpine", "/bin/sh"]。先頭がイメージ名で、その後ろがコンテナの中で走らせるコマンドになります。

Step 3実行中コンテナをどこに記録するか

ここからが本題です。mydocker ps を作るには、まず「今動いているコンテナ」を知っている必要があります。知るためには、起動したときに書き残しておかなければなりません。

置き場所とファイル名を決めます。internal/container/state.go の冒頭がそれです。

ここで何を記録していないかにも目を向けてください。

  • レイヤのパス（Lowers）を記録していない。あれはイメージ側の資産で、コンテナが所有しているものではないからです。記録すると「コンテナを消すときにこれも消すのか?」という迷いが生まれます。持っていないものは消せない——これは事故を防ぐ設計です
  • upper と work のパスを記録していない。どちらも containers/<ID>/ の下にあるので、ID から導けます。導けるものを二重に持つと、片方だけ書き換わったときに壊れます
  • 終了コードや終了時刻を記録していない。mydocker は「終わったコンテナ」を docker ps -a のように保持しません。終わったら片付ける、が原則です

逆に CgroupDirs を「複数」持っているのは、第04章の cgroup v1 の事情です。v1 ではコントローラごとにディレクトリが分かれる（memory/・cpu/・pids/）ので、片付ける対象が複数になります。v2 なら 1 つ。環境によって数が変わるものは、数を決め打ちせずスライスで持つのが安全です。

// NewID は 12 桁のコンテナ ID を作る。docker の短い ID と同じ見た目にしてある。
func NewID() string {
	b := make([]byte, 6)
	if _, err := rand.Read(b); err != nil {
		return strconv.FormatInt(time.Now().UnixNano(), 16)
	}
	return hex.EncodeToString(b)
}

func containersDir() string      { return filepath.Join(Root, "containers") }
func stateDir(id string) string  { return filepath.Join(containersDir(), id) }
func statePath(id string) string { return filepath.Join(stateDir(id), "state.json") }

6 バイトの乱数を 16 進にすると 12 文字。a10f2703bb37 のような、見覚えのある形になります。crypto/rand を使っているのは、math/rand だと プログラムを起動するたびに同じ列が出る（種を明示しないと固定されていた時代の名残）という事故があり得るからです。ID の衝突は「別のコンテナの記録を上書きする」という最悪の形で現れるので、ここはけちらないほうがいい。

もし乱数の取得に失敗したら、現在時刻のナノ秒を 16 進にしたものを返します。ID を作れずに起動を諦めるより、少し弱い ID で動くほうがましという判断です。

パス組み立ての 3 関数が小文字始まり（＝パッケージ外から見えない）なのも意図的です。「/var/lib/mydocker/containers/xxx という文字列を組み立ててよいのはこのファイルだけ」という縄張りを作っている。他の場所で filepath.Join(Root, "containers", id) と書けてしまうと、置き場所を変えたいときに探し漏らします。

// Load は ID から状態を読む。前方一致でも引ける（docker と同じ使い勝手）。
func Load(id string) (*State, error) {
	if s, err := loadExact(id); err == nil {
		return s, nil
	}
	// 前方一致
	entries, err := os.ReadDir(containersDir())
	if err != nil {
		return nil, fmt.Errorf("コンテナが見つかりません: %s", id)
	}
	var hit []string
	for _, e := range entries {
		if e.IsDir() && strings.HasPrefix(e.Name(), id) {
			hit = append(hit, e.Name())
		}
	}
	switch len(hit) {
	case 0:
		return nil, fmt.Errorf("コンテナが見つかりません: %s", id)
	case 1:
		return loadExact(hit[0])
	default:
		return nil, fmt.Errorf("ID %s は %d 件に一致します。もう少し長く指定してください", id, len(hit))
	}
}

func loadExact(id string) (*State, error) {
	b, err := os.ReadFile(statePath(id))
	if err != nil {
		return nil, err
	}
	var s State
	if err := json.Unmarshal(b, &s); err != nil {
		return nil, fmt.Errorf("%s の状態ファイルが壊れています: %w", id, err)
	}
	return &s, nil
}

ただし、曖昧なときに勝手にどれかを選ばないことが重要です。2 件以上に一致したら「もう少し長く指定してください」と言って止まる。rm の対象が「たぶんこれだろう」で決まってしまうのは危険すぎます。削除に関わる操作では、曖昧さは必ずエラーにする。

MarshalIndent で整形して書いているのも、人間が cat したときに読めるようにするためです。実務のサーバなら 1 行にまとめて書くところですが、ここは教材であり、そして デバッグのときに読めること が最優先です。

Step 4PID は再利用される

さて。state.json に PID を書きました。mydocker ps は「そのコンテナが生きているか」を知りたい。素直に考えるとこうです。

素朴案（これは間違い） state.json に書いてある PID = 16144 /proc/16144 が存在する？ ├ はい → 生きている └ いいえ → 死んでいる

実際、これでほとんどの場合はうまくいきます。うまくいってしまうところが厄介です。ではどこで壊れるのか。

Linux の PID は使い回されます。プロセスが終わると、その番号はいずれ別のプロセスに配られます。番号は 1 から順に増えていき、上限（多くの環境で 4194304 か 32768）に達したら 1 に戻ってまた配り直す。有限の資源なので、必ずぐるりと回ってきます。

だから、こういうことが起こり得ます。

PID の再利用が起こす誤判定 時刻 → ① mydocker run … PID 16144 でコンテナ起動 state.json に pid: 16144 と記録 ② コンテナ終了 PID 16144 は空き番号に戻る （このとき mydocker が SIGKILL されて記録が消せなかったとする） ③ …しばらく時間が経つ… 番号が一周する ④ 誰かが cron ジョブを起動 たまたま PID 16144 を割り当てられる ⑤ mydocker ps /proc/16144 は「ある」 → ★死んだコンテナが Up と表示される → ★mydocker rm は「まだ実行中です」と拒否する → ★片付けたくても永久に片付けられない

⑤ の 3 行目が本当に効きます。後片付けができなくなるのです。この章の主題は後片付けですから、生死判定の誤りは直接その足を折ります。

では、どうすれば「同じプロセスだ」と確信できるのか。答えは起動時刻を一緒に見ることです。

PID は再利用されますが、PID と起動時刻の組は事実上一意です。同じ番号が同じ時刻（システム起動からのクロック数）に生まれることは、番号が一周する時間を考えればまず起こりません。Linux は各プロセスの起動時刻を /proc/<pid>/stat に持っています。

⚠ 落とし穴 · PID は再利用される

/proc/<pid> の存在だけでは「同じプロセスがまだ生きている」ことの証明になりません。終了したコンテナの PID が別のプロセスに割り当てられると、「まだ生きている」と誤判定します。

この誤りは、ほとんどの場合に正しく動くという形で現れるので、テストでも本番でもなかなか表に出ません。出るときは、たいてい「なぜか rm できないコンテナがある」「ps に幽霊が出る」という、原因の見当がつかない不具合として現れます。

対策は、PID と一緒に起動時刻を記録し、両方が一致したときだけ生存とみなすこと。この 1 手で問題は消えます。docker や systemd のような本物のツールも、同じ理由で同じことをしています。

ついでに言うと、これは PID に限った話ではありません。「再利用される識別子だけで同一性を判定してはいけない」は、ファイルディスクリプタでも inode 番号でもデータベースの ID でも同じように現れる、一般的な落とし穴です。

実装がこれです。

internal/container/state.go（5）— IsAlive
// IsAlive はそのコンテナの PID 1 がまだ生きているかを返す。
//
// ⚠ /proc/<pid> の存在だけでは足りない。PID は再利用されるので、
//
//	起動時刻まで一致してはじめて「同じプロセス」と言える。
func (s *State) IsAlive() bool {
	if s.PID <= 0 {
		return false
	}
	st, err := readProcStat(s.PID)
	if err != nil {
		return false
	}
	if st.state == "Z" { // ゾンビは死んでいる扱い
		return false
	}
	if s.StartTime != 0 && st.startTime != s.StartTime {
		return false // PID が再利用された別のプロセス
	}
	return true
}

4 つの関門を順に通ります。

  1. PID <= 0 なら死んでいる。記録が壊れている場合の保険です。0 のまま /proc/0 を見に行っても意味がありません
  2. /proc/<pid>/stat が読めなければ死んでいる。プロセスが存在しなければこのファイルもありません
  3. 状態が Z（ゾンビ）なら死んでいる扱い。ゾンビは「もう終わっているが、親がまだ wait していないので番号だけ残っている」状態です。中でコマンドを走らせることはできませんから、生きているとは呼べません
  4. 起動時刻が違えば別人。これが今回の追加分です

4 番目の条件に s.StartTime != 0 && が付いているのに注目してください。起動時刻が記録できなかった場合（＝ 0）は、この検査を飛ばすという意味です。起動時刻の取得に失敗することはまずありませんが、失敗したときに「すべてのコンテナが死んでいることになる」よりは、「PID だけで判定する昔ながらの挙動に落ちる」ほうが安全だ、という判断です。

そして /proc/<pid>/stat の読み取り。ここにもう 1 つの落とし穴が待っています。

internal/container/state.go（6）— readProcStat
type procStat struct {
	state     string
	startTime uint64
}

// readProcStat は /proc/<pid>/stat から状態と起動時刻を読む。
//
// この行の 2 番目のフィールドはコマンド名で、括弧に包まれている。
// ⚠ コマンド名に空白や括弧が入りうるので、素朴に空白で split すると位置がずれる。
// 最後の ")" を探してからその先を切るのが定石。
func readProcStat(pid int) (procStat, error) {
	b, err := os.ReadFile(filepath.Join("/proc", strconv.Itoa(pid), "stat"))
	if err != nil {
		return procStat{}, err
	}
	line := string(b)
	i := strings.LastIndex(line, ")")
	if i < 0 || i+2 >= len(line) {
		return procStat{}, fmt.Errorf("/proc/%d/stat を解釈できません", pid)
	}
	fields := strings.Fields(line[i+2:])
	// ここでの fields[0] は元の 3 番目のフィールド（state）に当たる。
	// 起動時刻は元の 22 番目なので fields[19]。
	if len(fields) < 20 {
		return procStat{}, fmt.Errorf("/proc/%d/stat の項目が足りません", pid)
	}
	start, err := strconv.ParseUint(fields[19], 10, 64)
	if err != nil {
		return procStat{}, err
	}
	return procStat{state: fields[0], startTime: start}, nil
}

// ReadStartTime は起動直後の子プロセスの起動時刻を読む（State に記録するため）。
func ReadStartTime(pid int) uint64 {
	st, err := readProcStat(pid)
	if err != nil {
		return 0
	}
	return st.startTime
}

strings.LastIndex(line, ")") という、一見なんだかよく分からない行があります。これが今回の要です。

LINUX メモ · /proc/<pid>/stat の読み方

/proc/<pid>/stat は、そのプロセスの情報を空白区切りの 1 行にまとめたファイルです。50 個以上のフィールドが並んでいます。先頭のほうはこうなっています。

番号名前意味
1pidプロセス番号
2commコマンド名。丸括弧で包まれている
3state状態を表す 1 文字（R 実行中 / S 待機 / Z ゾンビ など）
4ppid親のプロセス番号
………
22starttimeシステム起動からの経過時間（クロックチック単位）で表した起動時刻

ここで問題になるのが 2 番目の comm です。コマンド名には空白も丸括弧も入り得ます。たとえば (my prog) や (foo) bar) のような行が普通にあり得る。すると、素朴に空白で分割したときにフィールドの位置が後ろへずれます。

// 正常な場合（コマンド名に空白なし）
// 16144 (sleep) S 16143 … ← 空白で切ると starttime は 22 番目

// コマンド名に空白がある場合
// 16144 (my prog) S 16143 … ← 空白で切ると 1 つずれて 23 番目になる

ずれた位置から読んだ数値はまったく別の意味の数です。エラーにならず、静かに間違った値が返ります。生死判定がでたらめになります。

定石は、最後の ) を探して、その先だけを空白で分割することです。コマンド名の中に ) があっても、行の最後の ) は必ず comm の閉じ括弧だからです（3 番目以降のフィールドは数値と 1 文字の状態だけで、括弧は出てきません）。

切った先を数え直すと、fields[0] が元の 3 番目（state）になります。したがって元の 22 番目は fields[22-3] = fields[19]。コード中のコメントに書いてあるのは、この対応関係です。「なぜ 19 なのか」が読者に伝わらない 19 はマジックナンバーなので、必ずコメントを添えます。

ちなみに i+2 で切っているのは、) の次が空白で、その次から state が始まるからです。strings.Fields は連続する空白をまとめて扱ってくれるので、実は i+1 でも動きます。i+2 にしてあるのは「閉じ括弧と空白を確かに越えた」という意図を示すためです。i+2 >= len(line) のチェックは、その先に本当に中身があるかの確認になります。

ReadStartTime のほうは、コンテナを起動した直後に呼ばれます。第01章で見た container.Run の中に、この 2 行がありました。

internal/container/run.go — Run の一部（再掲）
	pid := cmd.Process.Pid
	st.PID = pid
	st.StartTime = ReadStartTime(pid)

子プロセスを起動した直後、まだ生きているうちに起動時刻を読んで記録しておく。これが後の生死判定の基準になります。

Step 5ps を作る

道具が揃いました。ps は「containers/ の下を全部読んで、生きているものだけ並べる」だけです。まず一覧を作る側から。

internal/container/state.go（7）— List
// List は実行中のコンテナだけを返す。
//
// 死んだのに記録が残っているもの（mydocker 自身が強制終了された場合など）は
// 一覧には出さないが、**勝手に消しもしない**。マウントが残っている可能性があり、
// 確認せずに消すのが最も危険だからである。片付けは mydocker rm で明示的に行う。
func List() ([]*State, error) {
	entries, err := os.ReadDir(containersDir())
	if err != nil {
		if os.IsNotExist(err) {
			return nil, nil
		}
		return nil, err
	}
	var alive []*State
	for _, e := range entries {
		if !e.IsDir() {
			continue
		}
		s, err := loadExact(e.Name())
		if err != nil {
			continue
		}
		if s.IsAlive() {
			alive = append(alive, s)
		}
	}
	sort.Slice(alive, func(i, j int) bool { return alive[i].CreatedAt.Before(alive[j].CreatedAt) })
	return alive, nil
}

読みどころが 3 つあります。

1. ディレクトリが無いのはエラーではない。os.IsNotExist(err) のときは nil, nil を返します。mydocker をインストールして最初に mydocker ps を打ったとき、/var/lib/mydocker/containers/ はまだ存在しません。それは「コンテナが 0 件」であって「失敗」ではない。「まだ何もない」と「壊れている」を区別するのは、道具として当たり前の礼儀です。

2. 壊れた記録は黙って飛ばす。loadExact が失敗したら continue。1 つの壊れた state.json のせいで ps 全体が失敗すると、まさに調べたいときに調べられない という最悪の状況になります。

3. 作成順に並べる。sort.Slice で CreatedAt の昇順。os.ReadDir はファイル名順（＝ランダムな 16 進文字列の順）で返してくるので、そのままだと打つたびに順番が変わって見えます。同じ状態なら同じ表示になることは、目視で差分を見るときに効きます。

GO メモ · text/tabwriter

表を整形するとき、素朴には fmt.Printf("%-14s %-38s ...") のように桁数を決め打ちします。これは動きますが、イメージ名が長いと崩れ、短いとスカスカになります。しかも桁数はコードの中に何度も書かれるので、1 か所直し忘れると列がずれます。

標準ライブラリの text/tabwriter はこれを解決します。使い方は 3 手です。

  1. w := tabwriter.NewWriter(os.Stdout, 0, 0, 3, ' ', 0) でライタを作る
  2. 各列をタブ文字 \t で区切って w に書く
  3. 最後に w.Flush() を呼ぶ

Flush を呼ぶまで tabwriter は出力を溜め込みます。全部の行が揃ってはじめて各列の最大幅が決まるからです。決まってから、幅を揃えて一気に吐き出す。だから Flush を忘れると何も表示されません。これは tabwriter でいちばんよくある事故です。

NewWriter の引数は順に、出力先・最小セル幅（0）・タブ幅（0）・パディング（3）・埋める文字（' '）・フラグ（0）です。4 番目の 3 が「列と列の間に最低 3 文字あける」という指定で、mydocker ps の出力で列間が 3 スペース空いているのはこれです。

そして最後の fmt.Printf("合計 %d 件\n", ...) は w ではなく os.Stdout に直接書いていることに注意してください。w.Flush() を先に呼んでいるので順番は崩れません。この行はタブを含まないので、表の列揃えに巻き込みたくないのです。

なぜ「合計 N 件」を出すのか

コードのコメントに 「★件数を実数で出す。「0件でも緑」を防ぐため、テストはこの行を数える」 とあります。これは見た目の親切心ではなく、テストが空振りしないための仕掛けです。

こういうテストを書いたとします。

# コンテナを起動して、ps に出ることを確かめたい（この書き方は駄目）
mydocker run --quiet alpine sleep 20 &
mydocker ps | grep -q alpine && echo OK

一見よさそうです。しかし grep が失敗したときも、&& の左が偽になるだけで、スクリプト全体は成功で終わるかもしれません。あるいは ps の実装が壊れて 1 行も出さなくなっても、テストの側に「何件出るはずか」という期待値が書かれていなければ、0 件でも「失敗 0 件」で緑になります。

これは私が第04章の cgroup でも踏んだ罠と同じ形です（「上限が効いていることを確かめたつもりが、テストのほうが間違っていた」）。「何も起きなかった」と「正しく動いた」を、テストが区別できていないのです。

そこで ps は必ず末尾に 合計 N 件 を出します。テストはこの N を読んで、期待値と突き合わせる。0 件なら 0 件だと明示的に主張させることで、空振りが空振りとして検出されるようになります。E2E テストの実際の行はこうです。

$ python3 e2e_test.py
  OK   10 回連続で起動・終了してもすべて成功する（実数で確認: 10/10 件成功）

「実数で確認」という言葉が入っているのは、この方針を自分に課している印です。この考え方は mydocker info の overlay 数: 0 件 にも同じように効いています（Step 8）。

ps の出力を作ったので、次に自然にやりたくなるのがこれです。

PID は 4 列目（CONTAINER ID / IMAGE / COMMAND / PID）だから $4。理屈は通っています。そして壊れました。実際に取れたのは sleep 40 の 40 でした。

理由は明白です。COMMAND 列に空白が入るから。awk は空白で列を切るので、sleep 40 は 2 列に見えます。列がずれる。

これは Step 4 の /proc/<pid>/stat とまったく同じ形の失敗です。「空白区切りの整形出力は、値の中に空白が入った瞬間に壊れる」——ここまでで 2 回踏みました。

教訓は 2 つ。

  • 整形出力は人間のためのもの。列幅も列順も、読みやすさのために将来変わり得ます。機械がそれを解析する前提にしてはいけません
  • 機械が読むときは構造化されたものを読む。mydocker の E2E テストは、ps の出力ではなく /var/lib/mydocker/containers/<ID>/state.json を直接読んで PID を取り出すように直しました。JSON なら空白が入っても壊れません

ついでに言えば、これが Step 3 で「状態をファイルに、しかも JSON で置く」ことに価値があったもうひとつの理由です。人間向けの表示と、機械向けの真実を、別々に持っておく。

LINUX メモ · setns(2) の制約

setns(fd, nstype) は「fd が指している名前空間に、呼び出し元を参加させる」システムコールです。fd はどこから取るのか——/proc/<pid>/ns/ の下にあるファイルを開いて得ます。

/proc/<pid>/ns/
  ├ pid     ← そのプロセスが属する PID 名前空間
  ├ mnt     ← マウント名前空間
  ├ uts     ← ホスト名の名前空間
  ├ ipc     ← プロセス間通信の名前空間
  ├ net     ← ネットワーク名前空間
  └ user    ← ユーザー名前空間

これらは普通のファイルではなく、名前空間そのものへの参照です。開いて setns に渡すと、その名前空間に入れます。

ところが、名前空間の種類ごとに制約が違います。この章に関係するのは次の 2 つです。

  • PID 名前空間の setns は、呼び出し元自身には効かない。効くのはそのあとに作る子プロセスから。第01章で unshare(CLONE_NEWPID) について見たのと同じ理屈です（走っている最中に自分の番号が変わったら困るから）
  • マウント名前空間の setns は、呼び出し元がシングルスレッドでなければならない。スレッドが 2 本以上あると EINVAL で失敗します

2 つ目が厄介です。マウント名前空間は「どのファイルシステムがどこに見えるか」という、プロセス全体の世界観を決めるもの。スレッドごとに違う世界に住んでいる状態は意味が通らないので、カーネルは「全スレッドまとめて移す」か「そもそも許さない」かを選び、後者を選びました。

そして——Go のランタイムは常にマルチスレッドです。あなたが goroutine を 1 つも作らなくても、ガベージコレクタとスケジューラのために裏で複数の OS スレッドが走っています。つまり、素の Go からマウント名前空間へ setns することはできません。

本物の runc はこの一点のために、cgo で C のコンストラクタを書いています。C の __attribute__((constructor)) を使うと、Go のランタイムが起動してスレッドを増やす前にコードを走らせられる。その一瞬（＝まだシングルスレッドの瞬間）に setns を済ませてしまう、という荒業です（nsexec という名前で知られています）。

さあ、判断のときです。mydocker は「Go の標準ライブラリだけで書く」を前提にしています。cgo を持ち込むとその前提が崩れ、読者にとっても難度が跳ね上がる。選択肢を並べてみます。

internal/container/run.go — Exec
// Exec は実行中のコンテナの中でもう1つコマンドを走らせる。
//
// 実現の仕方:
//   - PID / UTS / IPC 名前空間は setns で **既存のコンテナのものに参加する**
//   - マウント名前空間だけは新しく作り、同じ merged ディレクトリを根にする
//
// なぜマウントだけ別扱いなのか: setns でマウント名前空間に入るには
// **呼び出し元がシングルスレッドでなければならない**（多スレッドだと EINVAL）。
// Go のランタイムは常にマルチスレッドなので、cgo を使わずにこれは満たせない。
// 同じ overlay の merged を根にすれば、見えるファイルは完全に同一なので実害は無い。
// （この割り切りは 03_implementation.md に判断として記録してある）
func Exec(st *State, argv []string, env []string) (int, error) {
	if !st.IsAlive() {
		return 1, fmt.Errorf("コンテナ %s は実行中ではありません", st.ID)
	}

	// ⚠ setns はスレッド単位の操作である。fork もこのスレッドから行われる必要があるので、
	//    goroutine を OS スレッドに固定してから触る。
	runtime.LockOSThread()
	defer runtime.UnlockOSThread()

	// pid 名前空間への setns は「呼び出し元自身」ではなく「これから作る子」に効く。
	// つまりこの後の cmd.Start() で生まれる子が、コンテナの PID 名前空間に入る。
	for _, ns := range []struct {
		name string
		flag int
	}{
		{"uts", syscall.CLONE_NEWUTS},
		{"ipc", syscall.CLONE_NEWIPC},
		{"pid", syscall.CLONE_NEWPID},
	} {
		path := filepath.Join("/proc", fmt.Sprint(st.PID), "ns", ns.name)
		f, err := os.Open(path)
		if err != nil {
			return 1, fmt.Errorf("%s を開けませんでした: %w", path, err)
		}
		_, _, errno := syscall.Syscall(sysSetns, f.Fd(), uintptr(ns.flag), 0)
		f.Close()
		if errno != 0 {
			return 1, fmt.Errorf("%s 名前空間に参加できませんでした: %v", ns.name, errno)
		}
	}

	syncR, syncW, err := os.Pipe()
	if err != nil {
		return 1, err
	}
	args := append([]string{"init", st.Merged, st.Hostname, orSlash(st.Workdir)}, argv...)
	cmd := exec.Command("/proc/self/exe", args...)
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags:   syscall.CLONE_NEWNS,
		Unshareflags: syscall.CLONE_NEWNS,
	}
	cmd.Stdin, cmd.Stdout, cmd.Stderr = os.Stdin, os.Stdout, os.Stderr
	cmd.Env = env
	cmd.ExtraFiles = []*os.File{syncR}

	if err := cmd.Start(); err != nil {
		syncR.Close()
		syncW.Close()
		return 1, err
	}
	syncR.Close()
	// exec では cgroup を触らないので、すぐに合図を送ってよい。
	_, _ = syncW.WriteString(syncReady)
	syncW.Close()

	return exitCode(cmd.Wait()), nil
}

GO メモ · runtime.LockOSThread

Go の goroutine は、OS スレッドの上を移動します。ランタイムのスケジューラが、空いているスレッドに goroutine を割り当てて走らせる。ある行はスレッド A で、次の行はスレッド B で実行される、ということが普通に起こります（システムコールで一度ブロックした後などが典型です）。

普段はこれで何も困りません。ところが setns のようなスレッド単位で効くシステムコールを使うと、話が変わります。

	setns(pid 名前空間)   ← スレッド A で実行。効果はスレッド A に付く
	（ここで goroutine がスレッド B に移動したら…）
	cmd.Start()            ← スレッド B で fork。★名前空間に入っていない子が生まれる

効果を付けたスレッドと、実際に子を作るスレッドが違ってしまう。しかも、いつ移動するかはこちらから制御できません。テストでは動いて本番で稀に壊れる、という最悪の形のバグになります。

runtime.LockOSThread() は「この goroutine を、今走っている OS スレッドに固定する」という宣言です。以後 runtime.UnlockOSThread() を呼ぶまで、この goroutine は他のスレッドに移りません。逆に、そのスレッドで他の goroutine が走ることもありません。

これで「setns したスレッドから fork する」が保証されます。defer runtime.UnlockOSThread() で関数を抜けるときに解除するのも忘れずに。解除しないままにすると、そのスレッドが専有されたままになります。

この関数が必要になる場面は、実は決まっています。スレッドに紐づく OS の状態を触るときです。setns・unshare・setuid 系、そして OpenGL のようにスレッドローカルな文脈を持つライブラリを呼ぶとき。Go の日常のコードでは一生使いませんが、カーネルの近くまで降りると必ず出会います。

もうひとつ、標準ライブラリの穴を埋めている箇所があります。syscall.Syscall(sysSetns, ...) の sysSetns です。

この教材は外部ライブラリを使わない決まりなので、番号を自分で持ちます。システムコールは結局のところ「番号を指定してカーネルに飛び込む」だけの仕組みなので、番号さえ分かれば syscall.Syscall で直接呼べます。

番号は CPU アーキテクチャごとに違います。amd64 なら 308、arm64 なら 268。ここで Go のビルド機構が効いてきます。ファイル名の末尾が _linux_amd64.go なら、Linux の amd64 でビルドするときだけこのファイルがコンパイルされる。_linux_arm64.go も同じ。だから両方に同じ名前の定数を書いておけば、ビルドするアーキテクチャに応じて自動的に正しいほうが選ばれます。#ifdef のような仕掛けを書かずに済む、地味に気持ちのいい仕組みです。

	if code != 0 {
		return &ExitError{Code: code}
	}
	return nil
}

Load → Exec → 終了コードを ExitError に包む。それだけ。Step 1 で見た「入り口は薄く」がここでも効いています。

Step 7★後片付け — この章の本番

ここからが、この章でいちばん大事な話です。

コンテナが終わったとき、片付けるものが 3 つあります。

  1. cgroup ディレクトリ（/sys/fs/cgroup/.../mydocker/<ID>/）
  2. overlay のマウント（containers/<ID>/merged）
  3. コンテナ用ディレクトリ（containers/<ID>/ 丸ごと。state.json・upper・work を含む）

素朴に書くとこうなります。

// 素朴案（これは危険）
os.Remove(cgroupDir)
syscall.Unmount(merged, 0)
os.RemoveAll(containerDir)

3 行。何も難しくないように見えます。この 3 行が、条件が揃うとイメージを丸ごと消します。

なぜ消えるのか

umount は EBUSY（デバイスが使用中）で日常的に失敗します。珍しい状況ではありません。

  • コンテナのプロセスがまだ完全には終わっていない
  • 誰かのシェルの作業ディレクトリがそのマウントの中にある
  • そのマウントの中のファイルを誰かが開いたままにしている
  • exec で入ったプロセスが残っている

これだけで EBUSY です。そして上の素朴案は戻り値を見ていません。Unmount が失敗しても、次の行の os.RemoveAll(containerDir) に進みます。

ここで何が起きるか。containerDir の下には merged/ があります。merged/ はマウントされたままです。マウントされたディレクトリの中身は、下層（lowerdir）＝展開済みのイメージレイヤそのものです。

アンマウント失敗を無視して削除に進むと何が起きるか containers/<ID>/ ├ state.json ├ upper/ ← 消えてよい（このコンテナの書き込み） ├ work/ ← 消えてよい └ merged/ ← ★まだマウントされている │ │ overlay 越しに見えているのは… ↓ layers/sha256_55afa1ecc21d…/ ← ★イメージの実体 ├ bin/ （他のコンテナも使う共有資産） ├ etc/ └ … os.RemoveAll(containers/<ID>/) は merged/ の中を再帰的に辿って削除しようとする ↓ ★マウント越しに layers/ の実体まで消える ↓ 次に mydocker run すると「レイヤのディレクトリがありません」 もう一度 pull し直すしかない。他のコンテナも巻き添え。

rm -rf はマウントポイントを特別扱いしません。そこにあるファイルを、あるがままに消します。overlay 越しに見えているファイルを消せば、消えるのは下層の実体です。

この事故が恐ろしいのは、エラーが出ないことです。umount の失敗は無視され、RemoveAll は成功します。プログラムは正常終了します。壊れたことに気づくのは、次にコンテナを起動しようとしたときです。

⚠ 落とし穴 · umount 失敗を無視して削除に進む

アンマウントの成否を確かめずに削除へ進んではいけません。これは「気をつけましょう」という話ではなく、コードの構造で防ぐべきものです。

mydocker では 3 つの関所を置いています。

  1. overlay.Mount.Unmount() は、成功したように見えても IsMountPoint で本当に外れたかを確認する。外れていなければエラーを返す
  2. 呼び出し元（Run の cleanup と Cleanup）は、アンマウントが失敗したらそこで return する。削除の行に到達しない
  3. RemoveRecord は、削除の直前にもう一度 isMounted で確認する。マウントされていれば削除せずエラーを返す

3 番目は一見むだです。呼び出し元が既に確認しているのだから。むだではありません。これは「将来、誰かが順序を間違えて RemoveRecord を直接呼んだとき」の最後の砦です。取り返しのつかない操作には、二重の関所を置く。

もうひとつ。アンマウントに失敗したとき、mydocker は状態ファイルも残します。中途半端に消して「何が残っているか分からない」状態を作るより、全部残して人間が調べられるようにするほうが安全だからです。片付け損ねたものは mydocker rm であとから回収できます（Step 9）。

では実装を見ます。

internal/container/run.go — Cleanup（全文）
// Cleanup は1つのコンテナの痕跡を片付ける。rm コマンドと、異常終了の後始末に使う。
//
// ⚠ 順序が命。「アンマウント → 削除」であり、**前者が失敗したら後者に進まない**。
func Cleanup(st *State) error {
	if st.IsAlive() {
		return fmt.Errorf("コンテナ %s はまだ実行中です。先に終了させてください", st.ID)
	}
	var firstErr error

	for _, dir := range st.CgroupDirs {
		if err := os.Remove(dir); err != nil && !os.IsNotExist(err) {
			firstErr = fmt.Errorf("cgroup ディレクトリを削除できませんでした (%s): %w", dir, err)
		}
	}
	if st.Merged != "" && overlay.IsMountPoint(st.Merged) {
		m := &overlay.Mount{Merged: st.Merged}
		if err := m.Unmount(); err != nil {
			// ★アンマウントに失敗したら絶対に削除へ進まない
			if firstErr == nil {
				firstErr = err
			}
			return firstErr
		}
	}
	if err := RemoveRecord(st); err != nil && firstErr == nil {
		firstErr = err
	}
	return firstErr
}
後片付けの順序（Cleanup の分岐） Cleanup(st) │ ├ まだ生きている？ ──はい──→ ★エラーで即座に戻る │ 「まだ実行中です。先に終了させてください」 ↓ いいえ ① cgroup ディレクトリを rmdir（複数あり得る） │ 失敗しても firstErr に控えて続行 ↓ ② merged はマウントされている？ │ ├─いいえ──────────────────────────────┐ ↓ はい │ umount(merged) │ │ 失敗（EBUSY 等）→ MNT_DETACH を1度試す │ ↓ │ 本当に外れたか？（IsMountPoint で確認） │ │ │ ├─いいえ──→ ★ここで return。 │ │ 削除に進まない。 │ │ 状態ファイルも残す。 │ ↓ はい │ └────────────────────────────────────────┘ ↓ ③ RemoveRecord(st) └ ★もう一度 isMounted で確認（二重の関所） ├ マウント中 → 削除せずエラー └ 外れている → os.RemoveAll(containers/<ID>)

順に読みます。

まず生死の確認。生きているコンテナを片付けるのは論外です。mydocker rm で実行中のものを指定すると、ここで止まります。

次に cgroup。ここで os.Remove（＝ rmdir）を使っているのが重要です。

⚠ 落とし穴 · cgroup は rm -rf では消えない

cgroup のディレクトリを片付けようとして os.RemoveAll（＝ rm -rf 相当）を書くと、失敗します。cgroupfs は通常のファイルシステムではないからです。

あの中に見える memory.limit_in_bytes や cgroup.procs は、ディスク上のファイルではなくカーネルが見せている窓です。個別に unlink することはできません。rm -rf は中身を 1 つずつ消そうとして、そこで失敗します。

正しいのは ディレクトリそのものを rmdir することです。中の「ファイル」はディレクトリと一緒に消えます。mydocker が os.RemoveAll ではなく os.Remove を使っているのはこのためです。

そして rmdir は、その cgroup の中にまだプロセスが残っていれば失敗します。これは正しい挙動です。プロセスが残っているのに上限の枠を消してしまったら、そのプロセスは上限のない世界に放り出されます。だから mydocker はこの失敗を握りつぶさず、エラーとして返します。

os.IsNotExist(err) のときだけは無視しています。「もう無い」は「片付いている」ということなので、エラーにする理由がありません。片付け処理は何度呼んでも同じ結果になる（冪等である）べきです。

そして overlay。ここが本番です。st.Merged != "" と overlay.IsMountPoint(st.Merged) の両方を確認してから Unmount を呼びます。Unmount の中身は第06章で見たとおりです。

internal/overlay/overlay.go — Unmount（再掲）
func (m *Mount) Unmount() error {
	if err := syscall.Unmount(m.Merged, 0); err != nil {
		// MNT_DETACH は「今すぐ切り離し、参照が切れたら実際に外す」遅延アンマウント。
		// EBUSY のときの最後の手段として一度だけ試す。
		if err2 := syscall.Unmount(m.Merged, syscall.MNT_DETACH); err2 != nil {
			return fmt.Errorf("overlay を外せませんでした (%s): %w", m.Merged, err)
		}
	}
	// ★本当に外れたかを確認してからでなければ、呼び出し元は削除に進んではいけない。
	if IsMountPoint(m.Merged) {
		return fmt.Errorf("overlay がまだマウントされたままです: %s", m.Merged)
	}
	return nil
}

普通の umount が失敗したら MNT_DETACH を一度だけ試す。それでも駄目ならエラー。そして成功したように見えても、IsMountPoint でもう一度確かめる。「システムコールがエラーを返さなかった」と「目的が達成された」は別のことです。

最後に RemoveRecord。これが二重の関所の 3 つ目です。

internal/container/state.go（8）— RemoveRecord と isMounted
// RemoveRecord は状態ファイルとコンテナ用ディレクトリを消す。
//
// ⚠ 呼び出す前に必ずアンマウントを済ませ、**成功を確認してから**呼ぶこと。
//
//	マウントされたまま消すと、マウント越しに lowerdir（＝イメージの実体）まで消える。
func RemoveRecord(s *State) error {
	if s.Merged != "" && isMounted(s.Merged) {
		return fmt.Errorf("まだマウントされているため削除しません: %s", s.Merged)
	}
	return os.RemoveAll(stateDir(s.ID))
}

// isMounted はマウントポイントかどうかを親との st_dev 比較で判定する。
// 別のファイルシステムが被さっていれば、自分と親でデバイス番号が変わる。
func isMounted(path string) bool {
	var st, parent syscall.Stat_t
	if err := syscall.Lstat(path, &st); err != nil {
		return false
	}
	if err := syscall.Lstat(filepath.Dir(path), &parent); err != nil {
		return false
	}
	return st.Dev != parent.Dev
}

isMounted の判定方法が面白いところです。自分の st_dev（デバイス番号）と、親ディレクトリの st_dev を比べる。違えば、別のファイルシステムが被さっているということ——つまりマウントポイントです。mountpoint(1) コマンドと同じ考え方で、/proc/mounts を文字列で解析するより確実です（パスにエスケープが入る問題も避けられます）。

Step 8リークを数えて確かめる

後片付けのコードを書きました。では、それが本当に効いていることを、どうやって確かめますか?

これは真面目な問いです。片付けのコードは、正常系では「何も起きない」ことが正解です。何も起きないものをテストするのは難しい。しかも——

⚠ 落とし穴 · マウントのリークは静かに進行する

コンテナを 1 回起動して、1 個マウントが残った。これに気づく人はいません。何も壊れないからです。ディスクも減りません（overlay のマウント自体は容量を食わない）。エラーメッセージも出ません。mydocker ps にも出ません。

10 回起動して 10 個残っても、まだ何も起きません。100 回でも動きます。

症状が出るのは、ずっと後です。/proc/mounts が肥大してマウント操作が遅くなる。ディレクトリが削除できなくなる。upper に溜まった書き込みが解放されずディスクが埋まる。そのとき初めて「何かおかしい」となりますが、原因が「3 週間前から少しずつ漏れていたマウント」だと突き止めるのは、ほぼ不可能です。

だから、症状が出るのを待ってはいけません。数えるのです。「10 回起動して 10 個残っていないか」を、コードを書いた直後に、実数で確かめる。これが唯一まともな検査方法です。

同じ理屈が cgroup ディレクトリにも当てはまります。実際、この実装では「葉（.../mydocker/<ID>）は消えているのに、親の .../mydocker/ が残り続けていた」というリークを、数えることで発見しました。「配下にディレクトリが残っていない」というテストは通っていたのに、です。

数えるための道具は、第06章で作ってありました。overlay.CountMounts です。

internal/overlay/overlay.go — CountMounts（再掲）
// CountMounts は /proc/mounts に現れる、指定の種類のマウント数を数える。
// 「10回起動して10個残っていないか」を数えて確かめるために使う。
func CountMounts(fstype string) (int, error) {
	b, err := os.ReadFile("/proc/mounts")
	if err != nil {
		return 0, err
	}
	n := 0
	for _, line := range strings.Split(string(b), "\n") {
		f := strings.Fields(line)
		if len(f) >= 3 && f[2] == fstype {
			n++
		}
	}
	return n, nil
}

/proc/mounts の各行は「デバイス マウント先 種類 オプション …」という並びです。3 番目（f[2]）が種類なので、そこが overlay の行を数えればいい。第06章で見た、mydocker が実際に作る行はこうでした。

$ cat /proc/mounts

3 番目のフィールドが overlay。この行が 1 コンテナにつき 1 本現れ、片付いたら消えるはずです。

この関数を mydocker info に繋いであります。

使い方は簡単です。作業を始める前に mydocker info を打って数を控え、ひとしきり遊んだ後にもう一度打つ。数が戻っていれば漏れていません。増えていれば漏れています。それだけで、静かに進行するリークが目に見えるものになります。

▸ 動かして確認

E2E テストの「後片付けとリーク」の節を走らせた結果です。

$ python3 e2e_test.py
== 8. 後片付けとリーク (FR-10) ==
  OK   10 回連続で起動・終了してもすべて成功する（実数で確認: 10/10 件成功）
  OK   10 回起動しても overlay のマウント数が増えない（前 0 件 → 後 0 件）
  OK   テスト全体を通してホストのマウント数が元に戻る（開始 22 → 終了 22）

3 行それぞれが違うことを見ています。

  • 1 行目は「10 回とも成功した」。10/10 件成功 と実数で書いてあるのは、ps の 合計 N 件 と同じ理由です。0 回しか走らなくても緑になる、を防ぎます
  • 2 行目が今回の主役。10 回起動する前と後で overlay のマウント数を数え、0 件 → 0 件 と一致した。1 回でも漏れていたら 0 件 → 1 件 になり、そこで落ちます
  • 3 行目はもっと広い網です。overlay に限らず、ホストのマウント表全体の行数をテストの最初と最後で比べている。開始 22 → 終了 22。これは「mydocker がホストに何も置き土産をしていない」ことの証明です。overlay 以外の、たとえば /proc や /dev の貼り忘れも、この 1 行が捕まえます

3 行目の網が広いのは意図的です。自分が想定した種類のリークしか数えていないテストは、想定外のリークを見逃します。だから「総数が元に戻ること」という、種類を問わない検査を最後に置いています。

この「前と後で数を比べる」という形は、地味ですがとても強力です。何を漏らすかを事前に知らなくても、漏れたことは分かる。ファイルディスクリプタでも、一時ファイルでも、プロセス数でも、同じ形が使えます。

Step 9強制終了された場合

ここまでの後片付けは、すべて mydocker 自身が生きていることを前提にしていました。Run の最後で cleanup を呼ぶ。rm で Cleanup を呼ぶ。どちらも、コードが実行される機会があるから成り立ちます。

では——mydocker 自身が SIGKILL されたら?

SIGKILL（kill -9）は捕まえられません。ハンドラを書くことも、defer を走らせることも、ログを残すこともできません。プロセスはその場で消えます。OOM killer が動いたときも、管理者が痺れを切らして kill -9 を打ったときも同じです。

そのとき何が残るか。

mydocker が SIGKILL されたときに残るもの 残るもの 残らないもの ────────────────────────────── ──────────────────── containers/<ID>/state.json コンテナのプロセス └ pid が書いてある（そのプロセスは死んでいる） └ 親が死ぬと道連れ containers/<ID>/merged ★マウントされたまま （PID 1 が死ねば containers/<ID>/upper 名前空間ごと消える） cgroup ディレクトリ ★ この状態は「壊れている」わけではない。 ただ、片付けるべきものが片付いていないだけ。 → mydocker rm <ID> で回収できるようにしておく

ここで mydocker が取っている態度が、Step 5 で見た List のコメントです。もう一度読んでください。

internal/container/state.go — List のコメント（再掲）
// List は実行中のコンテナだけを返す。
//
// 死んだのに記録が残っているもの（mydocker 自身が強制終了された場合など）は
// 一覧には出さないが、**勝手に消しもしない**。マウントが残っている可能性があり、
// 確認せずに消すのが最も危険だからである。片付けは mydocker rm で明示的に行う。

2 つのことを同時に言っています。

1. 死んだものは ps に出さない。「実行中のコンテナを一覧する」コマンドなので、死んでいるものが混ざっていては嘘になります。IsAlive() が偽なら並べません。

2. しかし勝手に消しもしない。ここが肝心です。「死んでいると分かったのだから、ついでに片付けてしまえばいいのでは?」と思うでしょう。それがいちばん危険です。

理由は 2 つあります。

1 つ目。ps は「見るだけ」のコマンドだと誰もが思っているから。読み取り専用のつもりで打ったコマンドが、裏でディスクを消していたら、それは道具として信用できません。問い合わせるコマンドは、状態を変えない。

2 つ目。マウントが残っている可能性があるから。Step 7 でさんざん見たとおり、マウントされたまま削除に進むとイメージの実体まで消えます。それを ps の副作用として、利用者が何も知らないうちにやるなど、あり得ません。

だから mydocker は「見えないが、そこにある」という状態を許容します。片付けは mydocker rm <ID> で人間が明示的に指示したときだけ行う。そして rm は Step 7 の順序を守るので、安全に回収できます。

mydocker 自身を SIGKILL して残骸を作り、それを rm で回収した実際の記録です。

  2. しかし mount を数えると overlay が 1 個残っている。ps が嘘をついているのではありません。「実行中ではないが、片付いてもいない」ものが 1 つあるだけです
  3. mydocker rm f280be2460e3 で回収。片付けた ID が出力されます
  4. もう一度数えると 0 個。マウントが外れ、ディレクトリも消えました

2 と 3 の間が、この設計の要です。残骸は残るが、残骸だと分かる形で残り、明示的な指示で安全に回収できる。これが「勝手に消さない」の見返りです。

なお、残骸の ID は ls /var/lib/mydocker/containers/ で見つけられます。ps に出ないものを探すには、記録そのものを見るのがいちばん確実です。

ここで 1 つ、正直に書いておきます。本物の docker は、この問題をもっと大掛かりに解いています。常駐するデーモン（dockerd）が全体を見張り、起動時に前回の残骸を検出して回収する仕組みを持っています。mydocker にはデーモンがなく、コマンドを打ったときにだけ動きます。だから「起動時に自動回収」ができません。

それでも rm で回収できるようにしてあること、そして「残骸が残る場合がある」ことを隠さず書いてあることが、この設計の誠実さです。できないことを黙って隠すと、それは利用者が踏む地雷になります。

Step 10終了コードの翻訳

道具として最後に必要なのが、終了コードを正しく伝えることです。Step 1 で ExitError を作ったのは、この準備でした。

実装中に、こういう問題に当たりました。メモリ上限で殺されたコンテナの終了コードが 255 になっていたのです。

原因は Go の ExitError.ExitCode() の仕様です。シグナルで殺された場合、この関数は -1 を返します。「終了コードなど無い（シグナルで死んだのだから）」という意味で、これは正しい設計です。しかし、その -1 をそのまま os.Exit に渡すと——os.Exit は下位 8 ビットしか使わないので——255 になります。

255 では何も伝わりません。「OOM で殺された」のか「単にコマンドが 255 を返した」のか、区別がつかない。E2E テストも、この値では「上限が効いた」ことを検査できません。

シェルには昔からの慣習があります。シグナル N で死んだプロセスの終了コードは 128 + N とする。bash も sh もこうしています。

終了コード意味由来
0正常終了—
1〜125コマンド自身が返した終了コード—
130Ctrl-C で中断された128 + 2（SIGINT）
137強制終了された（OOM kill を含む）128 + 9（SIGKILL）
143終了を要求されて終わった128 + 15（SIGTERM）

この翻訳を行うのが exitCode です。

internal/container/run.go — exitCode
// exitCode は子プロセスの終了状況をシェルの終了コードに翻訳する。
//
// ⚠ シグナルで殺されたプロセスの ExitCode() は -1 を返す。これをそのまま os.Exit に渡すと
// 255 になり、「OOM で殺された」ことが利用者に伝わらない。
// シェルの慣習に合わせて 128+シグナル番号 を返す（OOM kill なら SIGKILL(9) で 137）。
func exitCode(err error) int {
	if err == nil {
		return 0
	}
	var ee *exec.ExitError
	if errors.As(err, &ee) {
		if ws, ok := ee.Sys().(syscall.WaitStatus); ok && ws.Signaled() {
			return 128 + int(ws.Signal())
		}
		return ee.ExitCode()
	}
	return 1
}

ee.Sys() は OS 固有の生の終了状態を返します。Linux では syscall.WaitStatus。これに対して Signaled() を聞けば「シグナルで死んだか」が、Signal() を聞けば「どのシグナルか」が分かります。

シグナルで死んだなら 128 + シグナル番号。そうでなければ普通の終了コード。*exec.ExitError ですらない（＝そもそも起動に失敗したような）エラーなら 1。

そしてこの数値が cmdRun で &ExitError{Code: code} に包まれ、main の errors.As で取り出され、os.Exit(ee.Code) で利用者に届きます。Step 1 で「なぜ ExitError が要るのか」と言っていた話が、ここで一周して閉じます。

終了コードが利用者に届くまで コンテナの中のコマンドが SIGKILL で死ぬ ↓ cmd.Wait() が *exec.ExitError を返す（ExitCode() は -1） ↓ exitCode(err) ├ ws.Signaled() → true └ 128 + 9 = 137 を返す ↓ container.Run が (137, nil) を返す ↓ cmdRun: code != 0 なので &ExitError{Code: 137} を返す ↓ main: errors.As で拾って os.Exit(137) ↓ $ echo $? 137 ← 利用者に「強制終了された」と伝わる

第04章の対照実験をもう一度、今度は終了コードだけを見るつもりで打ってみてください。

$ mydocker run --quiet alpine /bin/sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1'

1+0 records out

$ mydocker run --quiet --memory 10m alpine /bin/sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1'

上限なしなら 0、10MB の上限をかけると 137。しかも 2 つ目は何も出力せずに終わっています（dd がバッファを確保しようとした瞬間に殺されたので）。

もしこの 137 が 255 のままだったら、E2E テストの「OK 上限超過が OOM による強制終了として報告される (exit 137)」という検査は書けませんでした。正しい終了コードは、道具としての作法であると同時に、テストが検査できる形をつくることでもあります。

Step 11dead code の検査

最後に、この章を書き終えた後にやった検査の話をします。教材の本筋からは少し外れますが、「道具にする」という章の締めくくりとしては、これがいちばん大事かもしれません。

問いはこうです。「実装した」と言えるのはどういう状態か?

関数を書いた。ビルドが通る。テストも書いて、通った。——これで実装済みでしょうか。

違います。CLI から呼ばれていない機能は、利用者にとって存在しないのと同じです。要件が「イメージの WorkingDir をコンテナに反映する」なら、その値をレジストリから読んでいるだけでは要件未達です。読んだ値がコンテナの chdir まで届いていなければ、利用者は何も得ていません。

そこで、コマンドの入口から末端まで経路を辿って確認しました。3 か所見つかりました。

見つかったもの状態対処
container.DefaultBase定義しただけで誰も呼ばない削除
State.Basestate.json に書いているが誰も読まない削除（ID から導出できる）

4 行あるのは、State.Base と DefaultBase が対で見つかったからです。それぞれ性質が違うので、対処も違います。

DefaultBase と State.Base は削除しました。使われていない定数とフィールドです。State.Base のほうは state.json にも書き出されていたので、読む人にとっては「何か意味がある値」に見えてしまう のがたちが悪い。ID から stateDir(id) で導出できるものを二重に持っていただけでした。導出できるものを持たない——Step 3 で書いた方針の実践です。

overlay.CountMounts は繋ぎました。これは削除の候補でもありました。使われていないのだから消してもいい。しかし、この関数が数えているのはまさにこの章で問題にしているリークです。消すのではなく、mydocker info の overlay 数: %d 件 に繋いだ。Step 8 で見たあの行は、この検査から生まれたものです。dead code の発見が、機能の追加につながった珍しい例でした。

Image.WorkingDir は実装しました。これがいちばん深刻でした。レジストリからイメージ設定を読み、WorkingDir フィールドに格納するところまではできていた。しかしその値がコンテナに届いていなかったのです。Dockerfile に WORKDIR /app と書かれたイメージを動かしても、コンテナは / で起動していました。

ビルドは通ります。テストも（WorkingDir を検査していなければ）通ります。そして機能は存在しません。

直した経路がこれです。cmdRun が cfg.Workdir = img.WorkingDir で設定に入れ、Run が orSlash(cfg.Workdir) として init に位置引数で渡し、Init が pivot_root のあとで chdir する。入口から末端まで、切れ目なく繋がってはじめて「実装した」と言えます。

GO メモ · go vet は未使用の関数を検出しない

「そんなものはコンパイラが教えてくれるのでは?」と思うかもしれません。Go は未使用のローカル変数や未使用のimport をコンパイルエラーにする、厳しめの言語です。

しかし——未使用の関数・メソッド・型・定数・構造体フィールドは、エラーにも警告にもなりません。go vet も教えてくれません。

理由は明快です。Go にはパッケージという単位があり、エクスポートされた関数は「まだ誰も呼んでいないだけで、外から呼ばれるかもしれない」からです。ライブラリを書いている場合、パッケージ内から呼ばれていない公開関数はごく普通に存在します。コンパイラにはそれが「ライブラリの API」なのか「消し忘れ」なのか区別できません。

だから、この検査は自分でやるしかありません。mydocker では、関数名を全ファイルで数える素朴な走査を使いました。

for sym in $(grep -rhoP '^func (\([^)]*\) )?\K[A-Za-z_][A-Za-z0-9_]*' --include=*.go .|sort -u); do
  n=$(grep -rho "\b$sym\b" --include=*.go . | wc -l)
  [ "$n" -le 1 ] && echo "UNUSED?: $sym"
done

「定義の行以外にその名前が 1 度も出てこない関数」を探しているだけです。UNUSED? と疑問符が付いているのは、これが候補を挙げるだけのものだから。テストからだけ呼ばれる関数や、リフレクション経由で使われるものは誤検出します。最終的な判断は人間がします。

もっと賢い道具（staticcheck の U1000 など）もありますが、この教材は外部ツールに依存しない方針なので、grep 2 行で済ませました。粗くても、やらないよりはるかにましです。

この検査から得た教訓を、一般化して書いておきます。

  • 「実装済み・テスト通過」は「要件達成」ではない。利用者の入口から末端まで経路が繋がっているかを、要件ごとに辿る
  • 使われていないコードは、消すか繋ぐかの二択。放置は「あとで使うかもしれない」という名の負債です。読む人を毎回迷わせます
  • コンパイラが教えてくれる範囲を過信しない。Go は厳しい言語ですが、厳しいのは関数の内側だけです

つまずき FAQ

state.json をファイルに置くと、複数の mydocker が同時に走ったとき壊れませんか?

いい着眼点です。結論から言うと、この実装は完全な排他制御をしていません。ただし、壊れにくい形にはなっています。

まず、コンテナ ID は 6 バイトの乱数から作るので、別々の mydocker run が同じ containers/<ID>/ を触ることは実質ありません。書き込み先が最初から分かれているので、同時に run を打っても互いの記録を壊しません。

危ないのは「同じ ID に対して rm と exec を同時に打つ」ような場合です。Cleanup が IsAlive() を確認した直後にコンテナが起動して…といった隙間は理屈の上では存在します。本物の docker はデーモンが 1 つだけ状態を握ることでこれを避けています。

mydocker にデーモンを持ち込まなかったのは、この教材で説明したいものがカーネルの機能であって、分散状態管理ではないからです。ロックファイル（flock(2)）を 1 枚挟むだけでもかなり改善するので、手を動かしたい人にはよい練習課題になります。

ps で「死んでいるが残っているもの」も一覧に出してくれたほうが親切では? docker ps -a みたいに。

親切です。実際、docker はそうしています。この実装がそうしていないのは、機能を絞ったからで、原理的な理由ではありません。

ただ、もし追加するなら気をつけるべき点があります。「死んでいるものを表示する」ことと「死んでいるものを片付ける」ことを、絶対に同じコマンドでやらないことです。

Step 9 で書いたとおり、ps は「見るだけ」のコマンドだと誰もが思っています。そこに削除の副作用を混ぜると、うっかり打った ps がイメージを壊す可能性を生みます。問い合わせるコマンドは状態を変えない——これは守ったほうがいい線です。

実装するなら mydocker ps -a のように別のオプションにして、STATUS 列を Up / Exited と出し分けるのが素直でしょう。State に終了時刻や終了コードを足す必要も出てきます。

exec のマウント名前空間の割り切りって、結局どこで困るんですか? 実害が無いなら気にしなくていいのでは。

「日常的な使い方では困らない」が正確なところです。困る場面を具体的に挙げてみます。

  • コンテナ本体が起動後に自分でマウントをした場合。たとえばコンテナの中のプロセスが mount -t tmpfs を実行したとします。そのマウントはコンテナ本体のマウント名前空間にできるので、exec で入ったプロセスからは見えません。docker exec なら見えます
  • exec の中でマウントをした場合。逆も同じで、exec 側で行ったマウントはコンテナ本体からは見えません
  • /proc/self/mounts の中身が違う。マウント表そのものを見ると、本体と exec 側で違うものが並びます

逆に言えば、それ以外は同一です。ファイルの読み書きは完全に同じものを見ています（同じ overlay の merged が根なので）。プロセス一覧もホスト名も本物です。

「気にしなくていいか」については、気にしなくていいが、知っておくべきと答えます。境界を知らずに使うと、いつか原因不明の挙動として跳ね返ってきます。だから README.md の「既知の割り切り」に書いてあります。

umount が失敗したまま MNT_DETACH で外すのは、乱暴じゃないですか?

乱暴です。だから一度だけしか試しません。

MNT_DETACH は「今すぐマウント表から切り離す。ただし実際の解放は、まだ使っている人がいなくなってから」という遅延アンマウントです。使用中でも成功します。

これが安全なのは、「その場所からは確実に見えなくなる」からです。MNT_DETACH が成功すれば、containers/<ID>/merged はもうただの空ディレクトリです。RemoveAll しても、下層のイメージには届きません。私たちが恐れていた事故は起きません。

そしてそのあと、IsMountPoint で本当に外れたかを確認します。ここで外れていなければエラーにして削除に進まない。MNT_DETACH は「最後の手段だが、確認は省かない」という位置づけです。

本当に乱暴なのは、失敗を握りつぶして削除に進むことのほうです。MNT_DETACH はそれを避けるための手段であって、手抜きではありません。

今のコンテナは、ネットワークも隔離されているんですか?

されていません。ここははっきり書いておきます。

第01章で Cloneflags に並べたのは CLONE_NEWUTS・CLONE_NEWPID・CLONE_NEWNS・CLONE_NEWIPC の 4 つでした。CLONE_NEWNET がありません。つまりコンテナは、ホストのネットワーク名前空間をそのまま共有しています。

確かめるのは簡単です。

$ mydocker run --quiet alpine /bin/sh -c 'ip -o addr'
1: lo    inet 127.0.0.1/8 scope host lo\       valid_lft forever preferred_lft forever
2: eth0    inet 192.0.2.2/24 brd 192.0.2.255 scope global eth0\       valid_lft forever preferred_lft forever

この eth0 の 192.0.2.2/24 はホストのアドレスそのものです。コンテナから見ているのはホストの網です。ポートを開けばホストのポートが開き、ホストが見える先はすべて見えます。

これは docker run --network host に相当する状態で、隔離としては明らかに不完全です。なぜ実装しなかったのか、実装するなら何が必要なのかは、まるごと次章の主題です。

mydocker info の「overlay 数」は、他のプログラムが作った overlay も数えてしまいませんか?

数えます。CountMounts("overlay") は /proc/mounts の 3 番目のフィールドが overlay の行を全部数えるので、docker が動いていればその分も入ります。

それでも構わない、という判断です。この数字の使い方は「作業の前と後で比べる」だからです。前後で他のプログラムが overlay を増減させていなければ、差分は mydocker の分だけになります。

厳密にやるなら、マウント先のパスが /var/lib/mydocker/containers/ で始まる行だけを数えればいい。実際 E2E テストは、それに近いことをしています。

info のほうを素朴なままにしてあるのは、この数字が「絶対値としての正しさ」ではなく「増えていないこと」を見るためのものだからです。目的に対して必要十分なら、それ以上作り込まないというのも設計の一部です。

理解度チェック

次の問いに自分の言葉で答えてから、答えを開いてください。答えを見て「知っていた」と思えるかではなく、先に自分で言葉にできるかが分かれ目です。

Q1. /proc/<pid> が存在すれば「そのコンテナは生きている」と言えないのはなぜですか? どうすれば言えるようになりますか?

PID は再利用されるからです。プロセスが終わるとその番号は空き番号に戻り、番号が一周すると別のプロセスに配られます。終了したコンテナの PID がたまたま別のプロセスに割り当てられると、/proc/<pid> は存在するので「まだ生きている」と誤判定します。

この誤判定は 3 つの形で現れます。ps に幽霊が出る。rm が「まだ実行中です」と言って拒否する。結果として、片付けたくても永久に片付けられなくなる。

解決は、PID と一緒に起動時刻を記録し、両方が一致したときだけ生存とみなすことです。起動時刻は /proc/<pid>/stat の 22 番目のフィールドにあります。PID と起動時刻の組は事実上一意なので、これで別人を確実に見分けられます。

mydocker では State.StartTime に記録し、IsAlive() が st.startTime != s.StartTime を見ています。

Q2. /proc/<pid>/stat を空白で分割して 22 番目を取ってはいけないのはなぜですか?

2 番目のフィールドがコマンド名で、そこに空白や丸括弧が入り得るからです。コマンド名は丸括弧で包まれていますが、その中身は自由です。(my prog) のように空白が入れば、素朴に空白で分割したときにフィールドの位置が 1 つずれます。

ずれた位置から読んだ数値は、まったく別の意味の数です。エラーにならず、静かに間違った値が返ります。だから、この誤りは気づきにくい。

定石は、行の最後の ) を探して、その先だけを空白で分割することです。3 番目以降のフィールドには括弧が出てこないので、最後の ) は必ずコマンド名の閉じ括弧になります。

切った先を数え直すと fields[0] が元の 3 番目にあたるので、元の 22 番目は fields[19] です。mydocker の readProcStat はこれをやっています。

ついでに——これと同じ形の失敗を、この章でもう一度踏みました。mydocker ps の出力を awk '{print $4}' で解析して、sleep 40 の 40 を掴んだ話です。「空白区切りは、値に空白が入った瞬間に壊れる」は覚えて帰ってください。

Q3. 後片付けで「アンマウント → 削除」の順序を守り、しかも前者の失敗で止まらなければならないのはなぜですか? 守らないと何が消えますか?

イメージの実体が消えます。

umount は EBUSY で日常的に失敗します。プロセスが残っている、シェルの作業ディレクトリがその中にある——それだけで起きます。このとき失敗を無視して os.RemoveAll(containers/<ID>/) に進むと、その下の merged/ はまだマウントされたままです。

rm -rf はマウントポイントを特別扱いしません。merged/ の中を再帰的に辿って消そうとします。そこに見えているのは overlay 越しの lowerdir、つまり展開済みのイメージレイヤそのものです。共有資産なので、他のコンテナも巻き添えになります。

恐ろしいのはエラーが出ないことです。プログラムは正常終了します。気づくのは次に run を打って「レイヤのディレクトリがありません」と言われたときです。

mydocker は 3 つの関所で防いでいます。Unmount() が IsMountPoint で本当に外れたかを確認する。呼び出し元が失敗したらそこで return する。RemoveRecord が削除の直前にもう一度確認する。取り返しのつかない操作には二重の関所を置く。

Q4. exec でマウント名前空間だけ新しく作るのはなぜですか? それで実害が無いと言えるのはなぜですか?

マウント名前空間への setns(2) は、呼び出し元がシングルスレッドでなければならないからです。マルチスレッドだと EINVAL で失敗します。そして Go のランタイムは常にマルチスレッドなので、cgo を使わずにこの条件は満たせません。runc はこの一点のために cgo で C のコンストラクタを書いています。

そこで mydocker は、PID / UTS / IPC には setns で参加し、マウントだけ CLONE_NEWNS で新しく作って、同じ merged を根にするという手を取りました。

実害が無いと言えるのは、根にしているのが同一の overlay の merged だからです。同じディレクトリを 2 つの名前空間から見ているだけなので、見えるファイルは完全に同一です。プロセス一覧もホスト名も本物の名前空間に参加しています。

ただし完全ではありません。コンテナ本体が起動後に自分でマウントをした場合、それは exec 側からは見えません。この割り切りは README.md の「既知の割り切り」に明記してあります。できていないことを、できているかのように書かない。

Q5. mydocker ps が末尾に 合計 N 件 を必ず出すのはなぜですか?

テストが空振りしても緑になるのを防ぐためです。

「コンテナを起動して ps に出ることを確かめる」というテストを、grep の成否だけで書いたとします。すると、ps の実装が壊れて 1 行も出さなくなっても、テストの側に「何件出るはずか」という期待値がなければ、0 件でも「失敗 0 件」で緑になります。

「何も起きなかった」と「正しく動いた」を、テストが区別できていない状態です。

そこで ps は必ず件数を実数で出し、テストはその数を読んで期待値と突き合わせます。0 件なら 0 件だと明示的に主張させる。同じ考え方が mydocker info の overlay 数: %d 件 や、E2E の 10/10 件成功 にも使われています。

Q6. mydocker 自身が SIGKILL されて残った記録を、ps が勝手に片付けないのはなぜですか?

理由は 2 つあります。

1 つ目。ps は「見るだけ」のコマンドだと誰もが思っているから。読み取り専用のつもりで打ったコマンドが裏でディスクを消していたら、道具として信用できません。問い合わせるコマンドは状態を変えない。

2 つ目。マウントが残っている可能性があるから。Q3 で見たとおり、マウントされたまま削除に進むとイメージの実体まで消えます。それを ps の副作用として、利用者が何も知らないうちにやるのは論外です。

そこで mydocker は「一覧には出さないが、勝手に消しもしない」という態度を取ります。片付けは mydocker rm <ID> で人間が明示的に指示したときだけ。rm は Step 7 の順序を守るので安全に回収できます。

残骸は残るが、残骸だと分かる形で残り、明示的な指示で安全に回収できる。これが「勝手に消さない」の見返りです。

Q7. 「実装済み・テスト通過」でも要件未達になり得るのはなぜですか? go vet では見つからないのですか?

CLI から呼ばれていない機能は、利用者にとって存在しないのと同じだからです。関数を書き、テストを書き、そのテストが通っても、コマンドの入口から末端まで経路が繋がっていなければ、利用者は何も得ていません。

実際に mydocker で 3 か所見つかりました。container.DefaultBase と State.Base（誰も読まないので削除）、overlay.CountMounts（mydocker info に接続）、そして image.Image.WorkingDir（レジストリから読んでいたのにコンテナに反映していなかったので実装）。

go vet はこれを教えてくれません。Go は未使用のローカル変数やimport をエラーにしますが、未使用の関数・メソッド・型・定数・フィールドは検出しません。エクスポートされた関数は「まだ誰も呼んでいないだけで、外から呼ばれるかもしれない」からです。ライブラリとしては正当な状態なので、コンパイラには区別できません。

だから自分で検査します。mydocker では「定義の行以外にその名前が 1 度も出てこない関数」を grep で数える素朴な走査を使いました。粗いですが、やらないよりはるかにましです。

まとめ — 次の層へ

この章で、run しかできなかったものが道具になりました。mydocker ps で今動いているものを一覧でき、mydocker exec で動いているものの中を覗け、mydocker rm で後片付けもできる。そのすべてを支えているのは、/var/lib/mydocker/containers/<ID>/state.json というただ 1 つの記録と、そこに書いた PID + 起動時刻という小さな工夫でした。そして本番は後片付けのほうでした。「アンマウント → 削除」の順序を崩さない。前者が失敗したら後者に進まない。この一線を守るために、Unmount の確認・呼び出し元の return・RemoveRecord の再確認という三重の関所を置きました。守らなければ、umount の EBUSY ひとつでイメージの実体が消えます。エラーも出さずに。さらに、片付いたことを数えて確かめるところまでやりました。マウントのリークは静かに進行するので、症状が出るのを待っていては手遅れだからです。

しかし、このコンテナはまだ外とつながっていません。より正確に言えば、つながりすぎています。第01章で Cloneflags に並べたのは UTS・PID・MNT・IPC の 4 つで、CLONE_NEWNET がありません。つまり今のコンテナはホストのネットワーク名前空間をそのまま共有しているのです。コンテナの中で ip addr を打つと、ホストの eth0 がそのまま見えます。アドレスもホストのものです。これは docker run --network host に相当する状態で、隔離としては明らかに穴が空いています。プロセスもファイルシステムもホスト名も区切ったのに、網だけが素通しになっている。ここまで積んできた 6 枚の層の上に、最後の 1 枚が乗っていない状態です。

次章はネットワークの話をします。ただし、先に正直に書いておきます。この教材ではネットワークを実装していません。src/internal/network/network.go は存在しません。CLONE_NEWNET を足すだけなら 1 行ですが、それをやった瞬間にコンテナは外と一切通信できなくなります——新しいネットワーク名前空間には lo しかないからです。そこから使えるようにするには veth ペア・ブリッジ・IP アドレスの管理・NAT・ルーティングと、実装すべきものが一気に増えます。だから次章は「できたふり」をせず、なぜ着手しなかったのか、実装するなら何が必要になるのか、どこが難所なのかを地図として渡す章にしてあります。作らなかったものについて誠実に書くことも、道具を作ることの一部です。
